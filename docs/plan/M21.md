# M21 自我修改只有一条路径

> 路线图 P2 的第 3 个里程碑。计划的生命周期见 spec 09 §5。

## 目标

实现总纲 §1.3 的第二个不变式：接线与内核配置像插件代码一样，先经校验登记为代际，由注册表一个提交者生效与恢复；重启只恢复，不读取新的意图。插件代际的设置随它的第一个使用者 web 在 M23 加入。

## 对齐的判断

这里只记结论，理由在括号里的架构章节。

- **代际 = 内容 + 从内容求出的声明，声明不入库**（§4.5）：插件的声明函数是 `describe`，配置的是各张表的归属者。存下的旧声明会在宿主升级后成为第二个事实来源。
- **每张表有唯一的归属者**（§4.11）：与"校验只在插件里"是同一条规则。所有设置都在有名字的表里，时区因此放进 `[owner]`。
- **endpoint 是"服务 + 模型 + 密钥"唯一出现的地方**（§4.11）：profile 与 `[memory]` 按名字引用它。
- **配置与插件一视同仁**（§4.5）：差异只来自事实。配置代际登记即为健康；首次登记接纳在用的配置，不做真实调用。
- **组件是视图的函数**（§4.5）：启动只是第一份视图，没有"要重启才生效"的改动。
- **Session 选用的 profile 也是接线**（§4.10）：它的写入与应用配置由同一个提交者排序，竞争在源头消除。
- **撤销也是登记**（§4.6）：两种代际都以编号重新登记旧内容。Agent 没有回退类的工具，主人的 `rollback` 是机械恢复。
- **机制随第一个使用者加入**（§4.4）：插件设置、插件自带的凭证与出厂代际的新定义随 web 在 M23 加入。

## 范围

- **配置的格式**：`[owner]`、`[run]`、`[endpoint.*]`、`[profile.*]`、`[memory]`、`[telegram]`；`enco init` 的模板、`examples/` 与 spec 13 的模型文件同步。只支持当前格式，校验失败时指出对应的表。
- **归属者与声明**：内核解析自己的表；记忆与 Telegram 以 `TableOwner` 交给注册表；接线 `Use { user, endpoint, need }` 是解析结果的投影。
- **配置代际与视图**：记录是（编号, 文档），与插件代际共用编号；`ActiveConfig` 合起内容与声明；视图只经 `watch` 发布。
- **应用配置**：`enco config apply [--generation <N>]` 与工具 `config_apply` 同源；注册表求出声明、记下期望、在锁外探测新出现的使用、在锁内提交。部署与应用配置都只核对所依赖的活跃代际的编号。
- **`set_profile`** 经注册表写入；Round 开始时经 `session_view` 读取。
- **重启只恢复**：首次启动登记 `config.toml`；之后从活跃配置代际求出声明，不检查环境变量；宿主的表解析不了记入 `invalid`，内核的表解析不了就拒绝启动。
- **生效时机**：profile、`max_rounds`、时区、记忆的 endpoint 与索引身份、Telegram 都在各自的边界跟随视图。
- **撤销**：`plugin_deploy` 与 `config_apply` 接受代际编号；删除 `plugin_rollback` 工具，新增 `enco config rollback`；救生集以 `config_apply` 代替 `plugin_rollback`。
- **`enco status`**：活跃配置代际与历史、当前宿主解析不了的表、`config.toml` 与已登记内容的不一致。
