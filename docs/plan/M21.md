# M21 自我修改只有一条路径

> 路线图 P2 的第 3 个里程碑。计划的生命周期见 spec 09 §5。

## 目标

实现总纲 §1.3 的第二个不变式：接线与内核配置像插件代码一样，先经校验登记为代际，由注册表一个提交者生效与恢复；重启只恢复，不读取新的意图。插件代际的设置随它的第一个使用者 web 在 M23 加入。机制见 §4.5、§4.6。

## 对齐的判断

- **配置与插件一视同仁**（§4.5）：两者都是 Agent 对自身的外部性修改，登记、提交、生效、重启、撤销与不一致的报告都相同。差异只来自事实：接线在应用时就能用真实调用验证，所以配置代际登记即为健康，不需要试用。
- **撤销也是登记**（§4.6）：宿主只在有证据时自动回退；Agent 凭判断撤销，就是重新登记上一个版本，代码用 `plugin_deploy` 部署旧代际的制品，配置用 `config_apply` 应用旧内容；主人的 `rollback` 命令是不依赖模型的机械恢复。每个动词撤销它自己那一类修改，所以 Agent 没有回退类的工具，工具本身就是认知负担（§7）。
- **真实调用覆盖用途真正用到的能力**（§4.6）：回复用途带上一个工具定义，否则不支持工具调用的模型能通过应用，之后正常模式与安全模式都会失败。
- **机制随第一个使用者加入**（§4.4）：现在没有插件有配置，所以插件设置、插件自带的凭证与出厂代际的新定义都随 web 在 M23 加入。

## 范围

- **配置代际**：不属于任何插件的设置，即接线与内核配置：profile、endpoint 及其 `api_key_env`、timezone、渠道等。
- **应用配置**：`enco config apply` 与工具 `config_apply` 同源。
  - 跳过与活跃代际相同的部分，其余按目标状态整体校验：接线（含 M20 的凭证检查）与准入，以及对改变了的 endpoint 各做一次真实的最小调用，回复用途带上一个工具定义。
  - Session 选用的 profile 也是接线：删掉或改名一个仍有 Session 在用的 profile，整次拒绝并列出这些 Session（§4.10 第 3 条）。回退仍可以拆掉它，那时由 `profile.unknown` 报出。
  - 校验通过后，一次应用就是注册表的一次提交。
- **登记携带期望的活跃代际**：部署与应用配置都一样，提交时任何一项不一致就整次拒绝。删除 spec 11 §5 给部署的豁免：所有登记一律携带期望的活跃代际（§3.6 规则二）。
- **重启只恢复活跃代际。**
  - `serve` 启动时，`config.toml` 与生效中的配置不一致，或者文件无法解析，都在日志中警告。
  - 首次启动（包括第一次以新版本启动的现有 home）把 `config.toml` 登记为第一批代际，直接为健康。
  - 启动时不再检查环境变量：变量缺失时，用到它的那次调用以明确的失败结束（M20），节点照常启动。
- **生效时机**：
  - Round 开始时钉住配置；
  - 时区变化时，Scheduler 立即重新推算；
  - embedding 与渠道的变化，第一版报告需要重启。
- **撤销**（§4.6）：
  - `plugin_deploy` 接受一个代际编号，部署它的制品，设置取生效中的那份；照常校验与试用，历史只向前追加。
  - Agent 撤销配置就是用旧内容执行 `config_apply`。
  - `plugin_rollback` 不再是 Agent 的工具；`enco plugin rollback` 与新增的 `enco config rollback` 只在 CLI 中，属于机械恢复。
  - 救生集去掉 `plugin_rollback`，加入 `config_apply`。
- **`enco status`**：区分"`config.toml` 有从未登记的修改"与"已登记为代际 N 并被回退，原因是……"。插件源码的同一份报告随源码快照在 M24 加入。

## 规格

- 03：配置代际的存储；schema 加一。
- 04 §6：配置在 Round 开始时钉住。
- 05 §2：救生集去掉 `plugin_rollback`，加入 `config_apply`。
- 06：embedding 的变化（第一版需要重启）。
- 08 §1、§3、§4：`enco config apply` 与 `enco config rollback`；首次启动登记配置、之后重启只恢复并在不一致时警告；不再因配置无效或环境变量缺失拒绝启动（全新的 home 除外）。
- 11 §1、§4.1、§5、§8：配置代际；登记流程的两个入口；一次应用一次提交；删除部署的豁免；`plugin_deploy` 接受代际编号，`plugin_rollback` 只保留 CLI；status 的两种不一致。
- 12：profile 与 endpoint 经应用配置生效；删除在用的 profile 被拒绝；回复 endpoint 的真实调用带工具定义。

## 验收

- 把 endpoint 的模型名改成不存在的名字，执行应用配置：整次被拒绝，不登记任何代际，错误指出是哪个 endpoint。
- 回复 endpoint 换成一个拒绝带工具请求的服务（mock）：应用配置被拒绝，错误指出不支持工具调用。
- 删掉一个仍有 Session 在用的 profile，执行应用配置：整次被拒绝，错误列出这些 Session；用 `enco profile` 把它们切走之后重新应用，成功。
- 应用配置修改了 profile：下一个 Round 用新的 profile，不需要重启。正在进行的 Round 不受影响。
- 改了 `config.toml` 但没有应用，直接重启：活跃代际不变，日志里有警告。把 `config.toml` 写坏，或者去掉某个 endpoint 的环境变量后重启：节点照常启动，用到那个 endpoint 的调用以明确的失败结束。
- 应用配置校验期间，同一插件被部署了新代际：应用配置被拒绝，什么都不写；重新应用后成功。
- 同一插件的两次部署交错提交：后提交者被拒绝，活跃的是先提交的那条代际（M11 时两条都生效）。
- Agent 以代际编号重新部署上一个版本：产生一条新代际，制品与那个代际相同，进入试用。
- Agent 用旧内容执行 `config_apply`：产生一条新的配置代际，内容与之前的相同。
- `enco config rollback` 回到上一个配置代际：`enco status` 说明被回退的原因，并报出 `config.toml` 与活跃代际不一致。
