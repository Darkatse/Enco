# M30 对话回溯

> 路线图 P3 的里程碑。计划的生命周期见[路线图](../Roadmap.md)。

## 目标

主人在渠道中回复一条消息并发送 `/backtrack`，对话回到那条消息，之后从那时的状态继续；回到的是主人自己的消息时，Agent 重新回答它。对话之外的改动不撤销，模型与主人都会被告知。平台消息的身份随事实记录，这也是 P3 渠道接口的一部分：适配器换成 Wasm 插件之后，指认消息的方式不变。

## 对齐的判断

- **回溯移动的是对话的引用，Log 不改写。** Transcript 是 Log 的函数，「某条消息时的状态」就是 Log 到那里为止的投影，不需要另存。所以回溯只是一条事实：主人的命令被消费时记下的 `EventConsumed`，其中的 `Backtrack { to }` 指向主人选中的位置。当前的对话由回溯目标之前的 Log 接上这条命令及其后的条目组成，多次回溯按同样的规则递归求出。被离开的条目仍在 Log 中，检视与恢复照常；回到被离开那一段里的消息同样成立，几条线之间因此可以来回，不需要额外的结构。Session 的身份不变：分叉出新的 Session 要父指针、跨两份 Log 拼出历史、迁移渠道映射与 Binding，只有两条线需要同时运行时才值得。这是总纲「值不可变，身份稳定，可变的只是引用」与「状态是事实的函数」在 Session 上的应用。

  由历史派生的一切都按当前的对话求出：Transcript；压缩，目标在某次压缩之前就回到压缩前的完整历史，超出预算时 composer 照常再压缩；上一份回复计划，默认 composer 因此从目标当时的计划接着追加；记忆召回所看的最新输入；检视按 Attempt 的前缀重建的请求。

- **回溯的单位是一条输入或一个 Round 的结束。** Round 边界是唯一的安全点：一条回复连同它的工具调用是一个整体，从中间切开，历史里就会留下没有结果的工具调用。所以：
  - 指向一条输入，对话保留到这条输入，接着开始一个 Run 重新回答它；
  - 指向 Agent 的消息，对话保留到产生它的 Round 结束为止，那个 Round 是 Run 的最后一个时连同 Run 的结局；
  - 命令记下的是主人指向的位置本身，范围由 Log 的结构推出，不另记。

  指向输入暂时只有「重新回答」一种含义，需要「撤回这条输入」时再加。

- **回溯在两个 Run 之间生效，取代它之前送达的输入，只由主人发起。** 内核接受命令时检查目标在本 Session 的 Log 中，再取消正在进行的 Run（发出信号并等待静止）。有回溯待处理时，Session 不再开始新的 Round 或 Run；它在 Run 之间把回溯连同之前送达、尚未处理的输入一起消费，这些输入落在被离开的部分，不会被回答，之后送达的接在回溯后面，顺序仍是 Inbox 的顺序。入口只有主人的界面，即渠道命令与 CLI。Agent 没有这个工具：回退自己的对话没有清楚的用途，还会让它抹掉自己看到过的内容。

- **回溯不带文字，提示由 composer 叙述。** 主人的命令没有内容，给模型的提示是对处境的叙述，与「上一次工作为何停止」同类（Session 专题「事实进 Log，叙述进计划」）。所以 Event 只记目标位置，规范消息为空；出厂 composer 默认在目标之后写下提示，其他 composer 可以不写。提示从 Agent 的位置写：它看不到被离开的部分，只需要知道主人从哪里继续，以及对话之外的状态可能和对话对不上。
  - 指向 Agent 的消息：`The owner went back to the message above to continue from it. Anything changed since then stays changed: files, memories, schedules, plugins and other state outside this conversation may not match what it shows, so check them before relying on them.`
  - 指向主人的消息：`The owner went back to their message above and asks for a reply to it. Anything changed since then stays changed: files, memories, schedules, plugins and other state outside this conversation may not match what it shows, so check them before relying on them.`

- **对话之外的状态不回退。** 文件与其他外部效果本来不归 Enco；记忆、定时与插件代际在 Enco 中，但跨 Session 共享，各有归属者，Log 不替它们做主（Session 专题「Log 只记事实的骨架，条目永不删除」）。所以回溯只移动对话，提示与给主人的确认都写明这一点；需要撤销插件的改动时，用已有的 `self_rewind`。

- **平台消息的身份随事实记录，对应关系由查询得出。** 主人在渠道中指认一条消息，要从平台的消息 ID 找到 Log 位置，现在入站与出站都没有记下这个 ID。入站消息的 ID 是这条输入的来源，随 Event 记录；出站消息的 ID 是投递的结局，随投递结算记录，按顺序列出确认送达的各段，失败或结局未知时也列出已经确认的部分。连接的归属者用这两类已记录的事实查找：入站查本 Session 的 Log，出站查它自己的投递结算，不另建对应表。命令的回执不来自 Log，不能被指认；消息属于别的 Session 时，主人得到先切换的提示；本里程碑之前的消息没有记录，只能经 CLI 按 Log 位置回溯。

- **叫「回溯」（backtrack）。** 回溯是回到之前的一个选择点、换一条路走，走过的路不抹掉，与「Log 不改写、被离开的部分还能回去」吻合。不用「回退」「撤销」「回滚」：它们暗示做过的事被取消，而对话之外的改动都还在；「回退」已指代际的自动回退与主人回退，「撤销」已指把意图倒带再登记。也不用「倒带」：它已指插件意图（`enco rewind`、`self_rewind`），Agent 手上就有 `self_rewind`，提示里写 rewind 会被读成意图被倒带。「分支」在 SillyTavern 中是新建一个聊天，会误导成新的 Session。

- **契约与库按破坏性变化升级，不留兼容分支。** WIT 的 `event-body` 增加分支是破坏性变化，按插件专题「契约只包含已有使用者验证过的东西」升到 0.7.0，全部插件重建一次：出厂插件随宿主重建；home 中登记的源码插件经 `self_apply` 重新构建；按 0.6 构建的回退目标随之失效。库的版本升到 14：渠道 Event 的消息 ID 与投递结算的消息列表都是必填，不为旧记录留可空；不自动迁移，oracle-jp 由主人升级。主人确认以一次重建换取没有遗留分支的形态。

## 范围

- **core**：
  - `EventBody::Backtrack { to: LogPos }`，规范消息为空；
  - `EventSource::Channel` 增加 `message`，即平台的消息 ID；
  - `DeliverySettlement` 增加 `messages`，即确认送达的平台消息 ID。
- **内核**：
  - 当前对话：由 Log 求出当前这条线的一个函数，Transcript 的投影、压缩、上一份回复计划、记忆召回的最新输入与检视都经过它；
  - `Kernel::backtrack`：检查目标在本 Session 的 Log 中，接纳命令，取消正在进行的 Run；
  - Session actor：有回溯待处理时不再开始新的 Round 或 Run；在 Run 之间连同之前的输入一起消费回溯，指向输入时随即开始回答它的 Run。
- **渠道**：
  - 渠道动作 `Backtrack`，带被回复的平台消息 ID；没有回复时，主人得到用法提示；
  - 适配器的发送返回平台消息 ID，传送层按段收集，随结算记录；
  - 连接的归属者用已记录的事实把消息 ID 解析为本 Session 的 Log 位置，交给内核，再回复主人：
    - 指向 Agent 的消息：`Back at that message. Later messages are no longer part of the conversation; changes they made outside it were not undone.`
    - 指向主人的消息：`Back at your message; replying again.`
  - Telegram：入站记录 `message_id`；`/backtrack` 读取 `reply_to_message`；发送返回 `message_id`。
- **CLI 与守护进程**：`enco backtrack [--session <name>] <epoch>:<seq>`，位置取自 `enco log` 中条目的 `pos`。
- **WIT 0.7.0**：`event-body` 增加 `backtrack`；`transcript` 与 `previous` 的文档写明它们来自当前的对话，草案见下文。`CONTRACT_VERSION`、SDK 与全部插件随之重建。
- **出厂 composer**：叙述回溯，文字见上文；压缩时把它标为通知。
- **库**：版本 14，不自动迁移。
- **主人文档**：README 与 README.zh-CN 写明 `/backtrack` 与 `enco backtrack`，以及对话之外的改动不撤销。

## 设计

- Session 专题「Log 只记事实的骨架，条目永不删除」：压缩与回溯都只改变之后的计划看到哪一段历史。新增「回溯移动对话的引用，不改写 Log」，写单位、生效时机、只由主人发起与对话之外不回退，候选位置在 Log 一节。

## WIT 的变化（草案）

```wit
package enco:plugin@0.7.0;

    /// What an input says.
    variant event-body {
        /// A message from the owner.
        user-message(user-message),
        /// A scheduled reminder.
        reminder(reminder),
        /// A notice of an automatic rollback.
        generation-rolled-back(rollback),
        /// The owner went back to the message at this Log position; the transcript continues from it.
        ///
        /// When that message is an input, the backtrack asks for a reply to it. Changes made after
        /// it outside the conversation, such as to files, were not undone.
        backtrack(log-pos),
    }

    record compose-input {
        // …
        /// The conversation as it stands: after a backtrack, the Log up to its target, then
        /// everything from the backtrack on, so positions can skip.
        transcript: transcript,
        /// This Session's latest recorded reply plan in that conversation; absent at the start,
        /// or when it could not be read, which `omitted` then says.
        previous: option<plan>,
        // …
    }
```

## 验收

- 主人在 Telegram 中回复 Agent 的一条回复并发送 `/backtrack`，收到确认；下一条消息的请求（`enco inspect`）只含到那条回复为止的历史、回溯的提示与新消息。
- 回复自己的一条消息并发送 `/backtrack`：Agent 重新回答它，请求含到这条消息为止的历史与提示。
- 回溯时 Run 正在进行：Run 被取消并静止之后回溯才生效；回溯之前送达、尚未处理的消息不被回答，之后送达的接在回溯后面。
- 回到被离开那一段里的一条消息，那一段重新成为对话。
- 目标在一次压缩之前：回到压缩前的完整历史。
- 回溯之后的第一份计划以目标当时的计划为前缀。
- 记忆、定时与工作区文件不随回溯改变，提示写明这一点。
- 指向命令的回执、别的 Session 的消息、不在 Log 中的位置，或者没有回复就发送 `/backtrack`：被拒绝并说明原因，什么都不改变。
- 接纳回溯之后进程被杀：重启后回溯照常生效，且只生效一次。
- 按 0.6 构建的插件加载时被拒绝，并提示重建；出厂插件与重新登记的源码插件照常运行。

## 实施记录（2026-10-26）

代码已按本计划实现，验收仍待主人审核、Telegram 中的手动核对，以及 oracle-jp 的库升级与插件重建。

- 当前对话由内核的一个纯函数从 Log 求出，按位置截取，对任何目标都有定义；Transcript、压缩、上一份回复计划、记忆召回的最新输入与检视都经过它。
- 回溯目标的检查与「取消正在进行的 Run」都在 `Kernel::accept`，CLI 与渠道走同一个入口；渠道把回溯与连接状态在同一次提交中接纳，崩溃后不会生效两次。CLI 的 `enco backtrack` 与 `enco send` 一样由客户端给出 Event ID，重发只接纳一次。
- Session 在 Run 之间消费回溯；Run 在每个边界看到待处理的回溯就停下，这个 Round 已经回复时记为完成。是否要为指向输入的回溯开始 Run，只看 Log 的最后一条，所以崩溃之后照样成立。
- 平台消息 ID 随入站 Event 的来源与出站投递结算记录。查找出站消息时同时比对会话，因为 Telegram 的消息 ID 只在一个聊天内唯一。WIT 的 `channel-source` 不带消息 ID：composer 还没有使用者需要它。
- 刚送达、尚未被消费的输入，以及仍在发送中的投递，此时还没有记录，被指认时按「不在任何对话中」拒绝；这种窗口很短，不为它另设状态。
- 主人确认与拒绝的回执：`Send this as a reply to the message to go back to.`、`That message is in Session {name}; switch to it first.`、`That message is not part of any conversation.`。
- 手册渲染器顺带修正：变体的文档有多段时，空行带着缩进，生成的 `API.md` 因此有行尾空格；改为空行不缩进。
- `cargo xtask check` 通过（含审阅后的修订，269 项通过，2 项忽略），`git diff --check` 通过。

### 审阅后的修订（2026-10-26）

- 接纳回溯时的取消信号只在新接纳时发出。原先对每个回溯事件都发信号，CLI 回执丢失后用同一个 Event ID 重发时，Store 判为重复、不再接纳，信号却会取消之后无关的 Run。Run 在边界按 Inbox 中的事实停下，这一条决定回溯的效果；信号只负责让正在进行的 Run 及时停下，所以它应当只跟随新接纳的事实。另加测试锁住：重发的回溯不打断之后的 Run。
