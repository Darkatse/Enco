# M41 Provider 改为纯映射器，接入 Responses 与 Anthropic Messages

> 不属于某个阶段。实现路线图「之后」中 Provider 的 sans-I/O，流式补全仍留在之后；在此之上接入两种新协议。计划的生命周期见[路线图](../Roadmap.md)。

## 目标

- **Provider 不做 I/O。** Provider 插件只把规范请求编码成 HTTP 请求、把服务的响应解码成规范值。HTTP 由宿主发往 endpoint，响应先作为映射记录存下，再交给解码，Attempt 的结算引用这份记录。
- **两种新协议。** 主人可以经 OpenAI Responses 与 Anthropic Messages 接入模型服务，行为与已有的三个 Provider 一致：工具调用、图片、思考内容原样回放、实测用量、超长拒绝之后缩小重发。
- **顺带的两处。** 计划与请求的输出上限改为必填；Gemini 在 Run 中途压缩之后不再拒绝请求。

## 起因

- **新插件不该写两遍。** 路线图把 Provider 的 sans-I/O 与流式补全绑在一起，等 Telegram 的流式草稿出现时再做。现在要写两个新的 Provider，按现在的接口写完再改成纯函数，等于写两遍。所以先做 sans-I/O，流式仍等它的消费者。
- **Provider 是"外部只经映射器进入"剩下的例外。** 现在 `completion.complete` 经 SDK 的 `post` 调用 `host.http`，在同一个组件里解析响应（`sdk/src/http.rs`、`sdk/src/protocol.rs`），原始响应不入库。M40 为此付过代价：20→21 的迁移只能写 Python，按规则倒推 0.14 实际发出的那条消息。有原文的话，用新代际重新解码一次就够了。渠道早已是这个形态：`channel-plugin` 不导入任何东西，`Transport::record` 先存映射记录再调用映射器（`crates/enco-wasm/src/channel.rs`）。
- **HTTP 状态的分类各插件各做一份。** 连接失败、超时与各个状态码到失败码的映射，在每个插件链接的 SDK 里都有一份。
- **取样时发现 Gemini 的缺陷。** M40 起压缩可以停在本 Run 中途的 Round 结束处，剩下的历史以模型的工具调用开头，官方 Gemini 的两个模型对这样的请求都返回 400（见「真实样本」）。这是 M40 留在 oracle-jp 上待核对的一项，答案是不接受。

## 对齐的判断

### Provider 是零导入的映射器

- **接口。** `completion` 导出两个纯函数：
  - `encode(settings, request)` 给出 HTTP 请求；
  - `decode(response)` 把任何状态的响应译成补全、超长或失败。
  
  `embedding` 同样拆成 `encode` 与 `decode`。三个 Provider world 都不再导入 `host`，与 `channel-plugin` 相同。编码与解码在 `CallWorld::Mapper` 中运行：时钟固定，没有配置，也没有网络。Provider 本来就只接受 `{}` 作为配置（`empty_config`），所以不缺任何东西。
- **宿主持有传输，只发往 endpoint。** `encode` 给出的 `url` 是以 `/` 开头的路径，宿主把它接在 `settings.base-url` 之后，规则与渠道相同（`origins::Destinations`，Provider 不声明额外来源）。凭证的附加与回显的替换沿用 `host_imports::http`。
  - 发不出去或没有响应的，由宿主归为 `provider.network` 或 `timeout`，可以重试，与现在的 `post` 一致；
  - 请求本身不合法，例如去向不在 endpoint、方法或头部无效，是 `plugin.contract`；
  - 有响应的，不论状态，都交给 `decode` 判断。这与渠道的 `answered` 一致：401、429、413 与超长的说法都是协议的语义。
- **超时由编码决定，主人改插件就能改。**
  - **现在。** HTTP 在插件调用之内，无论 `timeout-ms` 写多少，都被 330 秒的调用上限截住；Provider 也都不写，用 300 秒的默认值。主人改不了，只能改宿主。
  - **改为。** HTTP 在两次插件调用之外，只受编码给出的 `timeout-ms` 约束，不写时用 300 秒的默认值。要改超时，就改插件的编码再登记，不必动宿主。
  - **取值。** 补全请求统一给 10 分钟，这是 Anthropic 与 OpenAI 官方客户端的默认值：按每秒 100 到 200 token 算，写满 65,536 token 要 5 到 11 分钟，300 秒不够。这个值放在 SDK 的一个常量里，五个 Provider 共用；嵌入请求照旧用各自的 30 秒。
  - **加长超时解决不了的。** 中转、反向代理与 CDN 常有自己的读超时，例如 nginx 默认 60 秒没有数据就断开，oracle-jp 的中转前面就是 nginx。非流式请求在生成期间一个字节也不发，可能在 Enco 等待之前就被中间设备切断。官方建议输出超过约 16K token 就用流式，根本的解法仍是流式补全。
- **embedding 不记录。** 嵌入向量不进 Log，没有需要追溯的结算。条数由宿主核对（`convert::embeddings` 本来就核对），插件删去自己的那份检查。
- **代价。**
  - WIT 升到 0.16.0，全部插件重建。
  - 内核的 Provider 端口多一个参数，结算多一个字段，库的版本升到 22。
  - 每个有响应的 Attempt 多存一条映射记录和一份正文 blob。正文通常是几 KB，生成图片的回复可能到 MB 级。
- **不放进来的。**
  - 流式补全：没有消费者，出现时再升一次主版本，加入分块解码。
  - 登记新代际时在历史响应上重放、逐条比较：这次先把原文记下来，重放需要的输入（代际、导出名、响应）都已在映射记录里。

### 响应先记录再解码，结算引用这份记录

- 宿主拿到响应之后，先把正文存成 blob，再存映射记录 `{generation, export: "completion.decode", arguments: {"response": {status, headers, body: <内容地址>}}}`，然后调用 `decode`。这与渠道的 `response_record` 是同一个写法。
- `AttemptSettled` 新增 `origin: Option<MappingOrigin>`，指向这次解码的映射记录。三种情况为空：
  - 请求没有得到响应；
  - 编码失败；
  - 取消，或者恢复时补记的结算。
  
  补全、超长与解码给出的失败都带 `origin`。解码 trap 时同样带着，所以解析失败也有出处。
- 进程恰好停在存下映射记录与提交结算之间，记录就成了无人引用的 blob。恢复照旧把 Attempt 记为被打断，与渠道附件的规则相同。

### 一种协议一个插件

扩展只回放给写下它的插件身份（`plan::resolve`），而 Responses 的整份输出、Messages 的整份 `content`、Chat Completions 的整份消息互不相通。所以一个插件身份只能对应一种协议。由此新增两个出厂插件，各有固定的身份，都只导出补全：

| 插件 | 协议 | 凭证 |
|---|---|---|
| `anthropic` | Anthropic Messages，`POST /messages` | `x-api-key` 头，无前缀，必需 |
| `openai-responses` | OpenAI Responses，`POST /responses` | `authorization` 头，前缀 `Bearer `，必需 |

### composer 决定内容，Provider 决定拼写

- **摘要留在 system 里**，composer 不为任何一种协议改变所有协议看到的内容。
- **协议要求、却不带新信息的结构，由 Provider 在编码时补上**，例如：
  - 角色放在哪里、怎样合并；
  - 调用与结果怎样配对，空的调用 ID 怎样补；
  - 缓存标记；
  - 协议要求的占位。

  已有先例：Chat Completions 把工具结果里的图片挪进一条 user 消息（`sdk/src/protocol/messages.rs`）；Gemini 给别家写的调用附上 `skip_thought_signature_validator`（`plugins/gemini/src/request.rs`）。改为 sans-I/O 之后，编码是钉在代际上的纯函数，线上请求可以由已记录的计划、调用参数与代际唯一求出。
- **影响信息量的跨协议差异**，例如能不能看图，由 endpoint 声明成能力交给 composer（`accepts`），composer 不知道各协议的拼写规则。
- **判据来自真实样本。** 历史以工具调用开头时，五个服务中只有 Gemini 拒绝：

  | 服务 | 以 assistant 文字开头 | 以工具调用开头 |
  |---|---|---|
  | Anthropic Messages（Haiku 4.5、Sonnet 4.6、Haiku/Sonnet/Opus 5.5） | 接受 | 接受（Haiku 5.5） |
  | OpenAI Responses（gpt-5.4-mini） | — | 接受 |
  | Chat Completions（OpenAI gpt-4o-mini、DeepSeek） | — | 接受 |
  | Gemini（3.5 Flash Lite、4 Argon） | 接受（3.5 Flash Lite） | **400** |

  所以修正落在 Gemini 插件：第一个 `contents` 是带 `functionCall` 的模型回合时，在它前面补一个固定文字的 user 回合。固定文字写在插件中，说明前面的回合没有显示，不带别的信息。实测补上之后 `gemini-3.5-flash-lite` 通过，`gemini-4-argon` 留到真实服务核对。

  Anthropic 的参考资料说首条消息必须是 user、角色必须交替，官方 API 实测两条都不成立，`anthropic` 插件不做这两种补救。

### 输出上限必填

- **现在没有任何生产者省略它。**
  - probe 总带着 endpoint 的值（`registry/probe.rs`）；
  - 用于补全的 endpoint 不写 `max_output_tokens`，配置本身就被拒（`settings.rs`）；
  - 出厂 composer 的回复计划与压缩计划都填了（`compose.rs`、`compaction.rs`）；
  - 存储还原时保留它（`store/plans.rs`）。
- **"服务的默认值"与窗口预算对不上。** composer 按 `budget.max_output_tokens` 在窗口里预留输出，服务的默认值是个未知数：Anthropic 没有默认值，OpenAI 的默认值可能是模型的上限。
- **改法。**
  - WIT 中 `completion.request` 与 composer `plan` 的 `max-output-tokens` 改为 `u32`；内核的 `ProviderRequest` 与 `ContextPlan` 随之改为 `u32`。
  - `bind_composition` 检查计划的输出上限在 1 与这份计划所属目标的预算之间，回复计划对回复目标，压缩计划对压缩目标；越界是 `plugin.contract`，写进 composer 的违规清单。预算属于内核，所以由内核检查。
- **存储。** `Some(n)` 与 `n` 序列化相同，计划的内容地址不变。升级前核对库中每条计划记录都有值，见「验收」。

### Anthropic Messages 的映射

- **版本。** 固定发送 `anthropic-version: 2023-06-01`。`2026-10-21` 只是收紧了采样参数等几处校验，Enco 用不到它带来的任何东西；旧版本在官方 API 上实测可用，Bedrock 上 4.7 之前的模型也只接受旧版本。
- **请求。**
  - 全部 system 消息依次放进顶层 `system`，与 Gemini 插件的做法相同。
  - user 消息：文字为 `text` 块，图片为 `image` 块（base64）。
  - assistant 消息：带本插件的扩展时原样发出整份消息；否则由规范部分组出 `text` 与 `tool_use`，`input` 由参数文本解析而来。空文字不发，服务拒绝空的 `text` 块。
  - 相邻的 tool 消息合成一条 user 消息，`tool_result` 按顺序排列，图片放在各自的 `tool_result` 里（实测接受）。
  - 空的调用 ID 按位置补上确定的 ID；调用与结果按 ID 配对，没有 ID 时按顺序配对。这与 Gemini 是同一条规则，收进 SDK 共用。
  - `max_tokens` 取请求的输出上限。
  - 顶层固定写 `cache_control: {"type": "ephemeral"}`，即自动缓存。实测不写就完全不缓存；写上之后第二次请求整段命中。
- **选项。** `settings.options` 只能新增字段，不能覆盖 `model`、`messages`、`system`、`tools`、`max_tokens`、`stream`、`cache_control`。思考与强度由主人在选项中写（`thinking`、`output_config`），插件不替模型选择。
- **响应。**
  - 规范部分是 `text` 块的文字与 `tool_use`，参数取 `input` 的紧凑 JSON。
  - 规范部分重新编码之后与服务返回的 `content` 不同，就把整份消息写进扩展。空值与空容器不算不同，与 M40 的规则一致。思考块（带 `signature`）、`tool_use` 上的 `caller`、引用都会让回复带扩展；只有文字的回复不带。
- **用量。** `input_tokens` 只是没有命中缓存的余数（实测 4，加上缓存读取的 8022 才是整段请求）。所以规范的输入是 `input_tokens + cache_creation_input_tokens + cache_read_input_tokens`，缓存命中是 `cache_read_input_tokens`。否则 M40 的实测会把前缀测得远小于实际，该压缩时不压缩。
- **停止原因。**

  | 服务给出 | 规范值 |
  |---|---|
  | `end_turn`、`stop_sequence` | `end-turn` |
  | `tool_use` | `tool-calls` |
  | `max_tokens`、`model_context_window_exceeded` | `max-tokens` |
  | `refusal`、`pause_turn`，以及其他值 | `other` |
- **超长。** 400 且说 `prompt is too long: N tokens > M maximum`：`counted` 为 N，`accepted` 为 M。输出不计入这个上限：输入 179,016 加上 `max_tokens` 30,000，超过 200,000 的窗口，照常回答。所以 `accepted` 就是 M，不像 DeepSeek 那样减去输出。413 照旧算不带数字的超长。其余状态按 SDK 共用的分类，529 属于 5xx。
- **思考块的前缀绑定。** 新账号在 Opus 5.5 等模型上受 preserved thinking 检查：前缀变了还回放旧思考块，会得到 400。主人的账号实测不受约束：改了 system 再回放仍是 200；带上 beta 头时，块被标为 `thinking_mismatch_allowed`。所以插件默认不发相应的 beta，见「待定」1。

### OpenAI Responses 的映射

- **无状态。** 固定写 `store: false` 与 `include: ["reasoning.encrypted_content"]`，不用 `previous_response_id`、`conversation` 与 `background`。上下文专题允许把服务端状态当作缓存，但那需要一条在服务丢了状态时退回完整请求的路径，现在没有使用者需要这份节省。这几个字段与 `truncation` 都是选项不能写的字段：`truncation: auto` 会让服务悄悄丢掉上下文。
- **请求。**
  - system、user 消息按原来的位置成为 `message` 项：文字为 `input_text`，图片为 `input_image` 数据 URL。
  - assistant 消息：带本插件的扩展时原样发出其中的全部输出项；否则由规范部分组出 `message`（`output_text`）与 `function_call`。
  - tool 消息成为 `function_call_output`：只有文字时 `output` 是字符串；带图片时是 `input_text` 与 `input_image` 的数组（实测接受）。
  - 工具定义是扁平的 `{type: "function", name, description, parameters, strict: false}`。显式写 `strict: false`：省略时 Responses 会自行把 schema 规整成 strict 模式，模型看到的约束就与我们声明的不同。
  - 输出上限写入 `max_output_tokens`。
- **选项。** 不能覆盖 `model`、`input`、`tools`、`max_output_tokens`、`stream`、`store`、`include`、`previous_response_id`、`conversation`、`background`、`truncation`、`instructions`。强度等由主人写（`reasoning`、`text`）。
- **响应。**
  - 规范部分是各个 `message` 项中 `output_text` 的文字与 `function_call`（ID 取 `call_id`）。
  - 整份 `output` 数组写进扩展，回放时原样发出。实测带着 `encrypted_content` 时，连同各项的 `id` 原样回放可以通过，不需要剥去 `id`。输出项总带 `id`、`status` 与 `phase`，所以每条回复都带扩展，正文在 Log 中存两份。
- **用量。** 输入取 `input_tokens`（已含缓存部分），缓存命中取 `input_tokens_details.cached_tokens`，输出取 `output_tokens`。
- **停止原因。**

  | 服务给出 | 规范值 |
  |---|---|
  | `completed`，且有 `function_call` | `tool-calls` |
  | `completed`，没有 `function_call` | `end-turn` |
  | `incomplete`，`max_output_tokens` | `max-tokens` |
  | `incomplete`，其他原因 | `other` |
  | `failed` | 带服务说明的 `provider.bad_response` |
- **超长。** 400 且 `error.code` 为 `context_length_exceeded`。服务不给数字，按 M40 的规则砍一半。413 照旧。

## 范围

- **WIT 0.16.0**
  - **共用的 HTTP 类型。** `types` 新增 `http-request` 与 `http-response`。它们取代 `host` 中的同名记录与 `channel` 的 `request`、`response`：同一种东西只有一个名字。
  - **completion 与 embedding** 改为 `encode` 与 `decode`；三个 Provider world 不再导入 `host`。
  - **输出上限必填。** `completion.request` 与 composer `plan` 的 `max-output-tokens` 改为 `u32`；composer 的违规清单加上输出上限。
  - `CONTRACT.md` 重新生成。
- **core**：`AttemptSettled.origin`。
- **内核**
  - **Provider 端口**：带上记录去处，返回结果与映射来源，见「内核端口（草案）」。
  - **Round**：调用时传入本 Provider 代际与 Store。probe 不传，因为 probe 时代码还没有代际 ID，结果也不进 Log；恢复补记的结算 `origin` 为空。
  - **类型与检查**：`ProviderRequest` 与 `ContextPlan` 的输出上限改为 `u32`；`bind_composition` 检查输出上限。
- **enco-wasm**
  - **Provider 的调用路径**：在 Mapper 中编码，经 `Destinations` 与 `host_imports::http` 发往 endpoint，存映射记录，在 Mapper 中解码；embedding 同样拆分，但不记录。
  - **传输失败的分类**从 SDK 搬到这里。
  - 新 WIT 的转换；渠道随类型改名。
- **enco-host**
  - **库的版本 22。** 旧的 `AttemptSettled` 写入 `"origin": null`，库中只留当前格式；计划记录的格式不变。
  - **出厂清单** `plugins/factory.rs` 加入两个插件，并分配身份。
- **SDK**
  - **Provider 的协议辅助**按纯函数重组：
    - 状态分类（含 413 一律超长），以及读出超长数字的协议钩子，供解码共用；
    - 调用与结果的配对；
    - JSON 请求的构造，以及补全请求 10 分钟的超时常量；
    - Chat Completions 的编码与解码。
  - **`post` 留给仍导入 `host` 的决策与工具插件**（TypeSafe）。
  - **`export!`**：Provider 的分支不再映射 `host`；SDK 自己的 world 显式导入 `host`。
- **插件**
  - **改写为编码与解码**：openai-compatible、deepseek 与 gemini；gemini 同时补上前导 user 回合。
  - **新增**：`anthropic` 与 `openai-responses`。
  - **出厂 composer**：输出上限改为必填。
  - **随 HTTP 类型改名修改引用**：telegram、discord、onebot 与 web；其余插件只需重建。
- **评测**：`evals/runner` 的镜像不读 `origin`，serde 本来就忽略未知字段，核对即可。
- **文档**
  - **Usage**：在介绍 `config.toml` 的位置列出五个 Provider 插件各自对应的协议，并说明 Responses 与 Anthropic 的选项写法。
  - **示例配置**：新增 `examples/` 中两种协议的 endpoint。
  - **`plugins/README.md`** 的表格加上两个插件。
  - 设计文档见下节。

## 不做

- 流式补全与流式草稿。
- 登记新代际时在历史响应上重放、比较。
- 服务端内置工具（Responses 与 Anthropic 的 web search 等）：选项不能覆盖 `tools`，而且需要先按上下文专题判断它们的效果是否限于那次补全。
- 服务端会话状态（`previous_response_id`、Anthropic 的 message threads）。
- Anthropic 的 beta 功能，见「待定」1。
- 需要刷新令牌的认证（OAuth 等）：零导入的 Provider 做不到，出现需要时由宿主持有。

## 设计

验收时提炼或改写：

- **插件专题**
  - 「外部只经映射器进入，映射器不做 I/O」：Provider 也是映射器，模型服务的响应先记录再解码，`AttemptSettled` 引用这条记录。
  - 「接口按导入方与能否单独提供划分」：加上一个插件身份只对应一种协议，因为扩展只回放给写下它的插件。
  - 「补全只由内核导入」中"插件经 `http` 自己调用外部模型"一句，限定为决策与工具插件。
- **上下文专题「协议差异留在 Provider」**：加上内容与拼写的分界。协议要求、不带新信息的结构由 Provider 在编码时补上，规则写在插件里；影响信息量的差异由 endpoint 声明成能力交给 composer。依据是本计划的样本表。
- **Session 专题「效果发生之前先记录」**：补上 Provider 的响应在解码之前记下、结算引用它，所以每次结算都能追溯到服务的原话。

## 不变式

| 不变式 | 由谁保证 | 怎样核对 |
|---|---|---|
| Provider 插件不能发起任何网络请求 | Provider world 没有导入；`CallWorld::Mapper` | 宿主加载测试：按 0.15 构建、导入 `host` 的 Provider 被拒绝并提示重建 |
| Provider 的请求只发往 endpoint 的来源 | enco-wasm：`Destinations` 只含 endpoint | enco-wasm 测试：编码给出别处的绝对 URL 是 `plugin.contract` |
| 有响应的 Attempt，结算引用解码之前存下的映射记录 | enco-wasm 的 Provider 路径；内核写 `origin` | 宿主集成测试：完成、超长、解码失败三种结算都带 `origin`，记录中的正文与服务发出的字节相同 |
| 没有响应时 `origin` 为空，失败照旧可以重试 | enco-wasm | 宿主集成测试：连接失败是可重试的 `provider.network`，没有 `origin` |
| 计划的输出上限在 1 与所属目标的预算之间 | 内核：`bind_composition` | 内核测试：超出预算与为 0 都是 `plugin.contract` |
| 扩展只回放给写下它的插件 | 内核：`plan::resolve` | 已有测试 |
| Gemini 请求的第一个回合不是带函数调用的模型回合 | gemini 插件的编码 | 插件单测；真实服务核对 |
| Anthropic 的规范输入用量包含缓存的写入与读取 | anthropic 插件的解码 | 用真实样本的单测 |

协议的编码与解码在各插件的单测中核对，样本按「真实样本」的原样写。经宿主边界的核对放在 `apps/enco/tests/integration/`，与 M40 的 `overflow.rs` 相同，经出厂插件与本地的 HTTP 假服务。

## 内核端口（草案）

```rust
#[async_trait]
pub trait Provider: Send + Sync {
    /// Complete a frozen request. With `record`, the service's response is recorded there before
    /// it is decoded. Dropping the future cancels local work.
    async fn complete(
        &self,
        settings: &ProviderSettings,
        request: ProviderRequest,
        record: Option<Recording>,
    ) -> Answered;
}

/// Where the responses a Provider decodes are recorded, and under which generation.
pub struct Recording {
    pub generation: GenerationId,
    pub store: Arc<dyn Store>,
}

/// How a completion call ended, with the recorded call that decoded the service's response.
pub struct Answered {
    pub result: Result<Completion, CompleteError>,
    /// Absent when no response arrived, when encoding failed, or without `record`.
    pub origin: Option<MappingOrigin>,
}
```

`Channel::open` 也是这样接收代际与 Store 的。`Embedding` 端口不变。

## 验收

- **Provider 不做 I/O**
  - 五个 Provider 插件的制品都不导入 `host`。
  - 按 0.15 构建的插件加载时被拒绝，并提示重建。
  - Provider 给出 endpoint 之外的绝对 URL 是 `plugin.contract`。
- **响应先记录**（宿主集成测试，本地 HTTP 假服务）：
  - 完成、超长与 401 三种结算都带 `origin`；映射记录的 `export` 是 `completion.decode`，正文 blob 与假服务发出的字节相同。
  - 连接被拒是可重试的 `provider.network`，结算没有 `origin`。
  - 解码 trap 的结算是 `plugin.trap`，仍带 `origin`。
- **原有行为不变**：
  - DeepSeek 带 `reasoning_content` 的多轮工具调用、Gemini 逐个调用的签名照常回放；
  - M40 的超长样本照常映射；
  - embedding 照常工作，条数不符由宿主报告。
- **Gemini 的前导回合**：
  - 第一个模型回合带函数调用时，编码在它前面补上固定文字的 user 回合；
  - 第一个回合是模型文字、或者已是 user 时不补；
  - 真实 Gemini 在 Run 中途压缩之后的下一个 Round 照常回复。
- **输出上限**：
  - composer 给出 0 或超过目标预算的输出上限，组装以 `plugin.contract` 失败；
  - 回复计划与压缩计划分别对照各自目标的预算。
- **Anthropic**（插件单测用「真实样本」的原样，经宿主边界一次）：
  - **请求的形态**：
    - system 进入顶层 `system`；
    - 相邻 tool 消息合成一条 user 消息；
    - 调用与结果按 ID 或顺序配对；
    - 图片与工具结果里的图片照常编码；
    - 顶层带 `cache_control`；
    - 选项覆盖保留字段时为 `provider.bad_request`。
  - **响应的映射**：
    - 带 `thinking` 的回复写整份扩展，回放时原样发出；
    - 只有文字的回复不带扩展；
    - 用量按三项相加；
    - 停止原因按上表映射。
  - **超长**：`counted` 为 224,032，`accepted` 为 200,000；413 为不带数字的超长；其他 400 是 `provider.bad_request`。
- **Responses**（同上）：
  - **请求的形态**：
    - 固定 `store: false` 与 `include`；
    - 选项写 `previous_response_id` 或 `truncation` 是 `provider.bad_request`；
    - 工具定义带 `strict: false`；
    - 工具结果里的图片编码为数组。
  - **响应的映射**：整份 `output` 进扩展并原样回放；`incomplete` 映射为 `max-tokens`。
  - **超长**：`context_length_exceeded` 映射为不带数字的超长。
- **真实服务**：实现之后各走一遍：
  - 官方 Anthropic 与官方 OpenAI 各完成一次带工具调用、多轮回放（含思考内容）的 Run；
  - 各走一次超长拒绝，确认 Round 缩小重发并完成回复；
  - 核对 `/status` 的实测用量与服务回报的一致，Anthropic 含缓存部分。
  
  结果记入本计划。
- **升级 oracle-jp**：
  - 库由主人从 21 升到 22：旧的 `AttemptSettled` 补上 `"origin": null`。
  - 升级前核对每条计划记录的 `max_output_tokens` 都有值。记录正文用 zstd 压缩，用库的读取路径或 `zstd -d` 核对；有空值就停下与主人对齐。
  - 库的版本不是 22 时拒绝启动。

## 待定

1. **Anthropic 的 beta 与思考块的前缀绑定**（M41 不做）
   - **机制。** Claude 5 一代模型的思考块签名记着产生它时的前缀：顶层 `system`、`tools` 的集合与此前的全部消息，并且链到上一个思考块。回放时服务核对前缀，前缀变了就是不匹配。换了模型的块由服务静默丢弃，不算不匹配。
   - **Enco 什么时候改变前缀。**
     - 压缩：摘要进入 system，保留下来的尾部回合还带着压缩之前产生的思考块；
     - 超长缩小时省略早先的历史；
     - 能力目录换代，`tools` 随之变化；
     - composer 不再沿用上一份计划，重新排出头部。
   - **谁受约束。** 2026-08-31 及之后创建的账号，在 Fable 5.1、Opus 5.5、Sonnet 5.5 上受约束；Mythos 5.1 不论账号新旧都受约束。受约束时，不匹配的请求以 400 失败（`Invalid signature in thinking block. The block is bound to a different conversation.`），原样重发也一样。不受约束时，块照样交给模型。主人的账号实测不受约束。
   - **受约束时的后果。** 那次请求是不可重试的 `provider.bad_request`。扩展留在 Log 里，之后每次回放都带着这些块，所以这个 endpoint 上的 Session 每次都会失败，直到换模型或回溯到压缩之前。
   - **服务给的控制。** 请求头 `anthropic-beta: thinking-binding-controls-2026-08-01`，加上正文 `thinking.block_binding.prefix_mismatch_behavior`：
     - `drop_block`：服务丢掉第一个不匹配的块及其后的全部思考块，照常回答，丢了哪些写在响应的 `input_transformations` 里；
     - `error`：400。

     实测：这个字段必须与 `thinking.type` 同时出现；只有头、没有字段时，不受约束的账号照常回答，块被标为 `thinking_mismatch_allowed`；没有头却写了字段是 400。
   - **难点。** `settings.options` 只合并进正文，表达不了请求头。
   - **三种写法。**
     - **自动加上**：正文的 `thinking.type` 为 `adaptive` 或 `enabled` 时，插件自动写上 `drop_block` 与请求头。主人不必做什么，但省略 `thinking` 时（Claude 5 一代默认就会思考）没有保护；不认这个 beta 的中转会因此拒绝每个请求。
     - **`betas` 选项**：仿照官方 SDK 的 `betas` 参数，选项里的 `betas` 数组由插件移进 `anthropic-beta` 头，其余照旧并进正文。主人这样写：`{"betas": ["thinking-binding-controls-2026-08-01"], "thinking": {"type": "adaptive", "block_binding": {"prefix_mismatch_behavior": "drop_block"}}}`。一条规则覆盖所有 beta 功能，例如 fast mode。
       - **不碰不变式。** 选项的含义本来就由插件定义，WIT 写的是"adapter merges into its request"，没有说正文。内核与宿主不解释选项：它们只作为 `settings` 的一部分，随 `AttemptStarted` 原样记下，并参与 M40 的组合身份。`betas` 不是密钥，凭证仍只经放置规则附加。编码是纯函数，线上的请求头可以由记下的选项求出。
       - **对 Agent 的代价只有一个键。** 这条规则写在插件的 README 与导航手册里；写错名字由服务以 400 拒绝，登记时的真实调用就会报出，不会悄悄失效。官方 SDK 正是这样写 `betas` 的，模型熟悉这个写法。
       - **插件内的代价。** 先从选项里取出 `betas`，再把其余部分交给 `apply_options`，只多几行。第二个插件也需要经请求头表达的参数时，再把这条规则收进 SDK。
       - **没有选通用的 `headers`。** 在 endpoint 上开一个写请求头的字段看起来更通用，但它是没有使用者的契约字段；`settings` 会原样记进 Log，这个字段会诱使人把令牌写进配置，绕过只经环境变量与放置规则附加的凭证机制；插件也看不到它，没法知道 `block_binding` 与它配套的请求头是否同时在场。
     - **由字段推出请求头**：正文里有 `thinking.block_binding` 时，插件加上它需要的头。只解决这一项。
   - **建议。** 出现第一个受约束的使用（新账号、Mythos），或第一个需要 beta 的功能时，用 `betas` 选项。
2. **Gemini 的空正文 404**（主人确认暂不处理）：M40 与本次取样都见过，同样的请求随后正常。现在归为 `provider.bad_request`，不可重试，Round 会换候选或失败。真实使用中频繁出现时再决定解码怎样归类。
3. **加密内容的估算**：composer 按扩展的字节数估算，Responses 的 `encrypted_content` 与 Anthropic 的 `signature` 会被高估。实测中一项 2,380 个字符的 `encrypted_content` 按字节约估 600 token，回放时服务只多计 74 token。沿用上一份计划时，实测前缀会吸收这部分，误差只在最近一次回复上；真的导致过早压缩时再处理。
4. **中转与兼容服务**：Kimi、MiniMax、智谱、OpenRouter 等提供 Anthropic 兼容或 Responses 兼容的接口，主人的密钥里都有。本次只核对官方服务。兼容服务在真实使用中遇到差异时，按"依赖的部分严格"在插件里处理，或者由主人换用 openai-compatible。
