# M29 composer 插件

> 路线图 P2 的第 11 个里程碑。计划的生命周期见[路线图](../Roadmap.md)。

## 目标

默认 composer 改为 Wasm 插件，Agent 以评测成功率为目标、以 Attempt 记录的用量（含缓存命中）为成本约束迭代它（上下文专题）。

## 对齐的判断

- **计划以完整内容的哈希为身份，存储只共享已经存过的部分**。"模型可见 ⟺ 已记录"要求每次 Attempt 先记下计划，现在每份计划都是一个完整的 blob。live-lookup 的一次试跑中，每份约 13 KB，其中工具定义约 10 KB（17 个工具），内联说明约 3 KB，每条 Log 引用约 45 字节。目录不变时，工具定义每个 Round 原样再存一遍；只追加的计划每份都比上一份长，总量随会话长度按平方增长，直到压缩开始新的系列。所以存储改为共享已有的部分：
  - 工具定义按内容寻址，计划中只存它们的哈希；
  - 新计划的条目以本 Session 上一份计划的全部条目开头时，存为"上一份计划 + 新追加的条目"，否则存全量。

  是否增量只由前后两份计划比较得出，不看计划出自哪个 composer：默认 composer 开始新系列时，以及重排历史的组装方式（例如 SillyTavern 式的），都自然走全量。按 composer 的身份分支，正是双向不泄露所拒绝的结构。

  这是 Store 内部的存储编码。Log 中记的仍是完整计划的哈希；检视、重试与下一次组装读到的总是完整计划，还原后按哈希核对，链上任何一环缺失都直接报错。所以"记录的就是模型看到的"不变，composer 的契约也不变。走全量的组装方式受上下文预算约束，每份计划都有长度上限，存储只随 Round 数线性增长；它每轮重复的内联内容（如角色卡、世界书）测出问题时，再像工具定义一样按哈希共享。

## 范围

- **composer 的 WIT 接口**，在本里程碑开始时单独讨论。主要问题是：每个 Round 都要把输入交给插件，而线上的历史已经有 22.5 万 token，是整份传过去，还是经宿主导入按需读取 Log 条目？倾向整份传入：
  - composer 的契约是"对显式输入的纯函数"（上下文专题），按需读取会让输入变成隐式的，契约测试还得另外记下它读了什么；
  - 22.5 万 token 约 1 MB，跨 Wasm 边界拷贝一次是毫秒级，相对一次模型请求可以忽略；
  - 真要优化，`ComposeInput.previous_plan` 已经提供了增量的形态（上一份计划加上之后的新条目），等测量证明需要时再做。
- 默认 composer 改为出厂的 Wasm 插件；原生的 `FactoryComposer` 保留，作为安全模式的策略。
- `AttemptStarted.composer` 记录 composer 的代际（`CodeRef::Generation`）。
- 挂在 composer 名下的事项（稳定性标注、按空闲时长开始新系列、缓存友好的披露策略）由 Agent 在评测下迭代，不作为本里程碑的验收条件。
- **计划的存储**（见对齐的判断）：
  - 工具定义按内容寻址存放；
  - 记录计划时与本 Session 上一份计划比较，决定存增量还是全量；
  - 还原时沿父链走到最近的全量计划，再按哈希核对。系列的边界自然截断父链，运行中上一份计划就在内存里，只有重启后的第一次组装要走一遍链，所以先不设链长上限，测出慢了再加；
  - 以后为 blob 设计回收时，计划的保留要沿父链计算。
- **Agent 怎样运行评测**：运行器与题目在 Enco 仓库中，不在 `ENCO_HOME`。Agent 在工作区取得与宿主版本对应的 Enco 仓库，经 shell 在后台运行运行器，把自己的 composer 作为被测的代际传入（M19），再读取 `result.json`。变体倾向给出插件的源码目录，在试跑中经正式路径构建，被评测的就是之后登记的同一份源码，届时 `enco plugin deploy <name> <path>` 可以删除；本里程碑开始时决定。
- **留出集推迟**：验证专题要求 Agent 开始对着任务集自我进化时，把留出集放到它够不着的地方。本里程碑只演示一轮迭代，谈不上记住答案，所以推迟到 Agent 开始反复迭代时，那时留出集放到另一个节点或另一个系统用户下。

## 设计

- 上下文专题的「composer 是每个 Session 的属性」与「修复工具的常驻是 Session 声明的要求，由内核校验」已经写入；原生的出厂 composer 留给安全模式，由插件专题「原生能力与插件经同一组端口接入，救生集始终有原生实现」覆盖。
- "计划以完整内容的哈希为身份，存储只共享已经存过的部分"，验收时判断是否提炼，候选位置是上下文专题「叙述逐字冻结在计划中」之后。
- 先定下的格式：composer 的 WIT 接口（待定）；计划的存储编码（增量或全量、工具定义的哈希），库的版本随之升级。

## 验收

- 部署一个改坏了披露策略的 composer 代际之后，仍能调用文件、Shell 与部署管理，并经正式路径回退：计划不满足声明的要求时按 composer 失败处理（上下文专题），Round 失败后进入安全模式（M22）。
- 计划的存储：
  - 默认 composer 连续运行若干 Round，每个 Round 新增的存储只与新追加的条目成正比；
  - 工具目录不变时，每个工具定义只存一份；
  - 不是追加形态的计划存全量；
  - 重启之后，任何一份计划还原出的内容都与记录的哈希一致。
- 以 Wasm composer 运行的已有评测题，按 `evals/README.md` 的判定规则不低于原生 composer。
- `many-tools` 上，Agent 至少完成一轮"修改 composer → 部署 → 评测"的迭代，结果写入运行记录。
