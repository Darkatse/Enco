# M29 composer 插件

> 路线图 P2 的第 11 个里程碑。计划的生命周期见[路线图](../Roadmap.md)。

## 目标

默认 composer 改为 Wasm 插件，Agent 以评测成功率为目标、以 Attempt 记录的用量（含缓存命中）为成本约束迭代它（上下文专题）。计划的存储只保存每次新增的部分，进入 SQLite，无人引用的 blob 按引用回收。

## 对齐的判断

- **计划以完整内容的哈希为身份，存储只共享已经存过的部分**。"模型可见 ⟺ 已记录"要求每次 Attempt 先记下计划，现在每份计划都是一个完整的 blob，而默认 composer 只在末尾追加，所以每份计划都把上一份的全部内容再存一遍。单份计划受上下文预算约束，长期是线性增长，但常数是整份计划。2026-10-24 在 VPS 上只读测量了 25 天的真实使用：
  - blob 共 659 MB，数据库 10 MB；其中 97.6% 是计划。358 MB 是当前库引用的 1342 份计划，中位数 284 KB，约每天 14 MB；另有 296 MB 是迁移按新格式重写计划之后留下的旧 blob，已无人引用；图片、超长结果全文与制品合计约 4.4 MB。
  - 对 358 MB 当前计划：每份单独 zstd 为 155 MB（2.3×）；按字节公共前缀再 zstd 为 8.3 MB（43×，`tools` 排在 `items` 之后，每份都带着整个工具目录）；工具目录按内容共享、条目以上一份为父再 zstd 为 4.3 MB（82×）；对上一份做 zstd 差分为 2.7 MB（133×）。工具目录中位 7.3 KB，全程只有 8 种；最长的一个系列有 203 份计划。

  所以冗余在计划之间，单份压缩只是补充。存储改为：
  - 工具目录按内容存为一个对象，计划记录只引用它；
  - 新计划的条目以本 Session 上一份计划的全部条目开头时，记为"上一份计划 + 新追加的条目"，否则记全量；还原链设上限，到上限也记全量，使还原的代价有界；
  - 每条记录以 zstd 压缩，写进 SQLite，与引用它的 AttemptStarted 在同一个事务中提交。先写 blob 再提交的两步之间崩溃会留下孤儿；同一个事务让它从结构上不可能出现，也就是"写入与接纳事实一起原子提交"。

  是否增量只由前后两份计划比较得出，不看计划出自哪个 composer：默认 composer 开始新系列时，以及重排历史的组装方式（例如 SillyTavern 式的），都自然走全量。按 composer 的身份分支，正是双向不泄露所拒绝的结构。

  这是 Store 内部的存储编码，身份与表示分开，与 LayerFS 的做法相同。Log 中记的仍是完整计划的哈希；检视、重试与下一次组装读到的总是完整计划，还原后按哈希核对，链上任何一环缺失都直接报错。所以"记录的就是模型看到的"不变，composer 的契约也不变。它每轮重复的内联内容（如角色卡、世界书）测出问题时，再像工具目录一样按内容共享。
- **路径会交出去的 blob 保持原样**。图片、超长结果的全文与发给主人的文件，以文件路径交给 Agent 与主人读取，压缩后按路径读到的就是乱码；它们本来也不大，图片已经是压缩格式。所以只有计划这类从不交出路径的内部记录换存储编码。
- **无人引用的 blob 按引用回收**。回收的条件"测出需要"已经满足：迁移留下了 296 MB 无人引用的计划。规则由引用推出：Log 与登记中按类型引用的内容都保留，没有引用的删除；被引用的旧内容是否删除属于保留策略，是主人的事，不在本里程碑。新库建表时开启 `auto_vacuum = INCREMENTAL`，以后计划记录有了保留策略，删除之后可以逐步把空间还给文件系统，不必重写整个库；它只在建库时能设，事后开启要做一次 `VACUUM`。按现在的用量，库与 blob 合计每天约增长 0.7 MB。

## 范围

- **composer 的 WIT 接口**，在本里程碑开始时单独讨论。主要问题是：每个 Round 都要把输入交给插件，而线上的历史已经有 22.5 万 token，是整份传过去，还是经宿主导入按需读取 Log 条目？倾向整份传入：
  - composer 的契约是"对显式输入的纯函数"（上下文专题），按需读取会让输入变成隐式的，契约测试还得另外记下它读了什么；
  - 22.5 万 token 约 1 MB，跨 Wasm 边界拷贝一次是毫秒级，相对一次模型请求可以忽略；
  - 真要优化，`ComposeInput.previous_plan` 已经提供了增量的形态（上一份计划加上之后的新条目），等测量证明需要时再做。
- 默认 composer 改为出厂的 Wasm 插件；原生的 `FactoryComposer` 保留，作为安全模式的策略。
- `AttemptStarted.composer` 记录 composer 的代际（`CodeRef::Generation`）。
- 挂在 composer 名下的事项（稳定性标注、按空闲时长开始新系列、缓存友好的披露策略）由 Agent 在评测下迭代，不作为本里程碑的验收条件。
- **计划的存储**（见对齐的判断）：
  - 工具目录按内容存为对象；
  - 记录计划时与本 Session 上一份计划比较，决定记增量还是全量；还原链的上限按还原耗时测定；
  - 记录以 zstd 压缩（引入 `zstd` crate），存进 SQLite，与 AttemptStarted 同一个事务提交；计划不再写成 blob；
  - 还原时沿父链走到最近的全量记录，再按哈希核对；
  - 计划记录以后的保留沿父链计算，本里程碑不删除计划记录。
- **blob 回收**：标记 Log、登记与 M28 的手册表按类型引用的 blob，删除其余；第一次运行清掉迁移留下的旧计划。新库开启 `auto_vacuum = INCREMENTAL`。
- **Agent 怎样运行评测**：运行器与题目在 Enco 仓库中，不在 `ENCO_HOME`。Agent 在工作区取得与宿主版本对应的 Enco 仓库，经 shell 在后台运行运行器，把自己的 composer 作为被测的代际传入（M19），再读取 `result.json`。变体倾向给出插件的源码目录，在试跑中经正式路径构建，被评测的就是之后登记的同一份源码，届时 `enco plugin deploy <name> <path>` 可以删除；本里程碑开始时决定。
- **留出集推迟**：验证专题要求 Agent 开始对着任务集自我进化时，把留出集放到它够不着的地方。本里程碑只演示一轮迭代，谈不上记住答案，所以推迟到 Agent 开始反复迭代时，那时留出集放到另一个节点或另一个系统用户下。

## 设计

- 上下文专题的「composer 是每个 Session 的属性」与「修复工具的常驻是 Session 声明的要求，由内核校验」已经写入；原生的出厂 composer 留给安全模式，由插件专题「原生能力与插件经同一组端口接入，救生集始终有原生实现」覆盖。
- "计划以完整内容的哈希为身份，存储只共享已经存过的部分"，验收时判断是否提炼，候选位置是上下文专题「叙述逐字冻结在计划中」之后。
- Session 专题「Log 只记事实的骨架」改写：计划不再存为 blob，而是库中按结构共享的记录；"记录保留多久是主人的策略"同时作用于计划记录与 blob。
- 先定下的格式：composer 的 WIT 接口（待定）；计划记录与工具目录的表、记录的编码（增量或全量、zstd）；库的版本随之升级，新库开启渐进回收。

## 验收

- 部署一个改坏了披露策略的 composer 代际之后，仍能调用文件、Shell 与部署管理，并经正式路径回退：计划不满足声明的要求时按 composer 失败处理（上下文专题），Round 失败后进入安全模式（M22）。
- 计划的存储：
  - 默认 composer 连续运行若干 Round，每个 Round 新增的存储只与新追加的条目成正比；
  - 工具目录不变时，每个工具定义只存一份；
  - 不是追加形态的计划存全量；
  - 重启之后，任何一份计划还原出的内容都与记录的哈希一致；
  - 计划记录与 AttemptStarted 同一事务提交，在两者之间注入故障，不留下任何计划记录；
  - 还原链达到上限时记全量，任何一份计划的还原步数不超过上限。
- blob 回收：Log 与登记引用的图片、全文、发出的文件、源码与配置，以及运行中代际的插件导航手册都保留，无人引用的删除；回收之后，检视、倒带与对比照常，删掉手册投影再启动仍能重建。
- 手动核对：在 oracle-jp 的真实历史上重新编码，计划的总存储与测量的估计（约 4 MB）同一量级。
- 以 Wasm composer 运行的已有评测题，按 `evals/README.md` 的判定规则不低于原生 composer。
- `many-tools` 上，Agent 至少完成一轮"修改 composer → 部署 → 评测"的迭代，结果写入运行记录。

## 待定

- composer 的 WIT 接口。
- **回收的触发方式**：守护进程启动时、开始服务之前自动运行（此时没有正在写入、尚未提交的 blob），还是主人的管理命令。
- **构建日志**：它存为 blob，却只以路径出现在结果文本里，按类型的引用找不到它。回收时是按文本中的路径保留，还是作为可回收的诊断，届时决定。
