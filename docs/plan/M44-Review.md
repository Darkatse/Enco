# M44 审阅：新机制与既有路径接合处的修正

> M44 实现之后的两轮审阅。2026-11-10 主人两次转来外部审阅意见，逐条对照代码核实之后，与主人对齐了下面的判断。修正属于 M44，与它一起验收；计划中被改动的段落已同步修订，见「对计划的修订」。

## 结论

- **问题集中在接合处**：新机制与既有的调度批次、健康门控、回溯、Profile 准入相接的地方，以及迁移用无类型 JSON 的形状猜测代替了类型边界。几乎都出自 M44 的实现。
- **修正的方法**：每一处都在源头修正，推广已有的规则，或删除造成分歧的条件，不在下游加补偿或第二道防线。
- **第二轮**：找到第一轮修正留下的两处缺口和一处措辞。
  - 准入只守护了视图的两端，没有守护中间。
  - "不取代输入的命令不改变对话"只用到了一个折叠。
  - 处境与调用的失败把加载失败也说成试用失败。
  - 三处同样在源头修正，见第 11 至 13 条。
- **不成立或不采纳**：Store 单个读取的撕裂（不成立）；按条件跳过提交时的物化（理由被夸大，修法会让"哪些条目相关"有两个定义）。

## 判断与修正

### 1. 三个定时工具在结算时按调用顺序、对着有效视图求值

- **事实**：
  - `schedule_create` 与 `schedule_cancel` 改为只读之后，与 `schedule_list` 落进同一个并发批次。建立与取消在结算时才写，列表在执行时就读，所以一条回复里先建立再列出，列表看不到建立。计划曾把这写成接受的行为，但同一族工具在同一条回复里从两个时刻回答，是认知上的不一致。
  - 计划本身就分裂了：取消对着已提交视图检查，列表读有效视图。主人取消已接纳、或一次性定时的提醒已经进入 Inbox 时，列表已经不列出它，取消却回答成功，随后提醒照样到达。
  - Round 开始时采样配置（`session_view` 返回的视图），composer 用它的时区；dispatch 却每批重读当前配置的时区，`schedule_list` 又读一次。
- **修正**：
  - `schedule_list` 与另外两个一样成为内置调用：执行时只解析参数，结算时由 actor 按调用顺序求值。三者读同一个视图，即本 Session 的有效视图。
  - Agent 问的是"这个定时以后还会不会提醒我"，只有有效视图答得准。计划为已提交视图给的理由是"actor 是唯一的写者"，但这条用不上：折叠按身份合并，重复的取消结果相同。读取与提交之间被接纳的取消或提醒，只会让这次取消成为多余，不会让任何事实出错。
  - 时区取 Round 采样的配置。dispatch 读当前视图，只为了健康门控。
  - `BuiltinTool` 去掉只为列表而持有的 `store` 与 `registry`。
  - 定时的已提交视图不再有生产代码读取，Store 的 `committed_schedules` 删去；测试改读有效视图或 Log 中的事实。
- **必须保持的行为**：
  - 一条回复内按调用顺序结算：先建立再列出，列表看得到；先建立再取消，取消成功；取消别的 Session 的定时或已不再有效的定时，结算为失败，什么也不写。
  - 结算之前中断的定时调用结算为失败，不留 `unknown`。

### 2. 健康门控只看健康记录

- **事实**：`Exports::failed` 先查到失败，再要求找到这个插件当前的路由，找不到就返回"没有失败"。自建插件没有回退目标、试用失败之后不再运行，路由随之消失，同一个 Round 下一批调用就会执行已经失败的代码。这是改写这个函数时为了在文字里写出插件名引入的回归：判断的前提被挂在了描述用的信息上。
- **修正**：
  - 是否失败只看健康记录；现在运行的代码只用来描述，可以没有。
  - 插件名取自 Round 开始时绑定这个工具的名字，也就是模型当时看到的名字。只有插件的工具才可能指向失败的代码，原生工具没有插件名，也不进入这个判断。
- **必须保持的行为**：同一批已获准的调用照常结算；之后的批次对失败的代码一律以 `plugin.rolled_back` 拒绝；没有可运行的旧版本时如实说明。

### 3. 不取代输入的命令不改变"欠一个回答"

- **事实**：回溯到一条输入时，actor 随后开始一个 Run 重新回答它；判断方式是"Log 的最后一条是回溯到输入"。Inbox 里回溯之后紧跟一条作用于 Session 自身的命令（或压缩请求）时，actor 先消费回溯，再消费命令，Log 的最后一条变成命令，于是 actor 进入空闲，那个 Run 永远不会开始。
- **修正**：
  - 把已有的规则"不取代输入的命令不改变对话"用到这个判断上：从 Log 末尾往回，跳过不取代输入的命令（`leaves_inputs()`，见第 12 条），看到的第一条是回溯到输入，就还欠一个回答。
  - 往回读的范围同步扩到被跳过的命令之前。
  - 不在 actor 的内存里另记标志。
- **必须保持的行为**：
  - 自身命令先在边界上生效，随后开始的 Run 在新的工作目录或 profile 下重新回答。
  - 空闲时单独收到的自身命令仍然只被消费，不开始 Run。
  - 之后的叫停仍然取代尚未开始的重新回答。

### 4. Profile 的准入与谱系的读取

- **准入保护 Session 接下来会经过的每个视图里的 profile**：
  - **事实**：子 Session 的 Round 沿谱系读祖先已提交的行。父仍是已提交的 A、待消费的命令改为 B 时，准入只看有效视图里的 B，放行了删除 A 的登记；子的下一个 Round 解析 A 失败。计划中"单机时这就是全部事实"写错了：仍在使用的 profile 不只是有效视图里的那个。
  - **修正**：Store 在一次读取里给出每个未归档 Session 接下来会经过的每个视图，准入保护其中所有的 profile。只保护已提交与有效两端还不够，见第 11 条。
- **一个 Round 的谱系一次读出**：
  - **事实**：`session_view` 对自己与每个祖先各读一次已提交的行，两次之间可能插进别的 Session 的提交，拼出从未同时成立的权限交集。
  - **修正**：Store 在一个读事务里读出整条谱系。
- **Store 的单个读取（不成立）**：`SqliteStore::run` 在整个闭包期间独占唯一的连接，同一个闭包里先读行、再读 Inbox，中间不会插进提交。但有的函数开了读事务，有的没有，写法不统一。统一为一条规则：一个回答需要多条语句时，在一个读事务里读。这样每个函数的一致性由它自己给出，不依赖连接的安排。Session、谱系、子 Session、定时、子状态与注册表的读取都照此。
- **必须保持的行为**：Round 内权限固定；有意的登记不会让正在运行或即将开始的 Round 因 `profile.unknown` 失败；外部读取看到一致的有效视图。

### 5. 迁移按类型找出处，只迁移被事实指向的映射记录

- **事实**：
  - 迁移在整棵 JSON 里把"恰好有 `call` 与 `index` 两个字段的对象"当作映射出处改写。这会进入插件拥有的不透明 JSON（`Part::Extension` 的数据、工具的参数与输出、连接状态里的 `protocol`），违反双向不泄露。
  - `records()` 只凭三个键名就在 `evidence` 表里认定映射记录，并删掉旧行。证据表也存外部的原始响应，同形的响应会被静默删掉，而且核对发现不了。
  - 连接的状态按 `Value` 改写，跳过了宿主状态类型的解码。
  - 补记定时的事实时，结算内容的解析失败被 `unwrap_or_default` 与 `.ok()` 吞掉；这原本是为了跳过失败结算的文字。
- **修正**：
  - **按类型找出处**：v23 的格式已经冻结，出处在持久化类型中的位置是固定的几处：
    - 渠道输入的来源；
    - 早先消息的出处；
    - 引用的抓取出处；
    - `AttemptSettled` 的出处；
    - 投递结算的出处；
    - 连接状态中早先消息的出处。
  - 文档先在 JSON 层改写格式变了的字段，再解码成当前类型，在类型上逐个改写出处。不透明的 JSON 原样不动。
  - **记录随出处迁移**：被出处指向的记录才迁移，每一条都必须能按 v23 的形式读出，否则不迁移；没有被指向的证据原样保留。映射器的参数里不含出处，记录之间没有引用，不需要检查。
  - **连接的状态按宿主的状态类型解码**：遍历出处的函数放在拥有这个类型的 channel 模块。迁移代码删除时，它成为死代码，编译器会指出它。
  - **补记定时只看成功的结算**：内容被截断时读完整文本；解析失败就报错。
- **必须保持的行为**：所有真实的出处与记录完整迁移；外部的原始响应与插件的不透明 JSON 原封不动；任何解析不了的真实引用都让迁移回滚。

### 6. 清空跟随出厂代码的设置，运行出厂代码本身

- **事实**：显式切回出厂代码、设置为空时，不产生代际。但跟随出厂代码的插件在 `config.toml` 中删空设置时，走设置变化的路径，产生了出厂字节加空设置的试用代际；试用失败时还会"回退"到相同的代码。
- **修正**：
  - "本宿主的出厂代码加空设置就是出厂代码本身"写成一个函数，两条路径共用。
  - 设置变化的路径在插件跟随出厂代码、目标设置为空时用它。这次登记记作跟随出厂代码，历史与说明写成切回出厂代码。
- **必须保持的行为**：设置的修改仍记进这次登记与替换记录，主人回退能恢复旧设置；目录源码编出相同的字节，也不当作出厂代码。

### 7. 已停下的 Session 照常接纳作用于它自身的命令；指名定时的 Event 只在定时有效时写入

- **事实**：
  - 主人取消定时改为投进所属 Session 的 Inbox 之后，那个 Session 因存储故障停下时，取消被拒绝，主人只能归档整个 Session。
  - 取消先在事务外读出定时，再投命令：两次并发取消都回答 true，定时恰好在两步之间提醒过也回答 true。
  - `command()` 把 `Accepted::Inactive` 当作成功吞掉。
  - `command()` 先查一次 actor 是否停下，`accept` 里又查一次，是一层重复。
- **修正**：
  - **停下的规则按命令的作用对象推出**：
    - `Kernel::accept` 拒绝停下的 Session，理由是没有人会处理它；这对输入与作用于对话的命令（回溯、压缩）成立，它们要等 actor 回答或改写对话。
    - 作用于 Session 自身的命令（改 profile、改工作目录、取消定时）在接纳时就进入有效视图，对除 Round 之外的所有读者生效，不等任何人，所以照常接纳；actor 恢复后再把它们记进 Log。
    - 这与子树叫停直接写进停下的 Session 的 Inbox 是同一个做法。
    - 删掉 `command()` 里重复的检查。
  - **写入前提从提醒推广到指名定时的 Event**：提醒与主人的取消都只在定时于有效视图中仍然有效时写入，否则为 `Inactive`。并发取消、取消与提醒的先后，都由写入的事务给出准确的 true 或 false。
  - **`command()` 不再吞掉结果**：取消把 `Inactive` 读作 false；改 profile 与工作目录遇到它是内部错误。渠道输入的写入同样穷尽匹配，不把它当作接纳。
- **必须保持的行为**：
  - 普通输入、回溯与压缩发给停下的 Session 仍然明确报错。
  - 取消不存在或已不再有效的定时回答 false。

### 8. 迁移不再检查制品的字节

- **事实**：迁移只检查运行中的代际有制品文件，漏掉了旧宿主的出厂代码。
- **为什么删掉而不是补全**：
  - 制品的字节归注册表：启动时它按哈希读出并校验，缺失或损坏是能追查到原因的加载失败。
  - 迁移不碰制品文件。v23 在同样缺文件时行为完全相同，所以迁移里的检查保护不了任何东西，补全它只会多一道防线。
- **修正**：迁移只核对它改写的东西：文档能按当前类型读出，身份能解析，外键成立，事实能重建。
- **必须保持的行为**：迁移照旧确定、可重复；任何改写不成立就不提交。

### 9. 注册表不吞身份错误；创建定时只算一次

- **事实**：
  - `factory::retain`、`retained_artifacts` 与恢复的候选三处用 `state.content(..).ok()` 吞掉身份错误。`retain` 在登记提交时拿到尚未写入的新代际，靠 `.ok()` 跳过它们；另两处会掩盖坏掉的引用。
  - 建立定时时，校验与求出下一次时刻各解析了一遍规则。
- **修正**：
  - `retain` 只看 `CodeRef::Factory` 的引用：出厂字节加设置构成的代际，字节在建立时已经写成文件，不需要查内容。
  - 另两处改为传播错误，并用一个只给出制品哈希的函数，不克隆设置。
  - 建立定时由一个构造函数一次完成校验，并给出下一次时刻。

### 10. 同一个名字只指一样东西

- channel 模块私有的 `enum Creation` 表示卡片或会话"建成了没有"，与 core 的 Session 创建记录 `Creation` 同名，在同一个 crate 里指两样东西。改名为 `Appearance`。它的 serde 格式只含变体名，持久化的内容不变。

## 第二轮的判断与修正

### 11. 准入守护 Session 接下来会经过的每个视图

- **事实**：
  - actor 先读 Inbox 的快照，再把其中作用于 Session 的命令记为消费；快照之后接纳的命令留在 Inbox。每次消费的是这类待消费命令按 Inbox 顺序的一段前缀，所以已提交的视图会逐个经过中间的视图，不会从已提交直接跳到有效。这个前缀由 actor 的三条消费路径给出：Round 边界、空闲时，以及叫停与回溯。
  - 第一轮的准入只保护两端。设想 Session 用 A，actor 已读到改为 B 的命令，提交之前又接纳了改为 C 的命令。这时删除 B 的登记只核对 A 与 C，被放行；actor 随后消费 B，下一个 Round 以 `profile.unknown` 失败。
  - 失败是可见的，但"登记不删除仍在使用的 profile"这条保证不成立。第一轮把"Session 还会读到哪些视图"当成了两个端点，它其实是一条路径。
- **修正**：
  - Store 在一次读取里给出每个未归档 Session 接下来会经过的视图：已提交的视图，以及它依次折叠每条待消费 Event 之后的视图；有待消费的 Event 时，最后一个就是有效视图。准入保护其中所有的 profile。
  - 中间的视图由提交时用的同一个折叠（`SessionRecord::consume`）给出，准入不另外判断哪种 Event 指名 profile。以后新增能改 profile 的命令，折叠的穷尽匹配会要求先决定它，准入随之覆盖。
  - 审阅建议保护"已提交的 profile 与全部待消费的 profile 命令"，集合与此相同；差别只在这份知识放在哪里。
- **不采纳的修法**：
  - 给消费加锁：删除可能早已通过，锁挡不住。
  - 消费时重新校验、拒绝或跳过命令：已接纳的命令消费即生效，消费是事实，不是又一次准入。
  - 由 Store 在提交时一次消费到最新：消费哪些命令是 actor 的事实，不能由 Store 替它决定。
- **边界**：
  - 待消费的命令指名的 profile 在命令被消费之前一直受保护。被拒绝的登记的原因写成 Session "现在或从之后的某个 Round 起" 使用它。
  - 已归档的 Session 不在其内：它已被叫停，归档之前读到的 Inbox 至多让进行中的 Run 再开始一个 Round，那个 Round 读到被删的 profile 时以 `profile.unknown` 失败，Run 照旧以叫停结束。
  - 若把已归档、仍有叫停待消费的 Session 也算进来，因存储故障停下的已归档 Session 就会永远挡住登记，所以不这样做。
- **必须保持的行为**：
  - 已接纳的命令消费即生效，事实仍记为 `EventConsumed`。
  - Round 只读已提交的视图。
  - 有意的登记不会让未归档的 Session 或它的子孙接下来的 Round 因 `profile.unknown` 失败。

### 12. 不取代输入的命令，在 core 命名一次

- **事实**：
  - 叫停的折叠（`ChildStateFold::input`）只跳过压缩请求。作用于 Session 的三种命令都被当作比叫停更新的输入，抹掉了叫停。
  - 于是父的上下文不再显示子被叫停，`/status` 也从"已叫停"变为空闲，而实际上没有任何工作恢复。待消费与已消费时都是如此。
  - 这与第 3 条是同一个判断。第一轮只把它用到"欠一个回答"的折叠，没有找出依赖同一判断的其他读者。
- **修正**：
  - `EventBody::leaves_inputs()` 给出不取代输入的命令：压缩请求与作用于 Session 的命令。它与 `supersedes_inputs()` 恰好把命令分成两类。
  - 依赖这个判断的读者都改用它：
    - 叫停的折叠跳过它们；
    - "欠一个回答"的折叠跳过它们；
    - 模型看不到它们（`canonical_message`）；
    - 空闲时它们单独被消费，不开始 Run。
  - 除叫停的折叠之外，另三处原来结果正确，但各自写了一遍这个集合；空闲时的消费还要靠前一个分支先排除取代输入的命令，才与它相等。
- **必须保持的行为**：
  - 叫停、回溯与普通输入对叫停、等待回答与回复去向的影响不变。
  - 不取代输入的命令不解除叫停，不开始或结束等待，不移动回复去向，模型看不到它们。

### 13. 给主人与 Agent 的文字只说代码失败了，不说何时失败

- **事实**：
  - 启动时恢复（`restore`）会把加载失败的运行中代际记为失败；回退时加载失败的候选同样记为失败。这两种代际此前都可能已经是健康的。
  - 状态从"登记的代码已失败、运行的是别的代码"推出回退的处境，并不知道失败是否发生在试用期，处境的文字却写成 "failed on trial"。
  - 调用的失败同样只读健康记录。一个 Round 绑定了健康的旧代码，期间新登记的代码试用失败，回退时旧代码又加载失败；这个 Round 再调用时，文字说旧代码 "failed on trial"，同样不实。
- **修正**：
  - 处境与调用的失败都写 "failed"，失败原文说明发生了什么；不为一句文字新增生命周期状态。
  - 回退通知（`PluginRolledBack`）只由试用中的健康门控产生，照旧说 "on trial"。
- **必须保持的行为**：失败的登记号、失败原文、运行的代码与下一步照旧如实显示。

## 不成立或不采纳

- **Store 单个读取的撕裂**：不成立，理由见第 4 条；写法统一为多语句的读开读事务。
- **按条件跳过提交时的物化**：
  - 提交时读的是本 Session 的定时，按 `session_id` 走索引，不是全表；所谓的 O(N²) 中，N 是一个 Session 的定时数。
  - 在折叠之外再写一个"哪些条目相关"的判断，它与折叠一旦不一致，物化就会静默出错，这正是"一个折叠"要避免的分歧。
  - 没有测量数据，不改。

## 验收

修正已经发生过的缺陷，补上对应的测试：

- **定时工具**：一条回复中先建立再列出、先建立再取消再列出，列表反映调用顺序；主人的取消已接纳、尚未消费时，Agent 取消同一个定时，结算为失败。
- **健康门控**：没有回退目标的自建插件在第一批调用中试用失败，同一个 Round 的第二批调用以 `plugin.rolled_back` 拒绝，不执行。
- **回溯**：Inbox 中回溯到输入之后紧跟改工作目录，随后的 Run 在新目录下重新回答；Log 末尾的判断与往回读的范围由已有的性质测试覆盖。
- **Profile**：Session 已提交的 profile 与待消费的命令不同时，删除已提交那个的登记被拒绝；待消费的命令先改为 B、再改为 C 时，删除 B 的登记同样被拒绝。
- **叫停**：叫停之后的压缩请求与作用于 Session 的三种命令，待消费与已消费时都不解除叫停。
- **停下的 Session**：停下的 Session 接纳主人的取消，之后到期的提醒不写入；发给它的普通输入仍然报错。
- **主人取消**：定时已经提醒过（一次性）或已被取消时，回答 false。
- **迁移**：插件的不透明 JSON 与外部响应中有同形的对象时，迁移成功且它们原样不动；指向的记录读不出时，迁移不提交。
- **出厂设置**：跟随出厂代码的插件删空设置后，运行出厂代码本身，没有试用中的代际。
- `cargo xtask check` 通过。
