# M20 契约 0.3 与凭证

> 路线图 P2 的第 2 个里程碑。计划的生命周期见 spec 09 §5。

## 目标

`describe` 定形，密钥只在传输层：插件永远看不到值，内核只认识变量名，Provider 从实现上就不特殊（§4.4、§4.11）。

## 对齐的判断

- **P2 是连续的实现路径**：里程碑只划分实施顺序，不构成架构边界。`config-schema` 与摘要、凭证共同构成声明，供 P2 的配置手册使用；内部契约需要改变时直接迁移全部调用者。
- **契约不预留**（§4.4）：0.3 只放 P2 已有明确用途的声明。插件自带的凭证（名字与 origin）随 web 在 M23 加入，路径前缀随 Telegram 插件在 P3 加入；需要时就升主版本。
- **`describe` 只放插件整体的事实与对导入的需求**（§4.4）：摘要、配置 schema、凭证。工具定义由 `tools` 接口自己声明，渠道资源由 `channel` 自己声明。
- **密钥的值只在传输层**（§4.11）：现在的值从组合根读出，经内核的三个端口、`Endpoint.api_key`、`settings.api-key` 一路传到插件，再由 provider-protocol 自己拼请求头、自己遮蔽。改为内核只传变量名，enco-wasm 在每次调用时组装绑定。这也提前解决了 spec 04 §2 记下的问题：composer 成为插件之前，要先把密钥从 `Profile` 中分离出去。
- **密钥与它对应的地址写在同一份配置里**（§4.11）：访问哪个模型服务是 Provider 调用的内容本身，服务写在 endpoint 里，密钥就写在 endpoint 旁，检查也随之在接线中。它是否齐备取决于 endpoint，不取决于插件代际，所以 M20 没有代际级的凭证准入，那随插件自带的凭证在 M23 加入。
- **重定向只在同一 origin 内跟随**（§4.11）：按请求的 origin 附加凭证是唯一的规则，宿主不重写重定向处理。

## 范围

- **`description`**：摘要、配置 schema、凭证声明。`{}` 必须合法写进 WIT 文档，不另设检查（§4.11）。
- **凭证**：`description.credential: option<credential>`，`credential = { header, prefix, required }`，附加到调用方选定的服务（`settings.base-url`），密钥来自同一个 endpoint 的 `api_key_env`。`option` 本身表达了至多一个；名字与 origin 随 web 在 M23 加入。
- **`settings` 删除 `api-key`。**
- **密钥的值只在传输层**：
  - 删除 `Provider`、`Embedding`、`Decision` 三个端口的 `api_key` 参数，以及 `Endpoint`、`EmbeddingEndpoint`、`DecisionEndpoint` 中的值；它们只保留 `ProviderSettings.api_key_env`。
  - enco-wasm 每次调用时组装绑定：放置方式来自加载时求出的声明，origin 取 `base_url`，值按 `api_key_env` 读取环境变量。变量缺失时这次调用以明确的失败结束。
  - 启动时仍检查变量是否存在：配置代际（M21）之前，启动就是配置生效的时刻。
- **`http` 的凭证语义**：
  - 去往绑定 origin 的请求自动带上凭证，`http-request` 不变；
  - 只在同一 origin 内跟随重定向，跨 origin 的 3xx 原样交回插件；
  - 交回插件的响应与失败消息中，密钥的值替换为 `[redacted:<变量名>]`，provider-protocol 中的遮蔽删除；
  - 宿主日志不输出注入之后的请求头。
- **接线检查加上凭证**：机械回退不受此检查阻挡；调用时仍按所选代际与 endpoint 核对，不匹配明确失败，不发起匿名调用。endpoint 写了 `api_key_env` 而插件没有声明凭证，或者插件声明为必需而 endpoint 没有写，都拒绝。
- **主版本不兼容**：0.2 的制品被拒绝，错误信息指明版本。回退的候选用尽时回到当前的出厂代际（§4.6），所以主人自己部署过的 0.2 代际在升级后加载失败时，插件仍有活跃代际。
- **三个出厂插件重建**：openai-compatible 声明可选的 `authorization` 头（本地服务可以不带 key），deepseek 与 typesafe 声明为必需；provider-protocol 中的鉴权头删除。

## 规格

- 03 §1.6：失败码 `credential.unavailable`。
- 04 §2、§6.4：三个端口删除 `api_key`；`ComposeInput.profile` 不再带密钥。
- 06：记忆的 embedding 与 decision 调用不再传 `api_key`。
- 07：WIT 0.3（`description`、`credential`、`settings`）、凭证绑定、同 origin 重定向、遮蔽、出厂插件重建、主版本不兼容的错误。
- 08 §3：启动时只检查变量是否存在，值不再读进内存中的配置。
- 11 §3、§4.1、§5、§6：回退的候选以当前出厂代际结尾；接线检查加上凭证。
- 12 §1、§3：`Endpoint` 不含密钥的值；密钥路径改为传输层按名字读取。

- WIT 升级到 0.3，三个出厂插件已重建。`describe` 保留摘要、配置 schema 与凭证声明；配置由插件接受或拒绝，宿主保留声明，不增加第二套配置校验。
- `complete`、`embed`、`decide` 共用一次调用的凭证绑定；内核和调用方只传变量名。HTTP 出口统一按 origin 附加凭证并遮蔽响应与失败，旧的密钥参数、插件鉴权头与插件遮蔽代码已删除。
- 凭证与 endpoint 是否相符只在准入时检查。回退与安全模式之后可能不相符，调用照常进行，由服务给出结果，恢复路径上不再多一道拒绝。启动恢复、自动回退与手动回退共用包含当前出厂代际的候选序列。
- 自审沿配置读取、注册表准入、三种调用、HTTP 返回、代际恢复逐路径核对归属与事实来源；没有按 Provider 身份分支，也没有另建凭证生命周期或恢复路径。配置代际与 endpoint 切换仍沿 M21、M22 的规划继续。

## 审阅后的收缩

- 删除调用时的凭证匹配检查：它重复了准入，还会让安全模式在出厂代际声明不同时拒绝一次本可成功的调用。`check_credential` 收回注册表，成为 `wiring_error`，先查接口再查凭证。
- 删除凭证解析中重复的 scheme 检查，传输层本来就检查每个请求。`base_url` 的整体有效性由 M21 应用配置时的真实调用验证，启动时不另加一层。
- 启动检查与调用时对"可用"的定义一致：变量必须已设置且非空。
- `Binding` 与总纲的 Binding 重名，改为 `CallCredential`；`Declaration` 改为 `Placement`，是否必需只交给 `Loaded.credential`。
- 凭证由三个调用处各自解析后显式交给 `invoke`；附加与遮蔽集中在 `http` 一处；契约版本收成常量 `CONTRACT_VERSION`；重定向策略提成具名函数。
- 基于 0.2 的制品加载失败、报错写明两个版本，已用临时组件手动核对一次（按测试准入不保留文案断言）。
