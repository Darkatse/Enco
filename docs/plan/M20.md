# M20 契约 0.3 与凭证

> 路线图 P2 的第 2 个里程碑。计划的生命周期见 spec 09 §5。

## 目标

用一次主版本升级完成必须破坏的改动（§4.4），同时让密钥只经宿主：插件永远看不到值，Provider 不再特殊（§4.11）。

## 范围

- **`describe(config)` 的返回记录**：摘要、配置 schema、凭证声明。这是 0.3 唯一要改的记录；工具定义随 M23 的 `tools` 接口加入。
- **`settings` 删除 `api-key`。**
- **`http` 的凭证语义**（§4.11）：
  - 去往绑定 origin 的请求自动带上凭证，放置方式为 `header` 或 `path-prefix`；
  - 宿主自己跟随重定向，每一跳按它的 origin 附加凭证。现在的 reqwest 默认跟随重定向，跨 host 时只剥离 `Authorization` 等少数请求头，`x-api-key` 会被带过去，所以这一条必须由宿主来做；
  - 交回插件的响应与失败消息中，密钥的值都被遮蔽（失败消息现在已用 `without_url()`）；
  - 宿主日志不输出注入之后的 URL 与请求头。
- **准入**：声明为必需的凭证在本节点取不到时不准入；部署时被拒绝，重启时只退出快照（§4.10 第 3 条）。
- **不带 origin 的凭证至多一个**：它们都绑定到 endpoint 的 `base_url`，多于一个就违反"两个凭证不能绑定同一个 origin"（§4.11），登记时拒绝；endpoint 写了 `api_key_env` 而插件没有这种凭证，同样拒绝。需要多个密钥的服务暂不支持。
- **`{}` 必须是合法配置**，得到插件的最小能力。
- **三个出厂插件重建**：Provider 声明 `authorization` 头的放置方式，origin 取 endpoint 的 `base_url`，值取 `api_key_env`；`provider-protocol` 中的鉴权头与遮蔽代码删除。

## 规格

- 07：WIT 0.3（`description`、`settings`、`http` 的凭证语义）、凭证绑定的实现、出厂插件重建。
- 11：凭证进入准入。
- 12 §3：密钥路径改为凭证绑定，`Endpoint.api_key` 不再传给适配器。

## 验收

- 三个出厂插件以 0.3 重建，通过 `cargo xtask check`。0.2 的制品被拒绝，错误信息指明主版本不兼容。
- 用 wiremock 模拟 Provider：请求带有宿主加上的 `Authorization`；插件收到的 `settings` 中没有密钥；服务把密钥回显在响应正文中时，插件看到的是 `[redacted:…]`。
- 跨 origin 的重定向不携带凭证，同 origin 的重定向携带。
- 必需的凭证缺失：部署被拒绝并说明原因；重启时环境变量消失：该代际不准入，原因写入 Log 与 `plugin_status`，节点照常启动。
- 手动一次：经凭证绑定与真实的 DeepSeek、Kimi 对话。
