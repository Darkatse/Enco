# M28 手册

> 路线图 P2 的第 10 个里程碑。计划的生命周期见[路线图](../Roadmap.md)。

## 目标

P2 主验收的前提：Agent 全程只读手册和插件源码，不读宿主源码，就能修好一个插件（上下文专题）。手册由源码自动导出，宿主与插件都一样：文档是源码的精华，Agent 先读文档定位，再读需要的那一小段代码。

## 对齐的判断

1. **文档分三层，各有唯一的来源。**
   - 契约：WIT 的 `///` 生成 `CONTRACT.md`，已有。
   - 代码：每个 crate 的 rustdoc，宿主（`enco-core`、`enco-kernel`、`enco-host`、`enco-wasm`、`apps/enco`）、SDK、出厂插件与 Agent 在 home 中写的插件都导出。出厂插件的源码不在 home 中，它们的导航手册与宿主的一样只在仓库中按需生成，手册投影只给出它们的运行时手册。
   - 代际：运行时手册，由已登记代际的声明（`tools.list`、`describe` 给出的配置 schema 与凭证、上限常量）加上这个代际源码的文档组成。

   Agent 的两种角色各取所需。运行中的 Agent 在 `ENCO_HOME` 维护插件，读手册投影中的契约、SDK 的 API.md、宿主的 API.md 与各插件的运行时手册；健康、历史与下一步由 `self_status` 与 `self_history` 回答，不属于手册。开发 Enco 的 Agent 在仓库中工作，另外读宿主各 crate 的导航手册，以及手写的常驻指令、设计、计划与教训。

2. **rustdoc JSON 是中间数据，Agent 读的是由它渲染的 Markdown。** 2026-10-24 实测，`enco-core` 的 JSON 2.3 MB，其中文档文字只有 24 KB，其余是 ID、源码位置、类型树与 impl 列表；`enco-kernel` 2.0 MB 中 35 KB，`enco-host` 2.5 MB 中 9 KB。直接交给模型既浪费上下文，又要它自己拼回结构，这正是上下文专题「Agent 据以行动的结果写成文档」所拒绝的。所以 JSON 只用来渲染手册与检查文档门禁；Markdown 按上下文专题的分层书写：第一段是 L0，正文是 L1，带标题的小节是 L2，签名放在代码块里，每一项附源码的文件与行号。`# Implementation` 小节只在描述能力的运行时手册中剔除，导航手册保留它。

3. **文档用固定工具链的 rustdoc 导出，经 `RUSTC_BOOTSTRAP` 取得 JSON。** rustdoc 的 JSON 输出是不稳定特性，稳定版直接拒绝 `-Z unstable-options`。实测在固定的 1.99.0 上设置 `RUSTC_BOOTSTRAP=1` 即可：`enco-core` 9 秒、`enco-kernel` 与 `enco-host` 各 12 秒，SDK 以 `wasm32-wasip2` 为目标 8 秒、0.5 MB；格式版本 61，对应 `rustdoc-types` 0.61.0。rustdoc 在宏展开之后运行，所以 SDK 中 wit-bindgen 生成的类型连同 WIT 的文档都在其中。
   - 不另装 nightly：门禁与主人的环境都会多一个工具链。
   - 不用 syn 自己解析：看不到宏生成的项，再导出要自己解析，等于维护一个简化的 rustdoc。
   - 不用 rust-analyzer 的库：依赖很重，接口每周在变。
   - 先例：cargo-semver-checks 在内部这样取得 rustdoc JSON；Linux 内核用固定版本的稳定编译器加 `RUSTC_BOOTSTRAP` 使用不稳定特性。

   代价是升级工具链时同步升级 `rustdoc-types`；工具链本来就固定，升级是一次有意的改动。`RUSTC_BOOTSTRAP` 只出现在导出文档的那一条命令里，并且导出用独立的目标目录：仓库中是 `target/rustdoc`，home 中是 `.data/target-doc`。2026-10-24 实测，proc-macro2、thiserror 与 anyhow 的构建脚本追踪 `RUSTC_BOOTSTRAP`；在同一个目标目录中交替普通构建与导出，proc-macro2、quote、syn、serde_derive、thiserror-impl 及其下游每次都重编，两个方向都是。独立的目录只多一份检查用的元数据，第一次是冷构建。

4. **公开接口与内部结构是两种产物。**
   - **API.md** 回答"这个库给调用方提供什么"，只给库 crate：`enco-core`、`enco-kernel`、`enco-host`、`enco-wasm` 与 SDK。全部生成，提交入库，由 `--check` 门禁比对，永不手改；接口一变，评审中就有 API.md 的 diff。
   - **导航手册** 回答"代码怎样组织、每个模块负责什么、要改某件事去哪里"，加 `--document-private-items` 生成，包括私有项。宿主的导航手册只在仓库中按需生成，不入库；插件的导航手册是它运行时手册的一部分。
   - 插件没有 API.md：插件对外的接口是 WIT 导出与声明，由运行时手册承担；它的 Rust 项都是内部实现，归导航手册。

5. **README 是一个单元的入口，一半手写、一半由制品生成。** 手写部分说明这个单元做什么、为什么、怎样配置、模型会看到什么；生成区由已构建的组件给出（调用它的 `describe` 与 `tools.list`），在登记时写入，已经实现。出厂插件在仓库中不提交 README：出厂代际按定义以空配置加载，手册投影给出的就是它准确的手册，再存一份只是重复的生成物，还要让 xtask 加载 Wasm。

6. **手册是 home 中的只读文件投影，用已有的动词读取。** Agent 用 `fs_read`、`fs_list` 读手册，用 shell 的 `rg` 搜索，不另设读手册的工具。
   - 工具要少：读与搜都已有动词。
   - 安全模式下也能读：`fs_read` 在救生集里，修复时读手册不必扩大救生集。
   - 总纲的 Plan 9 透镜：文件投影只用于查看，动作才用类型化调用。
   - 投影是派生状态：它是已登记代际与宿主内嵌文档的函数，注册表提交之后与启动时重写，删掉也能重建。
   - 放在 home 的顶层，与 `sdk/` 同类。顶层是主人与 Agent 按名字浏览、阅读或修改的东西；`.data/` 是 Enco 的库，Agent 只经类型化调用或结果给出的地址（构建日志、落盘的全文）触及它。手册要从索引一层层往下读，所以在顶层。意图只有 `enco.toml` 与 `plugins/`，登记不读手册。
   - 投影复用 `sdk/` 的 `FileTree::project`：完整所有权，多余的文件删除，手工改动在下一次重写时被覆盖。`README.md` 第一行写明它是生成的、只读；不设文件权限，也不让工具拒绝写入。

   布局如下，常规与安全模式的系统提示中都用一句话指出位置，修复时最需要读手册的正是安全模式：

   ```text
   ~/.enco/manual/
     README.md                 # L0：这里有哪些手册，每项一行
     contract.md               # 本宿主的 WIT 契约
     sdk/API.md
     host/<crate>/API.md
     plugins/<名字>/README.md   # 运行中代际的手册：说明、工具、配置、凭证、上限
     plugins/<名字>/code/…      # 这个代际源码的导航手册，按模块分文件；出厂插件没有
   ```

   宿主的 API.md 与 `CONTRACT.md` 是入库的生成物，嵌进二进制，启动时写出，所以运行时不需要宿主源码。SDK 的内嵌包随之去掉 `wit/CONTRACT.md`：插件构建用不到它，`sdk/` 只放构建输入，契约在 home 中只出现一处。SDK 的哈希因此变一次，插件在下一次登记时重编，字节相同，不产生新代际。

   插件的运行时手册由两部分组成，来源不同：
   - `README.md` 在写投影时由运行中的实例渲染，不另存；配置代际改变了工具，它随之改变。
   - `code/` 是构建的产物。构建时用 rustdoc 生成，渲染出的 Markdown 用 `FileTree::store` 按内容寻址存进库，由一张新表按源码哈希记下，写投影时取出。启动不能依赖 Rust 工具链（只有出厂插件的 home 本来就不需要它），所以投影的内容只能来自库，不能重新导出。某个源码哈希还没有手册时（M28 之前的构建），下一次构建补上，命中构建缓存时只补跑 rustdoc；源码没变的插件不花时间，耗时在实施时测定。

   投影只保留运行中的代际，历史由 `self_history` 回答。

7. **home 中的构建固定到宿主的工具链，由宿主指定并核对。** 宿主在 `~/.enco/plugins/<名字>` 中运行 `cargo clippy` 与 `cargo build`，没有指定版本，rustup 就用主人的默认工具链；构建之后的 `rustc -vV` 只写进构建记录，不做检查。目前版本一致只是巧合：本机默认的 stable 恰好是 1.99.0，oracle-jp 上主人把默认设成了 1.99.0，而那里的 home 只有出厂插件。版本一旦不同，rustdoc JSON 的格式与编译结果都可能不同（M24 的教训）。rustup 只在当前目录及其上级找工具链文件，SDK 的目录不是插件目录的上级，所以不能靠随 SDK 分发的文件。做法：
   - 版本只有一个来源：仓库的 `rust-toolchain.toml`，宿主构建时由构建脚本读出，写进二进制。
   - 宿主在 home 中的每一条构建命令（clippy、build 与导出 rustdoc）都设置 `RUSTUP_TOOLCHAIN` 为这个版本，它在 rustup 的优先级中高于目录覆盖与任何工具链文件，评测试跑走同一条路径；同时设置 `RUSTUP_AUTO_INSTALL=0`（rustup 1.28.1 起支持），不在构建中途替主人下载整个工具链。
   - 构建记录中的 `rustc -vV` 从记录改为核对：版本不符就让构建失败，例如不经 rustup 的 cargo 忽略了环境变量。
   - 缺少这个工具链或 `wasm32-wasip2` 目标时构建明确失败，并给出最小的安装命令，例如 `rustup toolchain install 1.99.0 --profile minimal --component clippy --target wasm32-wasip2`，版本由宿主填入。
   - 占用：2026-10-24 实测本机的 1.99.0 工具链 1.5 GB，其中离线文档 `rust-docs` 占 921 MB；构建与导出 rustdoc JSON 都不需要它，rustdoc 程序在 rustc 组件里。minimal 加 clippy 与 wasm 目标约 0.6 GB。仓库的 `rust-toolchain.toml` 也加上 `profile = "minimal"`，新装时不下载离线文档；已经装过的可以用 `rustup component remove rust-docs --toolchain 1.99.0` 删掉。

8. **文档注释是手册，写给使用者与维护者，不随代码无限膨胀。** 文档会成为 Agent 的主要地图，宿主却很薄：`enco-host` 只有 122 个项写了文档；宿主、内核、core、wasm、应用与 SDK 共 170 个模块文件，只有 43 个有 `//!`。补齐时守住写法：
   - **模块 `//!`**：一到三句，写它拥有什么、保证什么、不做什么并交给谁。例如 `A connection owns its routing state; adapters own only protocol interpretation.` 不写历史、实现步骤，也不列会随代码增长的清单。
   - **公开项 `///`**：一句，从调用方的角度写签名说不出的契约：保证、单位与范围、何时为空或失败、副作用。复述名字的句子不写，改写成它缺的那部分：`The path.` 不如 `Workspace-relative path as given; absolute paths are kept.`；`Original byte length, before protocol encoding.` 是好的例子。
   - **分层**：第一段会出现在索引里，必须独立成立；确有必要才加正文；`# Errors`、`# Implementation` 这类小节只在规则确实存在时写。
   - **行内 `//`**：照旧，只写非平凡的不变式与防止改错的理由。
   - **不写**：变更历史与被放弃的做法（在 git 里）、TODO、对代码逐行的复述、自明的"参见"。

9. **文档门禁只管机械上可以检查的，语义质量交给评审。** 门禁放在 `cargo xtask docs --check`，在 rustdoc JSON 上检查：JSON 中有准确的项名与种类，比扫描源码可靠。2026-10-24 在已经整理过的 `enco-core`（453 项）与 `enco-kernel`（662 项）上测量，复述名字的摘要共 1 处（`plugin` 写成 "The plugin."），第一段超过 160 字符的 5 处，占位符与超过三段的都是 0。五条规则：
   - 五个库 crate 与 SDK 的根上必须开启 `missing_docs`；
   - 不允许 `allow(missing_docs)` 或 `expect(missing_docs)`：不值得写文档的项应当不公开，而不是被豁免。唯一的例外是 SDK 中包住 wit-bindgen 生成物的 `bindings` 模块，门禁只认这一个位置，理由写明这些项的文档来自 WIT、由 CONTRACT 门禁负责。2026-10-24 实测 SDK 开启 `missing_docs` 有 45 处：手写的 7 处；生成的 38 处中，24 处是 WIT 的记录字段与变体分支没写 `///`，CONTRACT 门禁扩到字段与分支，在源头补上；另外 14 处是 wit-bindgen 自己的结构（命名空间模块 5 个、`use` 产生的类型别名 7 个、导出 trait 2 个），写不了文档；
   - 第一段不超过 160 字符，能放进索引的一行；
   - 第一段去掉停用词后不能只剩项名中的词；
   - 不能有 TODO、FIXME、XXX 或 TBD，要做的事写进路线图或计划。

   模块不强制写 `//!`：强制给几十行的小模块写，正好会催生复述式的膨胀；但写了就受同样的规则约束，导航手册的 L0 索引把没有摘要的模块明确显示为空。门禁拦不住换个说法的复述，所以语义质量由评审负责：API.md 入库，每一行文档的增减都在 diff 中可见，新写与大改的文档由主人审阅。

## 范围

- **导出**：`cargo xtask docs` 用固定工具链加 `RUSTC_BOOTSTRAP=1`、在 `target/rustdoc` 中生成 rustdoc JSON（引入 `rustdoc-types`），渲染为 Markdown；生成五个库 crate 的 API.md，`--check` 比对。文档单元有 cargo 的指纹，没变就跳过；变化时与测试、clippy 并行，对门禁时长的影响实施时测量。
- **文档门禁**：判断 9 的五条规则；先改掉现有超出 160 字符的 5 处与复述名字的 1 处。CONTRACT 门禁扩到记录字段与变体分支，补齐 WIT 中缺的 24 处；SDK 的 `bindings` 模块带唯一的豁免。
- **手册投影**：判断 6 的布局，放在 `~/.enco/manual/`，复用 `FileTree::project`；注册表提交之后与启动时重写；插件的导航手册在构建时于 `.data/target-doc` 中生成，存进库并由新表按源码哈希记下；宿主的 API.md 与 `CONTRACT.md` 嵌进二进制，SDK 的内嵌包去掉 `wit/CONTRACT.md`；常规与安全模式的系统提示指出位置。
- **运行时手册**（上下文专题）：来自 `tools.list` 的工具、来自 `describe` 的配置项（由 `config-schema` 生成）与凭证声明、上限常量，在写投影时由运行中的实例渲染；加上这个代际的导航手册。README 生成区随之更新。
- **评测题**：`adapter-drift` 与 `build-from-spec` 的夹具、mock 与评分进入 `evals/tasks/`，通过 `runner check`。评分只看公开的表面：mock 的状态与请求、`tool-calls.json` 与快照；运行器的快照加上 `enco history` 的输出。运行器只调用 `enco` 的命令行，没有命令能在 Session 之外调用插件的工具，所以不在部署的代际上跑契约测试，改由第二条输入让新代际处理一个新情况。
- **`missing_docs`** 扩展到 `enco-host`、`enco-wasm` 与 SDK（`enco-core`、`enco-kernel` 已有）；按判断 8 补齐宿主与 SDK 的模块文档与公开项文档，同时收拾已有的复述名字的文档。
- **工具链固定**：版本由仓库的 `rust-toolchain.toml` 写进宿主；home 中的构建命令设置 `RUSTUP_TOOLCHAIN` 与 `RUSTUP_AUTO_INSTALL=0`，构建后核对版本，缺少时给出最小的安装命令；仓库的 `rust-toolchain.toml` 加上 `profile = "minimal"`。

## 设计

- 上下文专题的「一份文档，两种读者」「文档过期是构建失败」「手册描述代际」验收时按实现改写：文档的三层与各自的来源，Markdown 是阅读形态、JSON 只是中间数据，手册是 home 中的只读投影，API.md 覆盖宿主各库 crate 与 SDK。
- 工程专题新增一条：文档由固定工具链的 rustdoc 导出，home 中的构建固定到同一工具链；文档门禁只管机械上可以检查的规则。
- 判断 8 与判断 9 在验收时提炼进常驻指令的"注释"与"文档与生成物"两条。
- 先定下的格式：手册投影的布局与各文件的版式（标题层级、签名与源码位置的写法）；运行时手册的内容；记录插件导航手册的表（源码哈希到手册树的清单哈希），库的版本随之升级。

## 验收

- `adapter-drift` 经正式路径通过。home 中没有宿主源码，运行器又检查工具调用没有碰到仓库与运行目录，所以通过就说明手册与插件源码足以修好插件。
- `build-from-spec` 通过：新建的工具插件在同一次任务的后续 Round 中被用上，运行时手册随代际生效。
- 已有题目按 `evals/README.md` 的判定规则不退化。
- `cargo xtask docs --check` 覆盖 `CONTRACT.md` 与五个库 crate 的 API.md；改动一个公开签名或它的文档，门禁要求重新生成，评审中出现对应的 diff。
- 文档门禁：去掉 crate 根上的 `missing_docs`、在 SDK 的 `bindings` 之外加上它的豁免、第一段超长、摘要只复述名字、留下占位符，各自让门禁失败，并指出位置；WIT 的记录字段或变体分支缺少文档，CONTRACT 门禁失败；`missing_docs` 在全部库 crate 与 SDK 上通过，clippy 无警告。
- 导出不拖累构建：交替运行 `cargo xtask docs` 与测试，依赖不重编；home 中先后两次登记，第二次构建不重编过程宏。
- 手册投影：启动之后 `~/.enco/manual/` 含有索引、契约、SDK 与宿主的 API.md、各插件的运行时手册；登记一个插件之后，它的手册反映新代际的工具、配置与代码文档；删掉整个投影再启动，不调用 cargo 就重建且内容相同；安全模式下 Agent 能用 `fs_read` 读到手册。
- home 中的构建只用固定的工具链：主人的默认工具链是别的版本时，仍用固定版本构建；没有装这个版本或目标时，构建明确失败并给出最小的安装命令，不会自动下载；不经 rustup 的工具链版本不符时，构建失败。

## 移交 MCP 里程碑

以下判断已经与主人对齐，但真实的大工具目录要到接入 MCP 才会出现：现在 21 个工具约 2.4k token，又在有缓存的前缀里，全部披露并无问题。所以它们不在本里程碑实施，M28 验收时随 `many-tools` 的题目草案一起移入 MCP 的计划。

1. **救生集保持常驻，按需披露只用于其余工具；常驻不由插件声明。** oracle-jp 上最新的计划中，工具目录 20 个（加上 M27 的 `message_send` 是 21 个）约 9.7 KB、2.4k token，救生集 8 个约 4.6 KB、1.2k token，位于稳定的前缀中，有缓存。救生集是 Agent 几乎每轮都用的读写、shell、状态、登记与倒带，改成"能找到"省得很少，却削弱了"写坏的 composer 拿不走修复工具"的保证。其余工具由默认 composer 给出 L0 目录（名字加一句话），常用的直接给完整定义，其余经 `capability_search` 展开；`capability_search` 在正常模式下由默认 composer 常驻，这是 composer 的策略，不是内核校验的不变式。

   一个工具是否常驻，取决于这个 Session 用不用它、上下文预算还剩多少、是哪一类 Session，这些插件都不知道；让插件自己声明，每个作者都会觉得自己的工具重要，最后全部常驻，按需披露也就失去意义。这也违背上下文专题"披露多少是 composer 的策略"与双向不泄露。所以常驻由拥有事实的三方决定：内核要求救生集常驻（Session 声明的要求）；主人在 composer 的配置中为某个 Session 或 profile 固定常驻的工具；其余由 composer 按 Log 中的使用记录、上下文预算与缓存稳定性取舍，常驻集只在开始新系列时调整。插件负责的是把工具描述的第一句写成准确的 L0 摘要，让它能被找到。默认 composer 在全部定义不超出预算时照旧全部披露，超出之后才改为常驻集、L0 目录与 `capability_search`。

2. **`capability_search` 像 grep 一样组合关键词，找到即展开。** 它会改变本 Round 能调用什么，所以必须是工具，不能是文件。
   - 参数：`keywords`（字符串列表）与 `match`（`all` 为默认，所有关键词都命中，相当于串起几个 grep；`any` 命中任意一个，相当于 `grep -e a -e b`）。不支持正则与排除词：正则多出一类"表达式写错"的失败，排除词很少用到。
   - 匹配：每个关键词不区分大小写，作为子串匹配工具名、所属插件、摘要、完整描述与参数名。工具描述是英文，工具说明写明用英文关键词。
   - 范围：本 Round 快照中尚未披露的能力。读文档用 `rg` 搜投影，不归它。
   - 排序：命中的位置（名字先于摘要，摘要先于描述），再看命中的关键词数，最后按名字。
   - 结果：至多 20 行，每行"名字（插件）— 摘要"，结尾说明这些工具从下一次请求起可以调用；超出时写还剩几个、加关键词缩小；没有命中时列出最接近的几个名字。用工具名作关键词就是展开这一个，所以不需要第二个工具。
   - 效果是 `ReadOnly`：它的效果就是随结算记下的披露，与 `message_send` 是同一个判断。结算按类型记下展开了哪些能力，composer 读这个事实决定下一份计划的披露，不解析结果文字；这是一处 Log 格式变化，库的版本随之升级。
