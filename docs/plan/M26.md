# M26 composer 插件

> 路线图 P2 的第 8 个里程碑。计划的生命周期见 spec 09 §5。

## 目标

默认 composer 改为 Wasm 插件，Agent 以评测成功率为目标、以 Attempt 记录的用量（含缓存命中）为成本约束迭代它（§7.1）。

## 范围

- **composer 的 WIT 接口**，在本里程碑开始时单独讨论。主要问题是：每个 Round 都要把输入交给插件，而线上的历史已经有 22.5 万 token，是整份传过去，还是经宿主导入按需读取 Log 条目？倾向整份传入：
  - composer 的契约是"对显式输入的纯函数"（§2），按需读取会让输入变成隐式的，契约测试还得另外记下它读了什么；
  - 22.5 万 token 约 1 MB，跨 Wasm 边界拷贝一次是毫秒级，相对一次模型请求可以忽略；
  - 真要优化，`ComposeInput.previous_plan` 已经提供了增量的形态（上一份计划加上之后的新条目），等测量证明需要时再做。
- 默认 composer 改为出厂的 Wasm 插件；原生的 `FactoryComposer` 保留，作为安全模式的策略。
- `AttemptStarted.composer` 记录 composer 的代际（`CodeRef::Generation`）。
- 挂在 composer 名下的事项（稳定性标注、按空闲时长开始新系列、缓存友好的披露策略）由 Agent 在评测下迭代，不作为本里程碑的验收条件。
- **Agent 怎样运行评测**：运行器与题目在 Enco 仓库中，不在 `ENCO_HOME`。Agent 在工作区取得与宿主版本对应的 Enco 仓库，经 shell 在后台运行运行器，把自己构建的 composer 制品作为被测的代际传入（M19），再读取 `result.json`。
- **留出集推迟**：§4.8 要求 Agent 开始对着任务集自我进化时，把留出集放到它够不着的地方。本里程碑只演示一轮迭代，谈不上记住答案，所以推迟到 Agent 开始反复迭代时，那时留出集放到另一个节点或另一个系统用户下。

## 规格

- 04 §2：composer 端口改由 Wasm 插件实现。
- 05 §4：`FactoryComposer` 作为安全模式的策略。
- 07：composer 的 WIT 接口。

## 验收

- 部署一个改坏了披露策略的 composer 代际之后，仍能调用文件、Shell 与部署管理，并经正式路径回退：计划不满足声明的要求时按 composer 失败处理（§7.1），Round 失败后进入安全模式（M22）。
- 以 Wasm composer 运行的已有评测题，按 spec 13 的规则不低于原生 composer。
- `many-tools` 上，Agent 至少完成一轮"修改 composer → 部署 → 评测"的迭代，结果写入运行记录。
