# M19 评测运行器与基线

> 路线图 P2 的第 1 个里程碑。计划的生命周期见 spec 09 §5。

## 目标

在改动任何 P2 机制之前，先造好测量仪器：Agent 能依据它的输出，可靠地决定接受还是拒绝一次改动。评测以后也是 Agent 自我进化的目标函数（§4.8）。仪器与题目同样重要：题目的格式、mock、评分与题目自检见 `evals/README.md`，这里只写运行器与验收。

## 范围

- **运行器**：Rust 编写，位于 `evals/runner/`，是独立的 Cargo 工作区（与 `plugins/` 相同），依赖与 `Cargo.lock` 都与主工作区分开；`cargo xtask boundaries` 拒绝它对宿主 crate 的依赖。它只启动 `enco`，按通用 JSON 解析管理命令的输出。
  - 命令：`run` 运行一个变体；`compare` 比较两个变体；`regrade` 用已有的快照重新评分；`check` 做题目自检。
  - 自己的配置写明被测的模型与评判：被测的模型就是一段 Enco 配置（endpoint、profile、`[embedding]`、`[decision]`），原样写进每个被测 home 的 `config.toml`；评判是一个 OpenAI 兼容的 endpoint。
  - Agent 以后可以经 shell 在后台运行它，再读取 `result.json`。
- **`enco send --wait`**：等这条输入所在的 Run 结束，以 JSON 输出它的结局。"所在的 Run"按 Log 认定：这条输入的 `EventConsumed` 之后的第一个 `RunEnded`，所以输入落进一个已在进行的 Run 时也有确定的答案。这是 CLI 契约的新增项，主人与 Agent 同样可以使用。
- **产出是比较**：
  - 变体 = (enco 二进制, 被测的代际)。被测模型、评判与题目在一次比较中固定。
  - `compare` 让两个变体在同一时间窗口内交错运行同一批题。服务商会在同一个模型名下更新模型，所以存下的结果不能跨时间比较。
  - `result.json` 记下可比性所需的事实：题目内容的哈希、二进制版本、被测代际（制品哈希与设置）、被测模型、评判模型与评判提示词的版本。比较之前核对，不一致就拒绝，并指出是哪一项。
- **判定规则**：
  - 一道题的全部评分项都通过才算成功。每道题运行 k 次（默认 5），报告通过次数与 k 次全部成功的比例；仪器错误的试验不计入，单独报告次数。任一道题的任一变体没有有效试验时，比较没有依据，结论为不采纳。
  - 比较按题进行。问的是"在这几道题上"，随机性只来自每次试验，所以每道题是一张 2×2 表（变体 × 通过与否），用单侧的 Fisher 精确检验，结果确定，不需要重抽样。题目这么少，对题重抽样回答不了"换一批题是否成立"，区间还会偏窄。
  - `compare` 接收目标题，回答 Agent 进化时的问题"目标题上更好，其余没有倒退"：
    - 目标题上新变体更好（单侧 p < 0.05）。多道目标题按题分层：统计量是新变体在各目标题上的通过次数之和，零假设分布是各题超几何分布的卷积，仍是精确检验；不同题的试验不当作同分布合并。只有一道目标题时就是 Fisher 检验；
    - 其余每道题都没有更差（逐题单侧 p ≥ 0.05）；
    - 两条都满足才采纳，否则指出是哪一条、哪道题。不指定目标时只检查没有倒退，用作里程碑的不退化门禁。
  - 用量（token 含缓存命中、Round 数、耗时）逐题报告，作为成本约束由 Agent 判断，不进入采纳规则；第一次以用量为目标的迭代出现时，再加对应的检验。
  - spec 13 写明这条规则的灵敏度：k = 5 时，一道题要从 5/5 掉到 1/5 才判为倒退（掉到 2/5 时 p ≈ 0.08）；k = 10 时，10/10 掉到 6/10 即可判出（p ≈ 0.04）。规则不变，按需加大 k，可以只对部分题加大。逐题检验有多重比较：5 道题都没有真实变化时，至少一道被误判为倒退的概率不超过约 23%（Fisher 是离散的，实际更低）。
- **一次试验**：
  - 准备：在中性的位置建 home（以人名命名的 HOME，其下的 `.enco` 是 `ENCO_HOME`，路径中不出现 evals、trial 或题目名），复制题目的 `home/`（保留可执行位），替换占位符；生成与 `enco init` 模板同形的 `config.toml`（被测的模型、题目的时区、取自题目预算的 `[run] max_rounds`、把外部服务指向 mock 的设置）；启动 mock 与拒绝代理；以白名单环境启动 `enco serve`（被测 home 的 `bin/` 放在 PATH 最前面，只放行被测模型所需的 key 与运行必需的变量，代理环境变量的大小写两种写法都指向运行器的代理，`NO_PROXY` 只列被测模型的地址）；部署被测的代际；构建并部署题目 `home/plugins/` 下的夹具插件（要等 M24 的 `plugin_build`，格式在这里定下）。
  - 运行：按顺序 `enco send --wait`；超过题目的 `timeout_secs` 时执行 `enco cancel`，这次试验记为失败并写明原因。
  - 快照：经 CLI 把一切可观察的状态导出到快照目录，包括由 Log 配对得出的工具调用表与对话文本，然后停止守护进程，把 home 移入试验目录。
  - 评分：每个评分项只读快照，`reference` 中的时间占位符按试验开始时刻替换，所以评分是快照与开始时刻的纯函数，可以离线重评分。
  - 每次试验各有自己的 home、守护进程与 mock 端口，互不干扰，可以用 `--jobs` 并行，上限取决于服务商的限流。
- **评分**有三种：`state` 用 JSON Schema 校验快照中的一个文件；`rubric` 由运行器直接调用评判模型，带参考答案与可选的证据文件，评判先写理由、最后一行给出 `PASS`、`FAIL` 或 `UNKNOWN`；`command` 留给前两种表达不了的情况。评判不经被测的 Enco：composer 组装的请求出自被测系统，比较两个二进制时测量工具会随之改变。评判模型与被测模型属于不同的家族，在一次比较中固定。
- **mock 只有一种**：静态路由加 JSON 集合，录制请求并导出最终状态；每个 mock 有一个真实形态的主机名，地址与时间经占位符注入。题目不需要写服务端代码，夹具命令用 POSIX sh 与 curl。
- **网络隔离与真实感出自同一个代理**：代理把发往 mock 主机名的请求交给对应的 mock，其余一律拒绝并写进结果。Agent 看到的是 `http://techdaily.io/feed/atom` 这样的地址，而不是本机端口，题目因此不留测试的痕迹（`evals/README.md` 质量清单第 9 条）。代理挡不住直接打开的 socket，但让"外部服务一律经 mock"成为可以检查的事实。新增一个访问网络的出厂插件时，由那个里程碑把它接到 mock，例如 web 在 M23 经 `urls`。
- **完整性**：运行器检查工具调用表，参数中出现运行器所在仓库或本次运行目录的路径时，这次试验记为失败并写明原因。被测 home 在这两处之外，Agent 正常工作不会触发它。
- **只排除测量仪器自身的失败**：mock、代理或评判出了问题记为仪器错误，不计入分母；被测对象启动之后的一切失败都算失败，包括 `provider.*` 与超时。失败码由被测的插件自己报告，不能据此排除试验，与安全模式的进入是同一个理由；服务商的故障同时影响交错运行的两个变体，是噪声而不是偏差。评判答 `UNKNOWN` 记为失败，它取决于被测的输出。
- **被测的代际**：默认是出厂代际。比较改进前后时，变体带上要部署的制品与设置，例如 Agent 修改过的 composer（M26），在每个全新的 home 中部署。
- **题目自检**（`check`）：校验格式与引用的文件；运行 `hidden/cases/` 中的案例（oracle 必须全过，null 必须整题失败，近似错误必须在对应的评分项上失败；rubric 的案例各评判两次，两次都必须符合期望）；再把被测模型换成只回一句固定话的 mock，端到端跑一遍，整道题必须失败。
- **结果**：写入 `target/evals/<run>/result.json`：可比性的事实；每次试验每个评分项的结局与原因、Round 数、用量（含缓存命中）、耗时、所用的代际与模型、试验目录的路径；比较时另有结论，以及每道题的通过次数与 p 值。失败的原因是 Agent 提出下一个假设的来源。
- **题目**：`memory-update` 与 `daily-briefing` 按 `evals/README.md` 的题目质量清单细化，带齐案例。两道题都加入了大量干扰信息，每个问题都有一个诱人的错误答案；评分要求全部写在输入或 home 的 `AGENTS.md` 中，题目经过一轮独立的对抗审阅。

## 规格

- 新写 13：运行器的命令与配置、变体、一次试验的流程、快照与派生文件、三种评分（含评判的固定提示词）、mock 与代理、占位符、比较与判定及其灵敏度、`result.json`（Agent 以后读取的接口，作为契约写明）、题目自检、文件布局与常量。题目的格式与质量清单留在 `evals/README.md`，13 引用它。
- 08 §1、§7：`enco send --wait`，只用已有的 `subscribe`、`send` 与 `log`，协议不变。
- 02 §2、§4–§6：`evals/runner` 是独立工作区，它的依赖（含新增的 hyper、hyper-util、http-body-util、form_urlencoded、jsonschema）写在自己的 `Cargo.toml`，不进入主工作区；lint 表多一份副本。
- 09 §1、§3、§4：`cargo xtask check` 对评测工作区执行 fmt、clippy 与测试，boundaries 检查它不依赖宿主 crate；测试分层增加"评测"一层；验收场景 A59–A69。

## 验收

- `enco send --wait` 输出这条输入所在 Run 的结局，与 `enco log` 中的 `RunEnded` 一致；输入落进已在进行的 Run 时同样如此。
- `check` 对 `memory-update` 与 `daily-briefing` 通过：全部案例符合期望，端到端空跑整道题失败。
- 运行器在全新的 home 中运行一道题：`hidden/` 不进入被测 home；占位符被替换为实际地址与时间，评判看到的 `reference` 与 Agent 看到的数据日期一致；被测 home 中的 `mail` 优先于系统的同名命令；快照中有 mock 的请求与最终状态、工具调用表与对话文本；评判的请求与回复写在试验目录中。
- `regrade` 在守护进程已经停止时，用已有的快照得到与原来相同的 state 评分结局；带 `--judge` 时按 `result.json` 中的评判配置重新评判，`judge/` 随之更新。
- 评判答 `UNKNOWN` 时该评分项失败；评判的回复不合格式或请求失败时为仪器错误，不计入分母。
- 被测模型的地址不可达时，这次试验记为失败，原因写明失败码；mock 无法监听时记为仪器错误。
- 某道题的一个变体没有有效试验时，比较的结论为不采纳，原因是没有有效样本。
- 传入一份 Provider 制品运行一道题：第一条输入之前，被测 home 中该插件的活跃代际就是它，`result.json` 记录这个代际。
- 经代理访问 mock 的主机名得到 mock 的响应；访问一个既不是被测模型、也不是 mock 的地址：被代理拒绝，违规写进结果。
- 超过题目的 `timeout_secs`：Run 被取消，这次试验记为失败并写明原因。
- 比较两份题目哈希不同的结果：被拒绝，并指出不一致的项。
- 指定目标题的比较：结论分别说明目标题是否更好、其余每道题是否倒退，附通过次数与 p 值。
- A/A 比较：`memory-update` 与 `daily-briefing` 以同一个变体跑两遍、各 k 次，不指定目标，端到端跑通。被判为倒退的题数作为这条规则误报的实测写进 spec 13；这份结果同时作为基线写入运行结果。
