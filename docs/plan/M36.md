# M36 角色说明与工作目录

> 路线图「Session 委派」阶段的第二个里程碑，不依赖 M35。计划的生命周期见[路线图](../Roadmap.md)。

## 目标

每个 profile 可以有 `profiles/<名字>.md` 角色说明，用法与 `AGENTS.md` 相同；每个 Session 有带节点的工作目录。主人可以用不同的根 Session 管理日常、编程、科研这样的项目，每个有自己的角色与工作目录；[M37](M37.md) 的子 Session 按角色工作，需要并行写入时各有自己的目录。

## 对齐的判断

- **profile 的名字是一段。** 现在 Session 与 profile 的名字都没有任何校验，而 profile 名在本里程碑中成为路径 `profiles/<名字>.md` 的一部分，TOML 的键可以是任意字符串，不校验就能读到 home 之外的文件。所以 core 引入「名字的一段」：非空，不含 `/`、空白与控制字符，不是 `.` 或 `..`。名字用来指认，所以不含空白：渠道命令的参数去掉首尾空白之后才比较，首尾带空白的名字永远选不中；各种空白字符看上去又一样，会造出分不清的名字。profile 名必须是一段，由配置中 profile 表的归属者在登记时检查；M37 用同一个类型构造 Session 的名字。约束在拥有事实的地方固定一次，读取 `profiles/` 的代码只消费已经成立的名字。

- **角色说明与 `AGENTS.md` 是同一种东西，按事实分两层。** profile 是角色，可以复用，数量随角色增长，不随 Session 增长；每个 Session 自己的事实（工作目录、用哪个 profile，M37 起还有父）记在 `SessionRecord` 中，不在配置里。
  - `[profile.<名字>]` 仍在 `config.toml`，是角色的配置，照旧登记，M37 加上 `description`。一张表只有几行，长的是说明文字。
  - `profiles/<名字>.md` 只放这个角色的说明文字，没有文件头，靠名字与 `[profile.<名字>]` 对应，与 `plugins/<名字>/` 同理。
  - 它与 `AGENTS.md` 按同一条规则使用：每个 Round 开始时由宿主的常驻说明来源读出，按来源与哈希记入计划，改了文件下一个 Round 生效，不登记。这是总纲「运行中的行为 ⟺ 已登记的代际」中常驻指令的规则：它是文本，在使用时记入计划。以后两者一起成为指令代际。
  - 两层管不同的事实。`AGENTS.md` 关于主人（偏好、全局规矩、私事），只给带 `owner_context` 的 Session；角色说明关于这个角色做什么、怎么做，给用这个 profile 的全部 Session，`owner_context = false` 时照样提供，所以群的说明正好写在这里。安全模式下两者都不提供。
  - 两者叠加，不互相替代：主人的规矩只写在 `AGENTS.md` 一处，不抄进每个角色。出厂 composer 先放 `AGENTS.md` 再放角色说明，由一般到具体，系统提示写明「角色说明针对这个 Session 的工作，比 `AGENTS.md` 更具体」；两者真的冲突时，由主人在写的时候避免。每份各自不超过上下文窗口的 10%，超出就整份省略并写明原因。
  - 「每个 Session 有自己的 AGENTS.md」的做法：需要时给它一个只属于它的 profile。有说明文件却没有对应的 `[profile.*]` 时，`enco status` 提示这个文件不会被读到。

- **工作目录（pwd）是带节点的默认目录，不是边界。** `SessionRecord` 记下 `(node, path)`。原生的文件工具按它解析相对路径，shell 默认在这里运行，`message_send` 的文件路径也按它解析；composer 告诉模型它在哪里。Agent 有 shell，任何目录都到得了，所以内核不承诺独占，也不把它当作权限；需要并行写入时，由父 Session 给子 Session 另指一个目录，例如它自己建的 git worktree（M37）。
  - 根 Session 的工作目录默认是 `home/workspace`，与现在的行为一致；主人用 `enco pwd` 修改。M37 的子 Session 默认继承父的，创建时可以另给一个，相对路径按父的工作目录解析。设置的目录必须存在于本机，否则命令或调用立即失败。
  - 与 profile 一样，Round 开始时钉住，`RoundStarted` 记下，修改从下一个 Round 起生效。
  - 节点现在总是本机，先把数据形态定下（多节点专题「单机阶段就固定事后补不上的数据形态」）。P4 中，Session 漫游到别的节点后，文件操作默认仍回到工作目录所在的节点，这是「三种位置相互独立」中的能力位置，对应 Plan 9 `cpu` 之后的 `/mnt/term`。本里程碑中工作目录不在本机时，原生文件工具明确失败。

- **项目说明不随工作目录读取。** 编程类的根 Session 可能希望读取工作目录中的 `AGENTS.md`，像 Claude Code 读 `CLAUDE.md`。到时候再定，角色说明已经覆盖「每个 Session 有自己的说明」。

- **契约与库各升一次，不留兼容分支。** `compose-input` 与 `session` 增加字段是破坏性变化，WIT 升到 0.11.0，全部插件重建一次；库的版本升到 17，不自动迁移，与 M30 以来的做法相同，oracle-jp 由主人升级。

## 范围

- **core**：名字的一段；工作目录 `(NodeId, 绝对路径)`；`SessionRecord` 增加工作目录；`RoundStarted` 记下本 Round 钉住的工作目录。
- **内核**：
  - 解析配置时，profile 名必须是一段，否则登记被拒绝并指出是哪个 profile。
  - 收集事实时，常驻说明来源分别给出 `AGENTS.md` 与本 Session 的角色说明：前者受 `owner_context` 控制，后者不受；安全模式下两者都没有。`ComposeInput` 增加角色说明。
  - `CallContext` 增加本 Round 钉住的工作目录。
  - 设置工作目录的方法：目录必须存在于本机，否则失败；从下一个 Round 起生效。
- **宿主**：
  - 常驻说明来源按 Session 的 profile 名读 `profiles/<名字>.md`，与读 `AGENTS.md` 同一个实现；文件不存在时没有角色说明。
  - 原生工具（文件工具、`message_send`、`shell_exec`）按 `CallContext` 中的工作目录解析，不再在组合根以 `home/workspace` 构造一次；工作目录不在本机时明确失败。
  - 状态提示没有对应 `[profile.*]` 的说明文件。
- **CLI**：`enco pwd <session> <path>`；`enco sessions` 显示工作目录；`enco init` 创建空的 `profiles/` 目录。
- **出厂 composer**：环境一节用 Session 的工作目录代替固定的 `workspace/`；在 `AGENTS.md` 之后新增角色说明一节，来源记为 `instructions:profiles/<名字>.md`，系统提示写明两层说明的关系；每份说明各自不超过上下文窗口的 10%。
- **WIT 0.11.0**：见下文。`CONTRACT_VERSION`、SDK 与全部插件随之重建。
- **库**：版本 17，`sessions` 增加 `pwd_node`、`pwd_path`；`RoundStarted` 的 JSON 增加工作目录。不自动迁移。
- **文档**：Usage 与 README 写明 `profiles/<名字>.md` 与工作目录；composer 契约中 home 的布局加入 `profiles/<名字>.md`。

## 设计

验收时提炼或改写：

- 总纲：概念表中 Session 的定义改为「身份 + Log + 工作目录 + 配置」；固定的词加入工作目录（pwd）；「运行中的行为 ⟺ 已登记的代际」中的常驻指令写明包括 `AGENTS.md` 与角色说明。
- Session 专题：新增「工作目录是默认位置，不是边界」；「Session 只记 profile 的名字」补上角色说明。
- 上下文专题：「正确性在内核，策略在 composer，线上格式在 Provider」列出角色说明这项事实，以及它与 `AGENTS.md` 各管哪一层。
- 多节点专题：「三种位置相互独立」写明工作目录的节点就是文件能力的默认位置。
- 先定下的格式：WIT 0.11.0（见下文）；库版本 17。

## WIT 的变化（草案）

```wit
package enco:plugin@0.11.0;

    /// A directory on a node, where a Session's file work happens unless it names another.
    record working-dir {
        /// The node whose file system holds it.
        node: string,
        /// Its absolute path on that node.
        path: string,
    }

    /// The Session the request is for.
    record session {
        // id, name, profile, created-at as before
        /// Where its file tools resolve relative paths and its shell commands run by default.
        pwd: working-dir,
    }

    record compose-input {
        /// The home's absolute path on the node running this Round.
        ///
        /// Its layout is part of this contract: `config.toml`, `profiles/<name>.md` for the
        /// profiles, `AGENTS.md` for the standing instructions, `plugins/<name>/`, `sdk/`,
        /// `manual/` and `workspace/`. `.data/` is Enco's own store and not part of it.
        home: string,
        // …
        /// The text of `profiles/<profile>.md` for this Session's profile, as read at the start of
        /// this Round; absent when the file does not exist, and in safe mode. Unlike
        /// `instructions`, it is supplied whatever the profile's `owner_context`.
        profile-instructions: option<string>,
        // …
    }
```

## 验收

- 新建或修改 `profiles/<名字>.md`：不需要登记，用这个 profile 的 Session 下一个 Round 的请求（`enco inspect`）含新的角色说明，计划记下它的来源与哈希；其他 Session 不变。
- 删除这个文件：下一个 Round 起没有角色说明。
- 群 profile 的说明出现在群 Session 的请求中，`AGENTS.md` 不出现；安全模式下两者都没有。
- 有说明文件却没有对应的 `[profile.*]`：`enco status` 提示它不会被读到。
- profile 名含 `/`、空白或控制字符，或者为 `..`：登记被拒绝，并指出是哪个 profile。
- `enco pwd main <目录>` 之后：进行中的 Round 不受影响；下一个 Round 中 `fs_read` 的相对路径、`shell_exec` 的默认目录与 `message_send` 的文件都在新目录；`RoundStarted` 记下它；请求中的环境一节显示它。目录不存在时命令被拒绝。
- 新建的 Session 工作目录是 `home/workspace`，行为与现在一致。
- 按 0.10 构建的插件加载时被拒绝并提示重建；出厂插件与重新登记的源码插件照常运行。
