# M44 事实归位：单机上就把每份事实放到它在 Space 中的位置

> P4 Space v1 的第一个里程碑。起于 2026-11-09 与主人对 P4 的讨论，阶段的判断见[路线图](../Roadmap.md)的 P4 一节。计划的生命周期见路线图。

## 目标

- **形状定下来，行为不变。** M44 之后，每份可变事实都有它在 Space 中的归属者与身份；M45 只加上控制平面与复制，不再改变任何事实的形状。仍然只有一个节点，看得到的变化只有「看得到的变化」一节列出的几处。
- **代际只来自登记。** 代际的身份由登记推出，不再有计数器；出厂代码与原生能力一样是宿主的内容，按内容标识，不是代际。登记的意图与本节点运行的引用和健康分开存放。
- **Session 的一切是它的创建记录与它自己的 Log 的函数。** profile、工作目录、定时与归档都是 Session 自己记下的事实；库中的 Session 行与定时行是物化，只在提交来源事实的那个事务里、由同一个函数写入。
- **Scheduler 只产出提醒。** 提醒的 Event ID 由（定时, 时刻）决定，恰好一次来自 Inbox 与 Log 的去重，不再需要专门的触发事务。
- **升级不丢记录。** 宿主把库从版本 23 一步迁移到 24；迁移之后从事实重建全部物化并逐行核对，不一致就不提交。

## 起因

P4 要让事实跨节点。跨节点的只能是控制平面的记录、单写者的流与内容（路线图 P4 一节）。下面这些事实现在不属于其中任何一类，或者身份只在一个节点上成立。

### 代际编号是节点内的计数器，已经写进永久的记录

- **计数器**：`GenerationId` 与 `RegistrationId` 都是 `u64`（`crates/enco-core/src/ids.rs:82`、`:93`）。代际号由 `next_generation` 取已有的最大值加一（`registry/state.rs:179`），插件代际与配置代际共用。
- **写进了哪里**：
  - Log：`AttemptStarted` 的 `composer` 与 `provider`（`entry.rs:55`、`:57`），`ToolCallStarted` 的 `CodeRef::Generation`（`entry.rs:82`、`capability.rs:20`），`RoundEnded` 失败时的活跃代际（`entry.rs:249`），回退通知 `RolledBack`；
  - 按内容寻址的证据：`MappingRecord.generation`（`mapping.rs:9`）；
  - 注册表的各张表；
  - WIT：composer 读到的回退通知 `rollback { trial: u64, replacement: option<u64> }`（`sdk/wit/plugin.wit:876`）。
- **后果**：第二个节点有自己的计数器，同一个号码在两边指不同的代码。证据的地址由内容决定，内容里带着号码，同一个地址在两个节点上就有两种含义。

### 出厂"代际"不符合代际的定义

- **定义**：总纲的概念表说，代际是"一份已登记、可以试用与回退的实现"。
- **出厂的记录**：不属于任何登记（`Origin::Factory`，由 `registry/factory.rs` 的 `record` 记下），状态恒为健康，不试用。它本身就是回退的终点。
- **用词**：设计文档中「出厂代际」与「出厂代码」各有九处，说的是同一样东西。
- **多节点**：不同版本的宿主带不同的出厂代码，记成计数器上的代际，就要每个节点各记一份。

### 注册表把意图与运行放在一起

- **一个结构装两类事实**：`RegistryState`（`ports/store/registry.rs`）里，登记、它写下的名字与代码、代际的内容是意图；`plugins` 的 `active`、`rollback_target`、`named_by`，代际的 `status` 与 `failure`，以及 `active_config` 是本节点运行的状态。
- **运行的事实写在了意图里**：`config_generations.previous` 记的是登记时本节点实际活跃的配置（`registration/commit.rs:126`），却存在配置代际的内容里。
- **与多节点专题不符**：专题已经写明期望状态在控制平面，实际状态与健康按节点记录。同一份代码在 VPS 上通过试用、在 Mac 上失败，是两条事实。

### Session 行被多处直接改写，Log 里没有对应的事实

- **直接写 `sessions` 行的路径**：
  - `set_working_dir`（`store/sessions.rs:84`）；
  - `set_profile`（`sessions.rs:67`，经 `registry/configuration.rs:321`）；
  - 叫停子树时写 `archived_at`（`sessions.rs:239`）；
  - 根的 `ensure`（`sessions.rs:106`）与渠道建群的 `accept_creating`（`configuration.rs:270`）；
  - 子 Session 随父的提交插入（`store/commit/deliveries.rs`）。
- **子的创建记录不全**：子 Session 的创建在父的 Log 里只留下 `Delegated { session, created, event }`（`entry.rs:131`），profile 与工作目录只在行里。
- **后果**：这些事实只存在于一个可变的行里，Log 中没有，别的节点无从得出。总纲说 Session 可以只凭 Log 重建，现在 profile、工作目录与归档做不到。

### 定时是由另一个归属者改写的独立状态

- **创建与取消直接写表**：`scheduler.rs:384` 的 `create`，`store/schedules.rs:19` 的 `insert` 与 `:38` 的 `cancel`。
- **取消不看归属**：Agent 的 `schedule_cancel` 只按 ID 取消，不看定时属于哪个 Session（`builtin.rs:238`）。
- **触发**：专门的事务同时推进 `last_due` 并投递提醒（`schedules.rs:72`），提醒的 ID 是随机的（`scheduler.rs:453`）。
- **后果**：定时属于它的 Session，却由 Scheduler 改写；Session 换节点时，它不会跟着走。

### 库的版本不符就拒绝启动

- `open` 只认 `SCHEMA_VERSION`（`store.rs:30`、`:125`），此前的格式变化都由主人手写脚本升级。路线图写着从 P4 起升级不丢记录。

## 对齐的判断

### 事实分三类，可变事实放在检查它的不变式所在之处

- **三类会跨节点的事实**：
  - **控制平面的记录**：小、可变、涉及不止一个归属者，按 CAS 改变。包括成员、Binding 的转移、租约、根目录与期望状态。
  - **单写者的流**：每个归属者一条，只追加，键是 `(epoch, seq)`。现在是 Session 的 Log，以后还有连接与记忆。
  - **内容**：按哈希寻址，不可变。包括计划、工具目录、证据、blob、制品、源码与手册。
- **两种不跨节点的东西**：
  - **节点的事实**：Inbox、运行的引用与健康、安全模式、构建缓存。
  - **物化**：由上面三类事实求出的索引，随时可以丢弃重建。
- **放置规则**：一份可变事实放在哪里，由检查它的不变式决定。只涉及一个归属者的，随这个归属者的流；跨归属者的放在控制平面，例如根名字唯一、登记不破坏已有的使用。
- **M44 的做法**：把库中每张表归入其中一类（见「归类」），存储的模块按类组织。单机时控制平面就是本机的库，M45 换成 openraft。

### 代际只来自登记，宿主的代码按内容标识

- **代际的身份**：按总纲的定义，代际只来自登记，所以它的身份就是"哪一次登记、哪个单元"，单元是一个插件或配置。
  - 身份由登记推出，代际不再有自己的计数器。
  - 唯一性有保证：一次登记对每个插件只有一个动作（`registration/commit.rs` 按插件逐个处理），配置至多一份，所以一次登记对一个单元至多产生一个代际。
- **登记号的来源**：登记号是唯一提交者给出的顺序。单机时是本机的下一个号，M45 起由控制平面的状态机给出。
- **宿主的代码按内容标识**：
  - 出厂代码是（插件身份, 制品哈希）；原生能力照旧是（名字, 版本）。
  - 两者都不登记、不试用，是回退的终点。
  - 不同版本的宿主自然得到不同的标识，同一个版本在各节点上是同一个标识，不需要任何节点去记。
- **一个类型**："运行的是什么代码"只有 `CodeRef` 一个类型，它有三种：代际、出厂代码、原生能力。Log、证据与回退通知都用它。
- **配置代际**：它的身份就是那次登记，`ConfigurationRef` 中重复的两个字段合为一个。
- **用词**：设计文档统一为「出厂代码」，不再说「出厂代际」。
- **跟随出厂代码的插件**：跟随也是登记，所以总是得到一个代际，内容是当前宿主的出厂制品加上它的设置，设置可以为空。出厂代码本身以空配置加载，是回退与安全模式的终点，不是代际。
  - 现在设置为空时复用出厂记录、不为空时才产生代际（`registration/prepare.rs:119`），这个分支删去。
  - 宿主换版本时，照旧经一次普通登记得到新的代际。代际专题中"跟随属于登记"的判断不变，只改用词（见「设计」）。

### 意图与运行分开存放

- **意图（控制平面）**：登记，以及它写下的名字、代码意图与代际的内容（制品、设置、来历）；配置代际的文档。
- **运行（节点）**：
  - 每个插件当前与回退的引用，它们由哪次登记写下；
  - 运行中的名字由哪次登记写下；
  - 每个代际在本节点的试用、健康与失败；
  - 当前的配置，以及每次登记之前本节点实际活跃的配置（主人回退时用它）。
- **写入方式不变**：登记同时写意图与本节点的运行，机械恢复只写运行。M45 起改为登记先在控制平面提交意图，各节点再各自跟随；M44 只把数据分开。

### Session 的一切是创建记录与它自己的 Log 的函数

- **创建由名字的权威记下**：
  - 根 Session 记在根目录（控制平面）；
  - 子 Session 记在父的 Log 里，`Delegated` 带上完整的创建记录。
  - 创建记录写明身份、全名、父、创建时间、初始节点、初始 profile 与初始工作目录。
- **此后的变化由 Session 自己记下**：选 profile、设工作目录、建立定时、取消定时与归档，各是一种条目。物化只读这几种条目、创建记录与被消费的提醒。
- **库中的 Session 行是物化**：
  - 由 enco-core 中的一个函数，从创建记录与 Session 自己的条目求出；
  - 只在提交来源事实的同一个事务里写入；
  - 读取的路径不变；M45 的副本用同一个函数得到同样的行。
- **这一条兑现的是**总纲中"Session 可以只凭 Log 重建"。

### 改变 Session 自身的命令在 Round 边界生效

- **主人的命令走 Inbox**：主人改 profile、改工作目录、取消定时，都是投进那个 Session 的 Inbox 的命令。actor 在下一个 Round 边界消费它们，并记下对应的条目；Session 空闲时就是立刻。这与「Round 开始时钉住所见」一致：profile 与工作目录本来就从下一个 Round 起生效。
- **第三类 Inbox 内容**：已有的两类，输入驱动 Run，命令关于对话、在两个 Run 之间生效。这一类关于 Session 自身：
  - 不驱动 Run，也不进入对话；
  - 在 Round 边界生效；
  - Run 的结束判断（`run.rs:67` 的 `pending.is_empty()`）与 composer 都不把它们当作输入。
- **Agent 自己的定时工具不经 Inbox**：它在本 Round 的提交里直接记下同样的条目，因为 Agent 就是这个 actor。所以一个事实只有一种条目；是谁引起的，由它前面的条目说明（被消费的命令，或工具调用）。
  - 定时工具的效果因此就是随结算记下的条目，中断时不会留下 `unknown`。
- **取消定时只能取消本 Session 的**：Agent 的 `schedule_cancel` 不再能取消别的 Session 的定时；主人的取消投给定时所属的 Session。
- **主人这边看到的**：
  - 命令在接纳时返回，说明从下一个 Round 起生效；
  - 检查照旧在接纳时做：profile 存在、工作目录是绝对路径；
  - `/status` 与定时列表同时读物化与待消费的命令，并且在同一个事务里读。消费与追加本来就在同一个事务里提交，分两次读会拼出从未成立的状态（Session 专题「读 Log 只读到读取依赖的事实」）。

### 归档是 Session 自己的事实，名字随后释放

- **归档记在哪里**：叫停带上"归档"，被 Session 消费时记下归档。
- **停止接收输入**：Inbox 的写入处看到已接纳的归档叫停，就不再写入，效果与现在的"先记下，再等静止"相同。
- **名字的释放**：在归档被消费之后。
  - **根**：由根目录释放。单机时在同一个事务里；M45 起是消费之后的一次控制平面命令。
  - **子**：同名的新子由父判断，父看到旧的子已归档才允许。归档不可逆，所以父看到的状态只会偏旧，不会出错；同名就拒绝，与现在相同。
- **已停下的 actor**：已经因故障停下的 actor，要到再次运行时才消费归档，这与现在的叫停相同；在那之前，名字不释放。

### 定时归 Session，Scheduler 只产出提醒

- **定时的事实在 Session 的 Log 中**：建立、取消、哪次提醒已被消费，都是 Session 的条目；库中的定时行是它们的物化。
- **物化按整份 Log 求出**：它随提交维护，不随回溯改变，对话之外的状态不回退。它只是按定时的身份把几种事实合起来，与条目的先后无关。
- **Scheduler 不再拥有状态**：它读物化与 Inbox 中尚未消费的提醒，算出下一次时刻；到期就把提醒作为普通的输入接纳。`fire_schedule` 与它的事务删去。
- **恰好一次来自身份**：提醒的 Event ID 由（定时, 时刻）决定。重启后重发、以后别的节点重发，都被 Inbox 与 Log 的去重吸收，不再依赖专门的触发事务。
- **补发规则不变**：宕机期间错过的触发只补最近一次。上一次提醒取物化与 Inbox 中较晚的那个。
- **与 M46 的关系**：M46 起，Scheduler 只为 Binding 指向本节点的 Session 产出提醒；M44 时所有 Session 都在本机。这一条兑现路线图中"定时跟着 Session 走"，多节点专题删去"定时是租约"。

### 由起因决定的 Event ID 只用在现在需要的地方

- M44 只改提醒，因为新的 Scheduler 依赖它。
- 渠道输入的 ID 改由更新键决定，留到 M48：它只在租约交接时有用，旧的随机 ID 也不妨碍以后的去重。

### 跨归属者的检查对着本节点知道的事实做

- **单机时不变**：登记照旧拒绝删除仍被未归档 Session 使用的 profile，检查读物化的 Session 行与待消费的 profile 命令。单机时这就是全部事实。
- **多节点时**：分区另一侧新建的使用，这个节点看不到；由 Round 开始时解析 profile 失败来报告，这与"祖先的 profile 解析不了时这一轮失败"是同一条规则。
- **措辞**：保证的范围写成"本节点知道的使用"，不写成全局。

### 升级只从上一个版本一步迁移，迁移之后从事实重建核对

- **怎样迁移**：打开版本 23 的库时，宿主先把库文件复制一份，再在一个事务里迁移到 24。迁移之后，正常的代码只读写当前格式。
  - 工程专题「持久格式只支持当前版本」改为：只读写当前格式，只从上一个版本迁移。
- **迁移做的事**：
  - 把旧的代码引用改写为新的身份：Log、Inbox、注册表与证据中的都改。证据的内容变了，地址随之改变，引用这些证据的出处一并改写。
  - 根的创建记录写进根目录；子的创建记录写进父 Log 中已有的 `Delegated`。M44 之前没有记下创建时的取值，所以按迁移时的取值写，计划在这里如实说明。
  - 每个定时在它的 Session 的 Log 末尾补记建立，已取消的再补记取消；已归档的 Session 补记归档。补记用的都是普通的条目，不为迁移另设种类。
- **核对**：迁移之后，用与提交相同的函数从事实重建全部物化，与迁移得到的行逐行比较。有任何不同，或者有代码引用、出处解析不了，就不提交，库保持原样。
  - 定时行的 `last_due` 与状态由此再次求出，正好检验新的物化与旧 Scheduler 记下的结果是否一致。
- **只保留一个版本**：迁移的代码只保留到下一次格式变化，届时换成新的迁移。不支持降级，需要时用迁移前的副本。M45 的 Space 版本在此之上加一条：全部成员都升级之后才定案。

## 归类

| 表 | 类 | 写入者 | M44 |
|---|---|---|---|
| `meta`（节点身份、安全模式） | 节点 | 内核 | 不变 |
| 根目录（新） | 控制平面 | 单机时为本机，M45 起为控制平面 | 根的创建记录与名字是否已释放 |
| `sessions` | 物化 | 提交来源事实的事务 | 由根目录、父 Log 中的创建记录与 Session 自己的条目求出 |
| `log` | 流 | Session actor | 新增几种条目；代码引用改为新的身份 |
| `context_plans`、`tool_catalogs`、`evidence` | 内容 | 提交引用它的事务 | 证据中的代码引用改为新的身份 |
| `inbox` | 节点 | Inbox 唯一的写入函数 | 归档叫停之后不再写入 |
| `schedules` | 物化 | Session 的提交 | 由 Session 的条目求出；Scheduler 不再写 |
| `connections`、`connection_updates`、`deliveries` | 流 | 连接 | 不变；M48 起按租约的 epoch 栅栏 |
| `registrations`、`registration_names`、`registration_code` | 控制平面 | 注册表 | 代码引用改为新的身份 |
| `plugin_generations`、`config_generations` | 控制平面（内容） | 注册表 | 只留内容，以（登记, 单元）为键；`previous` 移到节点 |
| `generations` | — | — | 删去：代际不再有计数器 |
| `plugins` | 控制平面（身份）与节点（引用） | 注册表 | 拆成插件身份与本节点的运行引用 |
| `config` | 节点 | 注册表 | 当前的配置与每次登记之前的配置 |
| 代际的健康（新） | 节点 | 注册表 | 试用、健康与失败 |
| `builds`、`manuals` | 节点缓存与内容 | 构建 | 不变 |
| blob 与制品文件 | 内容 | 写入者 | 不变 |

记忆的库在 M47 处理，不在此列。

## 看得到的变化

除此之外，主人与 Agent 看到的行为不变：

- **主人的命令**：`enco profile`、`enco working-dir` 与取消定时在接纳时返回，从下一个 Round 起生效，Session 空闲时立刻生效。profile 与工作目录本来就从下一个 Round 起生效；取消定时原来是立即的，Session 在 Run 中时，现在至多晚一个 Round。
- **定时工具**：
  - Agent 的 `schedule_cancel` 只能取消本 Session 的定时；
  - `schedule_create` 与 `schedule_cancel` 的效果改为只读：效果就是随结算记下的条目，与 `message_send` 同一个判断。所以中断时它们结算为失败而不是 `unknown`，也可以与其他只读调用并行。
- **跟随出厂代码的插件**：每次跟随的登记都产生一个试用中的代际。宿主带来有缺陷的出厂插件时，会回退到上一份代码。
- **归档**：已停下的 actor 被归档时，名字要等它再次运行、消费了归档之后才释放。
- **文字**：状态与历史中，代码写成"第几次登记的代码"或"出厂代码"，不再写代际号。
- **WIT**：WIT 升到 0.18，composer 读到的回退通知改为登记号与回退去向。

## 范围

- **enco-core**
  - **身份**：
    - `GenerationId` 改为（登记, 单元），单元是插件身份或配置；
    - `CodeRef` 增加 `Factory { plugin, artifact }`；
    - `AttemptStarted` 的 `composer` 与 `provider`、`RoundEnded` 失败时的活跃代码、`RolledBack` 的回退去向、`MappingRecord` 改用 `CodeRef`；
    - `ConfigurationRef` 合为登记号。
  - **代际的记录**：`GenerationRecord` 只留内容；`Origin::Factory` 与记录上的状态删去，试用与健康改为节点的事实。
  - **Event 与条目**：
    - `EventBody` 增加主人改 profile、改工作目录、取消定时三种命令，以及判断这一类的函数；
    - `Halt` 增加是否归档；
    - `EntryBody` 增加 Session 自身的几种条目：选定 profile、设定工作目录、建立定时、取消定时、归档；
    - `Delegated` 带上创建记录。
  - **物化**：Session 行与定时行各由一个纯函数从事实求出，提交、迁移与以后的副本共用。
  - **提醒的 ID**：`EventId` 增加由（定时, 时刻）求出的构造。
  - `API.md` 重新生成。
- **enco-kernel**
  - **注册表**：
    - `RegistryState` 拆成意图与本节点的运行；
    - 删去 `next_generation`；
    - 出厂代码直接从宿主的嵌入内容解析，不再记录（删去 `registry/factory.rs` 的 `record` 与 Store 的 `record_factories`）；
    - 跟随出厂代码的登记总是产生代际，删去按设置是否为空复用出厂记录的分支；
    - 安全模式比较的是活跃代码与配置的集合。
  - **Scheduler**：只读物化与待消费的提醒，到期经普通的接纳投递，不写任何表；删去 `fire_schedule`、`insert_schedule`、`cancel_schedule` 这三个端口方法。
  - **定时工具**：建立与取消在结算的提交里记下条目，效果改为只读；取消只认本 Session 的定时；列表读物化。
  - **actor**：
    - 在 Round 边界与空闲时消费改变 Session 自身的命令，先于下一个 Round 读取 Session；
    - Run 的结束判断与传给 Round 的输入都排除这一类；
    - 消费归档叫停时记下归档。
  - **内核的命令**：
    - `set_profile` 与 `set_working_dir` 改为接纳命令；
    - 主人取消定时投给所属的 Session；
    - 归档写带归档的叫停，照旧等静止。
  - **Store 端口**：
    - 删去 `set_working_dir`、`set_profile`；
    - `halt_subtree` 不再写 `archived_at`；
    - 根的创建与释放写根目录；
    - 物化只经提交写入。
  - **建子 Session**：委派结算时，`Delegated` 带上创建记录。
- **enco-host**
  - **库的版本 24**：按「归类」重排各表；存储的模块按类组织，物化的行只由提交路径调用物化函数写入。
  - **迁移**：从 23 到 24，复制库文件，在一个事务中改写，用物化函数重建核对，不一致就回滚。
  - **Agent 读到的文字**：状态与历史文档里的代码写成"第几次登记的代码"或"出厂代码"（`development/render.rs` 等）；定时工具的说明写明只作用于本 Session。
- **enco-wasm 与 WIT**
  - 映射记录与渠道的代码引用改用 `CodeRef`（`channel.rs`）。
  - WIT 的 `rollback` 改为失败的登记号与回退去向（某次登记的代码、出厂代码或没有），WIT 升到 0.18。CONTRACT.md 与出厂 composer 的叙述随之更新。
- **应用**
  - `enco profile`、`enco working-dir` 与取消定时，在接纳时返回"从下一个 Round 起生效"。
  - `enco schedules` 与 `/status` 显示待生效的改变。
- **文档**
  - 设计文档见「设计」一节；
  - Usage 中这几个命令的说明随之更新；
  - 验收后在路线图记下 M44。

## 不做

- **控制平面的共识、成员、配对与复制**（M45）：M44 的登记照旧在一个事务里同时写意图与本节点的运行。
- **Binding 的转移、封口与 outbox**（M46）：所有 Session 的 Binding 都是（本机, 1）。
- **渠道输入由更新键决定的 Event ID**（M48）。
- **记忆的持有者**（M47）。
- **节点专属的配置**，例如本机路径与 `localhost` 的 endpoint：P4 中按需在配置里写明节点。
- **为已停下的 actor 机械地归档**：见「待定」。

## 设计

验收时提炼或改写：

- **总纲**
  - 概念表中 Plugin / Generation 的定义不变；固定词中的 Factory 改为"出厂代码"，说明它是宿主的内容，不是代际。
  - 「承诺可恢复」中的"出厂代际垫底"改为"出厂代码垫底"。
- **代际专题**
  - 「插件与配置是同一种代际」：编号一句改为"代际的身份由登记推出，一个登记号就能定位它写下的任何代际"。
  - 「出厂代际属于宿主，跟随属于登记」改写为「出厂代码属于宿主，跟随属于登记」：出厂代码按内容标识，不是代际，不试用，是回退的终点。
  - 新增一条「登记的意图与本节点的运行分开记录」：意图跨节点，运行的引用、试用与健康按节点记录，同一份代码在两个节点上可以一好一坏。
  - 安全模式一条的措辞随之改为"出厂代码"。
- **Session 专题**
  - 新增「Session 的一切是创建记录与它自己的 Log 的函数」：创建由名字的权威记下，此后的变化由 Session 自己记下；库中的行是物化。
  - 「命令在 Run 之间生效」旁新增「改变 Session 自身的命令在 Round 边界生效」。
  - 「不需要的 Session 归档，不删除」改为：归档是 Session 自己的事实，名字在归档被消费之后释放。
  - 「定时是一串触发时刻，恰好一次来自单一事务」改为「定时是 Session 的事实，恰好一次来自由定时与时刻决定的身份」。
- **多节点专题**
  - 「单机阶段就固定事后补不上的数据形态」补上三类事实，以及"可变事实放在检查它的不变式所在之处"。
  - 「宁可暂时不可用，也不出现两个执行者」中，"渠道连接与定时是租约"改为只有渠道。
- **工程专题**
  - 「持久格式只支持当前版本」改为：只读写当前格式，只从上一个版本迁移，迁移之后从事实重建核对。

## 不变式

| 不变式 | 由谁保证 | 怎样核对 |
|---|---|---|
| 物化等于事实的折叠：每个 Session 行等于它的创建记录加上它自己条目的折叠，每个定时行等于它的条目与被消费的提醒的合并 | 物化只由提交路径经同一个函数写入 | core 的单测：按 actor 的提交方式构造历史（改 profile、改工作目录、委派、归档、建立与取消定时、提醒在 Run 中与空闲时被消费、回溯越过这些条目），对每个前缀比较折叠结果与提交后的行；迁移时的重建核对；验收时在 oracle-jp 的快照上重放 |
| 定时的物化与条目的先后无关 | 物化按定时的身份合并 | 同上，打乱同一组定时事实的顺序，结果相同 |
| 每个代码引用都能解析：代际在意图中，出厂代码的制品在库中，原生能力在宿主中 | 迁移的核对；登记与恢复只写 `CodeRef` | 迁移时逐条解析 Log、Inbox 与证据中的引用；集成测试照常通过 |
| 证据的地址只由内容决定，内容中不含节点内的编号 | `MappingRecord` 只引用 `CodeRef` | 迁移后每个出处都能读出它的证据 |
| 机械恢复不改意图 | 意图与运行是两个类型，`ActivationWrite` 只含运行 | 已有的回退与安全模式测试；补一条：自动回退之后意图的表逐字不变 |
| 同一次触发的提醒至多被消费一次 | 提醒的 ID 由（定时, 时刻）决定；Inbox 与 Log 的去重 | 内核测试：触发之后、消费之前重启，Scheduler 再次投递同一次提醒，只消费一次；错过多次只补最近一次 |
| 改变 Session 自身的命令只在 Round 边界生效，不驱动 Run，不进入对话 | actor 的消费路径；输入的过滤 | 内核测试：Run 中途改工作目录，进行中的 Round 不变，下一个 Round 使用新目录，Run 照常结束；空闲时立即生效且不开始 Run |
| 归档的叫停被接纳之后，Session 不再接纳输入；名字在归档被消费之后才能给新身份 | Inbox 唯一的写入函数；根目录的释放；父对子名的检查 | 已有的归档测试照常通过；补一条：归档叫停待消费时同名的子与根都被拒绝 |
| 迁移是确定的 | 迁移只读旧库与宿主的嵌入内容 | 同一个版本 23 的库迁移两次，结果逐字节相同 |
| 主人与 Agent 看到的行为不变，「看得到的变化」中列出的除外 | 以上各条 | 已有的集成与端到端测试照常通过，为列出的变化改写的断言逐条对应 |

## 实施顺序

1. **代码的身份与注册表的拆分**：core 的类型、注册表、存储、WIT 0.18、Agent 读到的文字。先做，后两步都要用到新的条目格式。
2. **Session 的创建记录与自身的事实**：条目、命令的类别、actor 的消费、物化函数、归档、根目录。
3. **定时归 Session**：物化、Scheduler、定时工具、提醒的 ID。
4. **迁移与重建核对**：在最终格式上写，用 oracle-jp 的快照反复试。

每一步结束时 `cargo xtask check` 通过，各步可以分开提交。

## 验收

- `cargo xtask check` 通过。
- 「不变式」中的测试全部存在并通过。
- **迁移**：在 oracle-jp 库的快照上：
  - 迁移成功，重建核对全部相同；
  - 记下迁移的耗时、改写的条目与证据数、库的大小；
  - 抽查 `main` 与一个带定时的 Session 的 `enco log`、`/status`、`enco schedules`、`inspect`，与迁移前一致；
  - 迁移两次，结果逐字节相同。
- **手动核对**：
  - 在 Run 中途用 `enco working-dir` 改目录，下一个 Round 才用上；
  - 取消一个定时，空闲时立刻生效；
  - Agent 建立一个一分钟后的提醒，它在下一个 Run 中被消费一次；
  - Agent 归档一个子 Session 后，立刻用同一个名字建新的子。
- **主人升级 oracle-jp 之后**：运行一天以上，已有的周期定时照常触发，没有重复的提醒。

## 待定

1. **"改变 Session 自身的命令"这一类的名字**。现有的词：输入驱动 Run，命令关于对话。需要一个不与「插件设置」「配置」撞上的词，代码中的判断函数随之命名。
2. **已停下的 actor 怎样归档**。照本计划，它的名字要到再次运行时才释放。坏掉的 Session 正是常被归档的对象，也许需要一个只有主人能用、不经 actor 的机械归档。可以等真实出现时再加。
3. **代码在文字中的写法**。给主人与 Agent 看的状态和历史中，代际原来写成"generation N"，现在要写成"第 N 次登记的 telegram 代码"或"出厂代码"。确切的措辞在实现时与主人一起定。
