# M44 事实归位：单机上就把每份事实放到它在 Space 中的位置

> P4 Space v1 的第一个里程碑。起于 2026-11-09 与主人对 P4 的讨论，阶段的判断见[路线图](../Roadmap.md)的 P4 一节；同日第一轮审阅之后，按三处源头修订：Session 自身的变化只有一种形态，归档进控制平面，代际只在登记带来宿主没有的内容时产生。11-10 与主人定下：Agent 对定时的改变随工具的结算记下；「命令」推广为不需要回答的 Inbox 内容，作用对象决定生效时机；给主人与 Agent 的文字按登记称呼代码。计划的生命周期见路线图。

## 目标

- **形状定下来，行为基本不变。** M44 之后，每份可变事实都有它在 Space 中的归属者与身份；M45 只加上控制平面与复制，不再改变任何事实的形状。仍然只有一个节点，看得到的变化只有「看得到的变化」一节列出的几处。
- **代际只在登记带来宿主没有的内容时产生。** 代际的身份由登记推出，不再有计数器；出厂代码与原生能力是宿主的内容，按内容标识。登记的意图与本节点运行的引用和健康分开存放。
- **Session 行是三处事实的物化**：名字的权威记下的创建记录、控制平面上的归档、Session 自己的 Log。
- **一个折叠，两个视图。** 已提交的视图给 Round，有效的视图（同一个折叠接着 Inbox 中待消费的命令与提醒）给其余所有读者。
- **Scheduler 只产出提醒。** 提醒的 Event ID 由（定时, 时刻）决定；它能否进入 Inbox，由 Inbox 唯一的写入函数按有效视图检查。
- **升级不丢记录。** 宿主把库从版本 23 一步迁移到 24；迁移之后从事实重建并逐行核对，不一致就不提交。

## 起因

P4 要让事实跨节点，而跨节点的只能是控制平面的记录、单写者的流与内容（路线图 P4 一节）。下面这些事实现在不属于其中任何一类，或者它们的身份只在一个节点上成立。

### 代际编号是节点内的计数器，已经写进永久的记录

- **计数器**：`GenerationId` 与 `RegistrationId` 都是 `u64`（`crates/enco-core/src/ids.rs:82`、`:93`）。代际号由 `next_generation` 取已有的最大值加一（`registry/state.rs:179`），插件代际与配置代际共用。
- **写进了哪里**：
  - Log：`AttemptStarted` 的 `composer` 与 `provider`（`entry.rs:55`、`:57`），`ToolCallStarted` 的 `CodeRef::Generation`（`entry.rs:82`、`capability.rs:20`），`RoundEnded` 失败时的活跃代际（`entry.rs:249`），回退通知 `RolledBack`；
  - 按内容寻址的证据：`MappingRecord.generation`（`mapping.rs:9`）；
  - 注册表的各张表；
  - WIT：composer 读到的回退通知 `rollback { trial: u64, replacement: option<u64> }`（`sdk/wit/plugin.wit:876`）；
  - 评测运行器镜像的类型：`evals/runner/src/enco/output.rs:58`、`:103`。
- **后果**：第二个节点有自己的计数器，同一个号码在两边指不同的代码。证据的地址由内容决定，内容里带着号码，同一个地址在两个节点上就有两种含义。

### 出厂"代际"不符合代际的定义

- **定义**：总纲的概念表说，代际是"一份已登记、可以试用与回退的实现"。
- **出厂的记录**：
  - 不属于任何登记（`Origin::Factory`，由 `registry/factory.rs` 的 `record` 记下），状态恒为健康，不试用；它本身就是回退的终点。
  - 跟随出厂代码、设置为空的登记直接复用这条记录（`registration/prepare.rs:119`），所以同一条记录会被几次登记与机械回退共同引用。
- **用词**：设计文档中「出厂代际」与「出厂代码」各有九处，说的是同一样东西。
- **多节点**：不同版本的宿主带不同的出厂代码，记成计数器上的代际，就要每个节点各记一份。

### 注册表把意图与运行放在一起

- **一个结构装两类事实**：`RegistryState`（`ports/store/registry.rs`）里，登记、它写下的名字与代码、代际的内容是意图；`plugins` 的 `active`、`rollback_target`、`named_by`，代际的 `status` 与 `failure`，以及 `active_config` 是本节点运行的状态。
- **运行的事实写在了意图里**：
  - `RegisteredName.previous` 记的是登记时本节点实际运行的名字引用（`registration/commit.rs:96`），主人回退时据此恢复（`activation.rs:258`）；
  - `ConfigGeneration.previous` 记的是登记时本节点实际活跃的配置（`registration/commit.rs:126`）。
- **与多节点专题不符**：专题已经写明期望状态在控制平面，实际状态与健康按节点记录。同一份代码在 VPS 上通过试用、在 Mac 上失败，是两条事实。

### Session 行被多处直接改写，Log 里没有对应的事实

- **直接写 `sessions` 行的路径**：
  - `set_working_dir`（`store/sessions.rs:84`）；
  - `set_profile`（`sessions.rs:67`，经 `registry/configuration.rs:321`）；
  - 叫停子树时写 `archived_at`（`sessions.rs:239`）；
  - 根的 `ensure`（`sessions.rs:106`）与渠道建群的 `accept_creating`（`configuration.rs:270`）；
  - 子 Session 随父的提交插入（`store/commit/deliveries.rs`）。
- **子的创建记录不全**：子 Session 的创建在父的 Log 里只留下 `Delegated { session, created, event }`（`entry.rs:131`），profile 与工作目录只在行里。
- **后果**：这些事实只存在于一个可变的行里，Log 中没有，别的节点无从得出。总纲说 Session 可以只凭 Log 重建，现在 profile、工作目录与归档做不到。

### 定时是由另一个归属者改写的独立状态

- **创建与取消直接写表**：`scheduler.rs:384` 的 `create`，`store/schedules.rs:19` 的 `insert` 与 `:38` 的 `cancel`。
- **取消不看归属**：Agent 的 `schedule_cancel` 只按 ID 取消，不看定时属于哪个 Session（`builtin.rs:238`）。
- **工具的效果在 Log 之外**：`schedule_create` 与 `schedule_cancel` 在执行中请 Scheduler 改表，结算只记下结果的文字，所以它们是有副作用的调用（`builtin.rs:103`、`:115`）。改表之后、结算之前中断，结算为 `unknown`，表里却已经改了。
- **触发**：专门的事务先检查定时仍然有效，再同时推进 `last_due` 并投递提醒（`schedules.rs:72`）；提醒的 ID 是随机的（`scheduler.rs:453`）。所以 `last_due` 记的是提醒进入 Inbox 的时刻，不是被消费的时刻。
- **后果**：定时属于它的 Session，却由 Scheduler 改写；Session 换节点时，它不会跟着走。

### 库的版本不符就拒绝启动

- `open` 只认 `SCHEMA_VERSION`（`store.rs:30`、`:125`），此前的格式变化都由主人手写脚本升级。路线图写着从 P4 起升级不丢记录。
- 库开着 WAL（`sqlite.rs:14`），已提交的内容可能还在 `-wal` 文件里，只复制主文件得到的副本不完整。

## 对齐的判断

### 事实分三类，可变事实放在检查它的不变式所在之处

- **三类会跨节点的事实**：
  - **控制平面的记录**：小、可变、涉及不止一个归属者，按 CAS 改变。包括成员、Binding 的转移、租约、根目录、归档与期望状态。
  - **单写者的流**：每个归属者一条，只追加，键是 `(epoch, seq)`。现在是 Session 的 Log，以后还有连接与记忆。
  - **内容**：按哈希寻址，不可变。包括计划、工具目录、证据、blob、制品、源码与手册。
- **两种不跨节点的东西**：
  - **节点的事实**：Inbox、运行的引用与健康、安全模式、构建缓存。
  - **物化**：由上面三类事实求出的索引，随时可以丢弃重建。
- **放置看的是谁检查它，不是谁引起它**：
  - 一份可变事实放在检查它的不变式所在之处。只涉及一个归属者的，随这个归属者的流；跨归属者的，放在控制平面。
  - 例如归档由叫停引起，但它约束兄弟之间与根之间的名字唯一，也约束所有生产者的写入，所以在控制平面（见下文）。
  - 有意命令的准入不是不变式，不决定放置。例如登记不删除在用的 profile，它对着提交者此刻看得到的事实检查，与代际专题中登记守住接线是同一类规则。
- **M44 的做法**：把库中每张表归入其中一类（见「归类」），存储的模块按类组织。单机时控制平面就是本机的库，M45 换成 openraft。

### 代际只在登记带来宿主没有的内容时产生

- **规则**：一次登记只在给某个单元带来宿主没有的内容时，才产生代际。单元是一个插件或配置；内容是源码编出的制品，或非空的设置；配置的文档总是来自登记。
- **身份**：代际的身份就是"哪一次登记、哪个单元"，由登记推出，不再有自己的计数器。
  - 唯一性有保证：插件的代际只由代码动作产生，一次登记对每个插件只有一个动作（`registration/commit.rs` 按插件逐个处理），配置至多一份。
- **登记号的来源**：登记号是唯一提交者给出的顺序。单机时是本机的下一个号，M45 起由控制平面的状态机给出。
- **宿主的代码按内容标识**：出厂代码是（插件身份, 制品哈希），原生能力照旧是（名字, 版本）。
  - 两者都不登记、不试用，是回退与安全模式的终点。
  - 不同版本的宿主自然得到不同的标识，同一个版本在各节点上是同一个标识，不需要任何节点去记。
- **跟随出厂代码的插件**：
  - 设置为空时，它运行的就是出厂代码本身：没有代际，不试用，也就不会"回退"到相同的字节与相同的空配置。`prepare.rs:119` 的分支保留，它是这条规则的推论，不是特例。
  - 设置不为空时，设置与出厂制品合成一个代际，照常试用。
  - 宿主换版本时，照旧经一次普通登记，把引用移到新宿主的出厂代码；回退目标留着旧宿主的出厂代码，它的制品照旧保留成文件。
- **一个类型**："运行的是什么代码"只有 `CodeRef` 一个类型，它有三种：代际、出厂代码、原生能力。当前与回退的引用、登记写下的代码意图、Log、证据与回退通知都用它。
- **配置代际**：它的身份就是那次登记，`ConfigurationRef` 中重复的两个字段合为一个。
- **用词**：设计文档统一为「出厂代码」，不再说「出厂代际」。

### 意图与运行分开存放

- **意图（控制平面）**：登记，以及它写下的名字（只记名字）与代码意图；代际的内容（制品、设置、来历）；配置代际的文档。
- **运行（节点）**：
  - 每个插件当前与回退的引用，它们由哪次登记写下；运行中的名字由哪次登记写下；
  - 每个代际在本节点的试用、健康与失败；
  - 当前的配置；
  - **每次登记在本节点替换掉的运行引用**：名字与配置各是什么。这是一条按登记记下的节点记录，取代 `RegisteredName.previous` 与 `ConfigGeneration.previous`；主人回退时读它，恢复的是本节点此前实际运行的东西。
- **写入方式不变**：登记同时写意图与本节点的运行，机械恢复只写运行。M45 起改为登记先在控制平面提交意图，各节点再各自跟随；M44 只把数据分开。

### 给主人与 Agent 的文字按登记称呼代码

- **Agent 在四个时刻读到代码的身份**：登记之后；被回退通知打断时；查看状态时；一次调用突然失败时。它能拿来操作的编号只有登记号：`self_history`、`self_rewind` 都接受它，主人回退也按登记。所以文字里只出现登记号，Agent 不必换算。
- **用词**：
  - 不出现 "generation"。对模型来说，这个词最先唤起的是文本生成，"generation 15 failed" 放在 Provider 的报错旁边，容易读成"第 15 次生成失败"。代际仍是设计与代码中的概念，文字按登记称呼它，不另起名词，所以不是第二个名字。
  - 以插件为主语时写 "runs registration 12"；需要名词时，只用 Agent 自己编辑的东西：code、settings、configuration、factory code。不改用 "version"，以免成为第二个名字。
  - 一个插件用的登记号，是最后一次改动它的代码或设置的那次登记，`self_status` 的说明写明这一条。
  - 回退只用一个动词 "rolled back to"，与通知的标题一致；"on trial" 与 "healthy" 沿用 `self_apply` 的说法。
- **每段文字按 Agent 发问的顺序写**：发生了什么，现在运行的是什么，什么没有变，或者重做一遍为什么没用。
- **通知只写事实，不指向工具**：回退通知发给引起失败的那个 Session（`registry/health.rs:60`），它可能没有 `self_status`。
- **写法**：实现以此为准，措辞的改动与主人核对。
  - `self_status` 的说明，中间两句改为下面这样；"a generation is one registered version…" 删去：

    ```text
    A table then shows config.toml and every plugin in three layers: running (what runs now),
    registered (what was last registered for it) and home (its files in the Enco home). Running
    and registered name the registration that last changed the code or settings, or say factory
    code, which ships with the host.
    ```

  - 状态表；配置一行原来的"代际号 · 登记号"只剩一个数：

    ```text
    | plugins/telegram | registration 12 · healthy | registration 15 · failed | matches |
    | plugins/web      | factory code              | factory code             | no directory |
    | config.toml      | registration 14           | registration 14          | matches |
    ```

  - 登记结果。结果本身就是这次登记，所以不写编号；`self_apply` 的说明同样改为 code 与 settings、"rolled back to what ran before"：

    ```text
    - plugins/telegram: new code · on trial
    - plugins/discord: new settings · on trial

    New code and settings start on trial: each becomes healthy after its probe and 20 successful
    calls while it runs; one that fails first is rolled back to what ran before.
    ```

  - 回退通知，即模型看到的原文：

    ```text
    [plugin rolled back] telegram failed on trial with registration 15 (timeout: no reply in 30 s)
    and was rolled back to registration 12. Registration 15 and the files in the home are unchanged.
    ```

    - 回退到出厂代码时写 "…and was rolled back to factory code."；没有可运行的时写 "…; nothing earlier can run, so it is stopped."
    - 最后一句挡住"我的改动被撤掉了"这个推断。
    - 通知不归因：坏在代码还是设置，只在处境中写明。
  - 调用失败。工具目录在 Round 开始时固定，本 Round 内重试仍会失败，所以写明从下一个 Round 起；没有可运行的时写 "its tools are unavailable from the next Round"：

    ```text
    not executed: telegram failed with registration 15 (timeout: …) and was rolled back to
    registration 12; calls from the next Round go to registration 12.
    ```

  - 处境：粗体标题直接说处境，事实里写明坏在代码、设置还是出厂代码；其余处境照同一规则改，例如 "It keeps running registration 12"、"This host cannot run registration 15: …"：

    ```text
    **plugins/telegram — rolled back to registration 12.** Registration 15's code failed:
    <message>. Registering the same source again changes nothing.

    **plugins/telegram — runs registration 12, not the registered 15.** Registering the same source
    again changes nothing.

    **plugins/telegram — stopped.** Registration 15's code failed: <message>. Nothing earlier can run.
    ```

  - 手册开头：
    - "Built from the source registered in registration 15."
    - "Factory code, shipped with the host."
    - 跟随出厂代码且带设置时："Factory code with the settings registered in registration 9."
    - 生成注释写 "from the code that runs"，索引行写 "this host cannot run it."
- **事件与 WIT 跟着改名**：core 的 `GenerationRolledBack` 改为 `PluginRolledBack`，WIT 的 `generation-rolled-back` 改为 `plugin-rolled-back`，与通知的标题一致；写 composer 的 Agent 读 CONTRACT.md 时也看到同一个说法。
- **旧记录的原文照旧**：Log 中旧的回退通知与工具结果，是模型当时看到的文字，迁移只改写结构化的字段，不改原文。

### Session 行是三处事实的物化

- **创建记录由名字的权威记下**：
  - 根 Session 记在根目录（控制平面）；
  - 子 Session 记在父的 Log 里，`Delegated` 带上完整的创建记录；
  - 创建记录写明身份、全名、父、创建时间、初始节点、初始 profile 与初始工作目录。Binding 此后的转移在 M46 由控制平面记下。
- **归档记在控制平面**，见「归档是控制平面的事实，沿树推出」。
- **此后的变化由 Session 自己的 Log 记下**：profile 与工作目录的改变只有一种形态，即被消费的命令（`EventConsumed`），与回溯、压缩的先例一致，不新增条目种类。定时的事实见「定时归 Session，Scheduler 只产出提醒」。
- **profile 与工作目录是引用**：接纳时检查 profile 存在、路径是绝对路径；使用时由 Round 开始时解析。消费总是生效，所以被消费的命令本身就是事实，不需要另记"生效了"。
- **库中的 Session 行是物化**：
  - 由 enco-core 中的一个函数求出；
  - 只在提交来源事实的事务里写入：actor 的提交、根目录与归档的写入；
  - 读取的路径不变；M45 的副本用同一个函数得到同样的行。
- **这一条兑现的是**总纲中"Session 可以只凭 Log 重建"：身份与名字来自名字的权威，是否还在用来自控制平面，其余都来自它自己的 Log。

### 一个折叠，两个视图

- **已提交的视图**：把创建记录、归档与 Session 的 Log 折叠起来，就是库中的物化行。
- **有效的视图**：用同一个函数，在已提交的结果之后，按 Inbox 的顺序接着折叠这个 Session 待消费的命令与提醒。Store 在一个事务里读物化行与待消费的 Inbox，这与 Session 专题中"消费与追加在同一个事务里，两者也在同一个事务里读"是同一条规则。
- **谁读哪个**：
  - Round 开始时读已提交的视图。作用于 Session 自身的命令在边界上先被消费，所以模型用到的都已经记下。
  - 其余读者都读有效的视图：`/status`、定时列表与 Agent 的三个定时工具、Scheduler、Inbox 写入函数的前提、迁移的核对。登记的准入读 Session 接下来会经过的每个视图，见「有意命令的准入」。
- **结果**：下游不再各自拼"物化 + 待消费的命令"，有效状态只有一个定义。

### 命令不需要回答，作用对象决定生效时机

- **Inbox 里只有两类内容**：输入要回答，驱动 Run；命令不需要回答，不驱动 Run，也不是对话中要回答的输入。「命令」由"关于对话"推广为"不需要回答"，不另起名词。
- **命令按作用对象分两种**：
  - **作用于对话**：回溯、叫停、压缩。它们改写对话或取代此前的输入，所以在两个 Run 之间生效，压缩由下一个 Run 的第一个 Round 兑现。与现在相同。
  - **作用于 Session 自身**：主人改 profile、改工作目录、取消定时，都投进那个 Session 的 Inbox。它们只影响 Round 开始时钉住的东西，所以在下一个 Round 边界生效，Session 空闲时就是立刻。这与「Round 开始时钉住所见」一致：profile 与工作目录本来就从下一个 Round 起生效。
- **一个穷尽匹配的函数**：
  - `EventBody` 上的一个函数说明命令作用于什么，输入没有；它与 `reply_destination` 一样穷尽匹配，新增一种 Event 时编译器要求先决定它。标识符在实现时定。
  - `is_command()` 由它推出。要的正是"不是输入"的调用点不需要改动：`transcript::input` 找普通输入时跳过命令，`check_backtrack` 回溯不能指向命令。
  - Run 的结束判断（`run.rs` 的 `inputs_wait`）、传给 Round 的输入与 composer 都只看输入。"只有 Run 的第一个 Round 消费压缩请求"是压缩自己的规则，`run.rs` 仍按压缩请求判断。
- **命令按对输入的影响也分两种**：
  - 回溯与叫停取代此前的输入（`supersedes_inputs()`）。
  - 压缩请求与作用于 Session 自身的命令不取代（`leaves_inputs()`）：模型看不到它们，它们不解除叫停，不改变等待与回复去向，空闲时单独被消费。
  - 叫停与"欠一个回答"的折叠、模型可见与空闲时的消费都按 `leaves_inputs()` 判断，不各自列举；等待与回复去向只看交互的输入，本来就不受它们影响。
- **只有主人的命令作用于 Session 自身**：Agent 对本 Session 定时的改变随工具的结算记下，不经 Inbox（见「定时归 Session，Scheduler 只产出提醒」）。
- **主人的取消投给定时所属的 Session。**
- **主人这边看到的**：命令在接纳时返回，说明从下一个 Round 起生效；`/status` 与定时列表读有效视图，所以待生效的改变立刻可见。
- **已停下的 Session 照常接纳作用于它自身的命令**：它们在接纳时就进入有效视图，不等 actor 处理；actor 恢复后再记进 Log。输入与作用于对话的命令要等 actor 回答或改写对话，所以停下时照旧报错。这与子树叫停直接写进停下的 Session 的 Inbox 是同一个做法。

### 归档是控制平面的事实，沿树推出

- **为什么在控制平面**：归档约束兄弟之间与根之间的名字唯一，也约束任何生产者向它投递的输入，是跨归属者的事实。
- **推出的规则**：一个 Session 已归档，当且仅当它自己或某个祖先在控制平面被记为归档。整棵子树的归档只是一条事实；以后在少数派一侧新建的子孙，也被它覆盖。
- **谁记下**：主人的命令或父的 `session_archive`，都经控制平面记下；单机时是本机的一个事务，同时沿子树更新物化的行，并把叫停投给已知的子树。
- **不需要任何 actor 消费**：名字在记下的同时释放。已停下的 Session 也随之归档，它的名字与子名字立刻可以给新身份。
- **叫停不变**：叫停照旧发给子树，只用来停下正在运行的工作、取代此前的输入；`Halt` 不需要"归档"标记。`Kernel::archive` 照旧等正在运行的 actor 静止。
- **Inbox 不变**：Inbox 唯一的写入函数照旧对已归档的 Session 不写入，读的是沿树更新过的物化行。
- **名字唯一的含义**：唯一性在每个目录里成立，即（父的身份, 一段名字）在未归档的 Session 中唯一。全名的唯一索引是它的推论，因为已归档的子树整个被排除，所以保留。
- **代价**：M45 起，少数派一侧不能归档，包括 Agent 的 `session_archive`。

### 定时归 Session，Scheduler 只产出提醒

- **定时的事实在 Session 的 Log 中**，库中的定时行是它们的物化：
  - Agent 的建立与取消，是工具结算上的字段；
  - 主人的取消，是被消费的命令；
  - 哪一次已经提醒过，是被消费的提醒。
- **物化按整份 Log 求出**：它随提交维护，不随回溯改变，对话之外的状态不回退。它按定时的身份把这几种事实合起来，与条目的先后无关；同一个定时被取消两次，结果相同。
- **Agent 的改变随结算记下**：
  - 三个定时工具同 `session_send` 一样是内置调用。执行时只解析与校验参数；列出的内容、本 Session 有没有这个定时、它是否仍然有效，都在结算时对着本 Session 的有效视图按调用顺序求出。这与 Session 专题「委派的检查在提交时按顺序做」是同一条规则：一条回复里先建立再列出，列表看得到建立；先建立再取消，取消看得到建立；检查不成立，这次调用就结算为失败，什么也不写。读取与提交之间被接纳的取消或提醒只会让这次取消成为多余：折叠按身份合并，重复的取消结果相同。
  - 改变作为 `ToolCallSettled` 的字段，与结算一起提交，与 `delegated` 同类。这就是归属与转移的规则：回调把写入作为返回值，由归属者与接纳的事实一起原子提交。
  - 三个定时工具因此都是只读的调用：中断时什么也没有提交，结算为失败，不会留下 `unknown`。
  - 取消有两种来源，主人的命令与 Agent 的结算，由同一个折叠合并。这与投递投影同时读 Round 的回复和 `message_send` 的结算同类：一件事只记一次，并不要求一种结果只有一种来源。
  - 不投给自己的 Inbox：那要为"本 Session 自己"新增一种 Event 来源，晚一个边界才生效，迁移时也只能在 Log 末尾补记从未发生过的命令。
- **Scheduler 不再拥有状态**：它读有效视图，算出下一次时刻，到期就把提醒作为普通的输入接纳。`fire_schedule` 与它的事务删去。
- **前提在 Inbox 唯一的写入处**：
  - 指名一个定时的 Event（提醒与主人的取消）能写入，当且仅当这个定时在有效视图中仍然有效：没有被取消（包括已接纳、尚未消费的取消），一次性的定时没有提醒过。
  - 这与"Session 已归档就不写入"是同一类前提，由归属者唯一的写入函数在事务里检查。它取代旧的触发事务中的那次检查，没有另加一层。
  - 于是，取消被接纳之后到期的提醒不会进入 Inbox；先进入 Inbox 的提醒按 Inbox 的顺序照常被消费。
- **恰好一次来自身份**：提醒的 Event ID 由（定时, 时刻）决定，重启后重发、以后别的节点重发，都被 Inbox 与 Log 的去重吸收。时刻是由规则推出的计划时刻，不取当前的时钟，所以无论哪个节点推出，同一次触发的 ID 都相同；时钟的偏差只影响提醒早到还是晚到。
- **补发规则不变**：宕机期间错过的触发只补最近一次，上一次提醒取自有效视图。
- **与 M46 的关系**：M46 起，Scheduler 只为 Binding 指向本节点的 Session 产出提醒；M44 时所有 Session 都在本机。这一条兑现路线图中"定时跟着 Session 走"，多节点专题删去"定时是租约"。

### 由起因决定的 Event ID 只用在现在需要的地方

- M44 只改提醒，因为新的 Scheduler 依赖它。
- 渠道输入的 ID 改由更新键决定，留到 M48：它只在租约交接时有用，旧的随机 ID 也不妨碍以后的去重。

### 有意命令的准入对着接下来的每个视图检查

- 登记照旧拒绝删除仍被未归档 Session 使用的 profile。"使用"读的是各 Session 接下来会经过的每个视图：已提交的视图是它与子孙的 Round 沿谱系读到的；actor 每次消费待消费命令的一段前缀，已提交的视图随之逐个经过中间的视图，直到有效视图。Store 在一次读取里给出它们，中间的视图出自提交时用的同一个折叠。待消费的命令指名的 profile，在命令被消费之前一直受保护。已归档的 Session 不在其内：它已被叫停，归档之前读到的 Inbox 至多让进行中的 Run 再开始一个 Round，那个 Round 读到被删的 profile 时以 `profile.unknown` 失败，Run 照旧以叫停结束。
- 这是有意命令的准入，与登记守住接线同类，对着提交者此刻看得到的事实检查，不是全局不变式。多节点时，分区另一侧新建的使用由 Round 开始时解析 profile 失败来报告，这与"祖先的 profile 解析不了时这一轮失败"是同一条规则。

### 升级只从上一个版本一步迁移，迁移之后从事实重建核对

- **怎样迁移**：打开版本 23 的库时，宿主先用 `VACUUM INTO` 写出一份完整的单文件副本，再在一个事务里迁移到 24。迁移之后，正常的代码只读写当前格式。
  - 工程专题「持久格式只支持当前版本」改为：只读写当前格式，只从上一个版本迁移。
- **迁移做的事**：
  - **代码引用**：来自代码与设置的代际改为（登记, 插件）；来源为出厂的记录一对一改为按内容标识的出厂代码，不论有几次登记引用过它；配置代际改为（登记, 配置）。Log、Inbox、注册表与证据中的引用都改写；证据的内容变了，地址随之改变，引用这些证据的出处一并改写。
  - **回退通知**：事件改名为 `PluginRolledBack`，结构化的字段改为失败的登记号与回退去向；通知的原文是模型当时看到的，照旧。
  - **节点记录**：`previous` 移进每次登记的节点记录。
  - **创建记录**：根的写进根目录；子的写进父 Log 中已有的 `Delegated`。M44 之前没有记下创建时的取值，所以按迁移时的取值写，计划在这里如实说明。
  - **归档**：为每个"不能由祖先推出"的已归档 Session 在控制平面记下归档。
  - **定时**：只用计划中的形态补记，不为迁移另设种类，取值来自旧表。
    - **建立**：在所属 Session 的 Log 中，找到结算内容带着这个定时 `id` 的那次 `schedule_create`，在原来的结算上补上字段。找不到就不提交，交给主人手动处理；只有改表之后、结算之前中断的调用会这样。
    - **Agent 的取消**：所属 Session 自己的 `schedule_cancel` 结算为已取消的，在原来的结算上补上字段。
    - **其余的取消**：主人经 CLI 取消的，以及别的 Session 取消的，在所属 Session 的 Log 中没有痕迹，补记为被消费的取消命令，追加在 Log 末尾。旧表没有记下取消的时刻，补记的命令按迁移的时刻记下。
    - **提醒**：已消费的与仍在 Inbox 中的提醒都不改写，随机的旧 ID 照旧；下一次时刻从有效视图推出，不会重发它们。
- **核对**：
  - 用与提交相同的函数从事实重建，拿有效视图与迁移前的行逐行比较。旧的 `last_due` 在提醒进入 Inbox 时就推进了，它对应的正是有效视图，所以 Inbox 中留有未消费提醒的库也能通过。
  - 身份都要能解析，外键成立。制品的字节不归迁移核对：迁移不碰制品文件，启动时注册表按哈希读出并校验。
  - 有任何不同或解析不了，就不提交，库保持原样。
- **只保留一个版本**：迁移的代码只保留到下一次格式变化，届时换成新的迁移。不支持降级，需要时用迁移前的副本。M45 的 Space 版本在此之上加一条：全部成员都升级之后才定案。

## 看得到的变化

除此之外，主人与 Agent 看到的行为不变：

- **主人的命令**：`enco profile`、`enco working-dir` 与取消定时在接纳时返回，从下一个 Round 起生效，Session 空闲时立刻生效；Session 因故障停下时照常接纳，原来会报错；待生效的改变在 `/status` 与定时列表中立刻可见。取消定时原来是立即的，Session 在 Run 中时，现在至多晚一个 Round。
- **定时工具**：
  - Agent 的 `schedule_cancel` 只能取消本 Session 的定时；
  - 建立与取消的效果随结算一起记下，中断时结算为失败而不是 `unknown`；
  - 三个工具都成为只读调用，可以与其他只读调用同批执行；它们在结算时按调用顺序求值，所以 `schedule_list` 看得到同一条回复中先前的建立与取消。
- **文字**：状态、登记结果、回退通知、调用失败、处境与手册中，代码按登记称呼，或写作出厂代码，不再出现 "generation" 与代际号，写法见「给主人与 Agent 的文字按登记称呼代码」。
- **WIT**：升到 0.18，`generation-rolled-back` 改名为 `plugin-rolled-back`，带失败的登记号与回退去向。

归档、出厂代码与跟随的行为都不变；已停下的 Session 照旧可以归档，名字立刻释放。

## 设计

验收时提炼或改写：

- **总纲**
  - 概念表中 Plugin / Generation 的定义不变；固定词中的 Factory 改为"出厂代码"，说明它是宿主的内容，不是代际。
  - 固定词旁补一句：Generation 是设计与代码的词；给主人与 Agent 的文字按登记称呼代际，不用这个词，需要名词时只用 code、settings、configuration 与 factory code。
  - 概念表中 Binding 的"渠道与定时是租约"改为只有渠道；状态归属表中定时的归属者改为 Session actor，Scheduler 只产出提醒。
  - 「承诺可恢复」中的"出厂代际垫底"改为"出厂代码垫底"。
- **代际专题**
  - 「插件与配置是同一种代际」：编号一句改为"代际的身份由登记推出，一个登记号就能定位它写下的任何代际"。
  - 「出厂代际属于宿主，跟随属于登记」改写为「出厂代码属于宿主，跟随属于登记」：只有登记带来宿主没有的内容时才产生代际；出厂代码按内容标识，不试用，是回退的终点；跟随出厂代码、设置为空时，运行的就是它。
  - 新增「登记的意图与本节点的运行分开记录」：意图跨节点；运行的引用、试用、健康，以及每次登记替换掉的东西按节点记录；同一份代码在两个节点上可以一好一坏。
  - 安全模式一条的措辞随之改为"出厂代码"。
- **Session 专题**
  - 新增「Session 行是创建记录、归档与它自己 Log 的物化」：三处事实各归其主；一个折叠，两个视图。
  - 「命令在 Run 之间生效」改为「命令不需要回答，作用对象决定生效时机」：作用于对话的在两个 Run 之间生效，作用于 Session 自身的在下一个 Round 边界生效；回溯与叫停取代此前的输入，压缩与作用于 Session 自身的命令不取代，也不改变等待、叫停与回复去向。
  - 「不需要的 Session 归档，不删除」改为：归档是控制平面的事实，沿树推出，名字在记下时释放。
  - 「定时是一串触发时刻，恰好一次来自单一事务」改为「定时是 Session 的事实，恰好一次来自由定时与时刻决定的身份」：Agent 的改变随工具的结算记下，检查在结算时按调用顺序做；主人的取消是作用于 Session 自身的命令；提醒的前提在 Inbox 唯一的写入处按有效视图检查。
  - 「对话之外的状态不回退」中，定时不再是"各有归属者"的一例：它归 Session，但物化按整份 Log 求出，回溯不改变它。
  - 「外部输入只有一个入口，同一种操作只有一份语义」中，Scheduler 不再是推进自身状态的内部归属者；取消定时的两种来源由同一个归属者记下、同一个折叠读出，仍是一份语义。
- **多节点专题**
  - 「单机阶段就固定事后补不上的数据形态」补上三类事实，以及"可变事实放在检查它的不变式所在之处；有意命令的准入另是一类"。
  - 「宁可暂时不可用，也不出现两个执行者」中，"渠道连接与定时是租约"改为只有渠道。
  - 「少数派一侧只继续自己持有的东西」补上：不能归档。
- **工程专题**
  - 「持久格式只支持当前版本」改为：只读写当前格式，只从上一个版本迁移，迁移之后从事实重建核对。

## 不变式

| 不变式 | 由谁保证 | 怎样核对 |
|---|---|---|
| 已提交的视图等于事实的折叠：每个 Session 行等于它的创建记录、归档与它自己 Log 的折叠，每个定时行等于它的事实的合并 | 物化只由提交路径经同一个函数写入 | core 的单测：按 actor 的提交方式构造历史（Round 边界与空闲时消费的改变、委派、归档、建立与取消定时、在 Run 中与空闲时被消费的提醒、越过这些条目的回溯），对每个前缀比较折叠结果与提交后的行；迁移时的重建核对；验收时在 oracle-jp 的快照上重放 |
| 有效视图等于同一个折叠接着待消费的命令与提醒 | Store 在一个事务里读两者；同一个函数 | core 的单测：任意已提交的历史与待消费序列，有效视图等于折叠 Log 再折叠待消费的部分；消费之后的已提交视图等于消费之前的有效视图 |
| 定时的物化与条目的先后无关 | 物化按定时的身份合并 | 同上，打乱同一组定时事实的顺序，结果相同 |
| Agent 对定时的改变与结算一起提交，只作用于本 Session，按调用顺序检查 | 结算的事务；`BuiltinCall` 的执行只解析参数 | 内核测试：一条回复中先建立再列出再取消再列出，列表反映调用顺序，定时已取消；取消别的 Session 的定时，结算为失败，什么也不写；结算之前中断，结算为失败，没有留下定时 |
| 已接纳的取消之后到期的提醒不进 Inbox；先进入的照常被消费 | Inbox 唯一的写入函数按有效视图检查 | 内核测试：取消已接纳、尚未消费时提醒到期，提醒不写入；提醒先写入、取消随后接纳，提醒按顺序被消费 |
| 同一次触发至多被消费一次；错过多次只补最近一次 | 提醒的 ID 由（定时, 时刻）决定；Inbox 与 Log 的去重 | 内核测试：提醒写入之后、消费之前重启，Scheduler 再次投递同一次提醒，只消费一次 |
| 作用于 Session 自身的命令只在 Round 边界生效，不驱动 Run，不进入对话 | actor 的消费路径；输入的过滤 | 内核测试：Run 中途改工作目录，进行中的 Round 不变，下一个 Round 使用新目录，Run 照常结束；空闲时立即生效且不开始 Run |
| 已归档，当且仅当自己或某个祖先被记为归档；名字在记下时释放 | 控制平面的归档；物化沿子树更新；Inbox 唯一的写入函数 | 集成测试：父有一个已停下的子，归档父之后，同名的新根立刻可以委派同名的子；投给旧子的输入被拒 |
| 跟随出厂代码、设置为空的插件运行出厂代码，不产生代际，不会回退到相同的代码 | 登记的规则 | 注册表测试：全新启动之后这类插件没有试用中的代际；带设置时照常试用并在失败时回退 |
| 身份都能解析 | 迁移的核对；登记与恢复只写 `CodeRef` | 迁移时按类型逐条解析 Log、Inbox、投递、连接状态与证据中的引用；集成测试照常通过 |
| 证据的地址只由内容决定，内容中不含节点内的编号 | `MappingRecord` 只引用 `CodeRef` | 迁移后每个出处都能读出它的证据 |
| 机械恢复不改意图；主人回退恢复的是本节点此前的名字与配置 | 意图与运行是两个类型；节点记录按登记记下替换掉的东西 | 已有的回退与安全模式测试照常通过；补一条：自动回退与主人回退之后，意图的表逐字不变 |
| 迁移是确定的，并且对 Inbox 中留有未消费提醒的旧库成功 | 迁移只读旧库与宿主的嵌入内容；核对用有效视图 | 同一个版本 23 的库迁移两次，结果逐字节相同；版本 23 的夹具迁移并通过核对，其中有未消费的提醒、Agent 建立与取消的定时、主人取消的定时 |
| 主人与 Agent 看到的行为不变，「看得到的变化」中列出的除外 | 以上各条 | 已有的集成与端到端测试照常通过，为列出的变化改写的断言逐条对应；`evals/runner` 读得了新的 `enco log` |

## 实施顺序

1. **代码的身份与注册表的拆分**：core 的类型、注册表、存储、WIT 0.18、`evals/runner` 的镜像、Agent 读到的文字。先做，后几步都要用到新的格式。
2. **Session 的三处事实与两个视图**：根目录、控制平面的归档、作用于 Session 自身的命令、actor 的消费、折叠函数与有效视图的读取。

- `cargo xtask check` 通过。
- 「不变式」中的测试全部存在并通过。
- **迁移**：在 oracle-jp 库的快照上：
  - 迁移成功，重建核对全部相同；

  - 迁移两次，结果逐字节相同。
- **手动核对**：
  - 在 Run 中途用 `enco working-dir` 改目录，下一个 Round 才用上；
  - 取消一个定时，空闲时立刻生效；
  - Agent 建立一个一分钟后的提醒，它在下一个 Run 中被消费一次；

## 实施中的调整

实施中与上文不同、或上文没有写到的地方，验收时与主人逐条核对：

- **实现之后的审阅**：判断与修正见 [M44-Review.md](M44-Review.md)，上文相关段落已随之修订。

- **配置代际以登记号为身份**：`GenerationId` 只是（登记, 插件）；配置代际的身份就是 `RegistrationId`，与「代际只在登记带来宿主没有的内容时产生」中"一个登记号就能定位它写下的任何代际"一致，少一种单元。
- **失败的 Round 记下 `ActiveCode`**：`RoundEnded` 的失败原来记代际号的列表，现在记活跃配置的登记号与每个运行中插件的代码；安全模式比较的就是它。
- **Inbox 写入的结果多一种**：`Accepted::Inactive`，指名的定时在有效视图中已不再有效的 Event（提醒与主人的取消）不写入。Scheduler 与主人的取消把它读作"定时已不再有效"；不指名定时的写入者遇到它是内部错误。
- **定时的折叠在 enco-core**：`ScheduleFold`（`crates/enco-core/src/schedule.rs`）按定时的身份合并事实，与次序无关；Log 折叠成已提交的视图，同一个函数接着待消费的 Inbox 折叠成有效视图。
- **主人取消定时的回答不变**：`enco schedules --cancel` 照旧回 `cancelled: true/false`，不写"从下一个 Round 起生效"。命令被接纳后，Inbox 就不再写入这个定时的提醒，对主人而言取消已经生效；推迟到 Round 边界的只是它在 Log 中的记录。
- **Agent 的取消失败**：不是本 Session 仍然有效的定时，以 `tool.failed` 结算，说明"不是本 Session 仍然有效的定时"。
- **补记的取消命令**：时刻取该 Log 最后一条的时刻，ID 取定时的身份，不取迁移的时刻与随机 ID。上文"按迁移的时刻记下"与验收的"迁移两次，结果逐字节相同"冲突，这里取后者；旧表本来就没有记下取消的时刻。
- **表结构的改动由 `schema.sql` 推出**：迁移在内存中用 `schema.sql` 建一个新库，与旧库的 `sqlite_master` 逐项比较；只允许本计划替换的 13 个表与索引不同，其余定义必须逐字相同，否则不迁移。迁移之后整个结构必须与新库相同。
- **映射出处按类型改写**：v23 的出处在持久化类型中只有固定的几处（渠道输入的来源、早先消息、引用的抓取、`AttemptSettled`、投递结算、连接状态中的早先消息）；文档先解码成当前类型，再逐个改写。被出处指向的记录才迁移，每一条都必须能按 v23 的形式读出；其余证据与插件的不透明 JSON 原样不动。
- **Log 的读取单独成模块**：`store/log.rs`，`store/sessions.rs` 只管 Session 行。
