# M37 委派

> 路线图「Session 委派」阶段的第三个里程碑，依赖 M35（已验收：`reply_skip` 与等待回音的判断，见 Session 专题「默认说话，没有输入在等待回音时才可以沉默」）与 [M36](M36.md)（名字的一段、角色说明与工作目录）。计划的生命周期见[路线图](../Roadmap.md)。

## 目标

主人可以这样使用 Enco：

- 让 Agent 把一件长任务交给后台的子 Session，自己继续和主 Session 聊；结果回来时，由 Agent 核对之后判断要不要告诉主人。
- 用一个门面 persona 与主人对话，实际工作委派给幕后的 Session。
- 让擅长不同事情的模型做不同的事：子 Session 按角色（profile）选用模型，每个角色有一句 `description`，也有自己的角色说明。
- 用不同的根 Session 管理不同的项目，各自长出子树。
- 需要时直接和某个子 Session 对话；不需要的子 Session 归档。

一句话：子 Agent 就是 Session，父子只经 Event 交互；内核只记谱系、向上投递、向下叫停，其余都是父 Session 中模型的判断。

## 参考

- **deepseek-harness**：几轮迭代后收敛到「持久 Session + 至多一个在线 activation + 唯一的 inbox」，与「分身就是 Session」同构；它的 inbox 不持久，自己写明重启会丢已接受的消息，Enco 的 Inbox 已经持久并按 Event ID 去重。它把「运行时对子任务结局的说明」与「子 Agent 自己说的话」分成两种来源，理由是合并之后会把子 Agent 没说过的话算在它头上。
- **pi/durable**：谱系（fork 的历史来源）与监督关系分成两条边；父 turn 用持久的等待挂起，前台 subagent 在内存中阻塞等子 Run，取消沿所有权向下、自下而上静止。
- **Clonoth**：反例。任务不持久，父指针分存两处，取消够不到异步子任务，结果按 Session 而不是按任务路由。
- **limcode-test**（主人认为体验最好）：子 Agent 是完整的对话，可打开、继续、直接对话，直接对话的回复不送给父；默认异步，「最后一条回复就是结果」，没有 submit 工具；每次请求附一张由持久事实重建的子任务状态卡；名册写在工具说明里；停止父 Agent 不级联。它的弱点：被唤醒必须说话，没有沉默的办法（M35 补上）；父↔子循环不计预算；核心两个文件约 8000 行、约 20 张表。
- **Raft**：没有指挥者；消息只在安全的边界送进 Agent；提醒只给数量不给正文，读不读由 Agent 判断。
- **OTP 与 Trio**：父 Session 监视子 Session（回报即 monitor 的 DOWN 消息），叫停沿树向下（link）；重启属于健康门控、安全模式与恢复。子 Session 的作用域是父 Session，不是父的某个 Run。

## 对齐的判断

### 结构

- **分身就是 Session；内核在树上只做三件事。** 子 Agent 是一个普通的 Session：有身份、Log、Inbox 与 actor，所以持久、崩溃恢复、漫游、检视、profile、composer 与安全模式全部照常，不需要新概念。父关系在创建时固定，此后不变。内核在树上只做三件事：记下谱系，把子 Session 交给父的内容投递上去，把叫停传下去。重试、改派、放弃与合并结果，都由父 Session 中的模型判断（总纲「自动机制只做有证据的事」）；按策略重启这类 OTP supervisor 的职责，在 Enco 中已经由健康门控、安全模式与恢复承担。所以总纲 Erlang 透镜中「父 Session 是子 Session 的 supervisor」改为「父 Session 监视子 Session、向下叫停」，阶段也不再叫「监督树」，改叫「Session 委派」。

- **委派是转移，不是调用。** `session_send` 在子 Session 的输入被接纳时就返回；子 Session 交给父的内容之后作为父的输入到达。阻塞式委派会让父的 Round 挂起几分钟：漫游、换代与压缩都要等这个唯一的安全点，主人的新消息也没人消费（总纲「Round 边界是唯一的安全点」）。子 Session 本来就要活得比父的 Run 长。一条回复里的几个 `session_send` 同批执行，并行派出是自然的。代价：只是问另一个模型一个问题，也要多一个父 Round，前缀缓存让它不贵。有界等待可以以后在 Round 边界加上，回报照常作为输入消费，不新增路径。

- **新 Session 从空的 Log 开始。** 子 Session 看不到父的对话，第一条输入就是父写的任务；此外它有自己的角色说明，有效权限带主人的上下文时还有 `AGENTS.md` 与记忆。长期的事实经记忆共享，对话不共享。再发给已有的子 Session 时，它带着自己的历史继续。不继承父的历史，原因有两个：委派的目的常常就是干净、更小的上下文，换用的模型窗口也可能更小；最适合写任务的是父模型，所以 `session_send` 的说明要求写全目标、背景、约束、期望的结果与验证方式。

- **子 Session 的名字是父名字下的路径。** 子 Session 的全名是 `<父的全名>/<短名>`，例如 `main/research`；父用短名称呼它。唯一性由结构保证，不必在多个根之间协调，谱系对人一目了然（Plan 9 的命名空间，`plugins/` 目录名同理）。根 Session 的名字是 M36 引入的「名字的一段」，子 Session 的全名是多段；所有创建 Session 的入口（`open_session`、渠道的 `/session`、群 Session、`session_send`，以及 M38 的话题 Session）都只能经名字类型构造。约束在拥有事实的地方固定一次，创建 Session 的代码只消费已经成立的名字。取自外部文字的名字（群 Session 的会话 ID，M38 的话题标题）经同一个转写函数成为一段：去掉首尾空白，中间连续的空白与 `/` 换成一个 `-`，删去控制字符；结果仍不是合法的一段时给不出名字，由调用方换一个来源。

### 通信

- **向下显式发送，向上沿回复去向。**
  - 向下是任务：`session_send(to, text)` 发给一个子 Session，`to` 是它的短名；短名不存在且给了 `profile` 时，创建这个子 Session。父成为子最近一条交互式输入的来源，所以子的回复会回到父。
  - 向上是消息：子 Session 的回复与 `message_send` 送往它的回复去向，即最近一条交互式输入的来源，这是现有规则（[projection.rs](../../crates/enco-host/src/channel/projection.rs)）。被委派的子 Session 的回复去向就是父。子 Session 的 `message_send` 一经结算就投给父，与发给主人时一样即时；子 Session 中途发现重要信息时，父在它的下一个边界就能看到。
  - 向上不用 `session_send`：父恰好是回复去向时，那会是同一件事的第二条路。按回复去向发，默认行为在各场景都对：门面模式下幕后的 `message_send` 到达门面，不会绕过它打扰主人；主人接管子 Session 之后，它自然发给主人。
  - 兄弟之间与跨树没有通道。自动的流动只向上，到主人为止；循环必须有人显式向下发送。

- **父 Session 是子 Session 的壳。** 子 Session 交给回复去向的内容（下称交付内容）与渠道投影求出的相同：以回复结束的 Round 的回复、`message_send` 的内容、没有完成的 Run 的结局（因叫停结束的除外，见「取消、叫停与归档」）。回复去向是父时，每一项成为父 Inbox 中的一条 Event，与产生它的 Log 条目在同一次提交中写入。这是内部归属者已有的规则，Scheduler 与注册表都这样投递（Session 专题「外部输入只有一个入口，同一种操作只有一份语义」）；所以恰好一次由提交保证，没有 `unknown`。求出交付内容的函数只有一个，渠道投影与向父的投递都调用它。Event 把子 Session 说的话（`SessionMessage`）与它的 Run 怎样结束的事实（`ChildRunEnded`）分成两种，由 composer 叙述。父收到的交付内容称为回报；其中了结父的等待的那些，即回复与没有完成的 Run 的结局，称为回音（M35），见「子任务状态」。
  - 恰好一次靠的是 Event 连同它的 ID 与源条目在同一个事务里落库，Scheduler 现在就这样随定时的状态记下它投递的 Event。P4 中父与子在不同节点时，同一个事务改为写进本节点的 outbox，重发用库里记下的 ID，接收方照常去重（多节点专题「少数派一侧只继续自己持有的东西」）。所以不需要从 Log 位置派生 Event ID，单机的形态到多节点也不推翻。
  - `SessionMessage` 沿用 `message_send` 已经记下的 `Outgoing`（文字与可选文件），同一种内容只有一个类型。它的规范消息只是文字；文件与图片一样，由内核在构造 composer 的输入时补上本地路径，由 composer 叙述（Session 专题「事实进 Log，叙述进计划」）。
  - 投给别的 Session 只有一个机制：Session 的一次提交可以带上投给其他 Session 的 Event，Store 在同一个事务里经 Inbox 唯一的写入函数写入，并检查前置条件（目标没有归档，本 Session 没有待处理的叫停）。向上的投递与向下的 `session_send` 都经它，P4 的 outbox 是它跨节点的形态，不为两个方向各设一条路。每次提交，actor 用交付内容的函数求出要投给父的 Event，随这次提交一起写入。

- **回报怎样呈现归 composer，重心是验收。**
  - 分工按事实的归属。交给父什么，由 core 中那一个求出交付内容的函数决定。内核把它记成 Event，规范消息只是子 Session 的原话，不加前缀，Log 里记的就是它说的话（「模型可见 ⟺ 已记录」：内核只负责校验、绑定和记录，不排版）。父的模型看到什么样子，由 composer 对这条输入的叙述决定，与它叙述提醒和注册表通知是同一条路（Session 专题「默认说话，没有输入在等待回音时才可以沉默」：每条输入的叙述只讲它自己要不要回答）。放在 composer，也让 Agent 能自己调整措辞并回退，不必切换宿主。
  - 父收到回报时要做的事，依次是：知道是哪个子 Session 交来的；把它当作子 Session 的说法而不是核对过的事实，依赖或转告之前先核对要紧的部分，子 Session 在同一台机器上工作，它写的文件、跑的测试父都看得到；决定下一步：接受，把修改意见发回同一个子 Session（它保留着上下文），交给别的子 Session，或者自己做；只把需要知道的结论用自己的话告诉它回复的一方，没有就 `reply_skip`。
  - 按归属分三处写，与 M35 中打扰标准的三层同理：
    - 每条输入的叙述。来自子的消息：来自哪个子 Session，它是待核对的说法，修改与补充就再发给它，最后是不要求回答的那一句。没有完成的 Run 的结局：它怎样结束，做过的工作还在它的历史与工作区中，可以继续、改派或自己做，最后同样是那一句。子 Session 收到的父的任务：来自父，回复会回到父；它是交互式输入，没有那一句。父是否还在等待子 Session 的回音，由子任务状态给出，叙述里不写。
    - 出厂 composer 的系统提示。能力里有 `session_send` 时加一节「委派」，讲收到回报之后怎样核对、追问与转告；并行派出几个会改文件的子 Session 时，先各给一个目录（例如 git worktree），创建时传给它们（M36「工作目录（pwd）是带节点的默认目录，不是边界」）。任务怎样写由 `session_send` 的说明要求（见「新 Session 从空的 Log 开始」），验收就对照其中期望的结果与验证方式。子 Session 的系统提示对应写怎样汇报：做了什么、怎样验证的、哪里还不确定、结果在哪里，让父可以核对（项目哲学「结果可以核对」）。
    - 主人自己的验收标准，例如代码任务必须跑过测试，写在角色说明或 `AGENTS.md` 中。
  - 叙述的草案（面向模型的文字用英文）：

    ```text
    The next message is from `research`, a child Session you delegated to. It is its account
    of the work, not checked fact: verify what matters before you rely on it or pass it on.
    To correct or extend the work, send `research` another message; it keeps its context.
    It does not ask for a reply; if there is nothing worth saying about it, you may end your
    turn with reply_skip.
    ```

    ```text
    `research` stopped before finishing: it failed (provider: timeout). What it did stays in
    its own history and in the workspace. Send it another message to continue, give the work
    to another child, or do it yourself. It does not ask for a reply; if there is nothing worth
    saying about it, you may end your turn with reply_skip.
    ```

- **委派恰好一次由提交保证，检查在提交时按顺序做。** `session_send` 的效果与 `message_send` 同类：它把要写的内容（新的子 Session 及它的第一条输入，或已有子 Session 的一条输入）作为结果交出，父的 actor 把它与 `ToolCallSettled` 在同一个事务中提交，所以 effect 是 `ReadOnly`。提交之前崩溃，等于什么都没发生，恢复把这次调用记为失败，模型可以重试；提交之后，子 Session 与它的输入都在。
  - 它是 M35 的内置调用枚举（`BuiltinCall`，工具进入快照时记下）的第二个成员：它交出的写入要随结算一起提交，只有 actor 做得到。`session_halt` 与 `session_archive` 和 `schedule_cancel` 一样调用归属者的方法，是普通的工具。
  - 结算记下这次调用交给了谁：目标子 Session、是否新建、投进它 Inbox 的 Event ID，与 `message_send` 记下 `Outgoing` 是同一个道理（事实进 Log）。`enco log` 因此看得到父派出了什么，[M38](M38.md) 的连接也从这里得知父有了新的子 Session。
  - 同一批中连续的 `ReadOnly` 调用并发执行，全部返回后才按调用顺序结算（[dispatch.rs](../../crates/enco-kernel/src/dispatch.rs)）。所以 `session_send` 执行时只解析参数、校验短名、检查新工作目录存在于本机；子 Session 是否已经存在、profile 与工作目录是否一致、本 Session 是否有待处理的叫停，都在提交的事务中检查。一条回复里先创建 `research` 再给它发第二条，第二条在提交时看得到第一条。这就是归属者带着前置条件提交的规则。
  - 创建 Session 要检查 profile 存在且之后不能被删，所以创建子 Session 的提交与渠道创建群 Session 一样经过注册表这一个提交者（`accept_creating` 的路径）。
  - 提交时的检查不成立是这次调用的结果，不是前提被破坏：事务什么也不写，返回原因，actor 把这次调用结算为失败，原因照录，然后照常运行。这时调用已经分派，码是 `tool.failed`；M35 的 `tool.refused` 只给分派之前就能判断、从未到达工具的拒绝。Store 只检查，不改写条目，actor 内存中的 Log 与库保持一致。
  - 名字就是地址，创建参数只在创建时生效：给已有的子 Session 发消息时带上与它不同的 `profile` 或工作目录，调用失败并说明它现在的值。

- **委托人由谱系决定，主人也可以直接和子 Session 对话。** 根 Session 的交互式输入来自主人的界面，子 Session 的来自父；主人把聊天切到子 Session 时，主人也是它的交互式输入来源。
  - 来自 Session 的输入方向相反，含义也相反：来自父的消息是交互式输入；来自子的输入与提醒、注册表通知同类，不改变回复去向，也不要求回答。否则根 Session 收到子的回报之后，会把给主人的回复发给子。叫停是命令，无论主人还是父发起都不是交互式的，不移动回复去向；否则主人叫停一个子 Session 之后，它之后的回复会改送给主人，父还会看到「回复去向是主人」。
  - 方向写在来源上。方向在生产时就已确定：`session_send` 一定向下，投递一定向上，父关系又在创建时固定。所以 `EventSource` 增加 `Parent` 与 `Child`（子的身份与全名）两个变体，而不是一个泛指 Session 的来源、再让判断函数以本 Session 的父为参数。判断因此只看 Event 自己（来源与种类），回复去向的函数与它的各个使用者都不必去查谁是父（总纲「在源头声明，不在下游防御」）。
  - 交互式与回复去向出自同一个判断。交互式输入就是把回复去向移到自己来源的输入（M35），所以 core 只有一个函数，给出一条输入的回复去处：CLI、某个连接的某个会话或者父 Session；不等回复的输入（提醒、注册表通知、来自子的输入与叫停）没有。它按来源与种类穷尽匹配，不用通配，新增来源时编译器要求先决定它；是否交互式就是它有没有值。Session 的回复去向是最近一条有回复去处的输入的那一个，还没有这样的输入时就没有；它不依赖连接。现在的 `route` 只回答「是不是本连接的会话」，CLI、别的连接与没有都得到同一个结果，委派之后不够用。宿主的路由、内核向父的投递与子任务状态中的「回复去向是主人」都经这一个函数，M38 的显示位置也经它。
  - composer 不再自己判断哪些来源是交互式的。M35 为了不升 WIT，让 composer 按 `event-source` 的文档自己匹配来源，规则于是在 core 的函数、WIT 的文档与 composer 中各有一份，`Parent` 与 `Child` 加入之后三处都要改对。本阶段本来就升 WIT，所以 compose-input 中每条输入带上内核的判断 `interactive`，由上面那个函数求出，composer 按它叙述；`event-source` 的文档不再列出哪些来源是交互式的。
  - 回复去向沿用现有规则，谁最后说话就回给谁：主人在子 Session 里说话是显式接管，回复留给主人，不送给父；父下次发来消息，去向回到父。父的任务被主人接手时，父不会被唤醒，它在子任务状态里看到「回复去向是主人」，由此知道主人接手了；limcode-test 也是这样。
  - 主人的消息是交互式输入，子 Session 必须回答。子 Session 的权限仍由谱系决定，主人亲自来说也不放宽。
  - 连接只跟随它投递过输入的 Session：主人在会话里给子 Session 发了消息，连接就跟随它，回复与进度卡自然出现在这个会话里，不需要新机制。
  - 子 Session 只由它的父创建：`/session` 与 `enco chat --session` 可以切到已有的子 Session，指向不存在的子 Session 时拒绝。

### 权限与限额

- **权限只能沿委派收窄。** 一个 Session 的有效权限是它自己 profile 的权限与父的有效权限之交，每个 Round 开始时从谱系与活跃配置求出（总纲「状态是事实的函数」）。祖先的 profile 解析不了时，这一轮失败，不按缺省放宽。
  - 工具：`profile.tools` 是权限上限，取交集。模型看见什么由 composer 的披露决定，那是关注点，不是权限。所以门面的 profile 可以给全部权限，只由它的 composer 披露 `session_send`，幕后的子 Session 照样有 shell；群的 profile 本身收窄，它的子 Session 不会超过它。
  - 主人的上下文：`owner_context` 取与。
  - 救生集的要求不超过权限：要求披露的救生工具，是救生集与有效工具之交。否则群 Session 选一个要求救生集的 profile 委派时，子 Session 的工具里没有救生工具，要求却还在，每个 Round 的计划都过不了校验；这个失败会按 composer 违反契约记到 composer 代际的健康上，内核自己的不一致会让一份好的 composer 被回退。安全模式下的工具同样是救生集与有效工具之交，两处一致。
  - 深度：根的深度为 0；深度达到上限时，`session_send`、`session_halt` 与 `session_archive` 不出现在这个 Session 的能力里，构造的调用不在本 Round 的快照中，分派以 `tool.unavailable` 拒绝。深度对一个 Session 是固定的，不随输入变化，所以不影响前缀缓存（上下文专题「能力随权限变化，不随输入变化」）。
  - 安全模式只在有效权限之上再收窄。工作目录不是权限，不参与收窄。
  - 子 Session 是否带开发工具，由主人在它的 profile 中决定。几个 Session 同时修改 home 并登记，由注册表这一个提交者处理：前提变了的那次登记被拒绝并说明原因（代际专题「校验在提交者之外，提交时核对前提」），不需要新机制；需要并行修改意图时，按路线图「并行修改意图」各自在工作副本中修改。

- **限额只有两个：深度与同时运行的子 Session 数。** `[run]` 中 `max_depth` 默认 1，即根可以委派，子不能再委派；limcode-test 与 deepseek-harness 的默认值也是 1。`max_concurrent_children` 默认 4，按节点计，见下一条。不设跳数上限：自动的流动只向上，父↔子的循环要模型每次显式发送；默认说话让它默认可见；limcode-test 也把父↔子的循环交给模型。观察到问题再加，届时给 Event 补一个带 serde 默认值的字段即可。

- **名额是节点的运行时资源，由内核这一个归属者持有，不入库。** 被限制的是本节点同时在执行的子 Session 的 Run。「某个 Session 正在一个 Run 中」归它的 actor，在 Log 中的痕迹是没有结束的 Run；重启时每个 actor 先恢复、把没结束的 Run 记为中断，之后才可能开始新的 Run，所以这个数在每次启动时天然是零。存一份计数就是第二个来源，崩溃时会与 Log 分歧。Inbox 中有待处理输入的 Session 数也不是它：那是需求而不是占用，运行中的 Session 在 Round 开始时已经取空了 Inbox，叫停与回溯也在 Inbox 里，却不需要名额。
  - 归属者：内核持有运行中的子 Session 与按到达排队的等待者，是一把计数锁。上限在每次准入时从当前视图读取，所以登记新配置立即对之后的准入生效；已经在执行的 Run 不被抢占，与执行中的工具调用可以执行完是同一条规则。容量固定的 `tokio::sync::Semaphore` 要在每次配置发布时增减许可，调低时还要记下尚未收回的许可，所以用这个小归属者，不用它。
  - 取得与归还：actor 在两个 Run 之间先处理叫停与回溯，再为下一个 Run 取得名额，然后才提交 `RunStarted`；名额是随 Run 的守卫，`RunEnded` 提交之后归还，任何退出路径都会归还。粒度是 Run，不是 Round：Round 的大部分时间在等模型，在中途让出换不来什么，只会让 Run 停在半路排队。
  - 等待：同时等名额、唤醒与关闭，被唤醒就回到循环开头重读 Inbox。叫停、回溯与归档都在取名额之前那一支被消费，所以不需要「打断等待」的专门机制；放弃等待时自动出队。
  - 谁需要：有父的 Session。根从不等待：名额限的是委派带来的扇出，根的数量由主人自己的动作决定。被主人显式接管的子 Session 同样排队，觉得不顺手时再改为「本 Run 起始的输入里有主人在等的交互式输入就免排」。
  - 不会死锁：持有名额的一方从不等待另一个名额，因为委派是转移，父的 `session_send` 在接纳时返回，父的 Run 结束就归还名额，与子何时开始无关。阻塞式委派会让持有名额的父等一个需要名额的子，只能按层分池；所以以后调大 `max_depth` 也安全。
  - 状态：`Kernel::status` 从这个归属者读出运行中、等待名额（排第几）或空闲；这是实时状态，不进 `ComposeInput`。

### 取消、叫停与归档

- **取消一个 Run 与叫停一棵子树是两件事。**
  - 取消照旧：向一个 Session 的当前 Run 发出信号，等待静止。子 Session 不受影响，因为它的作用域是父 Session，不是父的这个 Run。主人在 Telegram 里 `/cancel`，停的是眼前这次答错的回复，后台的研究照常进行。
  - 叫停（halt）是命令：在一个事务中按谱系求出子树，把一条叫停投进其中每个 Session 的 Inbox，再向它们的当前 Run 发出信号，等待整棵子树静止。子树的根收到的叫停，来源是发起者（主人的界面，或者它的父）；其余 Session 收到的来源都是 `Parent`：叫停沿树一级级传下来，与 Erlang 的 link 相同，叫停的内容写明子树的根与发起者。一个事务写下整棵子树只在单库时成立，P4 中跨节点的子树改为逐级经 outbox 传递，这一点记进多节点专题。每个 Session 在两个 Run 之间连同此前送达的输入一起消费叫停，不开始新的 Run，此前的输入不会被回答。因叫停而停下的 Run 以 `Halted` 结束，与 `/cancel` 的 `Cancelled` 分开：Run 先提交结局、之后才消费叫停，只有结局本身能让交付内容的函数从 Log 认出它，渠道因此不会再发一句「Run cancelled.」。这与回溯的生效方式相同：两者都是在 Run 之间生效、取代此前输入的命令，共用 actor 中同一条路径；回溯指向一条输入时随后开始一个 Run 回答它，叫停什么也不开始。
  - 叫停不叫醒任何人：被叫停的 Session 不向任何 Session 交出结局。叫停是主人或父的决定，发起的一方已经知道；要通知别人，正是叫停想要停下的那种工作。父在下一个 Round 的子任务状态里看到子 Session 被谁叫停、不再等待它的回音，所以主人直接叫停子 Session 之后，父不会把同一件事再派出去。
  - 叫停之后不再投进任何 Inbox：被叫停的 Session 可能还在完成手头的 Round，它在消费叫停之前产生的回复、消息与委派，都不能再唤醒或派出别的 Session，否则父的 Inbox 里会在叫停之后多出一条输入，又开始一个 Run。这条靠时序与提交时的检查兑现：被叫停的 Run 在边界停下并提交结局，actor 回到循环开头才消费叫停，在这之前叫停一直待处理；带投递的提交在事务中看到本 Session 有待处理的叫停，就按「提交时的检查不成立」处理：投递不写入，回复与结局照常记入自己的 Log，产生投递的工具调用（`session_send`、给父的 `message_send`）结算为失败（「已被叫停」）。投给主人的渠道不受影响：主人自己发起叫停，最后一条在途的回复送到也无妨。
  - 等名额的 Session 也能被叫停：等待会被唤醒打断，消费叫停不需要名额，否则名额满时叫停一个等待中的子 Session 会一直等下去。整棵子树静止，指其中每个 Session 既没有进行中的 Run，Inbox 中也没有待处理的叫停。
  - 叫停不改变对话：回溯让对话回到目标位置，叫停只是一条命令，它与被它取代的输入都留在对话中，由 composer 叙述这些输入没有被回答。两者都不是输入；回溯不能指向叫停，与不能指向另一条回溯同理。
  - 入口：主人对任何 Session 可用（`enco halt` 与渠道的 `/halt`）；父 Session 的模型对自己的子 Session 用 `session_halt`。它与 `schedule_cancel` 一样调用归属者的方法，主人的命令与 Agent 的工具是同一份语义；重复叫停没有额外效果，所以 effect 是 `Idempotent`。

- **不需要的 Session 归档，不删除。** Log 永不删除（Session 专题「Log 只记事实的骨架，条目永不删除」），清理内容属于路线图中 blob 与计划记录的保留策略。
  - 先记下归档，再等静止：在一个事务中按谱系求出子树，把叫停投进其中每个 Session 的 Inbox，再记下归档时间；随后与叫停一样发出信号、等待子树静止，再停掉它们的 actor。顺序反过来就有一个窗口：子 Session 消费完叫停就空闲了，在静止与记下归档之间到达的提醒或消息会开始新的 Run，归档停掉的就是一个正在运行的 actor。
  - 从那次提交起不再接收输入。约束只在一处：各归属者都经 Inbox 唯一的写入函数（[accept.rs](../../crates/enco-host/src/store/accept.rs) 的 `events_in`）把输入连同自己的状态转移一起提交，它在事务中看到 Session 已归档，就不写入，给出「已归档」，由归属者按自己的语义处理：渠道与 CLI 把错误交回发送方；注册表的回退照常提交，只是不发通知；Scheduler 见下一条。
  - 定时提醒随之取消，只由 Scheduler 改。归档提交之后，内核请 Scheduler 取消子树中的定时提醒，它与触发按顺序执行，`enco schedules` 随即不再列出；在归档提交与取消之间到期的，触发的事务看到「已归档」，把它改为已取消，不投递。`schedule_create` 同样拒绝已归档的 Session。归档不直接改库：Scheduler 内存中的日程还留着这条提醒，到期时提交落空，整个 Scheduler 会停下。
  - 不再占用 profile：登记配置时只看未归档的 Session 用不用要删的 profile。否则用过一次的 profile 永远删不掉，报错里的名字也可能已经属于另一个 Session。以后加恢复时，由恢复检查 profile 还在。
  - 不再有 actor：已归档的 Session 不接收输入，没有工作可做，静止之后停掉，启动时也不为它们开。它们的订阅在最后一条记录之后正常结束，跟随过它们的连接据此停止跟随，不当作错误（现在订阅关闭会让连接报错）。actor 把完整 Log 放在内存里，是所有 Session 共有的问题，群与话题的 Session 同样越积越多，应由 actor 在空闲时释放 Log 解决，不靠归档；本阶段不做，出现问题时再做。
  - 不再出现在父的子任务状态、`/session` 与 `enco sessions` 的列表中。
  - 名字被释放：名字的唯一性只在未归档的 Session 之间成立，以后用同一个短名 `session_send` 创建的是一个新身份的子 Session。这与插件删除后释放名字是同一条规则（插件专题「名字给人和模型，身份给记录」）。
  - Log 保留：`enco log` 与 `enco inspect` 按 ID 照常可用，`enco sessions --archived` 列出它们。
  - 名字只解析到未归档的 Session：CLI 与渠道中凡是按名字找 Session 的地方（`enco log --session`、`/session`、`/halt <名字>` 等）都只找未归档的，因为同一个全名可能先后属于几个身份。名字只对上已归档的 Session 时，报错列出它们的 ID，不替人猜是哪一个。
  - 渠道里指向已归档 Session 的路由按没有路由处理，并告诉主人。这由连接在路由时从事实求出，归档不去改连接的状态，连接的状态仍只有连接这一个写者。
  - 入口：父 Session 的模型对自己的子 Session 用 `session_archive`；主人对任何 Session 用 `enco archive <名字>` 与 `/archive <名字>`。同一个归属者方法，effect 为 `Idempotent`。本阶段归档是单向的，需要恢复时再加。
  - 渠道里的 `/archive` 必须带名字。Telegram 点一下菜单里的命令就直接发出，不带名字就归档本会话的 Session 的话，在主会话里误点一下，`main` 连同整棵树就单向归档了。不带名字时它只列出可以归档的 Session，与不带参数的 `/session` 列出 Session 是同一个约定，也与 CLI 一致。`/halt` 保留不带名字的用法：叫停之后再发消息就能继续，「全部停下」也正该点一下就生效。

### 子任务状态

- **子任务状态只推送在关键时刻才变的事实，实时状态按需查看。** 这对应 limcode-test 的状态卡与名册。
  - 成本：composer 的输入每个 Round 都带着这些事实，但进不进上下文由 composer 决定。出厂 composer 把子任务状态与可选的 profile 当作来源，像召回的记忆一样记下哈希：哈希没变就不再写，变了就在本次新增段的开头写一份。所以进上下文的成本是变化次数乘以内容大小；前缀保持不变，同一个 Run 的后续 Round 与压缩之后也都不会漏掉最新的状态。
  - 推送的事实：每个子 Session 的短名、profile、父是否在等待它的回音、让它停下的叫停、回复去向是不是主人。它们几乎都和父本来就会看到的事件同时变化：它自己发出任务、子的回音到达、叫停、主人接管，所以多写的很少。能委派时再推送可选的 profile：名字、`description` 与它的回复模型（名字、模型、能看什么、预算）；它只随配置变化，一个系列里基本只写一次。每项事实按归属者自己的类型给出，模型与能看什么取自配置，不靠主人在 `description` 里再写一遍（上下文专题「正确性在内核，策略在 composer，线上格式在 Provider」）。
  - 不推送实时状态：运行中、等待名额、空闲每个 Run 都会来回变，最近一次的结局也会随子的回复或 `ChildRunEnded` 作为输入到达。需要时用 `self_status`；完整对话用 `enco log --session <全名>`。都不需要新工具。
  - `self_status` 与 `enco status` 仍是同一份文档（[status.rs](../../crates/enco-host/src/status.rs)），按树列出本节点未归档的 Session 与实时状态，模型从全名认出自己在哪。不按调用者另列一节子树：那要把调用者传进一份本来与调用者无关的文档，`main` 调用时又与整棵树重复。
  - 不改成完全拉取：limcode-test 的经验是状态卡让模型不会忘了自己的子 Session。最容易忘的有两个时刻：压缩之后，以及并行派出几个子 Session、收到其中一个的回复、要判断其他的是否都完成了。只在变化时推送，用很低的成本保住这一点。
  - 事实来源：谱系与配置之外，推送的事实都从子 Session 已提交的 Log 与 Inbox 求出，不读 actor 的内存，所以同一份库任何时候求出的结果都一样。父刚发出的消息与叫停，在被消费之前只在子的 Inbox 中。

- **父是否在等待它的回音**：用 M35 的 `unanswered_input`，作用于子 Session 的 Log 接上它 Inbox 中尚未消费的输入；求出的输入来源是 `Parent`，父就在等待它的回音。一个事实只有一个函数：M35 用它决定 `reply_skip` 能否成功，这里用它决定父看到什么。回音在 M35 中已经定义：以回复结束的 Round，或者没有完成的 Run 的结局；回复去向是父时，两者都投给父，后者就是 `ChildRunEnded`。子 Session 中途的 `message_send` 不是回音。本阶段给这个函数加一条：消费过的叫停取代此前的输入，等待随之作废。
  - 由此得出的三种情况各有说明：父刚发出、子还没消费的消息接在 Log 之后，算作在等待；主人接管之后，最近一条等待回音的输入来自主人，父不再等待，由「回复去向是主人」说明；叫停使等待作废，由「让它停下的叫停」说明。
  - 只看回音，不看子 Session 是否还在运行。回复了父之后，子 Session 可能还要处理自己的提醒或主人的消息：回复之后 Inbox 不空，Run 就继续（[run.rs](../../crates/enco-kernel/src/run.rs)），这与父无关。如果按「取走它的 Run 是否结束」判断，父收到回复时会同时看到「还在等待」；而以 `Completed` 结束的 `RunEnded` 不投递任何东西，状态变了也唤不醒父，委派看起来就卡住了。回复所在的 `RoundEnded` 与之后的 `RunEnded` 本来是两次提交，没有别的输入时两者之间也有一个空档。
  - 它变化的时刻与唤醒父的事件一致：由假变真发生在父自己 `session_send` 的提交中；由真变假的那次提交一定同时投给父一条回音。例外只有两个，都按设计不唤醒父：叫停由「让它停下的叫停」说明，主人接管由「回复去向是主人」说明。回音在父的 Round 取走输入之后才到时，状态先变，回音在下一个 Round 被消费；父的 Inbox 不空，Run 会继续，不会漏掉。
  - 父的任务是交互式输入，子 Session 回答它时不能 `reply_skip`，所以父的输入之后不会只跟着不投递的 Round。

### 名字、契约与不做的事

- **名字与默认值。**
  - 工具：`session_send`、`session_halt`、`session_archive`，与 `message_send`、`schedule_cancel`、`reply_skip` 同一种写法。
  - 命令：`enco halt`、`/halt`、`enco archive`、`/archive`、`enco sessions --archived`。「叫停（halt）」避开已有的「停止」（Session 与渠道因故障停下）、「中断」（`RunEnd::Interrupted`）与「取消」（停一个 Run）。
  - 限额：`[run]` 中的 `max_depth = 1` 与 `max_concurrent_children = 4`，与已有的 `max_rounds` 同一种写法。limcode-test 同时运行 8 个，Raft 每台机器 5 个；个人助理常在 VPS 或笔记本上编译与测试，取 4。

- **面向模型的文字沿用上下文专题「面向模型的文字只用模型看得到的东西来说」。**工具说明讲机制，对任何 composer 都成立，不提子任务状态怎样呈现；判断标准写在出厂 composer 的系统提示里，叙述只提一句；拒绝与失败的原因说明下一步，例如给已有的子 Session 带上不同的 `profile` 时，写明它现在用的是哪个、不带 `profile` 就能发给它；note 只指 composer 写在消息前的说明。新出现的词是 child Session，系统提示的「委派」一节第一次用到时说明：你派出的另一段对话，有自己的历史，回复回到你这里。

- **契约与库各升一次，不留兼容分支。** WIT 升到 0.12.0，全部插件重建一次；库的版本升到 18，不自动迁移，与 M30 以来的做法相同，oracle-jp 由主人升级。

- **本阶段不做的事。**
  - **Brief 不作为委派的 Attempt 用途。** 委派时父模型本来就在写任务，它就是子 Session 的第一条 Event，两边都已记录；另起一次 Brief 请求是同一份内容的第二条路。Brief 留给 P4 的漫游。
  - **不设 `session_read`，也不用文件投影查看 Session。** 子 Session 交给父的内容已经带着它的话与结局，关键状态随变化推送，实时状态在 `self_status` 中，细节用 `enco log` 与 `enco inspect` 查看。实时状态做成文件会不停重写，读到的可能是旧的，还多一份表示；以后需要按文件浏览 Session 时，可以由 Observer 维护一个只读投影（Plan 9「文件投影只用于查看」）。
  - **继承父的历史（fork）**：需要时，子 Session 的第一条记录写明它的历史从父 Log 的某个位置之前开始，它的对话由父到那里为止的对话接上它自己的；Log 不可变，这条引用永远成立。子 Session 的有效权限没有主人的上下文而父有时必须拒绝，否则父对话中的私事会越过收窄。
  - **外部 Agent 运行时不是 Session。** Claude Code、Codex 这类外部执行者是能力，经调用使用，结局按 `ok / failed / unknown` 结算；它们没有 Enco 的 Log、Inbox 与 actor，不进委派树。长时间运行的外部任务需要「完成后成为一条 Event」的路径，那是另一件事，出现需求时单独设计。
  - **有界等待、跳数上限、兄弟与跨树的消息、自动建 worktree、恢复已归档的 Session、清理 Log 内容、委派时临时指定模型、空闲时释放 actor 的 Log**：都等真实需求出现，各自都能在本阶段的结构上加进来。

## 范围

- **core**：
  - Session 名字类型：根是一段，子 Session 的全名是用 `/` 连接的多段；全部创建入口只经它构造。把外部文字转写成一段的函数；群 Session 的名字由宿主把连接名与会话 ID 拼成 `<连接名>:<会话>` 之后经它转写。
  - `SessionRecord` 增加 `parent` 与归档时间。
  - `EventSource` 增加 `Parent` 与 `Child`（子的身份与全名）；`EventBody` 增加 `SessionMessage`（沿用 `Outgoing`）、`ChildRunEnded`（没有完成的 Run 的结局）与 `Halt`（子树的根与发起者）。三者的规范消息：`SessionMessage` 只是它的文字，另两种为空，由 composer 叙述。
  - `RunEnd` 增加 `Halted`：因叫停而停下的 Run 的结局；交付内容的函数据此排除它。
  - `ToolCallSettled` 记下调用交给了哪个 Session：目标、是否新建、投进它 Inbox 的 Event ID。
  - 一条输入的回复去处：按来源与种类穷尽匹配，取值是 CLI、某个连接的某个会话或者父 Session；不等回复的输入没有。M35 的逐条判断改为「有没有回复去处」。Session 的回复去向是最近一条有回复去处的输入的那一个；宿主的路由、内核向父的投递、子任务状态与 compose-input 中每条输入的 `interactive` 都经它。
  - 求出交付内容的函数从渠道投影移到这里，渠道与向父的投递共用；M35 的 `unanswered_input` 改用它定义的回音，并加上「消费过的叫停使等待作废」。
- **内核**：
  - 内置工具 `session_send`、`session_halt` 与 `session_archive`；`session_send` 加入 M35 由分派识别的内置调用枚举，另两个是普通工具。
  - `Commit` 可以带上投给其他 Session 的 Event：Store 在同一个事务里经 Inbox 唯一的写入函数写入，并检查目标没有归档、本 Session 没有待处理的叫停；检查不成立时事务不写入，返回原因。
  - `session_send` 执行时只解析参数、校验短名、检查新工作目录；其余检查与写入在结算的事务中按调用顺序进行；检查不成立时事务不写入，调用结算为失败并照录原因。创建子 Session 的提交经过注册表；提交之后启动子 Session 的 actor 并唤醒它。
  - 子 Session 的每次提交在回复去向是父时带上投给父的 Event，提交之后唤醒父；恢复写下的结局同样投递。
  - 每个 Round 开始时沿谱系求出有效权限（工具、`owner_context`、救生集的要求、深度）；祖先的 profile 解析不了时这一轮失败。
  - 名额的归属者：运行中的子 Session 与按到达排队的等待者，上限在准入时读当前视图；actor 处理完两个 Run 之间的命令之后取得，`RunEnded` 提交之后随守卫归还；等待时同时等唤醒与关闭，被唤醒就重读 Inbox。
  - 叫停：在一个事务中按谱系求出子树并接纳，子树的根收到的来源是发起者，其余是 `Parent`；发出信号，等待子树中每个 Session 既无进行中的 Run、也无待处理的叫停；Run 在边界看到待处理的叫停就停下，结局是 `Halted`；actor 在 Run 之间消费它连同此前的输入，与回溯共用这条路径；带投递的提交看到待处理的叫停时，投递不写入，产生投递的调用结算为失败。`Kernel::check_backtrack` 拒绝指向叫停。
  - 归档：在一个事务中求出子树，写入叫停并记下归档时间；发出信号，等待静止，停掉它们的 actor；再请 Scheduler 取消它们的定时提醒。启动时不为已归档的 Session 开 actor；名字的唯一性只在未归档的 Session 之间成立；登记配置时 profile 的占用只看未归档的 Session。
  - `Accepted` 增加「已归档」：Inbox 的写入函数在事务中看到 Session 已归档时给出它，不写入。接纳输入的入口把它作为错误交回；Scheduler 触发时据此把那条提醒改为已取消，`schedule_create` 拒绝已归档的 Session；注册表的回退照常提交，不发通知。
  - 按名字或 ID 查找 Session 由内核提供，CLI 与渠道都经它：名字只匹配未归档的 Session，ID 匹配全部，包括已归档的；名字只对上已归档的时，报错列出它们的 ID。`open_session` 遇到多段的名字只查找，不创建。
  - `ComposeInput` 增加子任务状态（推送的那几项事实）与可选的 profile，子任务状态由子 Session 已提交的 Log 与 Inbox 求出，「父是否在等待它的回音」用 M35 的 `unanswered_input`；`Kernel::status` 带上谱系、名额的归属者给出的运行与等待，以及归档的状态。
  - 限额读自 `[run]`：`max_depth`（默认 1）与 `max_concurrent_children`（默认 4）。
- **宿主**：
  - `message_send` 的说明改为「发给你当前回复的一方：主人，或委派你的 Session」，在子 Session 中按回复去向即时投递。
  - 渠道新增 `/halt` 与 `/archive`：`/halt` 可以带名字，不带时指本会话的 Session；`/archive` 必须带名字，不带时列出可以归档的 Session。`/session` 可以切到已有的子 Session，指向不存在的子 Session 时拒绝；渠道的路由不因来自子 Session 的输入而改变；路由指向已归档的 Session 时按没有路由处理，并告诉主人。
  - 连接跟随的 Session 归档之后，它的订阅正常结束，连接停止跟随，不当作错误。
  - `self_status` 与 `enco status` 的文档、`enco sessions` 按树显示本节点未归档的 Session：profile、工作目录、运行中、等待名额或空闲。
  - `[profile.*]` 增加 `description`。
- **CLI**：`enco halt [--session <name>]`、`enco archive <session>`、`enco sessions --archived`；`enco chat --session` 可以进入已有的子 Session；`enco log` 与 `enco inspect` 改用内核的查找，现在的 `existing_session` 只在未归档的列表里找，归档之后按 ID 就找不到了。
- **出厂 composer**：
  - 按每条输入的 `interactive` 决定是否加不要求回复的那一句，不再自己匹配来源。
  - 叙述父派来的任务、子的消息及其文件、子 Session 的结局、叫停与被它取代的输入；来自子的输入以验收为中心，末尾带不要求回答的那一句，见「回报怎样呈现归 composer」。
  - 能力里有 `session_send` 时，系统提示加一节「委派」：收到回报之后怎样核对、追问与转告；并行派出会改文件的子 Session 时各给一个目录。
  - 子 Session 的系统提示说明它为谁工作；回复与 `message_send` 送给最近和它说话的一方，即父，或者直接来找它的主人；回复写明做了什么、怎样验证的、哪里还不确定、结果在哪里；需要超出权限的能力时，在回复中说明，交给委派它的 Session。
  - 子任务状态与可选的 profile 作为来源，哈希变了才在本次新增段的开头写一份。
- **WIT 0.12.0**：见下文。`CONTRACT_VERSION`、SDK 与全部插件随之重建。
- **库**：版本 18，`sessions` 增加 `parent`（可空，引用 `sessions.id`）与归档时间；名字的唯一约束只覆盖未归档的 Session。叫停、新的 Event 与 `RunEnd::Halted` 都在 Inbox 与 Log 已有的 JSON 中，是追加的变体，旧记录照常读出。不自动迁移。
- **文档**：Usage 写明委派、叫停与归档、`/cancel` 与 `/halt` 的区别、子 Session 的名字与限额、直接和子 Session 对话。

## 设计

验收时提炼或改写：

- Session 专题：把「分身就是 Session」改写为「委派」一节，依次为：内核在树上只做三件事；委派是转移；向下显式、向上沿回复去向，父是子的壳；委派的检查在提交时按顺序做；委托人由谱系决定，主人也可以直接对话；权限只能沿委派收窄；不需要的 Session 归档，不删除，归档先记下再等静止，已归档的 Session 不接收输入，约束在 Inbox 唯一的写入处。「取消是发出信号，再等待静止」删去「取消沿监督树传播到子 Session」。新增「在 Run 之间生效、取代此前输入的命令」，回溯与叫停是它的两个实例，取消只针对 Run；M30 计划中「回溯移动的是对话的引用，Log 不改写」与「回溯在两个 Run 之间生效」至今没有提炼进设计文档，借这一条一并写入。叫停不是交互式的，不移动回复去向；因叫停停下的 Run 以 `Halted` 结束。新增「交互式与回复去向出自一个不依赖连接的函数」：它按来源与种类穷尽匹配，交互式就是有回复去处；M35 那一条中「同一个逐条判断也决定回复去向」随之改写，composer 从契约中读到内核的判断，不再自己匹配来源。新增「Event 的来源写明它与接收者的关系」：方向在生产时确定，判断只看 Event 自己。「默认说话，没有输入在等待回音时才可以沉默」（M35）补上：子任务状态中「父在等待它的回音」是同一个事实，叫停使等待作废。新增「投给别的 Session 只有一个机制」：提交带上 Event，向上、向下与跨节点的 outbox 都是它。新增「名额是节点的运行时资源」：由内核这一个归属者持有，不入库；委派是转移，所以持有名额的一方从不等待另一个名额。
- 渠道专题：命令不带参数时查看，或作用于本会话；不可逆的 `/archive` 必须带名字，因为菜单里点一下就会发出。
- 总纲：Erlang 透镜的一行改为监视与叫停；固定的词加入委派、叫停（Halt）、归档、子 Session 的全名。
- 上下文专题：新增或并入「profile 的工具是权限上限，披露是关注点」，以及救生集的要求不超过权限；新增「回报怎样呈现归 composer，重心是验收」，写明交付内容、记录与叙述的分工；子任务状态只推送关键时刻才变的事实，「父在等待它的回音」按回音而不是 Run 的结束判断，它变化的提交同时唤醒父。
- 多节点专题：「复制与上下文是两个轴」中「派出一个干净的子任务」改为由委派的第一条消息承担，Brief 只用于漫游；跨节点的 Session 间投递经 outbox，用随源条目记下的 Event ID 去重；一个事务写下整棵子树的叫停只在单库时成立，跨节点时逐级传递。
- 先定下的格式：WIT 0.12.0（见下文）；`EventSource` 的 `Parent` 与 `Child`、`EventBody` 的三个分支、`RunEnd::Halted` 与 `ToolCallSettled` 记下的投递；库版本 18。

## WIT 的变化（草案）

```wit
package enco:plugin@0.12.0;

    record session {
        // as in 0.11.0
        /// The Session that delegated to this one; absent for a Session the owner created. Inputs
        /// whose `event-source` is `parent` came from it.
        parent: option<session-source>,
    }

    /// Another Session, by identity and full name.
    record session-source {
        /// Its permanent ID.
        id: string,
        /// Its full name.
        name: string,
    }

    /// Who produced an input. (The paragraph M35 added on interactive sources moves to
    /// `event.interactive`.)
    variant event-source {
        // cli, channel, scheduler, registry as before
        /// The Session that delegated to this one, named in `session.parent`; a halt from further
        /// up the tree also arrives from here.
        parent,
        /// A Session this one delegated to.
        child(session-source),
    }

    record event {
        // id, received-at, source, body as before
        /// Whether its sender waits for a reply. The kernel decides it from the source and the
        /// kind, the same way it decides where replies go; while such an input awaits an answer,
        /// `reply_skip` fails.
        interactive: bool,
    }

    /// A recorded file, by reference rather than by its bytes.
    record file-ref {
        /// Its name, without the directory it came from.
        name: string,
        /// The size of the bytes.
        size: u64,
        /// The BLAKE3 digest of the bytes, in lowercase hex.
        content: string,
        /// The file that holds the bytes.
        path: string,
    }

    /// What another Session addressed to this one: a task from the parent, or a child's reply
    /// or message.
    record session-message {
        /// What it wrote; the canonical message carries only this.
        text: string,
        /// A file it sent.
        file: option<file-ref>,
    }

    /// A stop of a whole subtree.
    record halt {
        /// The Session at the top of the halted subtree, by full name.
        root: string,
        /// The Session that halted it, by full name; absent when the owner did.
        by: option<string>,
    }

    variant event-body {
        // user-message, reminder, generation-rolled-back, backtrack as before
        /// Words from another Session.
        session-message(session-message),
        /// A child's Run that ended without completing, and how; a halted child sends none.
        child-run-ended(run-end),
        /// This Session's work and that of its children were stopped; inputs that arrived
        /// before it were not answered. Unlike a backtrack, it leaves the conversation as it is,
        /// and it is not interactive: replies keep going where they went.
        halt(halt),
    }

    variant run-end {
        // completed, budget-exhausted, interrupted, cancelled, failed as before
        /// A halt of this Session or an ancestor stopped it.
        halted,
    }

    /// A child of this Session, by the facts that change only at moments its parent sees.
    ///
    /// Whether it is running right now is not here; `self_status` shows it.
    record child {
        /// Its name relative to this Session, as `session_send` takes it.
        name: string,
        /// The profile it uses.
        profile: string,
        /// Whether this Session awaits its answer: the latest of its inputs still awaiting an
        /// answer came from this Session. An answer is a reply that ends one of its Rounds, or the
        /// outcome of a Run that ended without completing; a halt ends the wait without one. While
        /// its replies go to this Session, each answer arrives here as input.
        awaiting: bool,
        /// The halt that stopped it, when it has received no input since.
        halted: option<halt>,
        /// Whether the owner spoke to it after this Session did, so its replies go to the owner.
        replies-to-owner: bool,
    }

    /// A reply model of a profile.
    record profile-endpoint {
        /// The endpoint, by its configured name.
        endpoint: string,
        /// The model it calls.
        model: string,
        /// What it accepts besides text.
        accepts: list<modality>,
        /// Its limits.
        budget: budget,
    }

    /// A profile a new child may use.
    record delegable-profile {
        /// Its name.
        name: string,
        /// What the owner wrote it is for.
        description: string,
        /// Its reply models, in configured order.
        reply: list<profile-endpoint>,
    }

    record compose-input {
        // as in 0.11.0
        /// This Session's children that are not archived, in creation order.
        children: list<child>,
        /// The profiles a new child may use; empty when this Session cannot delegate.
        profiles: list<delegable-profile>,
    }

    /// The commands the host understands.
    enum command-kind {
        // session, cancel, backtrack, everyone as before
        /// Halt the named Session and its descendants, or the conversation's Session when no name
        /// follows.
        halt,
        /// Archive the named Session and its descendants; with no name, list the Sessions that
        /// can be archived and archive nothing.
        archive,
    }
```

## 验收

- **委派与回报**：
  - 主人让主 Session 后台调研：它用 `session_send` 创建 `main/research` 并回答主人；研究进行中主人继续对话，主 Session 正常回答。
  - 研究完成后，主 Session 被唤醒，看到子 Session 的回复，告诉主人结果，或者调用 `reply_skip`；主 Session 之后的回复仍然发给主人。
  - 请求中这条回报的叙述写明它来自 `research`、是待核对的说法，并带不要求回答的那一句；`research` 收到的任务的叙述写明来自 `main`，没有那一句；能委派的 Session 的系统提示有「委派」一节。
  - 子 Session 中途用 `message_send` 送出一条发现：主 Session 在它的下一个边界看到。
  - 子 Session 回复后，父再给它发消息，它带着自己的历史回答。
  - 一条回复里先用 `session_send` 创建 `research`、再给它发第二条：两条都成功，按顺序进入它的 Inbox。
  - `enco log --session main` 中，`session_send` 的结算写明交给了 `research`、是否新建与 Event ID；`research` 收到的输入来源是 `Parent`，`main` 收到的回报来源是 `Child`。
- **主人直接对话**：
  - 主人在 Telegram 中 `/session main/research` 后发消息：子 Session 回答主人，回复与进度卡在这个会话里；`main` 不被唤醒，它下一个 Round 的子任务状态显示回复去向是主人。
  - 之后 `main` 再用 `session_send` 发消息：子 Session 的回复回到 `main`。
  - 子 Session 的一个 Run 中主人发来消息：从消费它的 Round 起，`reply_skip` 的调用失败，子 Session 回答主人。
  - `/session main/unknown` 被拒绝，并说明子 Session 只能由它的父创建；`enco chat --session main/research` 可以进入。
- **失败与恢复**：
  - 子 Session 的 Run 失败，或被进程中断：父收到 `ChildRunEnded`。
  - 在 `session_send` 的提交之前与之后各杀一次进程：之前的什么都没留下，调用记为失败，重试只创建一个子 Session；之后的子 Session 与它的第一条输入恰好各一份。
- **叫停**：
  - 主人叫停 `main`：整棵子树静止，未确认的副作用记为 `unknown`；叫停之前送达、尚未处理的输入不被回答；没有 Session 因此被唤醒，主人只收到命令的回执，渠道里没有「Run cancelled.」；被停下的 Run 在 Log 中以 `Halted` 结束；`main` 在叫停生效之前提交的 `session_send` 结算为「已被叫停」，没有派出任何东西。
  - 主人在 Telegram 中直接 `/halt main/research`：`main` 不被唤醒；它的下一个 Round 中，子任务状态显示 `research` 被主人叫停，父不再等待它的回音，回复去向仍是 `main`。
  - 父调用 `session_halt`：工具在子树静止之后返回；父不会被这个子 Session 唤醒，子 Session 在叫停生效之前完成的回复也不投给父。
  - 名额已满时叫停一个等待名额的子 Session：它立即消费叫停，不等名额。
  - 叫停之后进程被杀：重启后叫停照常生效，且只生效一次。
  - `/cancel` 只停 `main` 的当前 Run，`main/research` 继续运行，之后照常回报。
- **归档**：
  - 父调用 `session_archive` 归档 `research`：它的子树先被叫停；它不再出现在父的子任务状态与 `/session` 列表中，不再有 actor，重启后也没有；`enco log` 按 ID 仍能读出它的 Log，`enco sessions --archived` 列出它。
  - 之后再用短名 `research` 调用 `session_send` 并给出 profile：创建一个新身份的子 Session。
  - 某个会话的路由指向已归档的 Session：下一条消息按没有路由处理，主人得到说明。
  - 归档并重建 `research` 之后，`enco log --session main/research` 读出新的那个；只剩已归档的同名 Session 时，命令报错并列出它们的 ID，按 ID 可以读出。
  - 主人曾在 Telegram 中直接和 `research` 对话，之后归档它：连接停止跟随它，渠道照常运行，`enco status` 中没有渠道错误。
  - 归档时主人恰好给 `research` 发消息：消息或者在归档之前送达，随叫停一起被消费而不回答，或者被拒绝并得到说明；归档之后它不会开始新的 Run。按 ID 向已归档的 Session 发消息同样被拒绝。
  - `research` 有一条每天的提醒：归档之后 `enco schedules` 不再列出它，到点也不唤醒任何 Session，Scheduler 照常运行。
  - 从 `config.toml` 删去只有已归档 Session 用过的 profile：登记成功。
  - 在 Telegram 中不带名字发 `/archive`：只列出可以归档的 Session，什么也没有归档。
- **权限与限额**：
  - 群的 profile 即使列出了 `session_send`，它创建的子 Session 也不会超出群的工具与 `owner_context`。
  - 群 Session 委派给一个要求救生集的 profile：子 Session 照常运行，不要求它拿不到的救生工具，composer 的健康不受影响。
  - 门面的 composer 只披露 `session_send`，幕后的子 Session 照样能用 shell。
  - 深度达到上限时 `session_send` 不在能力里，构造的调用被拒绝。
  - 超过同时运行数时，多出的子 Session 等待名额，`enco status` 显示「等待名额」与排位；主人的根 Session 不受影响。名额空出时，等待者按到达的顺序开始。
  - 调低 `max_concurrent_children` 并登记：正在执行的 Run 不受影响，之后的准入按新上限。
  - `max_depth = 2`、名额已满时子 Session 再委派：孙 Session 排队等待，子 Session 的 Run 照常结束并归还名额，没有死锁。
  - 名额满时重启：恢复之后没有 Session 持有名额，等待者照常开始。
- **寻址与名字**：
  - `to` 只能是自己的子 Session，没有办法指向兄弟或别的树。
  - 给已有的子 Session 带上不同的 `profile` 或工作目录时失败，并说明它现在的值；创建时给的工作目录不存在时失败。
  - 根 Session 的名字含 `/` 或空白时被拒绝。
  - 群 Session 的名字是 `<连接名>:<会话>`，会话 ID 中的 `/` 与空白转写成 `-`。
- **状态**：
  - 子任务状态出现在请求中：父刚发出、子还没消费的消息显示为父在等待它的回音；同一个 Run 的下一个 Round 与压缩之后都能看到最新的状态；子 Session 只是在运行与空闲之间切换时，不写新的状态，前缀不变。
  - 子 Session 回复父之后，因自己的提醒继续运行：父最晚在收到回复的那个 Round 里看到自己不再等待它的回音。
  - 子 Session 的 Run 失败：父最晚在收到 `ChildRunEnded` 的那个 Round 里看到自己不再等待它的回音。
  - 子 Session 中途用 `message_send` 送来消息：父仍在等待它的回音。
  - `self_status` 与 `enco status` 输出同一份文档，按树列出未归档的 Session 与实时状态。
  - 可选的 profile 列出 `description` 与它的回复模型。
- 按 0.11 构建的插件加载时被拒绝并提示重建；出厂插件与重新登记的源码插件照常运行。
