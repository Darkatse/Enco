# M38 渠道中的多 Session

> 路线图「Session 委派」阶段的第四个里程碑，依赖 M37（已验收：子 Session、回复去向的函数、`session_send` 结算记下的投递、归档后订阅正常结束，见 Session 专题「委派」一节与「回复去向由输入自己决定」）；卡片静默发送来自 M35（已验收）。计划的生命周期见[路线图](../Roadmap.md)。

## 目标

在 Telegram 与 Discord 中，一个话题或频道就是一个根 Session：主人私有的空间里每个话题是一个带主人上下文的根 Session，公开的群里每个话题是一个群 Session。子 Session 在渠道里也有自己的会话：连接为它建一个话题或子区，它为父工作时的进度显示在那里，主人在那里说话就是接管它；主人与根 Session 的对话里不出现子 Session 的卡片。这回答了路线图中「新话题是否开一个新 Session」与「子 Session 在渠道里怎样呈现」。

## 对齐的判断

- **话题就是会话。** 会话的身份本来就由映射器给出：Telegram 是聊天加 `message_thread_id`，Discord 是频道或子区。连接的路由表按会话记录，所以宿主不需要「话题」这个概念，工作主要在映射器：认出话题，按话题回复与显示卡片，给出话题的标题，为子 Session 建话题。现在的 Telegram 插件还不认识话题。Telegram 用[私聊话题](https://core.telegram.org/bots/features#topics-in-private-chats)：由主人在 @BotFather 中为 bot 开启；Bot API 9.3 起私聊中的消息带 `message_thread_id`，bot 可以按话题发送、改名与删除话题，9.4 起 bot 可以用 `createForumTopic` 在私聊中建话题。

- **主人私有的空间里，每个话题是一个根 Session；公开的群里，每个话题是一个群 Session。** 私有与公开决定 Session 是否带主人的上下文（Session 专题「公开聊天与私人助理分属不同的 Session」）。
  - Telegram 私聊里的话题只有主人能看到，所以每个话题是一个带主人上下文的根 Session；没有话题的私聊照旧默认挂到 `main`。
  - Discord 服务器里有谁，协议不保证，只能由主人在连接的配置中声明哪些服务器是私有的，其中的频道与子区按私有处理；不声明的一律按公开群，用群的 profile。
  - 公开群的论坛话题各自一个群 Session。

- **新话题自动建根 Session，名字取自话题标题。** 标题经 M37 的转写函数成为一段，转写不出时用群 Session 那样的 `<连接名>:<会话>`。与未归档的 Session 重名时依次加 `-2`、`-3`，因为话题可能就叫 `main`；这是话题新增的规则，群 Session 的名字由会话 ID 拼成，不会重名。标题之后改了，Session 的名字不变。在话题里用 `/session` 可以改绑。连接为子 Session 建的会话在建立时就绑定，所以不会被当作新话题。

- **一个会话只显示一个 Session，子 Session 也有自己的会话。** 主人要看到委派出去的工作，又不要它穿插在和根 Session 的对话里。看后台的工作与对话是两件事：把子 Session 的卡片放进根的对话，就把两件事挤进了一个会话；另设一个显示多个 Session 的会话，又要为它配上只读、命令的例外、开关、全节点的通知与单独的隐私规则。让子 Session 像根 Session 一样拥有自己的会话，两件事各在各的会话里，「会话 → Session」仍是唯一的一对一关系，接管、取消与叫停都沿用会话的现有语义；协议自带的话题列表就是总览。

- **活动跟着回复去向；回复去向是父 Session 时，显示在子会话里。**
  - 回复去向是本连接的某个会话：显示在那里；是 CLI 或别的连接：本连接不显示。这两条是现有规则，回复去向由 M37 中 core 的那个函数求出。
  - 回复去向是父 Session：显示在本连接为这个子 Session 建的会话（下称子会话）里，前提是子会话仍绑定着它。主人用 `/session` 把子会话改绑给别的 Session 之后，这个子 Session 在本连接不再显示。
  - 子会话在第一次需要显示时建立：子 Session 开始一个为父工作的 Run，而父此刻在本连接显示（父的回复去向是本连接的会话，或者父自己的子会话在本连接），就在父的会话旁边建一个。没有开始过 Run 的子 Session 不占话题；父此刻不在本连接显示时（例如主人正用 CLI），本连接不为它建，与根 Session 的回复去向不在这里时不显示是同一条规则。每个连接为一个子 Session 至多建一次，与卡片的创建同一种形态。
  - 主人在子会话里说话，回复去向移到这个会话，就是 M37 的显式接管，不需要 `/session`；之后父再派任务，回复去向回到父，显示仍在这个会话。主人在别的会话里 `/session` 切到子 Session 只改变路由，在那里说话同样是接管。
  - 连接从父的 Log 得知子 Session：它跟随父，`session_send` 的结算记下了交给哪个子 Session、是否新建（M37），连接据此跟随这个子 Session，并递归地跟随它的子 Session。内核不为此新增通知，内容仍只从 Log 读取，订阅只用来唤醒。重启后，连接从状态中记下的子会话恢复跟随。

- **会话里的视图按它是不是回复去向分两种。**
  - 回复去向所在的会话里有人在等回复：进度卡在回复送达之后删除，那里的痕迹是回复本身，沉默时什么也不留（M35）；Run 进行期间显示「正在输入」。这是现有规则。
  - 只用于显示的会话（子 Session 为父工作时的子会话）里没有人在等：不显示「正在输入」；Run 结束时把卡片改写成终态的一行：结局、用时与 Round 数，以及回复或笔记的第一行，例如 `✓ 7m, 6 rounds · 找到三篇相关论文……`。摘要只取 Log 中已记下的事实，不另调模型。子会话由此成为这个子 Session 的工作记录，最后一行就是话题列表里看到的那一行。
  - 两种会话由回复去向这一个事实区分，不按 Session 是根还是子区分。

- **子会话不持续打扰。** 建立时协议留下的一次性消息可以接受：Telegram 新话题里的「话题已创建」，Discord 父频道里的「开启了子区」。此后视图一律静默：卡片静默创建（M35），刷新与收尾都是编辑，不提醒。接管之后子 Session 回答主人的回复照常提醒，那时主人在等它，与根会话里一样。提醒按消息是视图还是回复区分，不按发消息的是根还是子。

- **子会话的标题与人开的话题区分开，排版归映射器。** 宿主交出子 Session 全名的各段，映射器排成一眼能与人开的话题区分的样子，例如 Telegram 写成 `research › papers`，并配一种只给子话题用的图标颜色（`createForumTopic` 的 `icon_color`）。根话题的标题是主人起的，bot 不去改。

- **子会话建在父的会话旁边，协议做不到就不显示。** Telegram 私聊的话题是平的，子话题与父的话题在同一个私聊里。Discord 是父所在频道下的子区；父在 Discord 私信里时建不了子区，子 Session 在 Discord 不显示。OneBot 没有话题，映射器给不出建会话的请求，子 Session 不显示，与 M37 相同。

- **子会话随子 Session 归档而收起。** 连接跟随的子 Session 归档之后，它的订阅正常结束（M37），连接请映射器收起子会话（Telegram 关闭或删除话题，见「待定」；Discord 归档并锁定子区），并在记下收起结局的同一次状态提交中删去这条绑定与子会话的记录。收起没有生效时，会话留下而绑定已经删去，之后在里面说话按新话题处理，与 M37「指向已归档 Session 的路由按没有路由处理」一致。

- **主人可以关掉自动建子会话。** 连接配置增加 `show_children`，默认 `true`。建话题是连接的行为，属于壳的事实，所以配置归 `[channel.<名字>]`，经登记生效、可以回退，Agent 也能改。关掉的含义是不再自动建：子 Session 为父工作时在本连接不显示；主人仍可以在某个话题里 `/session` 切到它并接管；`/sessions`、`enco status` 与父收到的回报照常；已经建好的子会话保持绑定，照常显示到归档。不放在 profile：profile 管 Session 自己的行为，显示在哪里是壳的事，放进 profile，内核就要知道渠道。按根区分的需要出现时，再加一个像 `/everyone` 那样按会话记在连接状态里的命令。

- **卡片分批节流。** 几个子会话常在同一个聊天里：Telegram 的速率限制按聊天计，一个私聊里的几个话题共用一个额度。进度卡本来就与投递的发送节奏分开（渠道专题「投递是壳在渲染 Log」），节流由宿主自己做，作用于连接的全部卡片：每个周期只编辑有变化的卡片，并有条数上限，按 Run 开始的顺序轮流；创建与收尾优先于刷新，落后的刷新直接跳过。数值是宿主的常量，Telegram 与 Discord 的映射器现在都没有声明发送节奏，不靠它。

- **创建不重复：结果未知的创建不再试，明确没有执行的请求等 `retry-after` 过后再试。** 这是渠道专题「每个 Run 只尝试创建一次，失败或未知就不再建」按它的理由改写，卡片与子会话一样。重发结果未知的创建，可能留下删不掉的第二张卡或第二个话题；协议明确没有执行、带着 `retry-after` 时，请求没有生效，创建、收尾、删除与收起等它过去再试不会重复，刷新则跳过，下一个周期本来就带着最新的内容。子会话的创建结果未知时，这个子 Session 在本连接不显示，主人可以新开一个话题，用 `/session` 切到它。

- **契约升一次，库与内核不变。** 渠道接口增加建立与收起会话、活动视图的收尾形态，WIT 升到 0.13.0，全部插件重建一次。子会话、卡片的交接都在连接已有的 JSON 状态中，库不变；连接得知子 Session 与归档都经 M37 已有的事实，内核不变。

## 范围

- **映射器**：
  - Telegram 认出私聊与群中的话题，按话题回复、显示卡片与「正在输入」，给出话题标题；在私聊中为子 Session 建话题（标题与图标颜色），收起时关闭或删除；新话题的服务消息不当作输入。
  - Discord 认出频道与子区，给出名字；在父所在的频道下为子 Session 建子区，收起时归档并锁定。
  - 卡片收尾时改写成一行。
- **宿主**：
  - 私有空间（Telegram 私聊的话题、主人声明为私有的 Discord 服务器）中，新会话的第一条消息建出一个根 Session，名字取自话题标题；公开群的话题各自建群 Session。
  - 连接配置增加 `show_children`；Discord 连接的配置增加私有服务器的声明。
  - 子会话：从父的 Log 得知子 Session 并跟随；子 Session 为父工作的 Run 开始而父在本连接显示时建立，至多一次，结局记在连接状态中；回复去向是父时显示在仍绑定它的子会话里；归档后收起并删去绑定。
  - 视图：回复去向所在的会话照旧；只用于显示的会话不显示「正在输入」，Run 结束时把卡片改写成一行。
  - 节流按「卡片分批节流」，全部创建按「创建不重复」。
- **WIT 0.13.0**：见下文。`CONTRACT_VERSION`、SDK 与全部插件随之重建。
- **库**：不变，子会话与卡片的交接都在连接已有的 JSON 状态中。
- **文档**：Usage 写明话题与在 @BotFather 中开启私聊话题、私有服务器的声明、子会话与接管、`show_children`。

## 设计

验收时提炼或改写：

- 渠道专题：「聊天是壳，Session 属于 Enco」补上：话题就是会话；私有空间的话题是根 Session，公开群的话题是群 Session；一个会话只显示一个 Session，子 Session 也有自己的会话，由连接在第一次需要显示时建立，随归档收起。「投递是壳在渲染 Log」补上：活动跟着回复去向，回复去向是父时显示在子会话；视图按会话是不是回复去向分两种；提醒按视图与回复区分；节流作用于连接的全部卡片；「每个 Run 只尝试创建一次」改写为「创建不重复」。
- Session 专题「公开聊天与私人助理分属不同的 Session」写明私有与公开由空间决定，Discord 的私有由主人声明。
- 先定下的格式：WIT 0.13.0 中活动视图与会话的部分（见下文）；话题标题的部分见「待定」。

## WIT 的变化（草案）

活动视图与会话的部分如下；话题标题怎样经渠道接口给出，见「待定」。`run-end` 沿用 composer 接口中的定义。

```wit
package enco:plugin@0.13.0;

    /// The line a Run leaves where nobody waits for its reply.
    record activity-summary {
        /// Seconds the Run took.
        elapsed-seconds: u32,
        /// The Rounds it used.
        rounds: u32,
        /// How it ended.
        end: run-end,
        /// Whether its last reply was kept as a note rather than delivered.
        skipped: bool,
        /// The first line of its reply or note, shortened by the host; empty when it has none.
        excerpt: string,
    }

    /// What to do with a Run's view.
    variant activity-update {
        /// Show or refresh the live view.
        view(activity-view),
        /// Rewrite the view as the line the Run leaves, where nobody waits for its reply.
        summary(activity-summary),
        /// Remove the view.
        remove,
    }

    /// Creates, refreshes, rewrites or removes a Run's view; absent when nothing needs sending,
    /// and for a new view when the protocol shows none.
    ///
    /// (the paragraphs on notifications, `shown` and `answered` as before)
    activity: func(
        conversation: string,
        shown: option<string>,
        update: activity-update,
    ) -> option<request>;

    /// The request that opens a child Session's own conversation beside `beside`, the
    /// conversation where its parent is shown; absent when the protocol cannot open one there.
    ///
    /// `session` is the child's full name, segment by segment; lay out the title so that it
    /// reads apart from the conversations people open. Opening may leave the protocol's one-time
    /// notice. After it, the host sends views there without notification; only replies to the
    /// owner ask for attention.
    open-conversation: func(beside: string, session: list<string>) -> option<request>;

    /// The conversation that an `open-conversation` request made beside `beside` created, or why
    /// it failed.
    opened: func(beside: string, response: response) -> result<string, fault>;

    /// The request that puts away a conversation opened for a child Session once that Session is
    /// archived; absent when nothing needs sending. The host reads its response with `answered`.
    close-conversation: func(conversation: string) -> option<request>;
```

## 验收

- **话题**：
  - Telegram 私聊开启话题：新话题的第一条消息建出一个根 Session，名字取自话题标题；回复与进度卡在这个话题里；没有话题的私聊照旧挂到 `main`。
  - 话题标题里的空白与 `/` 在名字中换成 `-`；话题叫 `main` 时，建出的 Session 叫 `main-2`。
  - 在一个话题里 `/session main/research`：之后这个话题里的消息与回复都属于这个子 Session。
  - Discord：声明为私有的服务器里，每个频道或子区是一个带主人上下文的根 Session；没有声明的服务器照旧按群处理。
  - 公开群的论坛话题各自一个群 Session。
- **子会话**：
  - `main` 在自己的话题里委派 `main/research`：私聊中出现一个新话题，标题与人开的话题可以区分；`research` 为 `main` 工作时，卡片静默出现在这个话题里，没有「正在输入」，Run 结束时卡片改写成一行，带结局、用时、Round 数与回复的第一行；`main` 的话题里没有它的卡片。
  - 子话题建立时只有协议的一次性消息；之后的刷新与收尾都不提醒。
  - `main` 被回报唤醒：卡片在 `main` 的话题里，静默出现，回复之后删除。
  - 主人在 `research` 的话题里发消息：回复照常提醒，卡片在回复送达之后删除；`main` 不被唤醒。之后 `main` 再派任务：卡片仍在这个话题，Run 结束时改写成一行，回复回到 `main`。
  - 在子话题里 `/cancel` 停的是 `research` 当前的 Run；不带名字的 `/halt` 叫停 `research` 的子树。
  - 创建之后还没有开始 Run 的子 Session 没有话题。
  - 主人正用 CLI 和 `main` 对话时 `main` 委派：Telegram 中不建话题，也不显示。
  - 主人用 `/session main` 把子话题改绑给 `main`：`research` 之后为父工作时不再显示，也不另建话题。
  - 归档 `research`：它的话题被收起，连接删去绑定；收起没有生效时，在留下的话题里说话按新话题建根 Session。
  - Discord：私有服务器频道里的根 Session 委派，子区建在这个频道下，父频道只多一条「开启了子区」的系统消息；根 Session 在 Discord 私信里时，子 Session 在 Discord 不显示。
  - OneBot：子 Session 不显示，行为与 M37 相同。
  - `show_children = false` 并登记：新的子 Session 不再建话题；已有的照常显示到归档；主人在某个话题里 `/session main/research` 之后可以接管它。
  - 建话题的结果未知：不再重试，这个子 Session 在本连接不显示；协议带着 `retry-after` 拒绝时，等它过去之后建立。
  - 重启之后：连接恢复对子 Session 的跟随，已建的子话题照常使用，不重复建立。
- **节流**：四个子 Session 同时运行：卡片按节奏轮流刷新；被协议限流后，每张卡最终都收尾成一行。群里会话的卡片被限流时，同样等过 `retry-after` 之后出现。
- 按 0.12 构建的插件加载时被拒绝并提示重建；出厂插件与重新登记的源码插件照常运行。

## 待定

1. **Telegram 私聊话题的协议细节**，在 M38 开始时对照当时的 Bot API 核对：话题标题怎样经渠道接口给出（话题的创建与改名事件）；私聊中能否关闭话题，不能就删除，删除会连同话题里的消息一起删掉，Log 不受影响；bot 建话题时的服务消息会不会提醒；话题模式下没有 `message_thread_id` 的消息归哪个会话。
2. **Discord 的细节**：私有服务器声明的配置写法；子区用公开还是私有的种类，以及它在父频道留下的系统消息。
