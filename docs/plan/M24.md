# M24 构建与部署

> 路线图 P2 的第 6 个里程碑。计划的生命周期见 spec 09 §5。

## 目标

Agent 经正式路径构建并部署自己的插件（§4.8）。

## 范围

- **git 集成**：`ENCO_HOME` 是一个 git 仓库（§4.8）。
  - `enco init` 初始化仓库；已有的 home 第一次以新版本启动时，由主人或 Agent 执行一次 `git init`，启动警告给出提示；
  - 自动提交使用一个固定的提交者身份，例如 `Enco <enco@localhost>`，与主人自己的提交区分开；
  - 自动提交只包含被构建的插件目录，工作区中其他未提交的修改保持原样。
- **`plugin_build`**：
  - 构建前自动提交插件目录，以这份内容快照为输入；
  - 使用仓库的 lint 表；
  - 诊断是结构化的，只返回前 N 条，完整日志存为 blob；
  - 每个代际记录插件身份、源码快照、`Cargo.lock` 摘要、制品哈希、WIT 版本与工具链；
  - 以 `{}` 配置更新 README 的生成区（§7.5、§7.6）。
- **`plugin_scaffold` / `plugin_rename` / `plugin_remove`**：维护 `plugins.lock`。只执行 `git mv` 时，构建被拦下，并提示改用 `plugin_rename` 或 `plugin_remove`。复制出来的目录在首次构建时得到新身份。
- **rename 与配置节**：活跃代际的设置按身份保存，不受影响；`config.toml` 中仍是旧名字的 `[plugin.<旧名>]`，由启动警告与 `enco status` 报出，由主人或 Agent 修改后重新应用（§4.11）。
- **`enco-sdk`（含宏）**：从现有的四个插件（openai-compatible、deepseek、typesafe、web）中提取重复代码，不预先设计。
- **插件的依赖从哪里来**（§4.8）：
  - `enco-sdk` 内含 WIT。插件以 git 依赖 `enco-sdk = { git = "https://github.com/Darkatse/Enco", tag = <宿主版本> }`，共享的 crate 同样如此；Cargo.lock 锁定到提交，所以代际记录的 `Cargo.lock` 摘要足以复现构建。`plugin_scaffold` 写出这样的依赖。
  - Enco 仓库里的出厂插件写同样的依赖，由插件工作区的 `[patch]` 指向本地路径，所以同一份源码在两边都能构建，复制时不用改。
  - 出厂插件的源码就是 Enco 仓库在宿主版本 tag 下的目录：复制进 `plugins/<保留名>/` 就能修改，身份按保留名对上。宿主升级不动主人仓库，改过的插件由 Agent 对照新 tag 用 git 合并。
  - 离线节点用 Cargo 的标准做法：已有缓存时 `--offline`、`cargo vendor`、源替换。宿主不另建机制，因为 crates.io 上的依赖本来也要联网，只替 SDK 解决一处并不能让构建离线。
- **救生集加入 `plugin_build`**：安全模式中修好代码之后能经正式路径构建。
- **意图与活跃代际的不一致**（§4.5）：`plugin_status` 像 `enco status` 对配置那样，区分插件源码"尚未构建或部署"与"已构建为代际 N，但活跃的已不是它（被回退，或被重新部署的旧版本取代），原因是……"，由插件目录的内容与代际记录的源码快照比较得出。撤销之后仓库里留着的仍是被撤销的源码，这份报告让 Agent 不会把同一份坏代码再部署一次。
- **评测的夹具插件**：运行器在部署变体之后，构建并部署题目 `home/plugins/` 下的插件（13 §4 第 6 步），M25 的题目用到它。

## 规格

- 02：`enco-sdk` 进入工作区与依赖表；插件工作区的 `[patch]`。
- 05 §2.6：新增的插件工具；`plugin_build` 进入救生集。
- 08：`enco init` 初始化仓库；新增的 `enco plugin` 子命令；`plugin_scaffold` 写出的依赖。
- 11 §8：命令与工具；`plugin_status` 报告源码与活跃代际的不一致。

## 验收

- `plugin_scaffold` 生成的插件经 `plugin_build` 与 `plugin_deploy` 生效，代际记录包含源码快照与工具链；自动提交只包含这个插件的目录，提交者是 Enco 的身份。
- 故意写错的代码：构建失败，返回结构化的前 N 条诊断，完整日志可以从 blob 读取。
- `plugin_rename` 之后，插件的身份、代际历史与设置不变。
- 只执行 `git mv`：构建被拦下并给出提示。复制出来的目录在首次构建时得到新身份。
- 把 Enco 仓库中 web 的目录原样复制进 `~/.enco/plugins/web/`，改一处可观察的行为，经 `plugin_build` 与 `plugin_deploy` 生效：新代际属于 web 的出厂身份，安全模式仍用出厂代际。
- 部署一份坏代码后，以代际编号重新部署上一个版本：`plugin_status` 报出源码与活跃代际不一致，并指出活跃的是重新部署的那个版本。
