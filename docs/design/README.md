# Enco 设计

Enco 是一个私人 Agent 助理：以 Rust 为内核，以 Wasm Component（WIT）为插件边界，可以在主人的多台设备之间漫游，能够修改、验证和回退自己的能力。

设计文档记录 Enco 中顺着常规思路推不出来、却决定系统性质的判断，以及它们的理由。系统是什么，由代码、rustdoc 与生成的契约回答；这里回答为什么是这样。本文是总纲，写问题、不变式、贯穿各处的思路、概念与源码地图；各领域的判断在同一目录的专题中展开。改动任何东西之前先读本文，动到某个领域时再读它的专题。

## 要解决的问题

- **能力演进**：Agent 的能力以它发现需求的速度演进，每次尝试的失败都便宜、可以恢复。
- **连续性**：对话、任务和上下文不被困在某一台设备或某一次进程里。

两者是同一个问题：一项进行中的 Agent 工作，在它脚下的代码、机器或进程变化时，怎样安全地继续？所以它们共用一套机制。

唯一不可妥协的要求：

> Agent 经正式路径提交的修改或迁移，不能破坏 Agent 和主人修复它的能力。

Agent 拥有完整的系统权限，可以用 shell 删除任何文件；不设沙盒，就没有架构能阻止这一点。所以这条要求只覆盖正式路径，即登记代际与漫游；正式路径之外，由不依赖模型的原生管理入口兜底。

主人的前提选择：

- Space 永远只属于主人。信任模型是单一所有者，不设计多方信任。
- 一致性偏 CP：宁可让某项操作暂时不可用，也不出现两个执行者。
- 宿主切换须经主人确认；自主权限以后显式开通。
- 个人化的长期记忆是私人助理的核心能力。
- 内核、协议、SDK 与插件自建；正确性极难且已经商品化的地基（wasmtime、tokio、SQLite、openraft、rustls）使用成熟库。
- 多作者的插件生态在 Space 落地之后开放。

## 不变式

下面八条是设计的主干。专题中的每个判断都从其中某一条推出；推不出来的，要么是一条新的不变式，经主人确认后写进这里，要么不属于设计。

**模型可见 ⟺ 已记录。** 进入模型请求的一切，都先成为 Log 中的记录。请求只有一个构造者，即本 Session 的 composer：它把组装结果冻结为 ContextPlan，按内容寻址记录，此后重试、查看与审计都只解析这份记录，不重新组装。所以 Session 可以只凭 Log 重建，换代码、换机器、崩溃之后都能继续。

**运行中的行为 ⟺ 已登记的代际。** Agent 对自身的每一种修改，不论是插件的代码、插件的配置，还是接线与内核配置，都先经校验登记为代际，再由注册表这一个提交者生效、回退与恢复；重启只恢复，不读取新的意图。所以 Agent 本身可以只凭注册表重建。常驻指令与 Skill 是文本，在使用时记入计划，由前一条不变式约束。

这两条互为对偶：前者让 Session 可以重建，后者让 Agent 可以重建。

**归属与转移。** 每份可变状态有唯一的归属者，由它按顺序处理变更，插件代码只在归属者的边界上替换，即 Erlang 的 gen_server。回调把写入作为返回值交出，归属者把这些写入与接纳事实一起原子提交。丢失更新、重投重复、游标倒退、并发登记互相覆盖、迟到的健康结果，都由这两条消解。派生状态是它的权威的函数，可以随时丢弃、从权威重建。

**Round 边界是唯一的安全点。** 模型可见的世界（能力目录、profile、时区）在这里换代，漫游在这里提交，执行权在这里检查，压缩与 Brief 在这里生成，崩溃后也从这里恢复。一个 Round 内模型看到的世界不变，所以每一步都能只凭记录解释。Provider 的代际在每次 Attempt 时选取并不违背这一点：请求已经记录，换的只是翻译协议的代码。

**双向不泄露。** 插件只看得到 WIT，这由 Wasm 物理保证；内核与宿主不按插件或服务的身份写业务分支，服务之间的差异由插件声明的能力表达，这由依赖方向与公开契约保证；插件之间只经导入的接口交互，由内核转发。宿主按操作系统平台做适配是它的正常职责。

**外部效果如实结算。** 调用的结局只有 `ok`、`failed`、`unknown` 三种。请求发出之后无法确认的，就是 `unknown`；有副作用的调用结局为 `unknown` 时不自动重试，由看得到记录的一方决定。trap 撤销不了已经发生的效果，所以重投以记录为准。

**外部进入 ⟺ 已映射且已钉住。** 外部是 Enco 无法设计、也无法控制的一切：第三方服务、模型服务、网页、文档、命令输出与聊天协议；能登记的插件与配置不属于外部。外部产生的内容先按原样记录，再由已登记的映射器译成规范值；外部声明的契约（例如一份工具目录）以定本写进意图，随代际固定，内容与定本不符就是带出处的失败。映射器只翻译，不做任何 I/O，规范值由内核自己的类型接纳，此后各层信任它。所以外部的变化只在一个位置、以一种失败出现，修复也只有登记这一条路。这一条与上一条互为对偶：上一条管出去的效果，这一条管进来的内容。

**单机是分布式的退化形式。** 单节点就是所有 Binding 都指向自己、控制平面只有一个投票者的情形，与多节点是同一套代码。事后补上代价很高的数据形态从第一天就固定（见多节点专题）；顺序来自结构，而不来自时钟。

## 贯穿设计的思路

下面几条思路在各个专题中反复出现，大多数具体判断是它们在某个领域的应用。通用的工程原则见 `CONTRIBUTING.md` 的项目哲学。

### 一种事情只有一条路

同一种语义只在一处实现，各入口只提供自己的数据。第二条路径就是第二套规则，它会与第一条慢慢分歧，维护者也要同时理解两者。所以插件与配置是同一种代际，撤销就是再登记一次，请求只由 composer 构造，扩展只有调用与转移两种形态，单机与多机是同一套代码。真实存在的差异，让它来自事实本身。

### 状态是事实的函数

能从已登记的事实求出的东西，就不另存，不另设标志，也不靠后台进程维持。存下来的派生结果会在规则变化后与重新求出的值并存，成为第二个事实来源；标志会卡住；后台对账会与前台的命令竞争。所以声明每次从内容求出，每个组件是注册表视图的函数，安全模式是本 Run 的 Log 的函数，意图与运行的不一致从登记事实推出，记忆索引在召回前与权威对账。

### 值不可变，身份稳定，可变的只是引用

内容一经记下就不再改变：制品、计划与已登记的源码和配置文件按内容寻址，配置文档与 Log 只追加。这些值都存在 Enco 自己的库里：引用一旦指向库之外，接纳就依赖一个归属者管不到的存储。插件与 Session 是身份，跨越变化保持不变；变的只是身份此刻指向哪个值，由归属者移动。所以问"内容变没变"比较值，问"是不是同一个、同一次"比较身份与引用：同一份出厂代码可以激活多次，复制来的源码可能编出相同的字节，名字也会改回去。

### 在源头声明，不在下游防御

错误在拥有相关事实的边界被排除一次：用类型让非法状态无法表示，由归属者在提交前检查前置条件。其余各层信任这个边界，不重复校验、捕获或兜底；状态无法确认时 fail fast，把原因交给调用者。这样每个约束只有一个位置，维护者改变它时知道该改哪里，缺陷也不会被半路的兜底掩盖。

### 承诺可恢复，不承诺不失败

插件会坏，服务会断，进程会被杀。设计的目标是让每一种失败都落在一个已知的、可以继续的位置：试用中的代际自动回退，出厂代际垫底，Round 失败进入安全模式，连接断开后按协议重连补收，无法确认的效果记为 `unknown`。恢复路径从不依赖被替换的东西本身，所以回退不经校验，原生管理入口不经模型。

### 自动机制只做有证据的事

决定交给掌握证据的一方：宿主看得到 trap 与契约违规，Agent 看得到任务是否完成，主人拥有权限。代际的回退与撤销按这条分担；宿主切换、采纳外来代码时的扩权与强制接管，由主人确认。

### 概念少而一致

上下文是稀缺资源，概念和工具本身就是认知负担。系统只有十个概念，新能力先确认它是哪个概念的实例、属于调用还是转移；能用已有动词表达的操作不另立工具；WIT 只包含已有使用者验证过的东西；同一个东西只有一个名字。

## 概念

> 一切发生的事都作为 Event 送到它的归属者，需要 Agent 处理的送进 Session 当前所在节点的 Inbox；内核以 Round 为单位执行"组装上下文 → 调用模型 → 执行工具"，每个 Round 钉住一份能力快照；事实写入 Log 并复制到 Space；插件只贡献能力，节点只提供位置，两者都不拥有事实。

| 概念 | 定义 |
|---|---|
| Event | 送给某个归属者（Session、连接、Observer）的一件事，带全局唯一 ID，可以去重 |
| Session | 身份 + Log + 工作区 + 配置（composer、按 Attempt 用途选用的 endpoint，可以取自命名的 profile）；单写者；可以有父 Session |
| Round | 一次模型请求及其全部工具调用与结果确认；一个 Event 唤醒的连续多个 Round 是一次 Run |
| Log | 追加式事实，键为 `(epoch, seq)`；模型上下文的唯一来源 |
| Capability | Tool、Provider、Channel、Context、Observer、Mapper；ID 为 `(节点, 插件名, 名称)` |
| Plugin / Generation | 能力的打包单位，名字是主人 home 中 `plugins/` 下的目录名，身份是 ULID / 一份已登记、可以试用与回退的实现，由内容与从内容求出的声明组成 |
| Host | 节点提供的机制：fs、exec、http、连接、定时、状态、blob、检索索引 |
| Node | 一个运行中的内核及其 Host：完整节点、Edge 节点，或只参与控制平面的见证者 |
| Space | 主人全部节点的集合；控制平面（成员、Binding、期望状态）由共识维护 |
| Binding | `key → (node, epoch)`，单写者资源的所有权：Session 是粘滞所有权，渠道与定时是租约 |

其余固定的词：Inbox、Run、Attempt、Entry、Transcript、Brief；ContextPlan、Composer、Candidate、ContextSource、策略点；Outcome、Failure；Provider、Completion、Endpoint、Profile；Artifact、Registry、Registration、Exports、Trial / Healthy / Failed、Factory、系统代际；Memory、Memories、MemoryIndex、recall；Schedule；SafeMode、Lifeline；Commit、Store；外部、Mapper（映射器）、定本。每个词只指一样东西，代码、日志、错误消息与文档都不另起同义词。

扩展只有两种形态：

- **调用**：工具、Provider、deliver。可能有外部效果，结局为 `ok / failed / unknown`。
- **转移**：渠道事件、Observer。回调返回写入，由归属者提交。

可变状态与它的归属者：

| 状态 | 归属者 | 替换代码的边界 |
|---|---|---|
| Session 历史 | Session actor | Round |
| 渠道连接的协议状态、游标、聊天与 Session 的映射 | 连接 actor，每个连接或账号一个 | 事件 |
| 插件的持久状态 | 状态作用域 actor：全局、每 Session 或每账号 | 调用 |
| 记忆及其索引 | 记忆的归属者（宿主）；索引是派生物 | 调用 |
| 由 Log 派生的索引 | Observer actor，持有 Log 游标 | 事件 |
| 代际、健康与接线 | 注册表，唯一的提交者 | 提交 |
| 定时 | Scheduler；多节点时只在持有定时租约的节点上运行 | 提交 |
| Binding、租约、期望状态 | 控制平面；单节点时就是本机 SQLite | 提交 |

路由只有五条规则：

```text
1. Event          → 它的归属者；Session 的输入 → Binding(session).node 的 Inbox
2. Round 开始      ⇐ 仅当 Binding(session) 指向本节点，且 epoch 为最新
3. Capability 调用 → 能力所在的节点：本地直接调用，远程经 invoke
4. 出站消息        → 持有 Binding(channel) 租约的节点
5. 事实            → 写入本地 Log，按 epoch 栅栏异步复制到 Space
```

## 五个透镜

| 透镜 | 做到极致的地方 | Enco 拿走的 | 它的教训与 Enco 的对策 |
|---|---|---|---|
| Erlang | 隔离进程、邮箱、位置透明、supervision、热代码加载 | 归属者 actor 持有状态，代际是可替换的回调模块；健康门控是代际的 supervisor，父 Session 是子 Session 的 supervisor | 位置透明掩盖部分失败，netsplit 后要人工收拾，最多两个代码版本 → 远程调用显式返回 `unknown`，控制平面用共识，记录与钉住的实例数量不限，恢复只留两份制品 |
| Plan 9 | 按进程组合的命名空间，`import`，`cpu` | 每个 Round 的能力快照是一个命名空间，由本地与远程导出的能力组成；roam 就是 `cpu` | 一切皆文件会丢失动作的语义 → 动作用类型化调用，文件投影只用于查看 |
| Smalltalk | 活的 image，系统在运行中修改自己 | 自我修改的闭环，`status` 与 `inspect` | image 不可复现、会腐烂，包之间的方法覆盖让结果取决于加载顺序 → 源码是意图，登记把源码与制品按内容寻址记进自己的库；要改变一个插件的行为就改它的源码并登记 |
| Lisp | 代码即数据，eval 与 REPL，语言扩展自身 | Log 是数据；请求是 composer 对当前输入的纯函数，并作为数据记录；工具调用是被内核 eval 的程序 | 无限扩展导致方言碎片化 → 少量类型化的贡献与 WIT 契约 |
| 边界类型 | 外部数据在边界上一次译成静态类型：F# 与 Idris 的类型提供器、Elm 的 decoder、Typed Racket 的 `require/typed` 与归责、TypeScript 的内容映射器 | 外部只经映射器进入；映射器的结果由内核自己的类型接纳，此后就是证明；失败指回外部与原文 | 提供器现查活的数据源使构建不确定，生成的代码绕过检查；切在紧耦合处的细粒度边界可慢百倍；TS 的映射器是任意进程，只能靠信任开关 → 映射器是零导入的 Wasm 组件，对定本与原文的纯函数；契约以定本钉进代际；边界只切在整份外部内容上 |

## 源码地图

依赖方向：`enco-core` ← `enco-kernel` ← `enco-host` / `enco-wasm` ← `apps/enco`。内核不依赖 wasmtime、网络或具体平台。

| 要找的东西 | 位置 |
|---|---|
| 领域类型：ID、Event、Log 条目、ContextPlan、代际 | `crates/enco-core` |
| Session actor、Run 与 Round、Attempt、计划校验、工具分派 | `crates/enco-kernel/src/` 的 `session`、`run`、`round/`、`attempt`、`plan`、`dispatch` |
| Transcript、崩溃恢复、定时、请求查看 | `crates/enco-kernel/src/` 的 `transcript`、`recovery`、`scheduler`、`inspect` |
| 注册表、内核的配置表与 profile | `crates/enco-kernel/src/` 的 `registry/`、`settings`、`profile` |
| 内核与外界的边界（端口）、上限常量 | `crates/enco-kernel/src/ports/`、各 crate 的 `limits.rs` |
| SQLite、blob、制品库 | `crates/enco-host/src/store/`，模式在 `schema.sql` |
| 出厂 composer、工作区上下文、原生工具 | `crates/enco-host/src/` 的 `composer`、`context`、`tools/` |
| 记忆、渠道与 Telegram | `crates/enco-host/src/` 的 `memory/`、`channel/`、`telegram/` |
| 插件运行时、宿主导入、凭证 | `crates/enco-wasm` |
| 组合根、守护进程、本地协议与 CLI | `apps/enco/src` |
| 插件源码的值、构建、登记、历史与倒带 | `crates/enco-host/src/development/`；分发的 SDK 在 `sdk/` |
| 完整状态、需要关注的情况与下一步 | `crates/enco-host/src/status/`，文档渲染在 `development/render/` |
| 插件契约 | `sdk/wit/plugin.wit`，生成的 `sdk/wit/CONTRACT.md` |
| 出厂插件：Chat Completions、Gemini 原生协议、结构化决策与网页 | `plugins/` |
| 评测题与黑盒运行器 | `evals/` |
| 门禁：`cargo xtask check` | `xtask/` |

## 维护设计文档

设计是判断的回归测试。测试守住行为，设计守住判断：维护者（人或 Agent）没有提醒时，会被需求和眼前的代码推向别处，这里的条目把他们拉回来。

- **准入**：只为决定系统性质、却无法从代码与常规思路推出的判断写条目；它通常已经在讨论或评审中纠正过一次。代码、类型、测试与门禁已经表达的，不写。
- **形态**：标题是判断本身，写成一句陈述。正文先写为什么，回到它所推出的不变式或思路，再写由此得出的结果；"不做什么"写成"只有""唯一""恰好"这样的限定。有代价时写明代价；判断由某个类型、边界或门禁保证时，末尾写一行"落点"。专题内的条目按推导的顺序排列，所以专题的目录就是它的判断清单。
- **不写机制**：签名、字段、表名、常量、错误码与命令参数属于代码；只关乎一处代码的理由写在那处的注释里。
- **一处**：每个判断只写在一个专题里。总纲的思路只举例，不展开；条目之间按专题与标题引用，不编号。
- **生长**：新的判断在里程碑计划的"对齐的判断"中形成，或由 [LESSONS.md](../../LESSONS.md) 中见到三次的教训提升而来，验收时提炼进来。先尝试改写已有条目，推广成更一般的一条，再考虑新增；被取代的条目原地改写或删除，不留历史，历史在 git 里。
- **篇幅**：总纲与全部专题应当能一次读完；超出时，先找能合并的条目。
- **不写进度**：实施的进度在[路线图](../Roadmap.md)。
