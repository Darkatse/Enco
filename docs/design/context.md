# 上下文与手册

本专题展开"概念少而一致"在模型一侧的含义。Agent 友好的核心是认知负担轻，这里有两个读者：运行中的模型受上下文预算约束，开发中的 Agent 受理解成本约束。二者用同一套方法：分层，按需展开，每一层都能指向下一层。

## 组装

### 正确性在内核，策略在 composer，线上格式在 Provider

composer 是请求唯一的作者；内核与宿主给出事实、检查承诺并记录。每项事实都按它的归属者自己的类型完整给出：Log 的投影是内核的类型，记忆是记忆的记录，常驻说明是主人写下的原文。不按某个 composer 的需要挑选字段，也不装进通用的候选容器：按一个消费者裁剪的输入只适合那一个消费者，下一个 composer 出现时就要改宿主。只在有访问边界时少给，例如扩展字段归写下它的 Provider，composer 只看到大小。新的信息由它的归属者以自己的类型加入契约，随第一个使用者增长。composer 只选择能力 ID，内核从本 Round 的快照补上定义，因此它不能改写定义。插槽、排序、预算与取舍、披露多少、何时压缩、为缓存保持稳定的前缀，都是 composer 的策略。把请求映射为服务商协议，包括缓存断点这类线上机制，属于 Provider。前缀缓存是效率问题，不是正确性问题，所以内核不含缓存逻辑，只记录每次 Attempt 回报的用量与缓存命中，让缓存优化可以测量、可以迭代。渠道那边是同一个分工：宿主持有传输并负责提交，插件负责协议语义。

落点：内核的 `ComposeInput` 与 WIT 的 `compose-input` 逐字段对应，enco-wasm 的转换完整解构两侧，任何一侧新增字段或分支都编译不过，直到有人决定它怎样映射。

### composer 是每个 Session 的属性

每个 Session 绑定一个 composer：Agent 会话用默认的，角色扮演会话可以用 SillyTavern 式的，两者并存。内核不定义任何插槽，插槽是 composer 自己的词汇。composer 是与 I/O 无关的纯函数，只看参数、配置与制品。宿主在 Round 开始时采集常驻说明与记忆，固定时钟与随机种子；同一个代际在相同 Round、参数与选项下得到相同计划。每次组装都传入整份输入，不提供按需读取 Log 的导入，也不做增量传入：跨边界复制随输入线性增长，百万 token 的输入只要几毫秒，而一次模型请求以秒计。它的代际写入 Attempt，自己的角色卡与预设随制品登记。

profile 选择 composer 与选项，同一个代际可以服务不同的角色。选项 schema 属于加载后的代际；登记与运行共用绑定规则，在选定的代码上校验实际选项。Round 中途的换代与机械回退都可能使选项不再匹配，所以这项使用的可用性在绑定时成立，失败不归责于代码。

### 修复工具的常驻是 Session 声明的要求，由内核校验

Session 的配置可以声明要求，默认的 Agent 配置要求救生集常驻。内核按声明校验每一份计划，不满足的计划按 composer 失败处理：回退代际，或者进入安全模式，而安全模式的出厂 composer 永远带着救生集。所以一个写坏的 composer 拿不走 Agent 修复自己的工具。角色扮演一类的 Session 可以不声明这项要求。

### 模型只能调用被告知过的能力

Round 快照钉住全部可用的能力，计划中的披露集决定模型看见哪些：可调用的就是已披露的与快照的交集，包括本 Round 经搜索展开并已记录的。计划中的工具定义只从快照取得，分派只在披露集中查找。所以记录下来的定义，就是模型看到、也是它唯一能调用的东西。

### 叙述逐字冻结在计划中

composer 写下的说明（时间、上一次工作的结局、输入来源、召回的记忆）逐字记在计划中，此后原样回放。默认 composer 沿用本 Session 上一份计划，只在末尾追加新条目和它们的说明，所以 Agent 以后看到的历史，就是它当时看到的样子，前缀缓存也一直延伸到上一次的末尾。常驻说明与固定的记忆放在开头，因最新输入而召回的记忆放在它所回应的输入之前，二者分开，请求才能只追加；开头或已有条目的选择改变、或者压缩时，才开始新的系列。

### 计划的身份是完整内容，存储共享相同部分

连续请求的大部分内容相同，逐份保存会反复存入同一段历史，所以存储共享相同的部分，还原的代价有上限。共享与否只由前后两份计划的内容得出，不看计划出自哪个 composer。计划的身份始终是完整内容的哈希，存储形态不进入 composer 的契约，检视与请求解析都读取完整计划，所以存储方式可以改变，已记录的哈希不变。计划与引用它的 Attempt 在同一事务中接纳，存储不会留下未接纳的计划。需要文件路径的图片、全文与附件继续保存原始字节。

### 能看什么由 endpoint 声明，发不发由计划按条目记下

同一个协议背后的模型接受的内容不同，能看图片是模型的事实，所以由 endpoint 声明；是否把某张图片放进这次请求是上下文的取舍，所以由 composer 决定，内核检查选择是否符合目标声明。切换目标时重新组装，两者仍各负其责。

同一条消息里的图片共同表达一次输入，拆开发送会割裂它的含义，因此计划以整条记录为选择单位。图片是否发送与它是否存在是两件事：说明始终保留格式、大小与文件路径，未发送的原因写进计划。压缩保留这些说明，使后续模型仍能找到原始内容。

### 降级写进计划

被省略的内容一律连同原因写进计划：超出预算的指令与记忆、只按关键词完成的召回、没有完成的相关性判断、读不到的旧计划。计划随 Attempt 记录，所以每一次降级都能事后核对，`enco inspect` 能回答"这条记忆这次为什么没有出现"。

### 结果的预算由内核给出，工具按自己的单位停下

内核在每次调用中告诉工具结果可以内联多少字节。能分页的工具在预算内按自己的单位停下，并说明怎样继续，例如读文件时给出下一段的起始行；超出预算的结果由内核统一截断为预览，全文存为 blob。截断对所有工具相同，内核不按工具区分。Log 只记录结局与模型看到的内容，不另存工具的原始返回值。

### Agent 据以行动的结果写成文档

状态、历史与开发命令的结果，是 Agent 决定下一步的依据。字段堆成的 JSON 要模型自己拼出结论，既费 token，也不指路。因此这类结果写成文档，由已记录的事实推出需要关注的情况与下一步，不推断记录里没有的原因。情况、动作的目的与动作需要的输入各有明确的含义，文档只呈现这些判断；必须由 Agent 决定的输入明确留待填写，填好之后才是可执行的调用。数据只有一份，程序读取结构化事实，Agent 阅读同一份事实的文档。

一种目的只描述一种效果，借用相近的目的会让类型正确而话说错。失败的原因可以照录，但它指向意图的哪一部分，由产生原因的地方给出；下一步据此写出要修什么，写不出"修好原因"这样的含糊话。

落点：内核的 `Cause` 与 `IntentPart`；宿主的 `Attention`、带目的的 `Step`、每个工具唯一的 `DevelopmentTool` 声明，以及它们的文档渲染。

## 协议

### 协议差异留在 Provider

只有多家协议共有的含义才进入规范类型；只属于一种协议的东西由 Provider 自己处理：thinking 签名与 reasoning 内容放进扩展字段，内核只把它回放给产生它的插件身份，不解释内容；服务端的会话状态只当作缓存，Log 中始终有完整的请求；服务端内置工具只允许效果限于那次补全的，会产生外部效果的必须作为 Enco 的工具接入，经过分派与结算。

图片输入具有跨协议的共同含义，进入规范消息；工具结果里的图片在线上协议中怎样表达，由 Provider 翻译。需要原样回放整份回复的协议，把整份内容放进自己的扩展，规范部分只从这份内容求出，内核无需理解签名的位置。

落点：`plan::resolve` 按来源代际的身份过滤扩展字段。

## 披露

### 工具本身就是认知负担

每多一个工具，模型每次请求都要多读一份定义，注意力也更分散。所以能用已有动词表达的操作不另立工具，常驻的只有救生集，其余按需披露。所有可披露的条目共用三个级别：L0 是名称加一句话，L1 是完整描述与 schema，L2 是细节与引用，按需读取。这是 Agent Skills 三级结构在工具、Skill、插件与远程能力上的推广；超长结果落盘、Brief 的引用都是 L2 的实例。

### 脚本中的调用仍逐个分派

模型可以把一组工具调用写成一段脚本，在宿主的沙箱中执行，唯一的能力是把调用交回本 Round 的分派。每个嵌套调用照常检查披露、经过策略点、按结局结算并记入 Log，结果只交给脚本，模型只看到脚本的输出。脚本整体是有副作用的调用，中断后记为 `unknown`，不重跑；结算列出已经开始的嵌套调用与它们的结局，模型据此不重复它们。

## 手册

### 文档分三层，各有唯一的来源

Agent 先读文档定位，再读需要的那一小段代码，所以文档应当是源码的精华，而不是另一份手写的说明。文档按来源分为三层：契约来自 WIT 的 `///`；代码来自每个 crate 的 rustdoc，库 crate（宿主的各库与 SDK）有回答"给调用方什么"的 API.md，每个 crate 都有回答"代码怎样组织、改某件事去哪里"的导航手册；代际来自运行中的实例的声明，加上它源码的导航手册。插件没有 API.md：它对外的接口是 WIT 导出与声明，Rust 条目都是内部实现。

两种 Agent 各取所需。运行中的 Agent 在 home 中读契约、SDK 与宿主的 API.md 和各插件的运行时手册，不需要宿主源码；开发 Enco 的 Agent 在仓库中另外读宿主的导航手册与手写的设计。

### 一份文档，两种读者

面向模型的文本与开发文档出自同一段源码注释：第一段是 L0 摘要，正文是 L1，带标题的小节与链接是 L2；只面向开发者的内容写在 `# Implementation` 小节里，提取给模型时剔除。一段 WIT 的 `///` 因此同时流向插件 SDK 与宿主绑定的 rustdoc、CONTRACT.md 与运行时手册；工具参数类型的字段文档就是模型看到的参数说明，工具说明只写行为。两份手写的说明迟早会分歧，一份来源不会。

### 文档过期是构建失败

CONTRACT.md 与各库 crate、SDK 的 API.md 是生成物，提交入库，由 `--check` 门禁比对。公开接口的变化因此以 API.md 的 diff 出现在评审中。插件 README 的生成区在每次构建时由组件重写，面向模型的文本中的上限由常量生成。文档是否过期不靠自觉。

落点：`cargo xtask docs --check`。

### 手册按查找的顺序排版，每个条目只说一次

rustdoc 的 JSON 只是中间数据：文档文字只占百分之一左右，其余是 ID、源码位置与类型树。直接交给模型，既浪费上下文，又要它自己拼回结构，正是"Agent 据以行动的结果写成文档"所拒绝的。所以 JSON 只用来渲染手册与检查文档门禁，Agent 读的是渲染出的 Markdown。导出时不做筛选：JSON 包含私有与隐藏的条目，显示什么由每种手册自己决定；文档规则因此能看到全部条目，私有模块上的豁免也查得出来。读者先要知道有什么，再看是什么，最后才读细节，版式照这个顺序排：

- 一级标题是模块，二级是条目，三级是成员。每个模块开头是索引，一行写一个条目的种类、名字与第一段摘要，就是 L0；没有摘要的写明 `(no summary)`，缺口一眼可见。
- 条目先给源码位置与声明，再给文档：签名已经说清的，不必再从文档里读。
- 一个条目经几条公开路径都能到达时，只在首选路径展开：最短的路径，一样短时取声明处而不取再导出；其余路径写"same as"指过去。读者不必比较两份一样的说明。
- 代码照源码的写法呈现：宏展开出的签名（例如 `#[async_trait]`）还原成 `async fn`，它加上的生命周期也一并去掉；私有条目不写 `pub`。
- 实现一律写出声明，例如 `impl<I: Clone> Clone for Message<I>`、`impl Clone for Wrapper<u8>`：它对哪些类型、在什么条件下成立，都在声明里。只写 trait 名会把有范围的实现说成无条件的；范围或约束一变，API.md 就有差异。
- 插件的手册只描述作者写的代码。生成的绑定标了 `#[doc(hidden)]`，由契约说明；作者写在 trait 实现里的方法照常列出，插件的主要代码就在那里。
- 入库的 API.md 只写源文件不写行号，只有接口变化才改变它，评审中的 diff 因此只反映接口；不入库的导航手册写行号，用来定位。

落点：`crates/enco-manual`。

### 手册是 home 中的只读投影

工具要少，读与搜都已有动词：Agent 用 `fs_read` 读手册，用 shell 中的 `rg` 搜索，不另设读手册的工具。`fs_read` 在救生集里，所以安全模式下修复时也能读手册，系统提示在两种模式下都指出它的位置。手册放在 home 的顶层，与 `sdk/` 一样是按名字浏览的东西；`.data/` 是 Enco 的库，Agent 只经类型化调用触及。

投影是派生状态：它是已登记的代际与宿主内嵌文档的函数，只有一个写者，注册表每次提交之后与启动时整份重写，删掉也能重建，手工改动在下一次重写时被覆盖。启动不能依赖 Rust 工具链，所以宿主的 API.md 与契约嵌进二进制；插件的导航手册在构建时生成，按源码哈希存进库，投影只从库中取。

### 手册描述运行中的代际

插件的运行时手册由正在运行的实例给出：工具、配置 schema 与凭证来自以这个代际的配置求出的声明，代码说明来自这个代际源码的导航手册；回退到较早的代际时，就是那个代际自己的源码。插件 README 的生成区与运行时手册出自同一个函数。投影只保留运行中的代际，所以手册与实际执行的代码一致；历史由 `self_history` 回答，代际是否健康、接到了谁、下一步做什么，属于状态。
