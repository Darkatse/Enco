# 上下文与手册

本专题展开"概念少而一致"在模型一侧的含义。Agent 友好的核心是认知负担轻，这里有两个读者：运行中的模型受上下文预算约束，开发中的 Agent 受理解成本约束。二者用同一套方法：分层，按需展开，每一层都能指向下一层。

## 组装

### 正确性在内核，策略在 composer，线上格式在 Provider

内核只负责正确性：原样记录实际发出的请求，把披露的能力绑定到本 Round 钉住的代际，校验计划，执行安全模式。插槽、排序、预算与取舍、披露多少、何时压缩、为缓存保持稳定的前缀，都是 composer 的策略。把请求映射为服务商协议，包括缓存断点这类线上机制，属于 Provider。前缀缓存是效率问题，不是正确性问题，所以内核不含缓存逻辑，只记录每次 Attempt 回报的用量与缓存命中，让缓存优化可以测量、可以迭代。渠道那边是同一个分工：宿主持有传输并负责提交，插件负责协议语义。

### composer 是每个 Session 的属性

每个 Session 绑定一个 composer：Agent 会话用默认的，角色扮演会话可以用 SillyTavern 式的，两者并存。内核不定义任何插槽，插槽是 composer 自己的词汇；Context 贡献只用一小组共享的种类描述候选，再加上由具体 composer 解释的元数据。composer 是确定性的纯函数，同样的输入得到同样的输出，由契约测试检验，它的代际写入 Attempt 记录。

### 修复工具的常驻是 Session 声明的要求，由内核校验

Session 的配置可以声明要求，默认的 Agent 配置要求救生集常驻。内核按声明校验每一份计划，不满足的计划按 composer 失败处理：回退代际，或者进入安全模式，而安全模式的出厂 composer 永远带着救生集。所以一个写坏的 composer 拿不走 Agent 修复自己的工具。角色扮演一类的 Session 可以不声明这项要求。

### 模型只能调用被告知过的能力

Round 快照钉住全部可用的能力，计划中的披露集决定模型看见哪些：可调用的就是已披露的与快照的交集，包括本 Round 经搜索展开并已记录的。计划中的每个工具定义必须与快照中的完全相同，分派只在披露集中查找。所以记录下来的定义，就是模型看到、也是它唯一能调用的东西。

### 叙述逐字冻结在计划中

composer 写下的说明（时间、上一次工作的结局、输入来源、召回的记忆）逐字记在计划中，此后原样回放。默认 composer 沿用本 Session 上一份计划，只在末尾追加新条目和它们的说明，所以 Agent 以后看到的历史，就是它当时看到的样子，前缀缓存也一直延伸到上一次的末尾。常驻的候选放在开头，因最新输入而召回的候选放在它所回应的输入之前，二者分开，请求才能只追加；开头或已有条目的选择改变、或者压缩时，才开始新的系列。

### 能看什么由 endpoint 声明，发不发由计划按条目记下

同一个协议背后的模型接受的内容不同，能看图片是模型的事实，所以由 endpoint 声明；是否把某张图片放进这次请求是上下文的取舍，所以由 composer 决定，内核检查选择是否符合目标声明。切换目标时重新组装，两者仍各负其责。

同一条消息里的图片共同表达一次输入，拆开发送会割裂它的含义，因此计划以整条记录为选择单位。图片是否发送与它是否存在是两件事：说明始终保留格式、大小与文件路径，未发送的原因写进计划。压缩保留这些说明，使后续模型仍能找到原始内容。

### 降级写进计划

被省略的内容一律连同原因写进计划：超出预算的指令与记忆、只按关键词完成的召回、没有完成的相关性判断、读不到的旧计划。计划随 Attempt 记录，所以每一次降级都能事后核对，`enco inspect` 能回答"这条记忆这次为什么没有出现"。

### 结果的预算由内核给出，工具按自己的单位停下

内核在每次调用中告诉工具结果可以内联多少字节。能分页的工具在预算内按自己的单位停下，并说明怎样继续，例如读文件时给出下一段的起始行；超出预算的结果由内核统一截断为预览，全文存为 blob。截断对所有工具相同，内核不按工具区分。Log 只记录结局与模型看到的内容，不另存工具的原始返回值。

### Agent 据以行动的结果写成文档

状态、历史与开发命令的结果，是 Agent 决定下一步的依据。字段堆成的 JSON 要模型自己拼出结论，既费 token，也不指路。因此这类结果写成文档，由已记录的事实推出需要关注的情况与下一步，不推断记录里没有的原因。情况、动作的目的与动作需要的输入各有明确的含义，文档只呈现这些判断；必须由 Agent 决定的输入明确留待填写，填好之后才是可执行的调用。数据只有一份，程序读取结构化事实，Agent 阅读同一份事实的文档。

一种目的只描述一种效果，借用相近的目的会让类型正确而话说错。失败的原因可以照录，但它指向意图的哪一部分，由产生原因的地方给出；下一步据此写出要修什么，写不出"修好原因"这样的含糊话。

落点：内核的 `Cause` 与 `IntentPart`；宿主的 `Attention`、带目的的 `Step`、每个工具唯一的 `DevelopmentTool` 声明，以及它们的文档渲染。

## 协议

### 协议差异留在 Provider

只有多家协议共有的含义才进入规范类型；只属于一种协议的东西由 Provider 自己处理：thinking 签名与 reasoning 内容放进扩展字段，内核只把它回放给产生它的插件身份，不解释内容；服务端的会话状态只当作缓存，Log 中始终有完整的请求；服务端内置工具只允许效果限于那次补全的，会产生外部效果的必须作为 Enco 的工具接入，经过分派与结算。

图片输入具有跨协议的共同含义，进入规范消息；工具结果里的图片在线上协议中怎样表达，由 Provider 翻译。需要原样回放整份回复的协议，把整份内容放进自己的扩展，规范部分只从这份内容求出，内核无需理解签名的位置。

落点：`plan::resolve` 按来源代际的身份过滤扩展字段。

## 披露

### 工具本身就是认知负担

每多一个工具，模型每次请求都要多读一份定义，注意力也更分散。所以能用已有动词表达的操作不另立工具，常驻的只有救生集，其余按需披露。所有可披露的条目共用三个级别：L0 是名称加一句话，L1 是完整描述与 schema，L2 是细节与引用，按需读取。这是 Agent Skills 三级结构在工具、Skill、插件与远程能力上的推广；超长结果落盘、Brief 的引用都是 L2 的实例。

### 脚本中的调用仍逐个分派

模型可以把一组工具调用写成一段脚本，在宿主的沙箱中执行，唯一的能力是把调用交回本 Round 的分派。每个嵌套调用照常检查披露、经过策略点、按结局结算并记入 Log，结果只交给脚本，模型只看到脚本的输出。脚本整体是有副作用的调用，中断后记为 `unknown`，不重跑；结算列出已经开始的嵌套调用与它们的结局，模型据此不重复它们。

## 手册

### 一份文档，两种读者

面向模型的文本与开发文档出自同一段源码注释：第一段是 L0 摘要，正文是 L1，带标题的小节与链接是 L2；只面向开发者的内容写在 `# Implementation` 小节里，提取给模型时剔除。一段 WIT 的 `///` 因此同时流向插件 SDK 与宿主绑定的 rustdoc、CONTRACT.md 与运行时手册。两份手写的说明迟早会分歧，一份来源不会。

### 文档过期是构建失败

CONTRACT.md、内核与 SDK 的 API.md、插件 README 的生成区与各种目录都是生成物，提交入库，由 `--check` 门禁比对。公开 API 的变化因此以 API.md 的 diff 出现在评审中，手工改动生成区会被拦下；面向模型的文本中的上限由常量生成。文档是否过期不靠自觉。

落点：`cargo xtask docs --check`。

### 手册描述代际

源码手册描述 home 中的源码；运行时手册描述正在运行的代际，由制品中嵌入的 WIT 与以该代际的配置求出的声明生成，以代际为键。所以手册永远与实际执行的代码一致，并且按节点区分。代际现在是否健康、接到了谁、在哪些节点上准入，不属于手册，属于状态。
