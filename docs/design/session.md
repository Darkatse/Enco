# Session：记录、Round 与恢复

本专题展开"模型可见 ⟺ 已记录"与"Round 边界是唯一的安全点"。Session 是连续性所在：它的全部事实都在 Log 里，所以换代码、换机器、崩溃之后，都能只凭 Log 继续。

## Log

### Log 只记事实的骨架，条目永不删除

条目记下发生了什么、结局如何、模型看到了什么文本，以及正文的哈希；正文（计划、超长结果）存为内容寻址的 blob。Transcript、压缩与恢复都建立在条目上，所以条目永不删除，压缩只是让后面的计划用摘要代替一段历史。记录保留多久是主人的策略，作用于 blob：缺失的 blob 被明确报告，进入请求时按省略记入计划。更正与遗忘属于其他归属者（例如记忆），Log 不改写。

### 事实进 Log，叙述进计划

Event 的规范消息只是生产者当时写下的文字：主人的话、Agent 写的提醒内容、注册表写的通知。到达时间、来源、上一次工作为何停止，这些处境由 composer 叙述，逐字冻结在它的计划里。规范消息形态是持久格式，已记录的计划靠它解析 Log 引用；把叙述留在 core 之外，改措辞就只影响新的计划，不改变 Log 的格式。

### 位置由归属者分配，Store 只检查

每个 Session 有一个 actor，它是这个 Session 的 Log 唯一的写者，按 `(epoch, seq)` 分配位置。Store 在同一个事务里检查前置条件：Binding 指向本节点且 epoch 一致，位置紧接着已有的最大位置，每条 `EventConsumed` 都对应本 Session 一条内容相同的待消费 Inbox 行。"只有归属者在写"因此是可以验证的事实。前置条件不成立说明前提已被破坏，actor 记下原因并停止，不尝试修补。

Inbox 是这个归属者的邮箱：任何人都可以投递，投递以 Event ID 去重，所以客户端可以放心重发；消费只经上面的提交。消费把 Event 原样记进 `EventConsumed`，同一次提交把它移出 Inbox，所以 Inbox 只放尚未消费的输入，一条输入只存在一处；去重同时看 Inbox 与 Log。投递的顺序由提交序号决定，接收时间只用于展示。

落点：`Store::commit` 的前置条件。

## 请求

### 请求只有一个构造者，记录之后只解析记录

composer 输出 ContextPlan，内核校验后先把它写成 blob，再提交引用它的 `AttemptStarted`。此后重试、查看与审计都解析这一份记录，不重新组装，也不再读取上下文来源或工具定义；`enco inspect` 与 Round 共用同一个解析函数，看到的就是发出去的。已记录的请求在任何节点上解析为同一份内容，所以换机器继续时不需要重现上一次组装。

落点：Round 与 `Kernel::inspect` 共用 `plan::resolve`。

### Round 开始时钉住所见，Attempt 开始时选取代码

一个 Round 开始时钉住能力快照、profile 与主人的时区，模型在这一轮看到的世界不再改变。每次组装之前，再按最新的视图与本 Run 的 Log 选出 endpoint 与它背后的 Provider 代际：同一组合的重试复用已记录的计划；组合用尽或代码换了（例如自动回退），就重新选择并重新组装。composer 是纯函数，同样的输入得到同一份计划；换用 endpoint 时，它按新的预算与已记录的失败组装，上下文来源的采集结果保持不变。所以工具绑定以 Round 为单位，模型请求与适配器以 Attempt 为单位。

### Session 只记 profile 的名字

Session 选用哪个 profile 只记名字，每个 Round 开始时从活跃配置中解析。所以主人改一次配置并登记，就对所有用这个 profile 的 Session 生效；审计不受影响，每次 Attempt 记下的是实际用到的参数。仍有 Session 在用的 profile 不能被删掉或改名，登记这样的配置会被拒绝。

### 工具的结局按效果是否发生来定

结局回答的是"外部效果发生了没有"。所以 shell 命令以非零码退出仍是 `ok`：命令确实执行了，结果如实交给模型判断；超时或取消时进程已被终止，但可能已经部分执行，结局是 `unknown`；参数不合法或根本没能启动，才是 `failed`。

### 只读调用并行，其余按提出的顺序执行

一条回复中的工具调用由 Session actor 分批：相邻的只读调用为一批并发执行，幂等与有副作用的调用单独成批，按回复中的顺序逐批进行。归属者本来就是唯一的排序者，所以不另设锁：每批开始前一次提交这批调用的 Started，全部结束后按调用顺序结算，Log 的顺序只取决于回复本身，不取决于网络的快慢。获准执行的时点是每批准备的那一刻，此后发生的回退由下一批的准备拦下，与执行中的调用可以执行完是同一条规则。

### 结果能否使用，只在一处判断

回复既无正文也无工具调用、摘要为空，都由同一个函数判断，对所有协议相同。无法使用的结果照实记为完成（用量与扩展都留在 Log 中），这次 Attempt 按失败处理：换下一个 endpoint，全部用尽时 Round 失败，所以 Run 不会在什么也没交付时记为完成。结算、从 Log 推出用尽的组合与规范消息形态都调用这个函数，"无法使用"不另存：无法使用的回复照实留在 Log 中，但不进入对话。

## 中断与恢复

### 效果发生之前先记录

调用 Provider 之前提交 `AttemptStarted`，执行工具之前提交 `ToolCallStarted`。没有 Started 就意味着确定没有执行；有 Started 而没有结算，就是执行到一半被打断。恢复只凭这两类记录就能如实结算每一个调用，不需要猜测。

### 恢复如实结算被打断的工作，然后停下

恢复是 Log 的纯函数，启动时一次性提交：未结算的 Attempt 记为中断；开始了但没有结算的只读调用记为失败，其余记为 `unknown`；没有开始的调用记为未分派；Round 与 Run 以中断结束。下一步由看得到这些记录的一方决定：模型从工具结果和 composer 的说明中看到发生了什么，主人的下一条消息或 Inbox 中尚未消费的 Event 开启新的 Run。有副作用的调用因此不会被重新执行。

### 取消是发出信号，再等待静止

是否开始由内核决定，如何停止由被调用方负责。内核只在开始下一步之前检查取消，并在一个阶段结束后据此决定 Round 的结局；上下文来源与工具收到取消信号后停止等待，让已经开始的本地写入完成，静止之后才返回。唯一直接丢弃的是 Provider 请求，它不改变任何状态。取消沿监督树传播到子 Session。

## 入口

### 一个 home 只由一个进程持有

所有权由一把独占的文件锁表示，操作系统在进程退出时释放它，`kill -9` 也不例外；锁文件永不删除，否则新旧进程会各锁一个文件。socket 只是通信入口。锁在打开数据库与记忆索引之前取得，所以第二次启动不会触发恢复或索引重建。这是归属规则在节点上的应用。

### 外部输入只有一个入口，同一种操作只有一份语义

CLI 与渠道的输入都经内核的 `accept` 进入 Inbox；内部的归属者（Scheduler、注册表）在推进自身状态的同一个事务里投递 Event。主人的管理命令与 Agent 的工具调用同一组归属者的方法，例如取消定时、登记修改、遗忘记忆，所以一个操作只有一份语义。管理命令不经过模型；主人另有不经校验的机械恢复命令。

## 定时

### 定时是一串触发时刻，恰好一次来自单一事务

一次性提醒与周期定时是同一种东西，由主人或 Agent 创建，是内核的事实，不属于任何插件或代际。一次触发把定时的进度前移、把提醒投进 Inbox，二者在同一个事务里提交：提交之前崩溃，等于这次触发没有发生；提交之后，重启也不会再投递它。下一次触发从已记录的上一次推出，只在内存中保存。宕机期间错过的触发只补最近一次，并说明跳过了几次；模型从说明中看到触发时刻与到达时间，自己判断这次提醒是否还有用。

### 时间是主人的事实

时钟只提供 UTC 时刻；主人的时区写在配置的 `[owner]` 里，当地时间按它换算，所以同一个 Session 无论在哪个节点上，看到的时间都一样。主人改了时区，跟随主人时区的定时立即按新时区重新推算；向西改时区时，新时区当天已经过去的那次立即补发，与宕机后的补发是同一条规则。

## 多个 Session

### 分身就是 Session

多模型协作不需要新概念。需要另一套模型、composer 或上下文时，就委派给子 Session，父子构成 Erlang 式的监督树：子 Session 每结束一次 Run，内核就在同一次提交中给父 Session 发出一次回报；父 Session 只看到以 Event 到达的内容，父子只经 Event 交互，各自的 actor 始终能处理自己的 Inbox；取消沿树向下传播。同一个工作区同一时间只由一个 Session 写入，需要并行写就各用一个工作区，由父 Session 合并，例如用 git。指挥与专家、门面与幕后这类拓扑，都是 profile、Skill 与 composer 的组合。

### 主人确认是一种 Event 加一个等待中的命令

需要主人确认的命令进入等待状态，确认请求投到主人所有可达的界面与渠道；任一界面的应答写入 Log 后，命令继续执行。所有需要主人确认的事都走这一条路，不是新概念。
