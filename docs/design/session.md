# Session：记录、Round 与恢复

本专题展开"模型可见 ⟺ 已记录"与"Round 边界是唯一的安全点"。Session 是连续性所在：它的全部事实都在 Log 里，所以换代码、换机器、崩溃之后，都能只凭 Log 继续。

## Log

### Log 只记事实的骨架，条目永不删除

条目记下发生了什么、结局如何、模型看到了什么内容，以及正文的哈希；计划以完整内容的哈希寻址，存入库中的共享记录；超长结果、图片与发给主人的文件存为内容寻址的 blob。图片与文件的引用属于 Enco 的库，工作目录中文件以后的改变不影响已记录的内容。Transcript、压缩与恢复都建立在条目上，所以条目永不删除，压缩与回溯都只改变之后的计划看到哪一段历史。记录保留多久是主人的策略，作用于计划记录、映射证据与 blob；省略必须连同原因写进计划，已选入请求的内容读不出来则失败。更正与遗忘属于其他归属者（例如记忆），Log 不改写。

### 事实进 Log，叙述进计划

Event 的规范消息只是生产者当时交出的内容：交互式消息自己的文字、它引用的图片与自己的图片、Agent 写的提醒内容、注册表写的通知。引用的文字及关系由 composer 叙述，图片仍随同一条 Log 引用进入请求。到达时间、来源、上一次工作为何停止，这些处境由 composer 叙述，逐字冻结在它的计划里。规范消息形态是持久格式，已记录的计划靠它解析 Log 引用；把叙述留在 core 之外，改措辞就只影响新的计划，不改变 Log 的格式。

### 回溯移动对话的引用，不改写 Log

当前的对话是 Log 的函数：最近一次回溯的目标之前的 Log，接上这条回溯及其后的条目，多次回溯按同样的规则递归求出。回溯本身只是一条事实，主人的命令被消费时记下的 `EventConsumed` 指向主人选中的位置。被离开的条目仍在 Log 中，检视与恢复照常，回到被离开的那一段同样成立，几条线之间可以来回；Session 的身份不变，分叉成新 Session 要跨两份 Log 拼历史、迁移路由与 Binding，只有两条线需要同时运行时才值得。由历史派生的一切都按当前的对话求出：Transcript、压缩、上一份回复计划、记忆召回所看的最新输入与检视。所以目标在某次压缩之前就回到完整的历史，默认 composer 从目标当时的计划接着追加。

回溯的单位是一条输入或一个 Round 的结束：指向输入时对话保留到这条输入，随后开始一个 Run 重新回答它；指向 Agent 的消息时保留到产生它的 Round 结束。从一条回复中间切开，历史里会留下没有结果的工具调用。目标也可以是开头：清空就是回溯到开头，被离开的条目仍在 Log 中，所以清空可以复原。回溯是在 Run 之间生效的命令（见「命令在 Run 之间生效」），此前送达、尚未处理的输入落在被离开的部分。只有主人能发起，Agent 没有这个工具：回退自己的对话没有清楚的用途，还会抹掉它看到过的内容。

对话之外的状态不回退：文件与外部效果不归 Enco，记忆、定时与插件代际各有归属者，Log 不替它们做主。回溯不带文字，处境由 composer 叙述，并提醒模型对话之外的状态可能与对话对不上。

落点：内核的 `transcript::conversation`；`Kernel::accept` 检查目标并取消进行中的 Run。

### 读 Log 只读到读取依赖的事实，actor 只常驻这段尾部

每次读 Log 都从最新往回找内核自己记下的某条事实，例如本 Run 的开头、对话中最近一次压缩、上一次回复，更早的条目不影响结果。所以读多远只由 Log 中的事实决定，不看 composer，也不看字节数，当前的对话仍是 Log 的函数：压缩是内核检查、执行并记下的事实，换了 composer 照样投影；从不压缩的 composer，读到的就是整份 Log，与它每轮的输入一样大。actor 每个 Round 都读，于是把这段尾部留在内存里作为库的缓存，在它上面求值与在整份 Log 上相同；命令偶尔才读，往回读完即弃。追加的条目只让读的位置往后走，只有回溯会让它往回走，所以消费回溯之后按同样的规则从库里重新读。按位置取一条是点查，不是往回读。父看子的状态要同时读待消费的输入与 Log，消费与追加在同一个事务里提交，所以两者也在同一个事务里读，分两次读会拼出从未成立的状态。

落点：每个读取旁边的 `_reach`；内核的 `reach::read_back` 与 `LogTail`；Store 的 `log_before`、`log_entry` 与 `child_state`。

### 位置由归属者分配，Store 只检查

每个 Session 有一个 actor，它是这个 Session 的 Log 唯一的写者，按 `(epoch, seq)` 分配位置。Store 在同一个事务里检查前置条件：Binding 指向本节点且 epoch 一致，位置紧接着已有的最大位置，每条 `EventConsumed` 都对应本 Session 一条内容相同的待消费 Inbox 行。"只有归属者在写"因此是可以验证的事实。前置条件不成立说明前提已被破坏，actor 记下原因并停止，不尝试修补。

Inbox 是这个归属者的邮箱：任何人都可以投递，投递以 Event ID 去重，所以客户端可以放心重发；消费只经上面的提交。消费把 Event 原样记进 `EventConsumed`，同一次提交把它移出 Inbox，所以 Inbox 只放尚未消费的输入，一条输入只存在一处；去重同时看 Inbox 与 Log。投递的顺序由提交序号决定，接收时间只用于展示。

落点：`Store::commit` 的前置条件。

## 请求

### 请求只有一个构造者，记录之后只解析记录

composer 输出 ContextPlan，内核校验并绑定工具定义后，把计划与引用它的 `AttemptStarted` 在同一事务中提交。此后重试、查看与审计都解析这一份记录，不重新组装，也不再读取上下文来源或工具定义；`enco inspect` 与 Round 共用同一个解析函数，看到的就是发出去的。已记录的请求在任何节点上解析为同一份内容，所以换机器继续时不需要重现上一次组装。

图片以内容引用进入计划与查看结果，字节在冻结请求时由内核读出，同一请求的重试沿用这些字节。内容读不出来是请求本身的失败，发生在调用 Provider 之前，因而不影响 Provider 的健康。

落点：Round 与 `Kernel::inspect` 共用 `plan::resolve`。

### Round 开始时钉住所见，Attempt 开始时选取代码

一个 Round 开始时钉住能力快照、profile、工作目录与主人的时区，模型在这一轮看到的世界不再改变。每次组装之前，再按最新的视图选取 composer，并按本 Run 的 Log 选出 endpoint 与它背后的 Provider 代际：同一组合的重试复用已记录的计划；组合用尽、代码换了（例如自动回退）或服务以超长拒绝，就重新选择并重新组装。组合的事实（是否用尽、测出的用量、被拒的计划）都从 Log 求出，选择时挂到这个组合服务的每个目标上，不在内存里另存。composer 的选项在所选代际上绑定，失配只让这项使用不可用。composer 是纯函数，相同代际、Round 与输入得到同一份计划；换用 endpoint 时，它按新的预算与已记录的失败组装，上下文来源的采集结果保持不变。所以工具绑定以 Round 为单位，模型请求与适配器以 Attempt 为单位。

### 公开聊天与私人助理分属不同的 Session

私人助理带着主人的全部能力与私事；群是公开的场合，回复人人看得到，打开之后别人也能对它说话。一个 Session 的历史、计划与续轮是同一个上下文，能力与私事只能按整个 Session 划分。所以群使用新建的 Session，由 profile 声明可用工具与是否采集主人的上下文；范围在 Round 开始时固定，安全模式只在其上收窄，救生要求与工具范围在登记时一致。主人显式改变一个 Session 的 profile，是改变它此后的策略，已有的历史不变。

私有与公开由事实决定：一对一的会话天然私有；协议说不清谁在场的空间（realm，例如 Discord 的服务器）由主人声明是否私有。私有的会话中，主人与 bot 之间的那一个对话挂到 `main`，主人在 realm 里另开的对话各是一个根 Session，带主人的上下文（渠道专题「会话归哪个 Session，由私有与 realm 决定」）。

### Session 只记 profile 的名字

Session 选用哪个 profile 只记名字，每个 Round 开始时从活跃配置中解析。所以主人改一次配置并登记，就对所有用这个 profile 的 Session 生效；审计不受影响，每次 Attempt 记下的是实际用到的参数。仍有未归档的 Session 在用的 profile 不能被删掉或改名，登记这样的配置会被拒绝。角色说明也按这个名字选择，同一角色的 Session 共用做事的方法，各自保留自己的历史与工作目录。

### 工作目录是 Session 的事实，不是配置

角色可以复用，而每个 Session 在哪里工作各不相同；并行委派时，同一个角色也可能同时使用几个目录。把目录放进 profile 会一起搬动所有使用者；按 Session 写配置又会让运行时创建的 Session 与手工配置成为两个事实来源。因此工作目录与所选 profile 一样，是 Session 当前的引用：修改从下一个 Round 生效，进行中的 Round 不变，每轮使用的值记入 Log。这样 Session 的工作位置也能只凭记录解释。

### 工作目录是默认位置，在使用时检查

Agent 有 shell，工作目录不是权限边界，也不承诺独占。目录随时可能被删除、卸载或暂时不可达，设置时检查不能保证使用时可用；先设目录再准备内容也是正当用法。因此设置只固定节点与绝对路径，原生工具仅在解析相对路径或使用默认目录时检查可用性，绝对路径的调用不受它影响。不可用就明确失败，不创建工作目录，也不自动回退，否则一次工作可能被悄悄写散到两处。

工作目录由主人设置；Agent 可以用绝对路径或 shell 的单次目录参数在别处工作，不另设修改自身工作目录的工具。需要并行写入时由父 Session 各给一个目录，而不是由内核承诺隔离。

落点：core 的 `WorkingDir`；原生工具共用的 `local_working_dir`。

### 回复去向由输入自己决定，交互式就是有回复去处

Event 的来源写明它与接收者的关系：CLI、渠道的会话、委派它的父、它委派的子、Scheduler 与注册表。方向在生产时就已确定：委派一定向下，回报一定向上，父关系在创建时固定，所以判断只看 Event 自己，不必去查谁是父。一条输入的回复去处只由一个函数按来源与种类穷尽匹配：CLI、某个连接的某个会话或者父；提醒、通知、子的回报与叫停没有。交互式就是有回复去处；Session 的回复去向是最近一条有回复去处的输入的那一个，不依赖连接。宿主的路由、向父的投递、子任务状态与 composer 读到的交互式都出自它，新增来源时编译器要求先决定它。

落点：core 的 `Event::reply_destination`。

### 默认说话，没有输入在等待回音时才可以沉默

默认回复使漏掉沉默表现为一条多余但可见的消息，而不是静默丢失本该送达的提醒。交互式输入的发送者在等待回音。回音是了结等待的交付，即以回复结束的 Round，或没有完成的 Run 的结局；最近一次回音之后消费的交互式输入，在等待回音。这是 Session 的事实，不按 Run 划分：前一个 Round 已经回复主人的消息、下一个 Round 只取走提醒时可以沉默；回溯本身是交互式输入，在 Run 开始前被消费、其后尚无回音，因此不需特判。父的子任务状态中「在等待它的回音」是同一个事实；消费过的叫停使等待作废。

沉默是由内核在分派准备时检查条件的一种回复结局，不改变 Run 的推进；随附文字留在 Log 中作为笔记。每条输入的叙述只讲它自己要不要回答，逐字冻结在计划中；有没有输入在等待回音只由内核从 Log 求出。什么值得打扰主人分属三层：工具说明讲机制，出厂 composer 给默认标准，主人在常驻说明中定自己的门槛。

### 工具的结局按效果是否发生来定

结局回答的是"外部效果发生了没有"。所以 shell 命令以非零码退出仍是 `ok`：命令确实执行了，结果如实交给模型判断；超时或取消时进程已被终止，但可能已经部分执行，结局是 `unknown`；参数不合法或根本没能启动，才是 `failed`。

### 只读调用并行，其余按提出的顺序执行

一条回复中的工具调用由 Session actor 分批：相邻的只读调用为一批并发执行，幂等与有副作用的调用单独成批，按回复中的顺序逐批进行。归属者本来就是唯一的排序者，所以不另设锁：每批开始前一次提交这批调用的 Started，全部结束后按调用顺序结算，Log 的顺序只取决于回复本身，不取决于网络的快慢。获准执行的时点是每批准备的那一刻，此后发生的回退由下一批的准备拦下，与执行中的调用可以执行完是同一条规则。

### 结果能否使用，只在一处判断

回复既无正文也无工具调用、摘要为空或停在输出上限，都由同一个函数判断，对所有协议相同；停在上限的摘要没有写完，却会替换它本该概括的历史。无法使用的结果照实记为完成（用量与扩展都留在 Log 中），这次 Attempt 按失败处理：换下一个 endpoint，全部用尽时 Round 失败，所以 Run 不会在什么也没交付时记为完成。结算、从 Log 推出用尽的组合与规范消息形态都调用这个函数，"无法使用"不另存：无法使用的回复照实留在 Log 中，但不进入对话。

服务以超长拒绝请求也不是无法使用的结果。请求没有被执行，按效果它属于 `failed`，只是带着服务说出的事实，所以单独成为一种结局。毛病在这份请求太大，不在组合，所以它不让组合用尽：同一组合缩小之后再发（上下文专题「被拒的请求是一份测量，缩小只省略已经结束的 Run」）。缩小是否真的变小没有结构上可量的进展，所以每个 Round 的重发有上限，用完时 Round 带着服务的原话失败。

## 中断与恢复

### 效果发生之前先记录

调用 Provider 之前提交 `AttemptStarted`，执行工具之前提交 `ToolCallStarted`。没有 Started 就意味着确定没有执行；有 Started 而没有结算，就是执行到一半被打断。恢复只凭这两类记录就能如实结算每一个调用，不需要猜测。服务的回复也在解读之前记下，结算引用这份原文，所以每次结算都能追溯到服务的原话。

### 恢复如实结算被打断的工作，然后停下

恢复是 Log 的纯函数，启动时一次性提交：未结算的 Attempt 记为中断；开始了但没有结算的只读调用记为失败，其余记为 `unknown`；没有开始的调用记为未分派；Round 与 Run 以中断结束。下一步由看得到这些记录的一方决定：模型从工具结果和 composer 的说明中看到发生了什么，主人的下一条消息或 Inbox 中尚未消费的 Event 开启新的 Run。有副作用的调用因此不会被重新执行。

只读指除了随结算记下的内容，没有别的效果；中断后可以重试。发消息属于这种调用，交出的内容随调用结算一起记下，外部效果由渠道投递另行结算。

### 命令在 Run 之间生效

命令关于对话，不是要回答的输入，都在两个 Run 之间被消费。回溯与叫停还取代此前的输入：接纳时向当前 Run 发出信号，Run 在下一个边界停下；Session 在两个 Run 之间连同此前送达、尚未处理的输入一起消费它，这些输入不被回答。两者只差消费之后：回溯指向一条输入时开始一个 Run 回答它，叫停什么也不开始。被命令打断的 Run 如实记下原因（`Halted`、`Backtracked`），与取消分开；这些结局与其他没有完成的结局一样交给回复去向，由叙述说明发生了什么，交付不为哪一种开例外。叫停不是交互式的，不移动回复去向。

压缩请求两者都不做。上下文的长度只在组装请求时才有意义：在下一次组装之前压缩与立即压缩，模型看到的每一份请求都相同，所以它不打断正在进行的任务，也不取代此前的输入，由下一个 Run 的第一个 Round 兑现。忙时也不拒绝：宿主看到的空闲只是某一刻的快照，Run 之间消费的规则本来就在，拒绝只多出一次要主人重试的失败。

落点：命令的分类在 core 的 `EventBody`（`is_command`、`supersedes_inputs`）；actor 的 `command_end` 与 Run 之间的消费共用一条路径。

### 取消是发出信号，再等待静止

是否开始由内核决定，如何停止由被调用方负责。内核只在开始下一步之前检查取消，并在一个阶段结束后据此决定 Round 的结局；上下文来源与工具收到取消信号后停止等待，让已经开始的本地写入完成，静止之后才返回。Provider 请求与纯 composer 调用不改变任何状态，取消时直接丢弃等待。取消只停一个 Run，子 Session 的作用域是父 Session，照常运行。

## 入口

### 一个 home 只由一个进程持有

所有权由一把独占的文件锁表示，操作系统在进程退出时释放它，`kill -9` 也不例外；锁文件永不删除，否则新旧进程会各锁一个文件。socket 只是通信入口。锁在打开数据库与记忆索引之前取得，所以第二次启动不会触发恢复或索引重建。这是归属规则在节点上的应用。

### 外部输入只有一个入口，同一种操作只有一份语义

CLI 与渠道的输入都经内核的 `accept` 进入 Inbox；内部的归属者（Scheduler、注册表）在推进自身状态的同一个事务里投递 Event。主人的管理命令与 Agent 的工具调用同一组归属者的方法，例如取消定时、登记修改、遗忘记忆，所以一个操作只有一份语义。管理命令不经过模型；主人另有不经校验的机械恢复命令。

## 定时

### 定时是一串触发时刻，恰好一次来自单一事务

一次性提醒与周期定时是同一种东西，由主人或 Agent 创建，是内核的事实，不属于任何插件或代际。一次触发把定时的进度前移、把提醒投进 Inbox，二者在同一个事务里提交：提交之前崩溃，等于这次触发没有发生；提交之后，重启也不会再投递它。下一次触发从已记录的上一次推出，只在内存中保存。宕机期间错过的触发只补最近一次，并说明跳过了几次；模型从说明中看到触发时刻与到达时间，自己判断这次提醒是否还有用。

### 时间是主人的事实

时钟只提供 UTC 时刻；主人的时区写在配置的 `[owner]` 里，当地时间按它换算，所以同一个 Session 无论在哪个节点上，看到的时间都一样。主人改了时区，跟随主人时区的定时立即按新时区重新推算；向西改时区时，新时区当天已经过去的那次立即补发，与宕机后的补发是同一条规则。

## 委派

### 子 Agent 就是 Session，内核在树上只做三件事

需要另一套模型、composer 或上下文时，委派给子 Session：它有身份、Log、Inbox 与 actor，持久、恢复、漫游、检视与安全模式全部照常。父关系在创建时固定，子的全名是父全名下的一段路径，唯一性由结构保证。内核在树上只记谱系、把子交给父的内容投递上去、把叫停传下去；重试、改派、放弃与合并结果都是父中模型的判断（总纲「自动机制只做有证据的事」），按策略重启这类 supervisor 的职责已由健康门控、安全模式与恢复承担。指挥与专家、门面与幕后这类拓扑，都是 profile、Skill 与 composer 的组合。

### 委派是转移，不是调用

委派在子的输入被接纳时就返回，子交出的内容之后作为父的输入到达。阻塞的委派会让父的 Round 挂起：漫游、换代与压缩都要等这个唯一的安全点，主人的新消息也没人消费；子本来就要活得比父的 Run 长。代价是问一个问题也要多一个父 Round，前缀缓存让它不贵；有界等待以后可以在 Round 边界加上。新的子从空的 Log 开始：委派常为了更小、更干净的上下文，最适合写任务的是父的模型。

### 向下显式发送，向上沿回复去向，父是子的壳

子交给回复去向的内容与渠道求出的相同：回复、`message_send` 的消息、没有完成的 Run 的结局，求出它们的函数只有一个。回复去向是父时，每一项成为父 Inbox 中的一条 Event，与产生它的条目在同一次提交中写入，所以恰好一次。向上不另设工具：父恰好是回复去向时那是第二条路；按回复去向发，门面模式下幕后的消息到达门面，主人接管之后自然发给主人。子说的话与它的 Run 怎样结束分成两种 Event，免得把子没说过的话算在它头上。兄弟之间与跨树没有通道，自动的流动只向上，循环必须有人显式向下发送。

### 投给别的 Session 只有一个机制

Session 的一次提交可以带上投给其他 Session 的 Event，Store 在同一个事务里经 Inbox 唯一的写入函数写入，并检查前置条件：目标没有归档，本 Session 没有待处理的叫停。向上的回报、向下的委派与跨节点的 outbox 都是它。前置条件不成立时，回复与结局照常记入自己的 Log，只是不投递；以投递为效果的调用结算为失败。

落点：`Commit` 带上的投递，由 Store 的提交事务检查。

### 委派的检查在提交时按顺序做

同一批只读调用并发执行、按调用顺序结算，所以委派执行时只解析参数；子是否存在、profile 与工作目录是否一致、本 Session 是否有待处理的叫停，都在结算的事务中检查，一条回复里先创建再追加，第二条看得到第一条。检查不成立是这次调用的结果：事务什么也不写，调用结算为失败并说明原因。名字就是地址，创建参数只在创建时生效。

### 委托人由谱系决定，主人也可以直接对话

来自父的消息是交互式输入，回复回到父；来自子的输入与提醒同类，不移动回复去向、不要求回答，否则根 Session 收到回报之后，会把给主人的回复发给子。主人在子 Session 中说话就是接管：回复留给主人，父下次发来消息时回到父；父不被唤醒，从子任务状态得知主人接手。子只由它的父创建；主人可以切到已有的子，权限仍由谱系决定。

### 权限只能沿委派收窄

有效权限是自己 profile 的权限与父的有效权限之交，每个 Round 从谱系与活跃配置求出（总纲「状态是事实的函数」）；祖先的 profile 解析不了时这一轮失败，不按缺省放宽。工具与主人的上下文都取交集，深度达到上限时委派的工具不在能力里，安全模式只在其上再收窄。工作目录不是权限，不参与收窄。

### 名额是节点的运行时资源

被限制的是本节点同时执行的子 Session 的 Run。「正在一个 Run 中」归 actor，在 Log 中的痕迹是没有结束的 Run，重启后天然为零，所以名额由内核这一个归属者持有，不入库；存一份计数就是会与 Log 分歧的第二个来源。上限在每次准入时读取，执行中的 Run 不被抢占。委派是转移，持有名额的一方从不等待另一个名额，所以不会死锁。

### 叫停沿子树向下，不叫醒任何人

叫停在一个事务中按谱系求出子树，把叫停投进其中每个 Session 的 Inbox，再等静止，即子树中没有待处理的叫停：叫停只在两个 Run 之间被消费，那时它打断的 Run 已经结束，不另设标志。被叫停的 Session 不向任何 Session 交出结局：发起的一方已经知道，要通知别人正是叫停想停下的工作。这由「投给别的 Session 只有一个机制」的前置条件兑现，不另设规则。一个事务写下整棵子树只在单库时成立，跨节点时逐级传递（多节点专题）。

### 不需要的 Session 归档，不删除

Log 永不删除，归档只让 Session 不再接收输入：在一个事务中叫停子树并记下归档时间，再等静止、停掉 actor；先记下再等，静止与记下之间就没有窗口让新的输入开始 Run。约束只在 Inbox 唯一的写入处，各归属者都经它提交输入，它看到已归档就不写，由归属者按自己的语义处理。定时提醒随之失效，这由事实求出：提醒处于有效状态、它的 Session 没有归档才有效，归档不改提醒。名字只在未归档的 Session 之间唯一，可以给新身份；按名字只找未归档的，按 ID 照常读出历史。

## 确认

### 主人确认是一种 Event 加一个等待中的命令

需要主人确认的命令进入等待状态，确认请求投到主人所有可达的界面与渠道；任一界面的应答写入 Log 后，命令继续执行。所有需要主人确认的事都走这一条路，不是新概念。
