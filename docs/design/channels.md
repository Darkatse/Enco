# 渠道

本专题展开"归属与转移"在渠道上的应用。渠道是 Enco 与外界之间最容易出错的地方：连接会断，消息会重复，发出去的请求可能没有回音。这里的判断让每一条入站消息恰好被接纳一次，让每一次出站投递都有一个如实的结局。

### 聊天是壳，Session 属于 Enco

渠道中的聊天只是界面位置。一个聊天同一时刻挂在一个 Session 上，多个聊天可以挂在同一个 Session 上；新聊天默认挂到 `main`，主人用命令切换或新建。命令不经过模型：写法由适配器识别，含义由宿主执行。只有主人的账号能驱动 Session，发送者由宿主在读取时按配置核对，附件只为已授权的输入取回；其他人的消息只推进协议状态，不进入模型。

### 连接的归属者持有路由，适配器只解释协议

每个连接有一个归属者，它持有协议状态、聊天与 Session 的映射、入站与出站游标。适配器处理一条更新，返回新的协议状态与解析出的输入，自己不写任何状态；归属者把这些与 Event 一起经内核的 `accept` 一次提交。所以游标不会跑在已接纳的消息前面，提交失败时什么都没写，这条更新下一次还会取回，既不丢失，也不会处理两次。适配器换成 Wasm 插件时，这一层机制不变。

附件下载是读取工作，不占用连接的归属者，因此慢下载不阻塞已有回复的投递。内容先存入 Enco 的库，再随 Event 提交引用；没有提交的内容至多成为无人引用的 blob。无法查看的附件也是主人输入的事实，随消息记录原因，由 composer 告知模型。

落点：`channel::Adapter` 只返回转移，提交只经 `Kernel::accept`。

### 投递是壳在渲染 Log

归属者以出站游标跟随它送过 Event 的每个 Session，与入站游标对称；订阅只用来唤醒，内容一律从 Log 读取，订阅积压丢了消息也从游标重新读。Agent 交给主人的内容有两个生产者：Round 的回复与 `message_send` 记下的消息，共用路由与投递结算；消息一经结算就投递，回复等 Round 以回复结束才投递。它们发往该 Session 最近一条交互式输入的来源，提醒触发的 Run 因此发往主人最近说话的地方。每个壳读同一份 Log 得出同一个结论，彼此不需要协调；CLI 显示 Run 结局的方式与渠道相同。

出站内容是 Markdown 文字加可选的文件，由各生成方按 Markdown 书写，映射到渠道协议是适配器的事。协议能原生显示、并满足其成文限制的就原生显示，其余按原样文件发送。

### 每次逻辑投递恰好一条如实的结算

投递之前先记下"正在投递"，结局（`ok`、`failed` 或 `unknown`）与游标的推进在同一次提交中写入。请求确定没有到达的才重试；已经发出、结果无法确认的记为 `unknown`，不自动重发，5xx 也算在内，因为网关可能在转发之后才出错。启动时发现上次留下的"正在投递"，说明进程在发送途中停止，同样记为 `unknown`。结算只引用 Session 与 Log 位置，不复制正文；一次失败结算之后继续处理后面的消息，不会卡住连接。

### 停止是取消轮询，再等在途的投递结算

停止渠道时，先取消轮询与订阅，丢弃长轮询的请求是安全的，它没有外部效果；然后不再开始新的投递，等正在发送的那一次完成并结算，已经发出的请求不能丢弃。停止期间产生的回复，下次启动时从 Log 补发。

### 渠道换代承诺的是可恢复

替换渠道代码时默认在事件边界切换回调；新代码接续不了当前的协议状态，就按协议重连并补收，例如 Telegram 用 offset，Discord 用 RESUME。一次替换可能短暂断线，其间的消息由补收取回。渠道是视图的函数：配置变了，旧连接一退出就按最新的表启动，即使旧连接的结算失败了，因为它已经静止；只有归属任务没有正常退出、无法证明静止时才停下并报错。

### 渠道的故障只停下渠道

token 无效、连接状态损坏或配置解析不了时，渠道停止，原因写进 `enco status`，CLI 与其他 Session 照常工作。网络错误按退避重试，守护进程照常运行。
