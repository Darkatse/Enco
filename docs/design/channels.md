# 渠道

本专题展开"归属与转移"在渠道上的应用。渠道是 Enco 与外界之间最容易出错的地方：连接会断，消息会重复，发出去的请求可能没有回音。这里的判断让每一条入站消息恰好被接纳一次，让每一次出站投递都有一个如实的结局。

### 聊天是壳，Session 属于 Enco

渠道中的聊天只是界面位置，Session 的历史与策略由 Enco 持有。私聊默认挂到 `main`，主人可以切换或新建；群各自新建 Session，边界的理由见 Session 专题「公开聊天与私人助理分属不同的 Session」。名字相同不足以认领一份历史，因此群只认自己创建并记下的 Session 身份。

群里的话多数说给其他人听，只有发给 bot 的消息才驱动 Session，默认只认主人；主人可以对一个群开放成员提问。是不是发给 bot 由映射器解释，是不是主人由宿主在接纳时核对并记下，后来的配置变化不重写过去的身份。命令不经过模型，写法由映射器识别，含义与授权由宿主掌握。协议要求应答的输入，收到即确认，接纳之后回执：期限只关心收到，回执却要等接纳。这类输入的发送者无权时应答一句拒绝；不要求应答的命令照旧静默忽略，旁人无法借 bot 刷屏。此前的消息可以按主人设置的范围随提问交出，作为带发送者的引用；它们不单独驱动 Session，附件也只说明是什么。

### 连接的归属者持有路由，映射器只解释协议

每个账号只有一个连接归属者，它持有协议状态、聊天与 Session 的关系、前文与出站进度。配置名只是入口，协议与账号才标识这些事实：换密钥或改名不应失去历史，换账号也不应继承旧账号的路由。账号身份由映射器解释，宿主不从凭证格式推导身份。

映射器是纯的协议状态机，宿主持有传输、计时与凭证，照它的要求执行，自己不解释心跳、续接这类协议语义。所以协议的每一个判断都能在记录上重放，宿主也不会按协议分叉。外部内容先记录完整调用，每条记录自带当时的协议状态；计时到期不是外部内容。

收到与接纳分开：长连接不能为慢操作停下，否则心跳与交互的期限都会错过；业务效果却仍由唯一的归属者按顺序接纳。提交的协议状态从不越过尚未接纳的消息，所以重启后从已接纳处续接。按请求读取的协议，要等上一批消息接纳之后再读，因为新的读取会确认并删除上一批。

接纳键属于消息，只推进协议进度的事件没有键；效果只跟随新接纳的键，重发不重做命令或前文。键按协议的承诺使用：Telegram 在一周没有更新之后随机选择更新编号，与旧键相同的概率可以忽略。补收也以协议的承诺为限：Telegram 保留未确认的更新，Discord 只在会话仍可续接时补发，OneBot 的正向 WebSocket 不补收断线期间的事件。

附件下载是读取工作，不占用连接的归属者，因此慢下载不阻塞已有回复的投递。内容先存入 Enco 的库，再随 Event 提交引用；没有提交的内容至多成为无人引用的 blob。无法查看的附件也是输入的事实，随消息记录原因，由 composer 告知模型。取自外部内容的附件地址与映射器构造的请求分开：它只到映射器声明的来源，不带凭证，因为内容不能在持有凭证的服务上选择路径；落在别处时只是无法查看，不是映射器的过错，否则一条外链图片就能让映射器的代际回退。

落点：`ChannelAdapter::receive` 按顺序交出读取的结果；连接归属者经 `Kernel::accept` 提交消息、状态与输入。

### 投递是壳在渲染 Log

归属者以出站游标跟随它送过 Event 的每个 Session，与入站游标对称；订阅只用来唤醒，内容一律从 Log 读取，订阅积压丢了消息也从游标重新读。Agent 交给主人的内容有两个生产者：Round 的回复与 `message_send` 记下的消息，共用路由与投递结算；消息一经结算就投递，回复等 Round 以回复结束才投递。它们发往该 Session 最近一条交互式输入的来源，提醒触发的 Run 因此发往主人最近说话的地方。每个壳读同一份 Log 得出同一个结论，彼此不需要协调；CLI 显示 Run 结局的方式与渠道相同。

出站内容是 Markdown 文字加可选的文件，由各生成方按 Markdown 书写，映射到渠道协议是映射器的事。协议能原生显示、并满足其成文限制的就原生显示，其余按原样文件发送。一条内容排成几条协议消息同样属于版式：文本可以切段或改成文件，文件也可能独立发送。宿主只要求排版结果至少一条、每条非空，内容完整由映射器的行为核对承担。

发送节奏取决于协议所在的平台，等待却需要宿主的时钟。映射器声明节奏，连接让投递与普通命令回执共用它；这使所有消息遵循同一条发送路径，而协议以外的读取与进度提示保持独立。

进度卡是 Run 在对话里的即时视图，与投递共用投影规则，各有游标：观察不等发送，所以大文件上传不拖住进度；删除跟在最终回复之后。卡上只有工具名与结局，因为公开对话里人人看得到。每个 Run 只尝试创建一次，结局随连接状态交接，失败或未知就不再建，所以不会出现重复的卡；进程恰好停在远端创建与本地提交之间时留下的卡，按 60/95 接受。进度卡的失败不影响回复。

### 每次逻辑投递恰好一条如实的结算

投递之前先记下"正在投递"，结局（`ok`、`failed` 或 `unknown`）与游标的推进在同一次提交中写入。请求确定没有到达的才重试；已经发出、结果无法确认的记为 `unknown`，不自动重发，5xx 也算在内，因为网关可能在转发之后才出错。启动时发现上次留下的"正在投递"，说明进程在发送途中停止，同样记为 `unknown`。结算只引用 Session 与 Log 位置，不复制正文；一次失败结算之后继续处理后面的消息，不会卡住连接。

### 停止先发出取消，再等待在途的效果静止

停止渠道时，先取消读取与订阅，不再开始新的投递；确认、应答、进度卡和在途发送都等待结果，已发出的请求不丢弃。WebSocket 按映射器给出的关闭方式结束，使协议可以保留续接所需的会话。停止期间产生的回复，下次启动时从 Log 补发。

### 渠道换代承诺的是可恢复

替换渠道代码时默认在事件边界切换回调；新代码接续不了当前的协议状态，就按协议重连并补收，例如 Telegram 用 offset，Discord 用 RESUME。一次替换可能短暂断线，其间的消息由补收取回。渠道是视图的函数：配置或所用映射器的代际变了，旧连接一退出就按最新的视图启动，即使旧连接的结算失败了，因为它已经静止；只有归属任务没有正常退出、无法证明静止时才停下并报错。

### 渠道的故障只停下渠道

token 无效、连接状态损坏或配置解析不了时，渠道停止，原因写进 `enco status`，CLI 与其他 Session 照常工作。网络错误按退避重试，打开连接时同样如此。一个协议端尚未就绪，不应拖住其他连接或登记变化；打开的结果交回监督者，由它统一接纳账号，运行时的归属仍保持唯一。守护进程照常运行。
