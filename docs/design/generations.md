# 代际：自我修改

本专题展开"运行中的行为 ⟺ 已登记的代际"。能修改自己是 Enco 的第一个动机，也是它最危险的能力：一次坏的修改，可能让 Agent 失去修复自己的能力。这里的每个判断都服务于同一件事：经正式路径的修改都可以验证、可以撤销，而恢复从不依赖被修改的东西。

## 登记

### 插件与配置是同一种代际

Agent 对自身的修改，不论改的是插件代码、插件配置，还是接线与内核配置，都会改变下一刻运行的行为，也都可能让它失去修复自己的能力。所以它们遵循同一套规则：登记、提交、生效、重启、撤销与不一致的报告都相同。两种代际共用一个全局递增的编号，一个编号就能定位任何代际，Log 中的代码引用因此不依赖插件名，也不依赖代际的种类。

两种代际的差异只来自事实本身：插件代码的问题到运行时才暴露，所以插件代际要试用；接线在登记时就能用真实调用验证，所以配置代际登记即为健康；出厂的只有插件，所以安全模式只换插件代际。

落点：`Registry` 是两种代际唯一的提交者。

### 代际是内容，声明每次从内容求出

注册表只保存内容：插件代际是制品与设置（插件配置与密钥映射），配置代际是配置文档。声明，即导出的接口、凭证与接线，由声明函数从内容求出。插件的声明函数是它自己的 `describe`，随制品固定；配置的声明函数是各张表的归属者，属于宿主的代码。宿主升级之后，存下来的旧声明会与重新求出的值并存，成为第二个事实来源，所以声明只在登记、加载与还原时求出，从不入库。注册表因此不解释内容，它不认识任何一张表的含义，只按声明检查准入。

落点：库中不存声明；`ActiveConfig` 的声明字段私有于注册表，它只能由一次求值构造（`Declaration::into_active`）。

### 判断意图是否改变，只与已登记的意图比较

意图分三层：主人与 Agent 编辑的工作区，被接纳的已登记意图，以及运行中的代际。运行中的代际随登记改变，也随机械恢复改变；拿工作区与它比较，一次回退就会被随后的无关登记撤销。意图变了就登记，与运行中的内容是否相同无关：主人回退之后，把文件改成与运行一致，也是一次真实的意图变化。

意图的单位就是运行部件的单位：一个插件目录、一个插件的配置节、整份配置文档。所以插件设置只在它的配置节改变时产生新代际。代价：主人回退过配置之后，对配置文档的任何修改都接纳整份文档；要保留回退结果，先把文件改回运行中的那一份。

### 已登记的意图存在 Enco 自己的库里，git 只是主人与 Agent 的工具

工作区的版本历史夹着被拒绝的修改与主人自己的改动，不对应任何一层，所以已登记的意图有自己的历史：登记记下源码目录与配置文件的值，某次登记时的意图由截至那次登记的事实求出。这份历史只在 Enco 的库里（总纲「值不可变，身份稳定，可变的只是引用」），登记、状态、历史与倒带都只读它；git 与编辑器一样，只是主人与 Agent 在工作区里使用的工具。运行只依赖制品，源码只用于比较与倒带，所以按 blob 的规则保留，用到的内容已被清理时明确报告。代价：git 的历史里看不到登记，看历史与倒带要经 Enco 的命令。

### 一次登记交出代码与配置的全部变化

插件把配置字段改名时，新代码拒绝旧配置，旧代码拒绝新配置，分开登记，哪一半都会被拒绝。所以一次登记交出工作区相对已登记意图的全部变化，包括配置、代码、名字与删除，作为整体校验、一起提交。代价：别处一个改到一半的目录会挡住整次登记，修好或改回它即可。

### 校验在提交者之外，提交时核对前提

校验可能要几十秒：加载、求出声明、probe，以及对新出现的使用的真实调用，所以在提交者的锁外进行。提交只经过唯一的提交者：核对前提，按当前状态检查准入，写入并发布。提交时注册表的引用或最新登记已经变了，这次登记就作废，重新执行即可。这就是归属与转移中由归属者带着前置条件提交的规则。

库的事务就是接纳的分界：之前的失败让登记被拒绝；之后的清理，例如删除不再被引用的制品文件，失败时只作为警告随已接纳的结果返回，由下一次登记与启动时的核对补上。

### 登记记下意图与来源

相同的内容说明不了来历（总纲「值不可变，身份稳定，可变的只是引用」）。所以接纳时记下事实本身：一个插件的代码意图是源码目录还是出厂代码，设置代际沿用哪个代码代际，名字由哪次登记写下。名字与代码各自记录，登记代码或设置不重新写名字；否则主人回退一次改名之后，这个插件下次登记代码会把新名字写回来。

登记还记下发起者与发起者给出的理由：谁发起、为什么，只有发起者知道。改了什么从名字行、代码行与配置代际推出，读取时生成，不另存摘要。

### 登记的是制品，构建记录只是复用的线索

工具链与环境都会改变编译结果，字节不由源码唯一决定，所以代际以制品为内容，恢复只靠保留下来的制品。构建记录把（源码目录的值，SDK）对应到当时的制品，制品仍被保留时直接复用，工具链只记作来源。SDK 只随宿主变化；升级之后，自建源码在第一次显式登记时重建，因为构建与依赖锁的变化属于新的意图。

### 撤销是把意图倒带，再重新登记

撤销改的是意图文件：Agent 把意图倒带到某次登记，再登记一次，撤销之后工作区、已登记的意图与运行仍然一致；按编号重新激活旧代际，会留下一份与运行不符的意图文件。撤销照常校验与试用：旧内容在今天的宿主、环境与接线下是否成立，必须重新确认。

倒带倒回的是登记的历史：只改那次登记之后登记过的部分，尚未登记的工作不随之消失。名字是接纳时的记账（插件专题「名字给人和模型，身份给记录」），不随倒带改变，内容按身份写回它现在的目录。

### 配置在登记时验证，所以登记即为健康

接线是配置的声明：谁使用哪个 endpoint，需要它提供什么。登记配置时，注册表对新出现的使用各发一次真实调用：内容最小，参数与这个用途的正常请求相同，例如工具与输出额度，所以覆盖的正是它真正用到的能力；压低额度会让先思考的模型来不及作答，好的接线也通不过。任何一次失败，整次登记就被拒绝。坏接线因此在生效之前就被拦下，配置代际不需要运行时的试用。探测只发宿主固定的文本，不带任何 Session 的内容；结果交给调用方，经工具登记时就进入 Agent 的 Log。

登记代码时的 probe 与此分工：probe 只检查代码本身，不联网，也不依赖主人的配置；服务与接线由登记配置时的真实调用检验。这正对应代码与服务两条恢复路线。

## 生效

### 运行中的代码与配置都是已登记事实的函数

代码与配置只随登记与机械恢复改变。注册表只经一个出口发布视图，导出表与活跃配置总在同一份视图里；每个组件是视图的函数，启动只是它看到的第一份视图。所以每一种修改都在它的归属者的边界生效，不必重启，也没有后台对账；各组件跟随视图的边界写在 Session、记忆与渠道各自的专题里。

一个 Round 内工具的实现不会悄悄改变：Round 钉住的代际被标为失败时，本 Round 对它的后续调用明确失败，下一个 Round 才看到回退后的目录。

落点：视图只经 `Registry::subscribe` 的 `watch` 发布，当前值与变更通知是同一件事。

### 重启只恢复已登记的代际

代际才是运行的依据。已有登记时，重启不读取工作区，写坏的配置或未登记的删除都不会改变运行状态。第一次启动尚无可以恢复的状态，所以把配置、全部源码插件与出厂代码一起登记，这次登记失败就阻止启动；只登记配置，引用自建 Provider 的配置就无从启动。首次登记只检查内容与接线，不发真实调用，已有依赖缓存时可离线完成。

### 状态分别回答意图是否改变、运行是否一致

工作区有没有未登记的修改，与运行的是不是已登记的意图，是两个独立的问题。状态只报告记下的事实：主人回退不留记录，不同顺序的回退可以留下相同的结果，所以不一致由谁造成，状态说不出来。读取状态不触发构建。

状态只回答现在。历史只增不减，放进状态，状态就随时间变长，现在的事实被淹没；所以状态只带最近几次登记，完整的历史按页另读。状态按单元组织：配置与每个插件各占一行，同时给出运行中、已登记与工作区三层，两个问题在同一行里得到回答。每一层只带自己当前的代际与结局，历史失败不能代表现在的状态。

运行与登记差在哪里，只由注册表求出：两层都归它所有，它给出名字、代码或设置中哪一层不同，读取状态的一方只呈现这些差别，不再从代际编号去猜。

落点：注册表状态中的运行层与 `Difference`。

## 恢复

### 有意的命令守住接线，机械恢复只求回到能运行的状态

同一项检查，结果按命令的性质处理。登记是有意的命令：候选与新增、改动的使用必须可用，原来可用的不能因此不可用，被拒绝时不登记，也不激活；与命令无关的旧故障照常报告，不阻塞它，所以修复可以一项一项登记。回退与重启时的还原是机械恢复，恢复不能依赖被替换的东西本身，所以它们不经校验，可以拆掉接线；受影响的使用者停下并记下原因，节点照常运行。宿主升级后某张宿主表解析不了，也只让它的组件停下；只有内核的表解析不了才阻止启动，因为没有它们就无法运行 Session。

### 每个插件只留当前版与一个回退目标，最后落到出厂代码

新代际先试用，通过 probe 与前几次调用才晋升为健康；可归因于它的失败回到回退目标，再没有就回到当前宿主的出厂代码。只留一个回退目标：它运行不了时，更早的多半也运行不了。健康不等于语义正确，所以晋升之后仍保留回退目标，主人可以回到上一份代码；删除插件也保留它。制品文件随这些引用保留，出厂代码被引用时同样写成文件，旧宿主不在之后仍能回到它。

### 出厂代际属于宿主，跟随属于登记

出厂代际是宿主自己的内容，以空配置加载并随二进制记下，不属于任何登记。它不依赖主人的配置，因此始终可以作为安全模式与机械恢复的落脚处；连空配置都加载不了，是宿主缺陷，由宿主切换的健康检查兜底。

已登记为出厂代码的意图依赖宿主，宿主一变，这份意图的内容就变了。所以启动还原之后，宿主经同一个入口为它提交一次普通登记，只看已登记的意图；工作区中尚未登记的复制或删除，等到下一次显式登记。被拒绝时保持当前版，照常运行并报告原因；拒绝没有推进意图，下一次登记自然包含它。

### 健康只统计能归因于代际本身的失败

trap、契约违规与 probe 失败说明这份代码坏了。网络中断、限流、凭证失效在所有版本上都一样，回退解决不了它们，只会把好代码换掉。失败只在插件运行时的边界归类一次，健康门控只读这个分类。归因只看失败本身：一份更严格的修正本来就会比旧版本失败得多，失败的多少说明不了哪个更对。健康只说明运行层面没有问题，语义是否正确由 fixture、契约测试与评测回答。

### 宿主回退，Agent 撤销，主人兜底

宿主只在试用中的代际出现可归因的失败时自动回退。修改在语义上是否更糟，由 Agent 判断，它把文件意图倒带再登记；内容由宿主决定的登记（跟随、SDK 变化后的重建）与直接登记的制品，改回文件也回不到之前的运行状态，靠主人回退。主人不依赖模型、网络与构建，以一次登记为单位机械回退其中仍在生效的部分，已登记的意图不变：一次修改常常同时改变几个插件与配置，主人不必先判断坏的是哪一部分。

仍在生效，就是当前引用正是这次登记写下的那一个。配置回到这次登记之前实际活跃的版本。

代价：插件代码坏了却只返回普通失败时，宿主不会自动回退。这些失败对模型可见，Agent 可以修复意图再登记。

### 每个恢复机制落在它所改变之物被固定的那一层

代码与服务是两条正交的路线：回退处理代码，备用 endpoint 处理服务。重试、回退与换 endpoint 以 Attempt 为单位，本 Run 中用尽过的（用途, endpoint 的参数, Provider 代际）组合不再尝试；安全模式以 Round 为单位，记住的是失败时的活跃代际。每个机制只记住它这一层固定的东西，所以失败不需要先分类：trap 与契约违规走回退，其余失败在重试用尽后换下一个 endpoint，全部用尽才进入安全模式；回退一个无关的插件，也不会让用尽的 endpoint 重新被尝试。备用 endpoint 是已登记配置中的另一项，运行中的行为仍然只来自已登记的代际。

### 安全模式是开关与本 Run 的 Log 的函数

安全模式让有出厂代码的插件改用出厂代际，其余插件保持自己的活跃代际，策略点改用原生实现，只暴露救生集，是 Agent 自愈的唯一起点。正常路径的 Round 失败后就进入，不设阈值，也不区分来源：安全模式救不了的失败，再失败一次几乎没有代价；失败的 Round 只停在组装或模型请求，没有分派任何工具，所以换成安全模式重来是安全的。它保持到活跃代际改变为止：任何一方登记或回退之后，下一个 Round 回到正常路径，Agent 的修复因此立即得到验证；新的 Run 也从正常路径开始。是否处于安全模式只取决于主人的开关与本 Run 的 Log，没有需要退出的状态。

配置代际在安全模式中保持不变，所以坏接线只能在登记时拦下。登记时的验证与安全模式合起来，才兑现"修复能力不被破坏"。

## 例外

### 宿主切换须经主人确认

恢复层级运行在宿主里，宿主之下没有另一层替它兜底，所以宿主是唯一不经代际自动生效的东西。Agent 可以自主完成新宿主的构建、测试与预检，再把切换作为待确认的命令提交；主人确认后由 supervisor 执行，健康检查失败就回到上一个二进制。插件的热替换不需要确认，因为它处在健康门控之下，恢复也不依赖被替换的东西。
