# 代际：自我修改

本专题展开"运行中的行为 ⟺ 已登记的代际"。能修改自己是 Enco 的第一个动机，也是它最危险的能力：一次坏的修改，可能让 Agent 失去修复自己的能力。这里的每个判断都服务于同一件事：经正式路径的修改都可以验证、可以撤销，而恢复从不依赖被修改的东西。

## 登记

### 插件与配置是同一种代际

Agent 对自身的修改，不论改的是插件代码、插件配置，还是接线与内核配置，都会改变下一刻运行的行为，也都可能让它失去修复自己的能力。所以它们遵循同一套规则：登记、提交、生效、重启、撤销与不一致的报告都相同。两种代际共用一个全局递增的编号，一个编号就能定位任何代际，Log 中的代码引用因此不依赖插件名，也不依赖代际的种类。

两种代际的差异只来自事实本身：插件代码的问题到运行时才暴露，所以插件代际要试用；接线在应用时就能用真实调用验证，所以配置代际登记即为健康；出厂的只有插件，所以安全模式只换插件代际。

落点：`Registry` 是两种代际唯一的提交者。

### 代际是内容，声明每次从内容求出

注册表只保存内容：插件代际是制品与插件配置，配置代际是配置文档。声明，即导出的接口、凭证与接线，由声明函数从内容求出。插件的声明函数是它自己的 `describe`，随制品固定；配置的声明函数是各张表的归属者，属于宿主的代码。宿主升级之后，存下来的旧声明会与重新求出的值并存，成为第二个事实来源，所以声明只在登记、加载与还原时求出，从不入库。注册表因此不解释内容，它不认识任何一张表的含义，只按声明检查准入。

落点：库中的代际只有内容列；`ActiveConfig` 的声明字段私有于注册表，它只能由一次求值构造（`Declaration::into_active`）。

### 登记只有一个流程：校验，然后提交

校验在锁外进行，可能要几十秒：加载、求出声明、probe，以及对新出现的使用的真实调用。提交只经过唯一的提交者，在锁内完成：核对期望，按当前状态检查准入，写入并发布。登记从活跃代际继承了一半，部署继承设置，应用配置继承制品，所以提交携带校验所依赖的那几个活跃代际作为期望，任何一个变了，这次登记就整个作废，重新执行即可。并发的部署与迟到的健康结果都由这一条处理，它就是归属与转移中由归属者带着前置条件提交的规则。

### 撤销是重新登记旧内容

部署与应用配置都接受一个代际编号，用它的内容再登记一次，这就是 Agent 撤销修改的方式。撤销走的是唯一的那条生效路径，所以它经过同样的校验与试用，旧内容在今天的宿主与配置下是否仍然成立，也随之得到检查。每个动词撤销它自己那一类修改，Agent 不必再学一个工具。历史只向前追加，撤销本身也是一个有编号、可以再撤销的代际。

### 配置在应用时验证，所以登记即为健康

接线是配置的声明：谁使用哪个 endpoint，需要它提供什么。应用配置时，注册表对新出现的使用各发一次真实的最小调用，覆盖这个用途真正用到的能力，例如工具调用；任何一次失败，整次应用就被拒绝。坏接线因此在生效之前就被拦下，配置代际不需要运行时的试用。探测只发宿主固定的文本，不带任何 Session 的内容；结果交给调用方，经工具应用时就进入 Agent 的 Log。

部署时的 probe 与此分工：probe 只检查代码本身，不联网，也不依赖主人的配置；服务与接线由应用配置时的真实调用检验。这正对应代码与服务两条恢复路线。

## 生效

### 运行中的代码与配置都是已登记事实的函数

有意的修改都是命令，除此之外，代码与配置不会自己改变。注册表只经一个出口发布视图，导出表与活跃配置总在同一份视图里；每个组件是视图的函数，启动只是它看到的第一份视图。所以每一种修改都在它的归属者的边界生效，不必重启，也没有后台对账；各组件跟随视图的边界写在 Session、记忆与渠道各自的专题里。

一个 Round 内的实现不会悄悄改变：Round 钉住的代际被标为失败时，本 Round 对它的后续调用明确失败，下一个 Round 才看到回退后的目录。

落点：视图只经 `Registry::subscribe` 的 `watch` 发布，当前值与变更通知是同一件事。

### 意图在仓库里，运行时状态在仓库外

主人的 home 是一个 git 仓库，里面是意图：`config.toml`、`AGENTS.md`、`plugins.lock`、skills 与插件源码；Log、代际、制品与索引都在 `.data/` 下，不入库。意图有历史、可以比较与回退，运行时状态由归属者管理。插件源码与 `config.toml` 经登记成为代际；`AGENTS.md` 与 skills 是文本，在使用时读取，读到的内容记入计划。构建以插件目录的内容快照为输入，代际记下源码快照、依赖锁与工具链，所以每个代际都能复现，意图与代际的差异也能逐一说明。

### 重启只恢复已登记的代际

代际才是运行的依据。重启只恢复活跃代际，`config.toml` 与插件目录的新内容要经登记才生效，所以写坏的 `config.toml` 不会让节点起不来，崩溃也不会顺带生效一份没有经过校验的修改。只有第一次启动读取 `config.toml`：还没有任何配置代际时，它被接纳为第一个配置代际。它本来就在使用，所以只检查结构与接线，不发真实调用，升级时恰好断网也能启动。

### 意图与登记不一致时，从历史说明原因

撤销之后，仓库里留着的仍是被撤销的版本；没有提醒，Agent 可能把同一份坏代码再构建、部署一次。所以两种代际都报告意图与活跃代际的关系：一致；从未登记；或者已登记为某个代际，但已被回退或被之后的登记取代。原因从代际的顺序推出，不另外记录。

## 恢复

### 有意的命令守住接线，机械恢复只求回到能运行的状态

同一项检查，结果按命令的性质处理。部署、应用配置与首次登记是有意的命令：不能拆掉在用的接线，不能登记缺少必需凭证的代际，被拒绝时不登记，也不激活。回退与重启时的还原是机械恢复，恢复不能依赖被替换的东西本身，所以它们不经校验，可以拆掉接线；受影响的使用者停下并记下原因，节点照常运行。宿主升级后某张宿主表解析不了，也只让它的组件停下；只有内核的表解析不了才阻止启动，因为没有它们就无法运行 Session。

### 恢复层级：出厂 ← 健康 ← 试用

新代际先试用，通过 probe 与前几次调用才晋升为健康；出现可以归因于它的失败，就回退到更早的健康代际，最后落到出厂代际。出厂代际是当前宿主二进制中的制品加上空配置，所以它不依赖主人的设置，坏设置进不了安全模式。回退的候选总以当前二进制的出厂代际结尾，主版本的变化让旧制品全部无法加载时，插件仍有落脚处。

出厂插件的身份由宿主固定，Agent 复制出厂源码、修改后构建的代际仍属于同一个插件，层级不会因为修改而断开。宿主升级带来新的出厂制品时，活跃代际本来就是出厂制品的插件随之换上新的；主人部署过自己代码的插件保持不变。

### 健康只统计能归因于代际本身的失败

trap、契约违规与 probe 失败说明这份代码坏了。网络中断、限流、凭证失效在所有版本上都一样，回退解决不了它们，只会把好代码换掉。失败只在插件运行时的边界归类一次，健康门控只读这个分类。归因只看失败本身：一份更严格的修正本来就会比旧版本失败得多，失败的多少说明不了哪个更对。健康只说明运行层面没有问题，语义是否正确由 fixture、契约测试与评测回答。

### 宿主回退，Agent 撤销，主人兜底

撤销按各方掌握的证据分担。宿主只在试用中的代际出现可以归因的失败时自动回退。"这次修改是否更糟"没有这样的证据，交给 Agent 判断，它以编号重新登记上一个版本。主人有不经校验的回退命令，模型与网络都不可用时也能使用。

代价：插件代码坏了却只返回普通失败时，宿主不会自动回退。这些失败对模型可见，Agent 可以重新部署，修复能力不受影响。

### 每个恢复机制落在它所改变之物被固定的那一层

代码与服务是两条正交的路线：回退处理代码，备用 endpoint 处理服务。重试、回退与换 endpoint 发生在 Attempt 层，本 Run 中用尽过的（endpoint 的参数, Provider 代际）组合不再尝试；安全模式发生在 Round 层，记住的是失败时的快照。每个机制只记住它这一层固定的东西，所以失败不需要先分类：trap 与契约违规走回退，其余失败在重试用尽后换下一个 endpoint，全部用尽才进入安全模式；回退一个无关的插件，也不会让用尽的 endpoint 重新被尝试。备用 endpoint 是已登记配置中的另一项，运行中的行为仍然只来自已登记的代际。

### 安全模式是开关与本 Run 的 Log 的函数

安全模式让插件改用出厂代际，策略点改用原生实现，只暴露救生集，是 Agent 自愈的唯一起点。正常路径的 Round 失败后就进入，不设阈值，也不区分来源：安全模式救不了的失败，再失败一次几乎没有代价；失败的 Round 只停在组装或模型请求，没有分派任何工具，所以换成安全模式重来是安全的。它保持到快照改变为止：任何一方部署、回退或应用配置之后，下一个 Round 回到正常路径，Agent 的修复因此立即得到验证；新的 Run 也从正常路径开始。是否处于安全模式只取决于主人的开关与本 Run 的 Log，没有需要退出的状态。

配置代际在安全模式中保持不变，所以坏接线只能在应用时拦下。应用时的验证与安全模式合起来，才兑现"修复能力不被破坏"。

## 例外

### 宿主切换须经主人确认

恢复层级运行在宿主里，宿主之下没有另一层替它兜底，所以宿主是唯一不经代际自动生效的东西。Agent 可以自主完成新宿主的构建、测试与预检，再把切换作为待确认的命令提交；主人确认后由 supervisor 执行，健康检查失败就回到上一个二进制。插件的热替换不需要确认，因为它处在健康门控之下，恢复也不依赖被替换的东西。
