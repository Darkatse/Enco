# 验证

本专题写 Enco 怎样确认自己的行为：测试守住可观察的行为与不变式，门禁守住结构，评测衡量自我修改是否真的更好。测试的准入规则见 `CONTRIBUTING.md`；这里写的是测试与评测的形状。

## 测试

### 优先使用能覆盖行为的最高一层

主要的一层是集成测试：真实的内核、注册表、SQLite、原生工具、记忆与出厂 composer，只把模型与插件运行时换成脚本化的实现。恢复、计划校验、压缩、注册表与健康门控都在这一层经过真实路径验证。端到端测试以子进程运行守护进程，经过真实的协议、Wasm 插件与出厂代际，负责进程与协议边界；需要控制时刻或故障位置的行为留在集成层。单元测试只用于集成测试不易触达的纯函数。同一个断言只在一层出现，一个验收场景可以由已有测试共同覆盖。

### 替身只替换真实的边界

脚本化的 Provider、Runtime 与时钟都实现内核端口，所以被测的是生产中的同一条路径。健康门控的故障注入就是让脚本化的 Provider 返回 trap。测试辅助只放在测试目录中，生产代码只有一条路径。

### 并发用确定性的协调，时间用暂停的时钟

并发测试用 barrier、oneshot 与 `Notify` 协调。进程内的计时器用 tokio 的暂停时钟，退避与定时按先后立即到期；崩溃恢复也在进程内确定地模拟，在注入点停下运行时，再在同一个数据库上启动新的内核。子进程里的计时器无法虚拟，所以黑盒测试只断言结局，不断言时长；不可避免的真实等待各自成为独立的测试，与其他测试并行。端到端测试等待 Log 中期望的条目，外加一个总超时。

## 门禁

### 一个离线命令定义"通过"

`cargo xtask check` 检查格式、crate 边界与 lint 表、生成物是否过期、出厂插件的构建与 clippy，并运行全部工作区的测试。它不联网，所以随时可以在本地运行；需要联网的检查（例如依赖的安全公告）放在采纳外来代码的流程与 CI 中。它要快到每次改动之后都愿意运行。测试通过只说明行为没有退化，收尾仍以逐路径的审阅为准。

## 评测

### 评测是 Enco 的黑盒客户端

运行器只启动 `enco`、调用它的命令行、读取管理命令输出的 JSON，独立的工作区让它引用不了宿主的 crate。每次试验用一个全新的 home，外部服务一律经 mock；评判由运行器以固定的模型与提示词直接调用，不经被测的 Enco，测量工具不随被测对象改变。评分只看公开的表面，与插件只看 WIT 是同一条纪律。

### 评测的产出是两个变体的比较

进化要回答的是"这次改动是否更好"。服务商会在同一个模型名下更新模型，存下的分数不能跨时间比较，所以两个变体在同一时间窗口内交错运行同一批题。结论回答两个问题：目标题上是否更好，其余每道题是否没有倒退；判定用精确检验，任何一边没有有效样本就拒绝。

### 只排除测量仪器自身的失败

被测对象启动之后的一切失败都算失败，包括守护进程起不来、`provider.*` 失败与超时。失败码由被测的插件自己报告，所以它不能决定一次失败算不算数。服务商的故障同时影响交错运行的两个变体，带来的是噪声而不是偏差，并且在失败原因中看得见。每次等待都有时限，超时就是这次试验的失败，所以一个坏掉的候选也会在有限时间内得出结论。

### 留出集放在 Agent 够不着的地方

评测材料只放在题目的隐藏部分，不进入被测的 home；工具调用的参数中出现运行器仓库或本次运行目录的路径，就判为越界。Agent 拥有完整的系统权限，当它开始对着任务集自我进化时，留出集要放到另一个节点或另一个系统用户下，否则成绩的提升可能只是记住了答案。
