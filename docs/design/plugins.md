# 插件：边界、契约与生态

本专题展开"双向不泄露"与"外部进入 ⟺ 已映射且已钉住"。系统与插件互相泄露是插件系统最常见的问题，也是 Enco 自建插件系统的原因。这里的判断让边界由结构保证，让契约只描述真实存在的东西，让多个插件的组合只需要类型检查。

## 边界

### 边界的每个方向都由结构保证

插件只能调用 linker 提供的 WIT 导入，这由 Wasm 物理保证。内核与宿主不依赖任何插件 crate，插件身份在内核中只是不透明的 ID，唯一的契约是 WIT，这由依赖方向与门禁保证；服务之间的差异只能经插件声明的能力表达。插件之间只能导入对方导出的接口，由内核转发，接到哪个实现由主人配置决定。门禁检查依赖方向，是否按身份写了分支由评审把关。

落点：`cargo xtask boundaries` 覆盖每个插件与 SDK 的独立工作区，它们不能依赖宿主的 crate。

### 能用 Skill 就不写插件，能写插件就不改宿主

扩展有四层：Skill（流程知识与胶水，零构建）、MCP（复用现成生态）、Wasm 插件（类型化、常驻、可热替换、可跨节点）、原生 crate（内核、Host 机制、平台桥接，改动需要宿主重建与主人确认）。越往下越强，修改的代价也越高，所以总是选能解决问题的最上面一层。

### 扩展点只有 Observer 与少数几个策略点

Observer 只读原始事实，维护自己的派生状态，形态是转移。策略点由内核定义，只有三个：组装请求、预处理入站、放行工具调用；组装请求每个 Session 绑定一个，另外两个每个节点各一个，它们都以宿主固定的出厂代码作为安全模式的落脚处；由插件实现的策略使用内嵌的出厂代际。所以扩展彼此独立，结果与加载的先后无关。

### 插件只响应调用

连接、长轮询、定时器、Webhook 路由与插件状态都由宿主持有；插件导出反应函数，把写入作为返回值交给归属者。反应期间只允许只读或幂等的外部操作，例如 HTTP 读取、写入内容寻址的 blob；有副作用的写入只能作为返回值，所以 trap 意味着什么都没有提交，重投是安全的。插件需要的资源是声明，随代际固定，由宿主对账：没变的保留，变了的重建，删掉的撤销。契约因此更小，插件代码也只在归属者的边界上替换。

### 每次逻辑调用一个新 Store

Store 的作用域覆盖一次调用、它返回的全部流式结果与最终结算；`Arc` 只负责代码的回收。实测 trap 会让整个 Store 不可再进入，所以每次调用都从干净的实例开始，一次失败影响不到下一次。

### 调用的角色决定它能看到的世界

同一个组件的不同调用承担不同职责，所以外部能力按调用给出。composer 只看参数、配置与自己的制品，没有文件、环境变量与网络；它读到的时钟与随机数由 Round 固定。映射器只看参数，才能在历史原文上重放。声明（`describe`、工具定义、composer 的选项 schema）随代际固定，每次加载都重新求出，所以不能联网：否则同一个代际会随外部的变化声明出不同的内容，重启与回退也要依赖网络。probe 只检查代码，配置为空且不能联网。其他调用，包括登记配置时对新使用的真实调用，使用其正常的配置与传输能力。WASI 的基础导入由语言运行时产生，权限由宿主实际赋予的能力决定。

## 契约

### 契约只包含已有使用者验证过的东西

每个接口、字段与分支都随它的第一个使用者加入，形状由使用者检验，宿主也只为真实的需求写代码。插件源码归主人时，升主版本只是一次全部重建，所以需要破坏就升主版本。按 WIT semver，给已有的导出接口加函数、给 record 加字段、给 variant 加分支都是破坏性变化，因为宿主会对组件的导出做类型检查。

### 接口按导入方与能否单独提供划分

`completion`、`embedding` 与 `decision` 的导入方与约束不同，也可以单独提供（DeepSeek 只导出补全，TypeSafe 只导出判断），所以是三个接口。Chat Completions、Responses、Claude Messages 等协议对内核而言是同一件事，都导出 `completion`，协议的差异全部留在各自的插件里，内核不需要知道调用的是哪家服务。

### 制品自己说明导入与导出，`describe` 只说插件整体的事实

导入与导出从制品的结构中读出，是唯一的事实来源。`describe(config)` 给出摘要、配置 schema 与凭证，也是唯一接受或拒绝配置的地方；每个导出接口在自己的接口里声明它提供的东西，收到的都是已被接受的配置，只做投影。每个接口的声明只描述它自己，所以接口可以单独增减。

### 两种参数，按由谁选定区分

插件配置由主人为这个插件选定，随代际固定，调用时经宿主导入读取；调用参数由调用方在每次调用时选定，经函数参数传入。Provider 的参数随 Attempt 记录，composer 的输出逐字冻结在计划中。判据是同一个代际要不要同时以两种取值被使用：一个插件只有一个活跃代际，所以同一个 Provider 代际同时服务回复与压缩时，`base_url` 与 `model` 只能是调用参数；同一个 composer 代际服务不同角色时，profile 的选项也是调用参数。插件声明中的模型可见文本随代际固定；每次调用生成的内容按调用记录。

### 工具参数的 schema 是契约，进入时解析，记录保持原样

内核在分派时按声明检查每一次调用（工程专题「归一化与校验只在拥有事实的地方做一次」），就必须完全读懂声明；读不懂的部分检查不了，也就保证不了。所以规范 schema 是 WIT 中定义的一个 JSON Schema 子集：插件声明的 schema 在进入时解析，超出子集就拒绝，并指出工具与位置。校验只在声明进入时做一次，Log 记下发给模型的声明原文，读回历史时不按今天的规则重新校验，所以规则收紧之后，过去的计划仍读得回来。各家线上协议的 schema 方言，由 Provider 在编码时翻译，宿主不按服务分支。

落点：`InputSchema` 只能经解析得到；`DisclosedTool` 记录声明原文。

### 补全只由内核导入

只有内核能在请求发出之前把补全记为 Attempt，并与计划、钉住的代际绑定，所以插件导入 `completion` 会在准入时被拒绝，需要另一个模型就委派给子 Session。这样，Session 配置接上的模型只能经内核、以有记录的方式调用。插件经 `http` 自己调用外部模型，与调用其他外部服务相同，不在这条保证之内。

### 插件之间的接口只用值类型，并且能返回 `unknown`

插件之间的调用由内核转发，可能跨节点，被调方每次调用使用一个新 Store，照常结算。所以这些接口只传值，每个函数都返回内核定义的调用错误，其中包括 `unknown` 与 `unavailable`，调用方从签名上就知道要处理它们。这两条由契约 lint 检查。

## 命名与接线

插件系统的依赖地狱来自四个条件：共享的全局命名空间、通过修改别人来扩展、同名多版本加区间约束、没有人为一组插件的组合负责。前三个由结构消除：组件之间不共享任何东西，各自静态链接依赖；插件无法修改别人，也没有启动顺序；每个节点上每个插件只有一个活跃代际。第四个由系统代际承担。剩下的命名、接线、准入、演进与信任，各由下面一条规则处理。

### 名字给人和模型，身份给记录

插件名就是主人 home 中 `plugins/` 下的目录名，目录不会重名，唯一性由结构保证。身份是注册表在首次接受插件时分配的 ULID，标识"这个 Space 里的这一次安装"，不随插件发布，所以主人的记账只由主人的 Space 决定。名字与身份的对应是接纳时的记账，不是意图，所以只记在注册表中：放进 home 就成了可以编辑的意图，改回一份旧文件就能把名字接到另一个身份上，历史与设置随之错位。出厂插件是唯一的例外，身份由宿主固定。模型可见的工具名、CLI、配置用名字，Log 中的代码引用用不可变的代际，状态与历史用身份。操作的语义与文件系统一致：身份相当于 inode，改名不改身份，复制目录得到新身份。

名字与代码一样分三层：home 中的目录名、已登记的名字与运行中的名字。运行中的名字只属于在运行的身份。删除是一次登记，释放已登记的名字，之后同名的新目录得到新身份；主人回退按登记从新到旧撤销，同名的新身份总在删除之前被撤销，撤销删除时名字已经空出。

### 每个导入接到 Host，或恰好一个导出

依赖、槽位与贡献是同一件事，区别只在导入方要一个还是要全部。候选唯一时自动接上，并记下结果，之后新增的候选不会改变它；不唯一时由主人配置选择。"全部"类的导入彼此可交换，顺序由消费者决定，例如 Context 的顺序归 composer。要改变一个插件的行为，就改它的源码并登记新代际。

### 准入只取决于当前状态

代际能否进入快照，只看它自身的事实：导入都接上，环境中的必需凭证齐备，工具名不与原生工具或其他插件冲突。准入结果只由本节点各插件的活跃代际、Host 接口与环境决定，与到达这个状态的路径无关，所以登记、回退与启动都从 Host 出发对整份快照逐层计算；工具名冲突时双方都不准入，不按先来后到挑出赢家。插件之间的接线因此必须无环；两个插件互相需要，通常说明缺一个共同的归属者。使用者的要求不属于代际：某个使用接不上，停下的只是这个使用者，同一插件的其他使用照常。没有准入的代际连同原因记入计划，对模型可见；接不上的使用按使用报告。

### 只有代码消费者需要兼容规则

工具的读者是模型，它每一轮都读取当前的定义，所以工具可以随代际自由变化，改名让引用它的要求失效，由校验报出。接口的读者是代码，遵循 WIT semver。每个导入只接一个导出，检查就是类型检查。

## 外部

### 外部只经映射器进入，映射器不做 I/O

外部的格式与语义不由我们决定，它会变化，也会违反自己的协议；在各个插件里各自解析，外部的每一次变化都会成为某处偶然的解析错误，或者一次静默的误读。所以翻译只有一个位置：映射器是只看参数、没有外部能力的组件，输入外部的定本与原文，输出规范值与它在原文中的出处，或者一个指回原文的失败。连接、进程与 HTTP 这些传输由宿主持有并随代际对账，凭证与效果的结算也在宿主，映射器碰不到它们。规范值沿用已有的类型：能力类外部译成工具定义与 `Outcome`，内容类外部译成模型可见的文字与图片，输入类外部译成 Event。

同样的定本与完整入参总得到同样的结果，所以映射器的新代际可以在历史上重放，与旧代际逐条比较之后再登记。记录的单位是把外部响应交给映射器的一次调用：还原其解释需要的全部参数与代际，先记录再调用，解析失败也有出处。只保存成功译出的片段会丢掉整批失败的证据。代价是每份经过映射的外部内容多存一份原文。

只解释外部内容的映射器没有执行权限；渠道映射器还决定宿主带凭证执行什么请求、哪个发送者是谁，因此是受信任的协议适配。主人配置连接与密钥，就是批准它使用该账号。重放只运行纯函数，真实请求与效果的结算留在宿主。

### 外部的契约以定本钉进代际

在接纳的路径上现查外部，同一份意图会随外部的变化得到不同的行为，这违背"运行中的行为 ⟺ 已登记的代际"。所以外部声明的契约（工具目录、schema）先规范化，再作为文件写进意图，与插件源码一样登记、按内容寻址、可以对比与倒带；模型看到的定义从定本求出，刷新定本就是一次登记。外部与定本不符就是带出处的失败：新出现的工具或字段在登记之前对模型不可见，消失或改变的报告为漂移，由 Agent 或主人重新登记。没有可拉取契约的外部，例如网页，映射器本身就是契约，漂移表现为映射失败。

### 依赖的部分严格，其余原样保留

容忍协议之外的输入会让缺陷固化成事实标准，替外部猜测意图会产生静默的误读；而协议允许的写法都是合法输入，例如 ProtoJSON 把 `null` 读作未设置。所以映射器按外部自己的规则读取它依赖的部分，规则之外的输入一律失败；不依赖的部分原样保留，不硬塞进规范类型；对已知违规的修补只能是映射器中写明的规则，并在结果中可见。失败指明是哪个外部、哪份定本、原文的哪个位置，不归咎于调用方。

## 信任

### 权限就是导入，只在外来代码进来时检查

插件作者不是 Space 的成员，他们的代码在主人的授权下运行，权限就是它的导入；导入可以从制品中读出，所以权限清单由制品本身给出。采纳外来修订时，导入、渠道可到达的来源或凭证的去向超出该来源已批准的集合，就停在待确认状态，确认之前 home 与运行中的代际都不变。登记路径对所有插件相同，不看来源：Agent 本来就有 shell，限制它能改哪些代码没有意义。模型可见的文本随代际固定并按内容寻址，任何变化都产生新代际，所以主人批准的就是将要运行的文本。Skill 的脚本与 MCP 服务器在 Wasm 边界之外，采纳它们等于完全信任；只解释外部内容的映射器没有执行权限；渠道映射器使用账号的信任边界见「外部只经映射器进入，映射器不做 I/O」。

### 插件目录是完整的构建输入，它的值只由它自己决定

每个插件目录复制到主人的 home 就能独立构建，目录之外只依赖随宿主分发的 SDK，所以 SDK 总与当前宿主相配。目录的值是其中的文件，即相对路径与字节：哪些文件不是源码，由目录内的 `.gitignore` 声明；上级目录与本机的忽略规则不参与，权限与修改时间也不计入。所以同一个目录在任何节点上都是同一个值，复制目录就带上了它的规则。构建只读插件目录与 SDK：构建记录以目录的值与 SDK 为复用键；目录之外的 Cargo 配置与被忽略的文件会改变结果，却不在键里。

### 分发的单位是源码，生态开放有三个前提

外来插件按上游的某个版本以源码引入主人的 home，在 Space 内构建，本地修改与上游更新在 home 中合并，例如用 git；缺少的导入由 Agent 提议、主人确认后安装。插件源码全部归主人时，契约升主版本就是一次全部重建；多作者生态打破了这个前提，所以开放之前必须满足：`enco:plugin` 达到 1.0；宿主能同时链接历史版本的 world；`enco-sdk` 按 semver 发布。

## 配置与密钥

### 每张配置表有唯一的归属者

所有设置都在某张有名字的表里，每张表由它的归属者解析与校验：内核、记忆、渠道与各插件各有自己的表。宿主一侧的归属者与插件的 `describe` 作用相同，没有归属者的表被拒绝。表按领域命名，因为配置是写给主人看的。模型服务、模型名与密钥变量集中在 endpoint，其他使用者按名字引用它。

### 空配置必须合法

没写配置就是 `{}`，`{}` 必须得到最小能力，最小能力可以是没有工具。这条约定由用到它的地方自然检验：出厂代际以 `{}` 加载，插件构建时以 `{}` 生成 README。

### 插件永远看不到密钥的值

要防的，按现实程度排序：插件的缺陷把密钥写进 Log 或工具结果（插件由 Agent 编写和修改，这最可能发生）；提示注入诱导插件把密钥带到别处；外来插件把密钥发往别处。所以值只出现在传输层：内核与配置只认识变量名，宿主在每次调用时读取环境变量，把凭证附加到发往绑定 origin 的请求上；交回插件的一切都把值替换为变量名。值是环境事实而不是意图，不进入代际，轮换密钥要重启。Agent 本身不在防范之内，它可以读进程的环境变量。

### 密钥写在决定请求去向的那份配置旁边

对 Provider，访问哪个模型服务就是调用的内容，所以密钥写在 endpoint 里，经 profile 选定；对渠道，服务由连接选定，所以密钥写在连接配置里；对 web 这类插件，用哪个服务是插件的实现选择，所以密钥写在插件自己的配置里。系统中只有一个凭证概念：每份凭证声明若干处放置，各有自己的来源。含有调用方选定来源的凭证由调用方提供，全部来源固定的凭证由插件设置提供；同一份值可以用于多个已声明的来源。映射由主人写、由宿主读，能用哪些密钥只由主人决定。宿主只在同一 origin 内跟随重定向，所以"按请求的 origin 附加"是唯一的规则。

### 凭证的位置只由宿主决定

不可信的输入可以出现在发往绑定 origin 的请求里：代理式的服务（例如 Jina Reader）把要抓取的 URL 当作参数，而这个 URL 可能来自网页。所以插件只声明固定的放置方式：请求头及其前缀、请求路径的前缀，或帧中的 JSON 位置；宿主只在每处放置所绑定的来源写入凭证。渠道请求只能到达所选服务与代际声明的额外来源，允许连接某个来源不等于允许给它凭证。协议选择具体去向，宿主执行这两个独立的约束。

## 状态

### 插件状态只在宿主，由归属者串行写入

插件状态放在宿主的 KV 中，按插件声明的作用域由归属者串行写入，随 Space 复制，实例内存只作缓存。迁移遵循 expand-contract，并兼容 Space 中较旧的节点；破坏性迁移由归属者在替换边界执行一次，该插件因此放弃自动回退。数据格式兼容、并发访问正确、业务语义兼容是三个独立的条件：expand 规则保证第一条，归属者保证第二条，第三条靠契约测试。

## 原生能力

### 原生能力与插件经同一组端口接入，救生集始终有原生实现

能力原则上由插件提供。暂时编译在宿主里的能力与插件经过同一组端口接入，调用、取消与结算的规则相同，所以迁移成插件时调用方不变；迁移的条件写在路线图里。救生集保留原生实现；安全模式的策略点使用宿主固定的出厂代码，插件形式的策略点使用内嵌的出厂代际。两者都不依赖正在被替换的代码。新增原生能力是跨边界的变化，先与主人对齐。
