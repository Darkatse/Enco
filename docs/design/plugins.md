# 插件：边界、契约与生态

本专题展开"双向不泄露"。系统与插件互相泄露是插件系统最常见的问题，也是 Enco 自建插件系统的原因。这里的判断让边界由结构保证，让契约只描述真实存在的东西，让多个插件的组合只需要类型检查。

## 边界

### 边界的每个方向都由结构保证

插件只能调用 linker 提供的 WIT 导入，这由 Wasm 物理保证。内核与宿主不依赖任何插件 crate，插件身份在内核中只是不透明的 ID，唯一的契约是 WIT，这由依赖方向与门禁保证；服务之间的差异只能经插件声明的能力表达。插件之间只能导入对方导出的接口，由内核转发，接到哪个实现由主人配置决定。门禁检查依赖方向，是否按身份写了分支由评审把关。

落点：`cargo xtask boundaries`，插件工作区不能依赖宿主的 crate。

### 能用 Skill 就不写插件，能写插件就不改宿主

扩展有四层：Skill（流程知识与胶水，零构建）、MCP（复用现成生态）、Wasm 插件（类型化、常驻、可热替换、可跨节点）、原生 crate（内核、Host 机制、平台桥接，改动需要宿主重建与主人确认）。越往下越强，修改的代价也越高，所以总是选能解决问题的最上面一层。

### 扩展点只有 Observer 与少数几个策略点

Observer 只读原始事实，维护自己的派生状态，形态是转移。策略点由内核定义，只有三个：组装请求、预处理入站、放行工具调用；组装请求每个 Session 绑定一个，另外两个每个节点各一个，它们都有原生的出厂实现，由安全模式使用。所以扩展彼此独立，结果与加载的先后无关。

### 插件只响应调用

连接、长轮询、定时器、Webhook 路由与插件状态都由宿主持有；插件导出反应函数，把写入作为返回值交给归属者。反应期间只允许只读或幂等的外部操作，例如 HTTP 读取、写入内容寻址的 blob；有副作用的写入只能作为返回值，所以 trap 意味着什么都没有提交，重投是安全的。插件需要的资源是声明，随代际固定，由宿主对账：没变的保留，变了的重建，删掉的撤销。契约因此更小，插件代码也只在归属者的边界上替换。

### 每次逻辑调用一个新 Store

Store 的作用域覆盖一次调用、它返回的全部流式结果与最终结算；`Arc` 只负责代码的回收。实测 trap 会让整个 Store 不可再进入，所以每次调用都从干净的实例开始，一次失败影响不到下一次。

## 契约

### 契约只包含已有使用者验证过的东西

每个接口、字段与分支都随它的第一个使用者加入，形状由使用者检验，宿主也只为真实的需求写代码。插件源码归主人时，升主版本只是一次全部重建，所以需要破坏就升主版本。按 WIT semver，给已有的导出接口加函数、给 record 加字段、给 variant 加分支都是破坏性变化，因为宿主会对组件的导出做类型检查。

### 接口按导入方与能否单独提供划分

`completion`、`embedding` 与 `decision` 的导入方与约束不同，也可以单独提供（DeepSeek 只导出补全，TypeSafe 只导出判断），所以是三个接口。Chat Completions、Responses、Claude Messages 等协议对内核而言是同一件事，都导出 `completion`，协议的差异全部留在各自的插件里，内核不需要知道调用的是哪家服务。

### 制品自己说明导入与导出，`describe` 只说插件整体的事实

导入与导出从制品的结构中读出，是唯一的事实来源。`describe(config)` 给出摘要、配置 schema 与凭证，也是唯一接受或拒绝配置的地方；每个导出接口在自己的接口里声明它提供的东西，收到的都是已被接受的配置，只做投影。每个接口的声明只描述它自己，所以接口可以单独增减。

### 两种参数，按由谁选定区分

插件配置由主人为这个插件选定，随代际固定，调用时经宿主导入读取；调用参数由调用方在每次调用时选定，是函数参数，记在这次调用里。判据是同一个代际要不要同时以两种取值被使用：一个插件只有一个活跃代际，所以同一个 Provider 代际同时服务回复与压缩时，`base_url` 与 `model` 只能是调用参数；会改变模型可见文本的只能是插件配置，因为模型可见的文本随代际固定。

### 补全只由内核导入

只有内核能在请求发出之前把补全记为 Attempt，并与计划、钉住的代际绑定，所以插件导入 `completion` 会在准入时被拒绝，需要另一个模型就委派给子 Session。这样，Session 配置接上的模型只能经内核、以有记录的方式调用。插件经 `http` 自己调用外部模型，与调用其他外部服务相同，不在这条保证之内。

### 插件之间的接口只用值类型，并且能返回 `unknown`

插件之间的调用由内核转发，可能跨节点，被调方每次调用使用一个新 Store，照常结算。所以这些接口只传值，每个函数都返回内核定义的调用错误，其中包括 `unknown` 与 `unavailable`，调用方从签名上就知道要处理它们。这两条由契约 lint 检查。

## 命名与接线

插件系统的依赖地狱来自四个条件：共享的全局命名空间、通过修改别人来扩展、同名多版本加区间约束、没有人为一组插件的组合负责。前三个由结构消除：组件之间不共享任何东西，各自静态链接依赖；插件无法修改别人，也没有启动顺序；每个节点上每个插件只有一个活跃代际。第四个由系统代际承担。剩下的命名、接线、准入、演进与信任，各由下面一条规则处理。

### 名字给人和模型，身份给记录

插件名就是主人仓库 `plugins/` 下的目录名，目录不会重名，唯一性由结构保证。身份是 Space 在插件进入时分配的 ULID，记录在仓库根部的 `plugins.lock` 中，与 Cargo.lock 的分工相同；它标识"这个 Space 里的这一次安装"，不随插件发布，所以主人的记账只由主人的 Space 决定。出厂插件是唯一的例外，身份由宿主固定。模型可见的工具名、CLI、配置用名字，Log 中的代码引用用不可变的代际，状态与历史用身份。操作的语义与文件系统一致：身份相当于 inode，改名不改身份，复制目录得到新身份。

### 每个导入接到 Host，或恰好一个导出

依赖、槽位与贡献是同一件事，区别只在导入方要一个还是要全部。候选唯一时自动接上，并记下结果，之后新增的候选不会改变它；不唯一时由主人配置选择。"全部"类的导入彼此可交换，顺序由消费者决定，例如 Context 的顺序归 composer。要改变一个插件的行为，就改它的源码并部署新代际。

### 准入只取决于当前状态

导入都接上、必需凭证齐备的代际才进入快照。准入结果只由本节点各插件的活跃代际、接线、Host 接口与凭证决定，与到达这个状态的路径无关，所以部署、回退与启动都从 Host 出发对整份快照逐层计算。插件之间的接线因此必须无环；两个插件互相需要，通常说明缺一个共同的归属者。没有准入的代际连同原因写入 Log，对模型可见。

### 只有代码消费者需要兼容规则

工具的读者是模型，它每一轮都读取当前的定义，所以工具可以随代际自由变化，改名让引用它的要求失效，由校验报出。接口的读者是代码，遵循 WIT semver。每个导入只接一个导出，检查就是类型检查。

## 信任

### 权限就是导入，只在外来代码进来时检查

插件作者不是 Space 的成员，他们的代码在主人的授权下运行，权限就是它的导入；导入可以从制品中读出，所以权限清单由制品本身给出。采纳外来修订时，导入或凭证的去向超出该来源已批准的集合，就停在待确认状态，确认之前仓库与运行中的代际都不变。部署路径对所有插件相同，不看来源：Agent 本来就有 shell，限制它能改哪些代码没有意义。模型可见的文本随代际固定并按内容寻址，任何变化都产生新代际，所以主人批准的就是将要运行的文本。Skill 的脚本与 MCP 服务器在 Wasm 边界之外，采纳它们等于完全信任。

### 分发的单位是源码，生态开放有三个前提

外来插件按 commit 引入主人的仓库，在 Space 内构建，本地修改与上游更新用 git 合并；缺少的导入由 Agent 提议、主人确认后安装。插件源码全部归主人时，契约升主版本就是一次全部重建；多作者生态打破了这个前提，所以开放之前必须满足：`enco:plugin` 达到 1.0；宿主能同时链接历史版本的 world；`enco-sdk` 按 semver 发布。

## 配置与密钥

### 每张配置表有唯一的归属者

所有设置都在某张有名字的表里，每张表由它的归属者解析与校验：内核、记忆、渠道与各插件各有自己的表。宿主一侧的归属者与插件的 `describe` 作用相同，没有归属者的表被拒绝。表按领域命名，因为配置是写给主人看的。endpoint 是"服务、模型与密钥变量"唯一出现的地方，其他表按名字引用它。

### 空配置必须合法

没写配置就是 `{}`，`{}` 必须得到最小能力，最小能力可以是没有工具。这条约定由用到它的地方自然检验：出厂代际以 `{}` 登记，插件构建时以 `{}` 生成 README。

### 插件永远看不到密钥的值

要防的，按现实程度排序：插件的缺陷把密钥写进 Log 或工具结果（插件由 Agent 编写和修改，这最可能发生）；提示注入诱导插件把密钥带到别处；外来插件把密钥发往别处。所以值只出现在传输层：内核与配置只认识变量名，宿主在每次调用时读取环境变量，把凭证附加到发往绑定 origin 的请求上；交回插件的一切都把值替换为变量名。值是环境事实而不是意图，不进入代际，轮换密钥要重启。Agent 本身不在防范之内，它可以读进程的环境变量。

### 密钥写在决定请求去向的那份配置旁边

对 Provider，访问哪个模型服务就是调用的内容，所以密钥写在 endpoint 里，经 profile 选定；对 web 这类插件，用哪个服务是插件的实现选择，所以密钥写在插件自己的配置里。系统中只有一个凭证概念：不带 origin 的凭证附加到调用方选定的服务，带 origin 的附加到插件自己的服务。映射由主人写、由宿主读，能用哪些密钥只由主人决定。宿主只在同一 origin 内跟随重定向，所以"按请求的 origin 附加"是唯一的规则。

### 凭证的位置只由宿主决定

不可信的输入可以出现在发往绑定 origin 的请求里：代理式的服务（例如 Jina Reader）把要抓取的 URL 当作参数，而这个 URL 可能来自网页。所以插件只声明放置方式（请求头与前缀），由宿主把凭证写入这个固定位置，请求的其余部分不会带上它。

## 状态

### 插件状态只在宿主，由归属者串行写入

插件状态放在宿主的 KV 中，按插件声明的作用域由归属者串行写入，随 Space 复制，实例内存只作缓存。迁移遵循 expand-contract，并兼容 Space 中较旧的节点；破坏性迁移由归属者在替换边界执行一次，该插件因此放弃自动回退。数据格式兼容、并发访问正确、业务语义兼容是三个独立的条件：expand 规则保证第一条，归属者保证第二条，第三条靠契约测试。

## 原生能力

### 原生能力与插件经同一组端口接入，救生集始终有原生实现

能力原则上由插件提供。暂时编译在宿主里的能力与插件经过同一组端口接入，调用、取消与结算的规则相同，所以迁移成插件时调用方不变；迁移的条件写在路线图里。救生集与安全模式的策略点在有了插件版本之后仍保留原生实现，因为恢复不能依赖被替换的东西。新增原生能力是跨边界的变化，先与主人对齐。
