# 10 Telegram 渠道（M9）

Telegram 是第一个渠道，先用原生代码实现，登记在 `docs/decisions/native-exceptions.md`。它遵循架构文档 §4.3 的会话映射与投递规则。

代码分两层：

- `enco-host/src/telegram.rs` 是协议适配器。它知道 Bot API 的请求格式、怎样解析更新和命令、怎样拆分长消息、怎样判断一次请求失败的性质。P3 把这一层换成 Wasm 插件。
- `enco-host/src/channel.rs` 与 `channel/` 是共同机制，P3 之后仍留在宿主。它负责核对主人、维护聊天与 Session 的映射、接纳入站消息、从 Log 找出要投递的回复，并对每次投递结算。它不认识 Telegram，只通过 `channel::Adapter` 与适配器交互。

两层之间是架构文档 §3.6 所说的转移：适配器处理一条更新，返回新的协议状态和解析出的输入，由连接的归属者把它们一次提交。适配器自己不写任何状态。

渠道和 CLI 一样，只调用 Kernel 的方法（04 §3），不直接访问 Store。需要时间时，渠道使用组合根交给它的 `Clock`，与 `Memories` 相同。

## 1. 配置

```toml
[telegram]                              # 可选；存在时启用
token_env = "TELEGRAM_BOT_TOKEN"        # bot token 所在的环境变量
owner_user_id = 123456789               # 主人的 Telegram user ID
api_base = "https://api.telegram.org"   # 可选；测试与自建 Bot API 服务器使用
```

- 守护进程在打开任何存储之前读取 token。环境变量没有设置，或者 token 的格式不对，就拒绝启动。
- token 冒号前面的数字是 bot id，不需要联网就能得到。连接的键是 `telegram:<bot id>`，所以换一个 bot 会得到一份新的连接状态。
- Bot API 的 URL 里含有 token。reqwest 的错误要先用 `without_url()` 去掉 URL 再使用，日志只记方法名和错误的类别。
- 代理沿用 reqwest 的默认行为，读取 `HTTPS_PROXY` 等环境变量。

## 2. 连接状态

每个连接有一份状态，只有它的归属者写入，并且都经 `Kernel::accept` 提交。状态包括四部分：

- 协议状态：共同机制不解读它，由适配器决定内容。Telegram 在这里保存下一次 `getUpdates` 的 offset。
- 映射：每个聊天当前挂在哪个 Session 上。
- 出站游标：这个连接送过消息的每个 Session，处理到了 Log 的哪个位置，以及那时的投递目标（§4）。
- 正在进行的投递：发送之前写入，结算时清除。

## 3. 入站

一个辅助任务负责轮询：用已经提交的协议状态调用 `getUpdates`，把拿到的一批更新交给归属者，等这一批全部提交后，再用新的协议状态发起下一次请求。所以 offset 永远不会跑在已经提交的消息前面。

归属者按顺序处理每条更新，每条更新提交一次：新的协议状态、这条更新带来的 Event、映射的变化，一起经 `Kernel::accept` 写入。提交失败时什么都没有写入，这条更新下一次还会被取回，因此不会丢失，也不会被处理两次。

每条更新按下面的规则处理：

1. 不是主人发来的私聊文本（聊天类型不是私聊、发送者不是 `owner_user_id`，或者没有文本）：只推进协议状态，不进入模型。同时写一条 info 日志，包含发送者 ID、聊天 ID 和聊天类型，不包含消息内容。`owner_user_id` 配错时，主人可以从这条日志里查到自己的 ID。
2. 命令：适配器负责识别写法，共同机制负责执行，都不经过模型。
   - `/session`：按 Markdown 列表列出全部 Session，当前项写为 `- **main** (current)`，其余项写为 `- work`。
   - `/session <名字>`：打开这个 Session（不存在就创建，profile 为 `default`，12 §4），把当前聊天挂上去。
   - `/cancel`：取消当前挂着的 Session 正在进行的 Run。
   - 其他以 `/` 开头的文本，包括 Telegram 自动发送的 `/start`，都按普通消息处理。

   映射的变化和协议状态一起先提交，之后才执行取消、发送命令回执。所以每条命令最多执行一次。回执和 CLI 命令的返回一样只是即时回应，中途断了，主人重新发一次命令即可。
3. 普通消息：进入这个聊天挂着的 Session；还没有挂过的聊天，挂到 `main`。Event 的来源是 `EventSource::Channel { channel, account, conversation, sender }`。如果这个 Session 还没有出站游标，就为它建一个，和 Event 一起提交。

## 4. 出站

### 投递什么、发给谁

归属者订阅每个有出站游标的 Session：先订阅，再从游标的位置把 Log 读完。订阅只用来唤醒归属者，内容一律从 Log 读取；订阅积压丢了消息，也从游标重新读。

按 Log 的顺序往下读，记住两件事：

- 目标：最近一条交互式 `EventConsumed` 的来源。CLI 和渠道算交互式，提醒不算，所以提醒触发的回复发往主人最近使用的地方。只有目标是本连接的聊天时才投递。
- 回复：当前 Round 里最后一次完成的 Reply Attempt 的文本。

遇到下面两种条目时投递：

- `RoundEnded { end: Replied }`：投递这个 Round 的回复。
- 结局不是 `Completed` 的 `RunEnded`：投递一句简短的说明，比如"Run failed: …"、"Run cancelled."。这和 `enco chat` 显示 Run 结局的方式一致。

渠道出站文本约定为 Markdown，由各生成处遵守；适配器负责映射到渠道协议。目标聊天当前挂着的不是这个 Session 时，在消息前加独立段落 `[<Session 名>]\n\n`，保留正文首个块的结构。

每处理完一个 Round 或 Run 的结尾，游标就推进到那个位置，不管这次有没有投递。游标同时保存当时的目标，所以重启之后，提醒触发的回复仍然发往原来的聊天。

### 投递的结算

同一时刻最多只有一个发送在途，归属者知道它是命令回执还是 Log 投递。每次逻辑投递按三步进行：

1. 写入"正在投递"：Session、Log 位置和目标聊天。
2. 适配器把文本拆成若干段，按顺序发送。Telegram 使用 `sendRichMessage` 的 `rich_message.markdown`，由平台解析 Rich Markdown；每段源码最多 32768 个 Unicode 字符，优先在换行处分段，无换行时按字符边界拆分，保留全部源码，不解析 Markdown 块结构。块数、嵌套深度等其余协议限制由 Telegram 校验，拒绝仍走已有失败结算。
3. 把最终结局（`ok`、`failed` 或 `unknown`）、清除"正在投递"、推进游标，放在同一次提交里写入。

每次逻辑投递留下一条结算记录，只引用 Session 和 Log 位置，不复制回复的正文。

### 失败与重试

- 已经发送成功的段不再重发，只重试当前这一段。
- 请求确定没有到达的，退避后重试这一段，每段最多尝试 4 次：
  - 连接失败，请求根本没有发出；
  - Telegram 返回 429，按它给出的 `retry_after` 等待；
  - 其他明确可以重试的 4xx。
- 其他 4xx 属于永久拒绝，立即结算为 `failed`。
- 请求已经发出、结果无法确认的，结算为 `unknown`，剩下的段不再发送，也不自动重试：
  - 超时；
  - 连接中断；
  - 5xx：网关或自建服务器可能在转发之后才出错，所以 5xx 不能证明消息没有送达；
  - 响应格式不对。
- 启动时发现上次留下的"正在投递"，说明进程在发送途中停止，同样结算为 `unknown`。
- 等待网络和退避的时候，入站、`/cancel` 和其他连接照常工作。

## 5. 查看投递结果

所有逻辑投递的结算都保存在 Store 里，按提交顺序排列。同一个连接对同一个 Log 位置只能有一条记录。

`enco status` 的 `channels` 一项列出每个渠道是否在运行、停止的原因，以及最近 10 次 `failed` 或 `unknown` 的投递。每条都写明 Session、Log 位置、目标聊天和结局。要看原文，就用 `enco log --session <Session ID 或名字>`。

## 6. 生命周期与故障

- 守护进程在 Kernel 启动之后启动渠道。关闭时先停渠道，再调用 `kernel.shutdown()`（08 §5）。
- 停止渠道的顺序：
  1. 取消轮询和订阅。丢弃长轮询的请求是安全的，它没有外部效果。
  2. 不再开始新的投递。
  3. 等正在发送的那一次完成并结算。已经发出的请求不能丢弃。
- 停止期间以及停止之后产生的回复，下次启动时从 Log 补发。
- 轮询遇到网络错误时，按 1、2、4 …… 30 秒退避重试，守护进程照常运行。
- 连接状态损坏，或者 Telegram 返回 401、404（token 无效），渠道停止，原因可以在 `enco status` 里看到。CLI 和其他 Session 不受影响。
- 渠道早先停止的原因只在 `status` 里报告；之后正常关闭守护进程时，不再把它当作关闭失败。
- 一次投递失败并结算之后，继续处理后面的消息，不会卡住整个连接。

## 7. 范围与限制

不在范围内：图片、语音、文件、编辑与撤回的消息、群聊、多节点租约、Webhook。P3 只替换协议适配这一层，上面的归属与结算机制保持不变。

Telegram 服务器最多保留 24 小时内尚未取走的更新（[getUpdates](https://core.telegram.org/bots/api#getting-updates)）。本地的原子提交保证已经取到的消息不丢，但守护进程停机超过 24 小时，这期间的消息 Telegram 就不再提供了。
