# 09 门禁、测试与验收

## 1. cargo xtask

`xtask` 是一个普通的二进制 crate，在 `.cargo/config.toml` 中注册别名 `xtask = "run --package xtask --"`。

| 命令 | 作用 |
|---|---|
| `cargo xtask build-factory` | 构建出厂插件并复制到 `target/factory/`（07 §5） |
| `cargo xtask boundaries` | 检查工作区 crate 之间的依赖方向 |
| `cargo xtask docs [--check]` | WIT 文档检查，生成 `wit/CONTRACT.md`；`--check` 时只比较、不写入 |
| `cargo xtask check` | 仓库级检查：按下面的顺序执行，任何一步失败即停止 |

`cargo xtask check` 的顺序：

1. `cargo fmt --all --check`；对 `plugins/Cargo.toml` 与 `evals/runner/Cargo.toml` 各执行一次
2. `cargo xtask boundaries`；校验三个工作区共用的 lint 表与各 crate 的继承
3. `cargo xtask docs --check`
4. `cargo xtask build-factory`
5. `cargo clippy --workspace --all-targets -- -D warnings`；`cargo clippy --manifest-path plugins/Cargo.toml --target wasm32-wasip2 --all-targets -- -D warnings`；`cargo clippy --manifest-path evals/runner/Cargo.toml --all-targets -- -D warnings`
6. `cargo test --workspace --no-run`，构建出全部测试与 `enco`；然后三个工作区的测试同时运行：`cargo test --workspace`、`cargo test --manifest-path plugins/Cargo.toml`，以及以 `ENCO_BIN` 指向主工作区的 `enco` 运行的 `cargo test --manifest-path evals/runner/Cargo.toml`（评测运行器的测试要用真实的 `enco`，§3）。三者的构建目录互不相同，所以不会互相等待；输出在全部结束后按这个顺序打印

### 1.1 boundaries

用 `cargo_metadata` 读取工作区。对每个成员，收集它依赖的**工作区内** crate（包括 normal、build、dev 依赖），检查是否属于 02 §3 表中允许的集合。违反时列出"谁依赖了谁、允许的是什么"，退出码非零。

同样读取两个独立工作区：拒绝插件对宿主工作区 crate 的依赖，保证插件只通过 WIT 接入；拒绝评测运行器对宿主工作区 crate 的依赖，保证它是黑盒客户端。只检查依赖方向，不扫描源码文本。外部依赖由提问协议管控（01 §5），不在这里检查。

## 2. WIT 门禁与 CONTRACT.md

`cargo xtask docs` 使用 `wit-parser` 解析 `wit/`：

**检查**：包本身、每个 world、interface、类型定义（record、variant、enum、type 别名）与 function 都必须有非空的文档。字段与分支的文档可选。缺失时列出全部缺失项，退出码非零。

**生成** `wit/CONTRACT.md`，内容按源码顺序：

```text
<!-- Generated by `cargo xtask docs`. Do not edit. -->
# enco:plugin@0.3.0
{包文档}

## Worlds
### `provider-plugin`
{文档}
- Imports: `host`
- Exports: `lifecycle`, `provider`
（每个 world 一节）

## Interfaces
### `types`
{文档}
#### record `failure`
{文档}
| Field | Type | Description |
|---|---|---|
| `code` | `string` | {字段文档，没有则留空} |
…
#### func `complete`
```wit
complete: async func(settings: settings, request: request) -> result<completion, failure>
```
{文档}
（每个 interface、每个条目一节）
```

类型名按 WIT 语法渲染（`list<u8>`、`option<string>`、`result<completion, failure>`、`tuple<string, string>`）。

`--check`：在内存中生成后与现有文件比较；不一致时报错 `wit/CONTRACT.md is stale; run cargo xtask docs`。

## 3. 测试策略

遵循 `AGENTS.md` 的测试准入：只为可观察的行为、非平凡的不变式与边界、已经修复的具体缺陷写测试。**不要**写：每个类型的 serde 往返测试、对提示词模板文案或排版的断言、对 getter 或直接委托的测试、对 `CONTRACT.md` 内容的快照测试（门禁已经覆盖）。输入事实、当前时间、记忆与工具结果是否正确进入模型请求，属于行为核对。并发测试用 barrier、oneshot、`Notify` 协调，不用 sleep；需要时间推进时使用 `tokio::time::pause` 与可设置的 `TestClock`。

三层，优先使用能够覆盖该行为的最高一层，不在多层重复同一断言：

端到端负责真实协议、Wasm 和进程边界；需要控制时刻或故障位置的行为留在集成层。一个场景可以由已有测试共同覆盖，不要求每个验收编号对应一个独立测试。类型已经表达的约束不再用字段快照重测。

| 层 | 位置 | 内容 |
|---|---|---|
| 单元 | 模块内 `#[cfg(test)]` | 只用于集成测试不易触达的纯函数边界。目前有记忆索引的 `reconcile`（同一记忆的重复节点、无法解析的 payload、rev 不一致），以及评测运行器的检验与占位符（超几何分布、分层卷积、工作日偏移，13 §8–§9） |
| 集成 | `crates/enco-host/tests/` | Kernel + `Registry`（`ScriptedRuntime`）+ `SqliteStore`（临时目录）+ 原生工具 + `InstructionsContextSource` + `Memories`（临时目录）+ `FactoryComposer` + `ScriptedProvider` + `TestClock`。恢复、Transcript 投影、计划校验、composer 的预算与压缩、工具行为、注册表与健康门控都在这一层经过真实路径验证 |
| 端到端 | `apps/enco/tests/` | 以子进程运行 `enco serve`（`env!("CARGO_BIN_EXE_enco")`），临时 `ENCO_HOME`，各 endpoint（包括 `[memory]` 所选的）都指向 `wiremock` 服务；经过真实的 Wasm 插件与出厂代际 |
| 评测 | `evals/runner/tests/` | 运行器的完整流程对真实的 `enco`：路径经 `ENCO_BIN` 传入（§1）；被测模型与评判都是 `wiremock`，题目是测试目录中的小题 |

测试辅助：

- `ScriptedProvider`：实现 `Provider` 与 `Embedding`。按队列返回预设的 `Completion` 或 `Failure`，并记录收到的每个 `ProviderRequest` 与 `ProviderSettings`；可以在某次调用处阻塞在 barrier 上，用于模拟崩溃。`embed` 是确定性的：把文本的字符二元组做特征哈希（feature hashing）得到固定维度的向量并归一化，因此字面相近的文本向量相近；可以切换为返回 `provider.network` 失败。
- `ScriptedRuntime`：实现 `Runtime`。按制品的字节内容决定 `load` 的结果：预先登记的字节返回带 `ScriptedProvider` 的 `Loaded`（可以设定 probe 的结果、是否导出 embedding），其余返回 `LoadError`。健康门控的故障注入就是让某个代际的 `ScriptedProvider` 返回 `plugin.trap`，不需要真的构造会 trap 的组件。
- `TestClock`：`Clock` 的实现，时刻可以设置。主人的时区来自配置代际的 `[owner]`（12 §1）。
- **端到端测试中的等待**：测试辅助中写一个最小的本地协议客户端，订阅 Session 并等待期望的条目（例如 `RunEnded`），外加总超时；不要用固定时长的 sleep 或轮询代替。
- **计时器**：进程内的测试用 tokio 的暂停时钟（`start_paused`），让退避、定时等计时器按先后立即到期；阻塞线程池中的 SQLite 调用会暂停自动推进，不受影响。子进程里的计时器无法虚拟，也不为测试在生产代码中另开时间开关（01 §2），所以黑盒测试只断言结局，不断言时长；不可避免的真实等待（试验时限、重试退避）各自独立成一个测试，与其他测试并行。
- **进程内模拟 `kill -9`**：Kernel 和 Session actor 都在独立的 tokio runtime 内创建；在注入点阻塞后调用 `runtime.shutdown_background()`，用 Drop 通知确认执行中的 future 已被丢弃，之后才释放 Kernel 句柄，避免误走正常取消结算；然后在同一个数据库上启动新的 Kernel，检查恢复写入的条目。

这些辅助只放在测试目录中，不进入库代码。

## 5. 每个里程碑的完成条件

- 逐路径审阅概念、职责、状态归属和数据链路；可读性、可维护性与认知一致性是硬性收尾门控。
- 主人从第一性原理人工审核通过后才算验收；测试只核对行为，不代替审核。
- 该里程碑的验收场景通过。
- `cargo xtask check` 通过。
- 自检清单（01 §6）逐项确认。
- 偏离规格的决定已经说明理由并得到主人确认，规格已经同步为实际的实现。
- 里程碑结束时系统完整可用；过渡形态只存在于代码中，规格只描述最终形态。
- 计划的生命周期：阶段开始时，路线图写阶段目标与里程碑顺序，每个里程碑一份计划放在 [plan/](../plan/)（目标、范围、要更新的规格、验收、待定）。里程碑开始时计划定稿，规格按计划更新，验收场景写入 §4。实现中的偏离与手动核对记录写进计划。验收通过后，§4 中它的场景移入[存档](../history/)，存档同时记下实现与暂不实现的内容以及手动核对记录，之后不再更新；计划原文与真实运行数据移入本地的 `.archived_docs/plan/`，不进仓库。仍有效的"暂不实现"移入路线图或后续计划。
