# 认知一致性与维护成本

首要目标是长期可维护性：让维护者（人或 Agent）用少量连贯的概念理解系统，修改一项规则时自然知道应该改哪里，新增功能时能够沿已有结构继续生长。

做法是让同一种事情只有一条路。复杂度用于在源头把路合成一条，不要绕开现有结构做补偿。

结合当前仓库的 `AGENTS.md`、`CONTRIBUTING.md` 和 `docs/Architecture.md` 及其章节（下称"架构文档"）应用以下判断。

## 从整体需求推导结构

先理解主人希望完成的事情，再沿实际流程追踪数据、状态和行为。找出几个入口实际上共享的需求，以及当前复杂度从哪里产生。源码、实际使用和可复现的行为是判断依据。

思考方案时，把现有实现（包括架构文档本身）也当作可以改变的设计选择。如果当前问题来自职责分散、状态重复或数据路径别扭，就重新整理这段结构，让问题在共同机制中得到解决。

## 让同一种事情遵循同一套规则

把共同语义放在一处实现，各入口只提供自身的数据和上下文。功能模块表达实例的含义，共享机制承担共同的行为。状态有明确的来源，其他部分围绕它工作。

例如，Session 历史、渠道游标、插件状态和派生索引都是可变状态。与其为每一种分别设计并发、重投和热替换规则，不如让它们都遵循架构文档 §3.6 的两条规则：唯一的归属者按顺序处理变更；回调返回写入，由归属者原子提交。接入新的渠道或 Observer 时，它自然进入这条路径，维护者只需要理解一套规则。

入口或写入者之间出现分歧时，修改它们，让它们遵循同一协议；不在下游用观察、同步或补偿去调和分歧。例如某段内容需要让模型看到，就让它先成为 Log 中的记录，再经本 Session 的 composer 进入请求（§6、§7.1），不在请求发出前由别处补拼。

用这种思路检查新增的入口或能力：

- 它属于架构文档 §3.2 的十个概念中的哪一个？是"调用"还是"转移"？如果哪一个都不是，要么它其实是已有概念的实例，要么概念模型需要修订，而不是开一个特例。
- 它能否进入已有的共同路径？是否引入了第二个事实来源、第二条请求构造路径、新的生命周期阶段，或让内核、宿主按某个插件或服务的身份写分支？身份差异应改为插件声明的能力（§4.1）；按操作系统平台适配是宿主的正常职责。
- 发现的问题能否在源头修正，让所有入口一起受益？如果每个入口都需要自己的补丁，或者需要在下游补偿，应继续寻找真正共同的职责。

共同机制的边界由语义决定。把含义相同的规则收敛起来，把真实的差异清楚表达出来，形成可以持续演进的结构。

## 用重构换取后续开发的简单

当重构能够减少重复链路、隐含知识和反复补偿时，就直接调整相关结构和规划。可以接受一次较大的改动，换取以后每次修改都更直接。评价的是整个系统的理解和修改成本。动手前与主人对齐会改变行为和责任的决定，对齐后直接重构到位。

先把共同机制做完整，再按功能接入。迁移全部实际调用者，同步删除被替代的实现和旁路，更新原有说明（包括架构文档），让新结构成为正常的开发路径；只在旧结构外再加一层不算完成。分块实施应当逐步完成同一套架构。

模块通过清楚的接口隐藏内部细节。维护者理解当前功能和它依赖的少量契约，就应足以完成工作；对插件作者而言，这份契约就是 WIT 及其生成的 CONTRACT.md。好的抽象让调用者少想几件事，也让一次规则变化集中在合适的位置。

## 让复杂度与当前问题相称

优先复用已有的机制、标准库和平台能力，选择能够完整解决现实需求的简单方案。KISS 看概念、依赖和隐含知识；60/95 鼓励把精力投入主要的使用场景。

不为尚未出现的问题预先建机制，也不在各层重复防御；问题真正出现时，在它的源头修正。可恢复的小问题不阻塞主流程。需要提前确定的只是事后补上代价很高的结构，例如 §3.7 在单机阶段就固定 ID、日志键等数据形态，机制则在真正需要时再引入。

发现问题或评审指出漏洞时，先看能否通过推广已有规则、删除造成分歧的条件或特判来解决，再考虑新增规则。逐条追加的特例会叠加复杂度；一条推广后的规则常常能同时消解多处问题。

错误在负责的边界清楚表达，失败路径保持直接。性能优先从减少重复计算和数据搬运来改善；更多的复杂度需要实际问题支撑。

取舍时看长期净收益。必要的共同机制值得建设，一次重构也可以比不断追加小修补更经济。原则服务于判断，新的事实出现后，设计可以随之改变。

## 让代码之外的接口也容易理解

名称、工具参数、返回结果和文档使用一致的概念，并沿用使用者已熟悉的约定。面向主人与 Agent 的语言说明能力、结果和下一步，内部实现细节留在合适的位置。文字简洁明了、分工明确、中正平和。面向模型的文本与开发文档出自同一段源码注释（架构文档 §7.2），不要维护两份说明。

测试验证有价值的行为与不变式，随实现收敛重复和失效的内容。文档保留总纲、核心契约和重要理由，让读者按需进入细节。代码、测试和文档共同承担维护成本，应当一起整理。

收尾时逐个入口核对它是否已进入共同机制，并问：维护者需要理解的路径是否少了一条？再用下一次开发来检验这次设计：维护者是否更容易理解规则、找到修改位置，并沿同一条清楚的路径扩展功能？Agent 能否只读手册和相关源码就完成同类修改？

依据：`CONTRIBUTING.md` 的项目哲学，以及架构文档中已经作出的取舍（例如 §3.6 以两条推广后的规则吸收评审指出的多处问题，而不是逐条打补丁）。
